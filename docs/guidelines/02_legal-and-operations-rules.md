# 法令・実運用判断規約（02_legal-and-operations-rules.md）

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`

---

## 1. 目的と根本原則

本規約は、国土交通省の航空法・関連省令・告示・通達・取扱要領・ガイドライン・DIPS仕様を遵守しながら、**「現場で真に使いやすく、手数の少ない実用的アプリ」**を設計・開発するための判断基準を定めます。

### 最重要原則
**「原則だけを読んで、そのまま全部をアプリの強制入力にする」という機械的な設計は固く禁止します。**

基準アプリ（`ikifuse/autel-evo-lite-flight-log`）では、法令上の原則だけでなく、例外・柔軟な取扱い・条件付き適用・別紙管理・原本管理・手動補記の役割分担までを深く検証したうえで運用が構築されています。新アプリでもこの高度な知見を完全に継承します。

---

## 2. 法令確認における「8つの厳格区分」

法令や公的文書を根拠に要件や画面項目を検討する際は、必ず以下の8区分に分類して評価しなければなりません。

| 区分番号 | 区分名 | 定義と設計上の扱い |
|:---:|---|---|
| **1** | **法令上必須** | 航空法・施行規則で直接義務付けられている事項（飛行日誌の必須記載項目、特定飛行の許可等）。アプリまたは関連帳票で必ず記録可能とする。 |
| **2** | **ガイドライン上の推奨** | 国交省の取扱要領・ガイドラインに例示されているが、別の合理的手法や代替記載が認められている事項。現場の操作負担を考慮して入力方式を最適化する。 |
| **3** | **特定条件時のみ必要** | 事故・インシデント時、特定飛行該当時、第三者上空飛行時など、特定の事態が発生した場合にのみ記録が求められる事項。**平時の日常フライトで常設入力欄にしてはならない。** |
| **4** | **電子記録・独自様式で充足可能** | 国交省の標準様式と見た目が同一でなくとも、必要なデータ項目が網羅されていれば電子データとして有効と認められるもの。 |
| **5** | **別紙・原本・他帳票で充足可能** | アプリの日常画面で毎回入力・保存せずとも、マニュアル、機体原本、包括許可承認書原本などの別紙で保管・提示すれば足りるもの。 |
| **6** | **手動補記で充足可能** | アプリ内で全自動化せず、必要に応じて出力後の帳票へ手書き追記、またはスプレッドシート上での直接追記で法的に充足できるもの。 |
| **7** | **アプリ独自の安全・管理機能** | 法令上の義務を超えて、操縦者の安全確保や機材保全のために独自に設ける機能（バッテリー個体管理、装着確認フロー等）。 |
| **8** | **未確認事項** | 公開情報や現有資料だけでは確定できない事項。推測で勝手に必須化せず、「要確認」として扱う。 |

## 3. 正式記録全体の評価ルール（単独画面で完結させない思想）

記録の適法性を評価する単位は、**「スマートフォン画面の入力項目」単体ではありません。**

以下の要素すべてを合わせた**「正式記録全体」**として法令要件を満たしているかを判断します。

```text
【正式記録全体の構成要素】
1. スマートフォンアプリ（現場での入力・打刻・一時退避）
2. 飛行日誌（国交省様式1：飛行記録、様式2：日常点検記録）
3. 機体別点検整備記録（国交省様式3：原本台帳）
4. バッテリー個別管理履歴（BAT_1〜BAT_n 台帳）
5. 包括飛行許可・承認書の写し（別紙）
6. 無人航空機飛行マニュアル（別紙）
7. 現場で必要に応じて行う手動補記・修正記録
8. 将来出力される各種PDF/Excel/CSV原本
```

> [!IMPORTANT]
> 「国交省の様式にその欄があるから」という理由だけで、アプリの現場画面へ常設入力欄を追加してはなりません。
> 画面を複雑化させて現場の確認漏れや誤入力を引き起こすことは、かえって安全運航を損ないます。

## 4. 基準アプリ（autel-evo-lite-flight-log）の設計判断の継承

基準アプリで既に原則・例外・柔軟運用・実態まで検討され、採用されている設計判断を、一般的な教科書的解釈だけを理由に「違反のおそれ」「未解決」「作り直し」と断定して覆すことは禁止します。

### 特に継承すべき既存判断の例
1. **条件発生時記録の分離**:
   - 安全に影響を及ぼした事項（トラブル等）は、発生時のみ入力する（平時は入力不要または空欄保持）。
2. **予定と実績の明確な分離**:
   - 飛行計画（予定）の数値をそのまま飛行実績（完了）として自動確定させない。実績は現場での実際の離着陸時刻・実飛行時間に基づく。
3. **柔軟な飛行日誌の扱い**:
   - 同一ミッションや同一場所での一連の飛行における柔軟な集約・分割の扱い。
   - 日跨ぎ（夜間飛行等）が発生しても、機械的な強制エラー終了とせず、実時刻（ISO比較）で正しく日跨ぎ飛行を完結できること。
4. **バッテリー交換時の手数の最小化**:
   - 1フライトごとに全11項目の点検をやり直す不合理を排し、バッテリー装着・ロック・残量の「最小確認フロー」で素早く離陸できる実用性。
5. **手修正後の人間記録の尊重（計算継続思想）**:
   - 人間が過去の記録を手修正した場合、システムが過去を機械的に上書きして破壊せず、修正値を起点として以後の累計を正しく継続する思想。

## 5. 法令変更・新公的資料への対応ルール

航空法やDIPS仕様、国交省ガイドラインは将来改定される可能性があります。
法改正や新資料が確認された場合は、以下のステップを踏んで慎重に対応します。

1. **新資料の根拠確認**:
   - 改定された法令、告示、取扱要領の原文および施行日を確認する。
2. **既存判断との具体的差異の抽出**:
   - 従来の運用判断と具体的に何が矛盾するのかを明文化する。
3. **影響範囲の分析**:
   - 変更が必要なのはアプリの画面か、帳票出力レイアウトか、別紙運用か、マニュアル補記かを切り分ける。
4. **改修の最小化検討**:
   - 既存の柔軟運用や手動補記で対応可能か、それともアプリ改修が真に不可欠かを比較検討する。
5. **ADR（意思決定記録）への記録**:
   - 法令変更に伴うシステム改修を行う場合は、必ず `docs/decisions/` に経緯・理由・新旧対照を記録する。
