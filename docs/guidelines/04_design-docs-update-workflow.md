# 設計Docs更新ルーティン

最終更新: 2026-09-22
状態: CURRENT-ACCEPTED（全AI共通の作業手順。個別設計の採用状態は変更しない）

本書は設計Docs更新の共通ルーティン正本。2026-09-22のオーナー指示により、従来のAI固有Skillから読む順番・判断・反映・検査・保存の手順を移した。規約本文は以下の各正本へ一元化する。AI固有の入口・Skillは本書への薄い参照に限定し、別版の手順を持たない。

## 0. 変更の種類とDocs同期の判定

毎回、変更対象とその差分から次を判定する。ユーザーにこの恒久手順を再入力・再確認させない。

| 判定 | 同じ作業で行うこと | 完了条件 |
|---|---|---|
| 設計に影響する変更（モック・コード・設定を含む） | 影響する現在有効な正本Docsを特定し、変更とDocsを同期する。既決と比較候補・未決を区別する | 該当正本・変更物・直接の参照先に不整合がなく、必要な整合確認が済むまで完了としない |
| Docsの追加・移動・整理、共通ルールの変更 | 本書のResponsibility Checkと正本・参照・入口の更新手順を適用する | 必要情報・因果を保持し、旧参照や二重正本を残さない |
| 設計変更を伴わないGit整理（branch・tag等） | 設計仕様は書き換えない。現在のbranch・作業先等を記録した文書が実態と違う場合だけ、現在状態の記録訂正を行う | 過去の事実を残し、現在状態の誤記だけを必要最小限訂正する |
| その他の設計影響なしの変更 | 影響なしの理由を差分で確認し、直接必要な検査だけを行う | 無関係な設計Docsを更新しない |

**役割分離**: GitHubのmainの最新commitはリポジトリ全体の現在状態、docs配下の該当正本文書は現在有効な設計・仕様・規約、Git commit履歴は変更の証拠・履歴・復元点である。**commitが残ることを理由に設計Docs同期を省略しない。**

対象と直接関係する文書・節だけを読む。既読で内容が変わっていない規約を繰り返し読み直さず、同じ決定を再調査しない。明示依頼なしに全Docs・全コード・全Git履歴の横断監査へ広げない。検査スクリプトによる参照整合の走査と、設計内容の全体再監査は区別する。

## 1. 着手前

1. 依頼範囲と実装開始ゲートを確認する。本手順は実装の許可ではなく、明示的な開始指示なしにC1を含む実装コードへ進まない（[AGENTS.md](../../AGENTS.md) §2）。個別の明示指示があれば優先する。
2. branch・HEAD・`git status`で開始状態と既存の未commit変更を確認する。既存差分を捨てず、説明できない変更は止めて報告する。通常はmainで作業し、保存目的のbranchを作らない。
3. Git管理外の参照資料（99.2原本など）は、変更せず、追跡にも加えない（[移植記録](../migration/README.md)の各Step監査の扱い）。

## 2. 読む（入口から順に、必要な正本だけ）

1. [AGENTS.md](../../AGENTS.md) → [docs/00_index.md](../00_index.md)の対象入口 → 対象領域のREADME。全領域を一括で読まない。
2. 対象の正本を[概念別正本表](../architecture/README.md#3-主要概念の正本)で特定し、その文書と直接の関連文書を読む。
3. 規約を読む。
   - [構造・保守規約](../guidelines/01_structure-and-maintenance-rules.md) §6（Responsibility Check）
   - [設計証拠・因果規約](../guidelines/03_design-evidence-and-causality.md)
   - 法令・行政資料を新たに根拠として扱う場合は[法令・運用規約](../guidelines/02_legal-and-operations-rules.md)
4. 既決・未確定を確認する: [04_open-questions](../04_open-questions.md)、関係するADR（[ADR一覧](../decisions/README.md)）。既存Docsで決着済みの点は再質問しない（設計証拠・因果規約 §5）。

## 3. 判断する（毎回行い、結果を報告に残す）

1. **Responsibility Check**: 構造・保守規約 §6に従って判定し、追記先（既存文書／サブ文書／新文書・新領域）を決める。
2. **正本の一元化**: 概念別正本表で正本を特定する。登録と他文書の扱いは構造・保守規約 §6に従う。
3. **因果・状態・証拠**: 設計証拠・因果規約の§2（因果）・§3（状態ラベルと由来）・§4（実物確認）を適用する。オーナーへ確認するか自分で決めるかは§5で判断する。
4. **ADR判断**: [ADR一覧・運用ルール](../decisions/README.md)の記録対象と置換の規則に照らし、既存ADRで足りるか確認してから、追加・置換の要否を決める。

## 4. 反映する（この順）

1. 変更したモック・コード・設定に対応する正本文書 → 関連文書の参照 → 領域README → 概念別正本表 → [00_index](../00_index.md) → 04_open-questions（PENDING／VERIFYの所在）。実装開始ゲートに関わる場合は[23](../architecture/23_implementation-roadmap.md)。
   各段階は今回の変更に関係する項目だけを確認・更新し、影響のない文書を形式的に変更しない。規約・ルーティンの入口は[guidelines README](README.md)を使う。
2. 新設・移動・分割・廃止では、領域READMEと上位目次を同時に更新する（構造・保守規約 §6）。
3. 更新した文書の「最終更新」日を直す。

## 5. 検査する

1. リポジトリのルートで `python3 scripts/check_docs.py` を実行する。相対リンクとアンカー、表の列数、fence、入口からの到達性、追加行の個人情報・秘密情報、文書以外の差分を検査する。エラーが出たら直して再実行する。
2. モック・コード・設定と該当正本Docsの差分を照合する。設計影響ありなのに正本を同期していない場合は完了にしない。
3. 構造・保守規約 §6末尾の最終確認項目のうち、スクリプトで見られないもの（二重正本、旧仕様と履歴の区別、Phase）を、`git diff`を読んで確認する。
4. 依頼範囲外の変更・削除、承認済みADR本文の変更がないことを、`git diff`で確認する。

## 6. 保存と報告

1. 必要なテスト・Docs検査 → 今回のdiffと秘密情報・個人情報の確認 → commit → mainへpushの順で保存する。明示的な別指示は優先する（[AGENTS.md](../../AGENTS.md) §5）。
2. push結果を確認したら停止し、ユーザーの画面確認・次の指示を待つ。勝手に次工程へ進まない。
3. 報告に含める: 設計影響の有無と同期先（Git整理なら現在状態の訂正先）／どの責任をどの文書へ配置したか（Responsibility Checkの結果）／新規ADRの有無／状態区分／残った未確定／検査結果。
