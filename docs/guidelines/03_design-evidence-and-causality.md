# 設計検討の因果・状態・実物証拠の保持規約

最終更新: 2026-09-18\
状態: CURRENT-ACCEPTED（現時点の設計ベースライン。変更可能）\
由来: 99.2 §0・§1、および今回の再移植指示。出典の識別・確認範囲は[Step 1監査](../migration/99-2-step-1-causal-audit.md)。

## 1. 検討正本と正式設計正本を分ける理由

**当初の状態・問題**: 基準Docsには[構造規約](01_structure-and-maintenance-rules.md)による責任分離と[ADR](../decisions/README.md)による判断履歴がある。一方、99.2 §1は、AI実装が使用量制限で進まない期間にも設計を進め、会話で詰めた内容を失わず正式Docsへ渡す作業台が必要になった経緯を記録している。構造を扱う98と理由・比較・保留を扱う99、実Drive、旧アプリ、DIPS画面、原本・試作品に情報が分散していた（99.2による経緯記録）。

**検討・到達点**: 構造と理由を99.2へ一本化し、別98を恒久正本として並立させない。98/99は設計作業資料であり、一般利用者向けの生成物ではない。ただし、横断的な検討正本である99.2を、そのまま単一の正式仕様書にする判断ではない。正式Docsは[概念別正本表](../architecture/README.md#3-主要概念の正本)に従い、各責任領域へ必要な因果・条件・例外を移す。

**採らない整理と理由**: 結論だけを短縮転記すると、変更理由や適用条件が失われる。構造と理由を別の恒久正本へ分けると再び照合が必要になる。旧案を現行仕様と並列に残すと実装判断が分岐する。したがって重複する同じ意味だけを吸収し、過去案は現在へ至る経緯として保持する。原資料を削除する規則ではない。

## 2. 論点ごとに保持する因果

CURRENT-ACCEPTED。以下を各論点の詳細正本内で追跡可能にする。別冊の権限表・画面→保存先表・未確定一覧・根拠台帳を作って同じ詳細を重複管理しない。索引・監査表には要約と正本へのリンクだけを置く。

1. **発端・当初の状態**: 既存Docsの設計と当時の理由を示す。旧設計がない論点は「旧設計なし」とし、架空の過去案を作らない。
2. **問題・再検討理由**: 矛盾、現場上の不都合、満たすべき要求を示す。
3. **調査・確認した事実**: 何を見た・操作したか、何が分かったか、確認日・版・出典を示す。「確認済み」だけに縮めない。
4. **検討案と変更・却下理由**: 採らなかった案も、理由と適用条件を理解するために必要な範囲を残す。資料にない理由を補わない。
5. **さらに詰めた内容と現在の到達点**: 明示された訂正関係を辿り、画面とDrive・保存への反映先を結ぶ。
6. **例外・未確定事項**: 適用条件、判断待ち、根拠確認待ちを区別し、失われないよう同じ論点内へ残す。

後発情報であることだけを採用理由にしない。明示的な訂正関係、証拠の強さ、実Drive・原本・旧アプリ・現在運用を合わせて扱う。迷う情報は削除せず、相違と未確認範囲を残す。新証拠で変わった部分は、過去の理由を消さず同じ因果へ統合する。

法令を根拠とする論点は[法令・運用規約](02_legal-and-operations-rules.md)に従う。原則から現場上の問題、公式根拠、但書・例外・柔軟運用・許可承認経路と適用条件、アプリ設計までを保持する。一般論や「安全側」を理由に確認済みの柔軟運用を消さない。未確認の例外を推測で作らずVERIFYとする。本Stepでは法令やDIPSの現行仕様を新たに認定しない。

## 3. 状態ラベルと由来

以下の定義は今回のオーナー指示による。99.2にこの英語ラベルが記載されていたと扱わない。設計状態、証拠の確認状況、ADRの承認状態は別軸であり、文書全体の見出しだけで内部の未確定事項を確定へ昇格させない。

| ラベル | 意味・使い方 |
|---|---|
| CURRENT-ACCEPTED | 現時点で採用している設計ベースライン。後続の設計検討で変更可能。永久確定でもADR Acceptedでもない |
| CURRENT-PROPOSAL | 現在検討中の案。現在ベースラインとしての採用まで到達していない内容 |
| PENDING | 設計判断・内容が未確定。必要な判断と依存する範囲を残す |
| VERIFY | 根拠・実仕様・実物の確認が必要。確認すべき対象を残す |
| HISTORICAL | 過去の状態・案・判断。現在へ至る因果の一部として保持し、現行仕様として採用しない |
| EVIDENCE/EXAMPLE | 実物・観測・試作・例。存在や動作だけでは採用の証明にならない |
| NEW-PROPOSAL | 99.2にも既存Docsにも根拠のないAI独自の新規設計。既存決定と区別する |

99.2が現在案へ到達した内容を、ADRがProposedであることや今回実物を再確認していないことだけでCURRENT-PROPOSAL/PENDINGへ戻さない。同時に、現在案の根拠として引用された実物を今回確認したと偽らない。由来を「99.2の節」「基準Docsとcommit」「今回のオーナー指示」「AI新規提案」に分ける。技術上必要という説明だけでAI提案をCURRENT-ACCEPTEDにしない。

## 4. 実物確認と設計への反映

**発端・判断理由**: 99.2 §0は、利用者が実物を見て初めて不足や矛盾を見つけられることを理由に、実Driveを保存先の試作と設計確認の道具に位置づける。文章だけで検討を閉じる方法を採らず、人が見る帳票・台帳・管理表・画面から保存先への流れについて、確認可能な段階で該当の確認用ファイルにも反映する。

**現在の扱い（CURRENT-ACCEPTED）**: 因果の記録と実物への反映を対応づける。実物はEVIDENCE/EXAMPLEであり、確認用・叩き台と最終仕様を明示的に区別する。実物の存在だけで正式仕様に昇格させない。観測内容が現在の合意とどう対応するかを記録する。

99.2 §0の検証例は、個人環境で本人がアプリ管理者・操縦者を兼ね、実機2機と共用BAT7本を持つもの。既知の実データだけで確認し、推測値を足さない。これはEVIDENCE/EXAMPLEであり、人数・機数・BAT数を固定仕様にしない。同一機種複数機、多数BAT、複数人、会社・複数組織へ拡張したときに破綻しないかを検証する。実名・登録記号・非公開Drive識別子を公開Docsへ複写する必要はない。

**VERIFY-S1-EVIDENCE**: 本再移植では、99.2 §0・§1が挙げる個人運用環境の01〜07、現在地確認用ファイル、旧98/99各版の実物を再検証していない。99.2の経緯記録と今回の直接観測を混同しない。各依存設計を実装へ進める際は、対象・版・観測・設計判断への対応を確認する。原本の所在・確認範囲は[監査の証拠欄](../migration/99-2-step-1-causal-audit.md#2-証拠と確認範囲)から辿る。

この規約は個別タスクの書込権限を広げない。今回の依頼はGitHub DocsのStep 1であり、Drive編集・新規試作品作成は実施しない。

## 5. 質問と技術判断の境界

**問題と現在の判断（99.2 §0）**: 現在案や過去の却下理由を読まずに同じ質問を繰り返すと、検討を後退させる。利用者へ質問する前に99.2、該当正式Docs、関係する現在の実Drive確認用ファイルを読む。確認済みの事項は再質問せず、却下案を一般論で復活させない。

利用者へ確認するのは実運用・帳票・画面・残す記録等に影響する本当に未確定な判断とする。内部構造、ID、同期方式、技術用分割は、利用者の運用や見える出力を変えない範囲でAIが技術設計を担い、技術判断そのものを丸投げしない。新規の設計内容は§3に従い由来を区別する。

人が使う帳票・台帳を一枚で成立させる前提を技術都合で変える場合は、一枚では成立しない具体的理由と影響を説明し、合意後に設計へ加える。責任分離された内部モジュールを持つことと、人間向け帳票を未合意で複数タブへ分けることを混同しない。[設計目的](../00_goal.md#11-記入支援を中心に置くまでの因果)、[実装開始ゲート](../architecture/23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)に接続する。
