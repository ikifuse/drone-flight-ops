# 構造・分割・保守運用規約（01_structure-and-maintenance-rules.md）

最終更新: 2026-09-15
プロジェクト: `drone-flight-ops`

---

## 1. 目的と基本方針

本規約は、プロジェクト `drone-flight-ops` が今後大規模化（DIPS連携、地図、日誌、点検、バッテリー、オフライン同期、各種帳票出力など多数の領域を内包）しても、コードやドキュメントが複雑化・整理不能に陥ることを防ぎ、**「最初から壊れにくく、安全で、機能を追加しやすく、理解しやすい構造」**を永続的に維持するための運用ルールを定めます。

---

## 2. 分割・構造設計の9原則

モジュール、ソースコード、設計書の分割は、単なるファイルサイズや行数だけで機械的に決定してはなりません。以下の9つの観点を総合的に評価して判断します。

### 2.1 堅牢性（障害の局所化）
- 1つの機能の障害が他機能へ波及しないこと。
- DIPS APIの障害やメンテナンス時でも、飛行日誌や点検などの独立機能は影響を受けずに動作し続けること。
- 地図描画の不具合でバッテリー記録が壊れないこと。
- 保存失敗、通信失敗、リトライ処理が機能ごとに局所化されていること。

### 2.2 セキュリティ（秘密情報の隔離）
- 認証、API client_secret、トークン、個人情報（操縦者実名・連絡先等）、権限処理を一般のUI・業務ロジックから厳格に分離すること。
- ブラウザ側・クライアント側へ秘密情報を不用意に露出させない境界を設けること。

### 2.3 追加実装性（拡張の容易性）
- 将来、新しい機体モデルや新しいバッテリー種類を追加する際、既存コードを広範囲に修正しなくてよいこと。
- DIPSのAPI仕様変更があっても、影響範囲が専用アダプター内に限定されること。
- 新しい地図機能や新しい帳票出力形式（PDF/CSV等）を独立して追加できること。
- 変更頻度の高い領域（UIや外部連携）と、安定した中核領域（日誌・点検モデル）を分離すること。

### 2.4 役割分担性・責務分離（単一責任の原則）
- 1つのモジュールは可能な限り1つの主要責務を持つこと。
- UI、業務ロジック、外部API通信、データ保存・永続化、データ変換、認証を混在させないこと。
- 「この処理はどこに書くべきか」が誰にでも一目で判断できること。

### 2.5 保守性（修正範囲の最小化）
- 小さなバグ修正や仕様変更のために、巨大なファイル全体を読まなくてよいこと。
- 人間でもAIでも、修正対象のコードと影響範囲を即座に特定できること。
- 古くなった仕様や不要なコードを安全に特定・削除できること。

### 2.6 テスト容易性（検証の独立性）
- 各モジュールを単独でユニットテストできること。
- DIPSや地図サービス等の外部通信を容易にmock/stubへ置き換えられること。
- 実機や本番ネットワーク環境がなくても、主要な業務計算・整合性検証を自動テストできること。

### 2.7 変更影響の最小化（インターフェースの分離）
- 1箇所の仕様変更が、無関係な他ファイルへ連鎖的な修正を引き起こさないこと。
- 共通処理と業務固有処理を適切に分離し、データ変換の境界を明確にすること。

### 2.8 可読性・発見性（ナビゲーションの直感性）
- ファイル名、フォルダ名、目次を見ただけで、目的の処理や仕様へ直ちに辿り着けること。
- 毎回リポジトリ全体を全文検索しなくても、入口の目次から順を追って理解できること。

### 2.9 分割しすぎない（過剰分割の防止）
- 分割そのものを目的にしないこと。
- 1つの処理を追うために数十個の微小ファイルを行き来しなければならない状態や、依存関係がクモの巣状に複雑化する状態は避けること。

## 3. 「大きくなってから分割」の禁止（再編成の兆候）

コードや設計書が巨大化してから事後的に整理・分割すると、莫大な工数とバグ誘発のリスクが生じます。
以下の**兆候（Code/Doc Smells）**が1つでも現れた場合、作業をそのまま続行せず、直ちに構造の見直し・再編成を行います。

- **責務混在**: 1つのファイルが複数の明確に異なる責務（例: UI描画とAPI通信、日誌計算と地図描画）を持ち始めた。
- **変更頻度の集中**: 異なる機能追加や修正であるにもかかわらず、毎回同じファイルばかりを編集している。
- **理解コストの増大**: AIや人間が、小さな1行を直すために巨大なファイル全体を読み込まなければ安全性を確認できなくなった。
- **コード・仕様の重複**: 同種の判定ロジックやデータ構造の定義が複数箇所に散らばり始めた。
- **テスト困難**: 外部通信やUIが結合しているため、業務ロジック単体のテストが書けなくなった。
- **目次の形骸化**: 目次（00_index.md）を見ても、どこに目的の記述があるのか直感的に特定できなくなった。
- **セキュリティ境界の侵食**: API tokenや認証に関するコードが、一般の業務画面やユーティリティに浸食し始めた。

## 4. 定期的な構造レビュー手順と判定基準

### 4.1 実施タイミング
最低でも以下のタイミングで、作業を一旦停止してリポジトリ構造の点検（構造レビュー）を実施します。
1. 各Phase開始前（例: Phase B 開始直前、Phase C 実装開始直前）
2. 各Phase完了時
3. 大きな新機能（DIPS連携、地図、オフライン等）の実装着手前・追加後
4. データモデル（日誌、機体、バッテリー）の大規模変更時
5. 認証・保存方式の変更時
6. docsの大規模追記後
7. AIまたは人間が「既存構造の把握が難しくなってきた」と感じた時

### 4.2 構造レビュー・チェックリスト（合否判定）

| 評価軸 | チェック項目 | 合否確認 |
|---|---|---|
| **堅牢性** | 1機能の障害（DIPSダウン等）が他機能（飛行記録等）へ波及しない構造か？ | [ ] |
| **堅牢性** | 通信エラー時の再試行・復旧処理が特定の責務内に局所化されているか？ | [ ] |
| **セキュリティ** | secret、token、認証処理が一般機能から完全に分離されているか？ | [ ] |
| **セキュリティ** | クライアント側（ブラウザ/端末）へ秘密情報が露出していないか？ | [ ] |
| **追加性** | 新しい機体・バッテリー・帳票の追加で、既存コードの広範囲な修正が不要か？ | [ ] |
| **責務分離** | UI、業務ロジック、外部通信、データ永続化が同一ファイルに混ざっていないか？ | [ ] |
| **保守性** | 小さな仕様変更の際に、読むべき範囲が限定的か？ | [ ] |
| **テスト容易性** | 外部依存（DIPS、地図）をmockに差し替えて単体テストが可能か？ | [ ] |
| **可読性** | `docs/00_index.md` や各目次から、目的のファイルへ即座に辿れるか？ | [ ] |
| **整合性** | 設計書（docs）と実装コード・テストの間で仕様の乖離がないか？ | [ ] |
| **重複排除** | 同一概念の定義や同一ロジックが複数箇所へ重複していないか？ | [ ] |

## 5. ソースコード分割方針（設計上の責務）

採用済み技術構成のもと、実装コードは以下の**業務責務および技術境界**に基づいて独立ディレクトリ/モジュールへ分離します（巨大な単一ファイルへの追記は禁止）。

- `features/flight-plan`: 飛行計画の作成・編集・プリセット・計算
- DIPS業務ユースケース: 手動通報支援・確認記録。API通信は外部アダプター、秘密情報・トークンはバックエンド認証境界へ分離。
- 地図機能: 地図描画、空域レイヤー、POLYGON / CIRCLE / BUFFERED_LINE編集。ライブラリ選定はC5。
- `features/flight-log`: 現場状態遷移（離着陸・打刻・タイマー）、飛行日誌作成
- `features/inspection`: 飛行前点検（11項目）、飛行後点検（4項目）
- `features/aircraft-battery`: 機体台帳、バッテリー個体管理、累計時間管理
- `features/export-import`: 国交省様式PDF/Excel/CSV出力、CSV取込
- `core/offline`: ローカルファースト永続化、状態復元、同期キュー
- 認証境界: 認証管理・セッション。ブラウザに平文secret/tokenを持たせない。
- `core/audit`: 変更履歴、原本整合性検証、UUID発行
- `shared/`: 共通UIコンポーネント、日付時刻計算、バリデーション規約


上記の業務分類は機能の所在を考えるための例であり、現行の配置契約は [20_source-structure](../architecture/20_source-structure.md) に一元化します。C0はVanilla TypeScriptであり、将来ツリーの記述だけでフレームワーク導入やC1実装を開始しません。

## 6. docs変更時のResponsibility Check

新しい仕様を既存文書へ追加する前に、次の6点を判定してレビューに残します。

1. 既存文書の主要責務と同じ内容か。
2. 別のライフサイクルを持たないか。
3. 別の外部依存を持たないか。
4. 別のセキュリティ境界を持たないか。
5. 別Phaseで実装されないか。
6. 将来独立して変更される可能性が高くないか。

**2つ以上の観点で明確に分離される場合は、既存文書へ追記せず新文書またはサブ文書を作成します。** 1つでも重大な責務混在を見つけた場合は§3に従い構造を見直します。行数・容量だけでは判定しません。同一責務のフィールドカタログや状態表は、長くても一緒に読む必要があれば維持します。

- 正本となる概念を1文書に定め、[architecture README](../architecture/README.md#3-主要概念の正本)へ登録する。他文書は利用上必要な要約とリンクにする。
- README / Overviewは入口・責務・正本関係・読み順を担当し、詳細定義をコピーしない。
- 新設・移動・分割時は領域READMEと上位目次を同時更新する。00_indexは領域入口を登録し、全詳細ファイルの再羅列を要求しない。
- 各旧章・表・型・根拠・PENDINGの移行先を記録する。意味を修正した場合は根拠を示す。Accepted ADRの決定変更は新ADRによるSupersedes / Partially Supersedesで追跡する。
- 最終にリンク、アンカー、fence、見出し番号、入口からの到達性、二重正本、旧仕様と履歴の区別、Phase、privacy、文書限定差分を確認する。
- 微小な文書の乱立や、1つの仕様を理解するための10文書以上の往復を避ける。領域READMEから作業に必要な詳細へ直接案内する。

## 7. 画面仕様の記録規約（10項目規約）

99.2 §0の設計検討原則に基づき、本システムの各画面仕様を記述する際は、単なる「画面名」や「次にどの画面へ進むか」の列挙にとどめず、実装と検証に必要な意味を追跡できるよう、以下の**10項目**を標準フォーマットとして定義します。

1. **目的**: その画面でユーザーが達成すべき主たる業務目的。
2. **入口・進入条件**: どこから遷移してくるか、遷移できる前提条件（ロール、FSM状態等）。
3. **表示情報**: ユーザーに提示するデータ・ステータス・警告等。
4. **初期値・自動入力**: 画面表示時に自動設定・補完される項目とその算出ルール。
5. **主操作・副操作**: 画面内で実行可能なプライマリアクションおよびセカンダリアクション。
6. **操作後遷移**: 各ボタン押下やアクション完了後に進む次の状態・画面。
7. **戻る・中止・削除の扱い**: 中断操作、キャンセル、ブラウザ戻る、下書き破棄時の挙動。
8. **保存・更新時点**: 端末キャッシュ（IndexedDB）、Google Drive/Sheets、DIPS通報への保存・送信が発生する厳密なタイミング。
9. **権限・通信状態の差異**: 三層権限レイヤー（業務上の役割／アプリ機能上の権限／Google Drive上の実アクセス権）や Online / Offline による表示・操作制限の差。
10. **未確定・留意事項**: 設計検討段階で保留されている論点、検証待ち事項。

## 8. 新設責任領域および新規文書の審査基準

### 8.1 新規文書の作成を前提としない原則
- 新規文書（特に「新規提案」に分類される文書）は、作成ありきで進めてはならない。
- 既存の正本文書（`18_reports.md`、`27_output-boundaries.md` 等）で責任境界が明確に維持でき、保守性・テスト容易性を損なわない場合は、無理に独立文書を乱立させず既存文書へ適切に配置する。

### 8.2 新設責任領域（サブディレクトリ）の設置条件
新設が検討されている4領域（`identity-and-access/`, `drive-storage-schema/`, `presentation/`, `dips-infrastructure/`）を含め、新しい責任領域を設置する際は、以下の独立性が満たされていることを確認する。
- **独立した変更理由**: 他の業務ドメイン（飛行記録・点検等）と異なる頻度・契機で改定されるか。
- **独立した検証・監査性**: その領域単体でセキュリティ監査、インフラ検証、UI検証を完結できるか。
- **障害の局所化**: その領域の不具合や外部仕様変更が、コアの飛行日誌・点検記録へ波及しないか。
