# 新アプリ（drone-flight-ops）統合要件定義書

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`
目的: 現行自作アプリの強み（バッテリー個体管理・現場フロー）とワンエビneoの利便性（DIPS連携・地図機能）を統合した次世代システムの要件整理

---

## 1. 新アプリで追加が必要な機能一覧

現行アプリを基準とし、将来の「現場スマホ1台による一気通貫運用」を実現するために追加すべき機能一覧です。

1. **DIPS 2.0 API連携モジュール**
   - 機体一覧の自動取得（DRS API）
   - 飛行許可・承認情報の自動取得（FPA API）
   - 飛行計画の照会・検索（FPR API）
   - 飛行計画の新規通報・更新・取り消し（FPR API）
   - 通報エラー理由の解析・現場向け平易な日本語表示
2. **インタラクティブ地図・空域管理モジュール**
   - GPS現在地表示および飛行予定地点の地図ナビゲーション
   - 円形範囲作成（中心点指定＋半径m入力）
   - 多角形（ポリゴン）範囲作成（画面タップによる頂点追加・移動）
   - 航空法規制空域（空港周辺、DID人口集中地区、緊急用務空域等）の重ね合わせ表示
   - 過去に通報・飛行した範囲のプリセット保存とワンタップ呼出
3. **計画から日誌へのデータ自動引き継ぎ**
   - DIPS通報完了時の通報ID、機体、日時、場所、範囲、目的、許可番号を、現場飛行セッションへそのままバインド（二重入力の完全排除）
4. **汎用機体・機材マスター管理**
   - 機種・機体シリアル・登録記号・機体愛称（ニックネーム）の自由登録
   - 機体ごとの初期累計飛行時間、点検整備サイクルの独自設定
5. **有効期限・安全アラート機能**
   - 機体登録有効期限（3年）、包括許可承認期限（1年）、操縦者技能証明、機体定期点検期限（例: 20時間/100時間）の自動カウントダウンと事前警告
6. **オフラインファースト・ローカルキューイング機能**
   - 電波圏外でのドラフト計画作成、飛行前点検、離着陸記録、飛行後点検の完全スタンドアロン実行
   - 通信復帰後のワンタップ一括同期・DIPS通報
7. **標準帳票マルチエクスポート機能**
   - 国土交通省標準様式1（飛行記録）、様式2（日常点検記録）、様式3（点検整備記録）のPDF/Excel直接出力
   - 飛行空域地図画像を含めた「飛行計画書（通報確認書）」のPDF出力
   - 外部ツール連携用の汎用CSV出力およびCSVインポート

## 2. バッテリー管理要件（コア強みの発展）

バッテリー管理は、自作アプリ最大の強みとして最優先で維持・強化します。

### 2.1 バッテリー個体台帳
- **識別情報**: バッテリー個体ID（例: `BAT_1`〜`BAT_7`、任意文字列・QRコード/バーコード等に対応可能な柔軟性）。
- **属性情報**: 対応機種（EVO Lite専用、共通など）、製造年月、運用開始日、初期公称容量、現在のステータス（現役、保管中、点検中、廃棄）。
- **生涯統計**: 累計充電サイクル数、累計総飛行時間、累計使用回数。

### 2.2 飛行ごとのバッテリー紐付け記録
- 各飛行（離陸〜着陸）において、使用したバッテリー個体IDを必須記録。
- 飛行前残量（%）、飛行後残量（%）。
- サイクル数（機体アプリ等で確認できた場合に任意記録）。
- バッテリー所感・異常メモ（発熱の程度、急激な電圧降下、セルバランス異常、外観の膨らみ、端子の汚れ等）。

### 2.3 運航中のバッテリー交換フロー
- 着陸後、「同じ機体で継続」を選択した場合、即座に「バッテリー交換画面」へ遷移。
- 交換対象のバッテリー個体IDを選択（前回のBATと同じものを再充電・再装填した場合も区別可能）。
- 装着・確実なロックの確認、残量・温度・警告表示の有無の最小チェック（3ステップ）を経て、素早く次の離陸待機へ進めること。

### 2.4 バッテリー点検整備記録
- 満充電保存の回避状況、長期保管時のストレージ充電（約50〜60%）実施記録。
- 定期点検（端子清掃、外観確認）の実施日と点検者。

## 3. 飛行計画要件

現場でのDIPS 2.0通報および社内・自治体・土地所有者への提出用計画書を作成するための要件です。

### 3.1 計画属性
- **運航識別**: 計画を一意に識別する計画UUID、DIPS通報ID（通報完了後に付与）。
- **運航日時**: 飛行予定開始日時、終了日時（日跨ぎ許容）。
- **飛行場所・空域**: 飛行場所名称、住所/地名、中心緯度経度、飛行範囲（円の半径m、またはポリゴン座標列）、最大飛行高度（地表高 AGL / 海抜高 MSL）。
- **機体・人員**: 使用予定機体、操縦者名、技能証明番号、緊急連絡先電話番号。
- **飛行目的・方法**: 飛行目的（空撮、点検、測量、練習等）、特定飛行区分（DID、夜間、目視外、30m未満等）、許可承認書番号。
- **安全確保措置**: 補助者配置の有無、立入管理区画の設定方法（コーン、看板、監視員）。

### 3.2 テンプレート・過去計画の複製
- 過去に通報・実施した計画をワンタップで「新規計画として複製」。
- よく使用する飛行場所・範囲・連絡先を「現場プリセット」として登録可能。

### 3.3 通報ステータス管理
- ステータス区分: `DRAFT`（下書き）→ `READY`（通報準備完了）→ `SUBMITTING`（送信中）→ `SUBMITTED`（通報完了）→ `FAILED`（エラー）→ `CANCELLED`（取り消し）。
- 誤操作による多重通報を防ぐ「送信ロック機構（二重通報防止）」。

## 4. DIPS 2.0 連携要件

国土交通省DIPS 2.0外部システム連携仕様に基づく要件です。

### 4.1 認証基盤（OpenID Connect）
- DIPS 2.0の分離された認証realmに対応可能であること:
  - 機体登録系: `drs-utm`
  - 飛行許可承認系: `drs-req`
  - 飛行計画通報系: `drs-fpl`
- 認可コードフロー（Authorization Code Flow）を安全に実行できること。
- `client_secret` や `access_token` / `refresh_token` を安全に管理・更新できること。

### 4.2 APIクライアント機能
- **機体情報取得**: `GET /utm/v1/aircrafts` を呼び出し、所有機体一覧（登録記号、機体ID等）を自動同期。
- **許可承認情報取得**: `GET /permissions` を呼び出し、有効な許可証情報を自動同期。
- **飛行計画検索**: 緯度経度・日時・半径を指定して周辺の他機飛行計画を取得・表示。
- **飛行計画通報**: DIPS公式仕様に準拠したJSONペイロードを生成し通報。
- **通報エラーハンドリング**: DIPS側から返るエラーレスポンス（ステータスコード、エラーフィールド、理由コード）を解析し、「どの項目をどう修正すべきか」をユーザーに平易に提示。

### 4.3 独立性と耐障害性（疎結合の原則）
- DIPS APIの通信断やメンテナンス時でも、アプリのローカル記録機能（点検・飛行・日誌）は完全に動作し続けること。
- 「DIPS通報の成功/失敗」と「飛行日誌の記録・保存」の責任を完全に分離すること。

## 5. 飛行日誌要件（航空法・国交省様式準拠）

航空法第132条の88に基づく飛行日誌の作成・備え付け義務を完全に満たす要件です。

### 5.1 様式1: 飛行記録
- 飛行ごとの記録項目:
  - 飛行年月日
  - 操縦者氏名
  - 飛行目的
  - 飛行経路（離着陸場所、経由地）
  - 離陸時刻（`HH:mm`）および着陸時刻（`HH:mm`）
  - 飛行時間（分単位）
  - 総飛行時間（その飛行時点での機体累計時間）
  - 安全に影響を及ぼした事項（不具合、トラブル、ニアミス等）

### 5.2 様式2: 日常点検記録
- **飛行前点検（11項目）**: 全般、プロペラ/フレーム、通信、推進、電源、自動制御、バッテリー、プロポ、灯火、カメラ、リモートID。
- **飛行後点検（4項目）**: 機体全般、プロペラ/フレーム、異常発熱の有無、その他特記事項。
- 点検年月日、点検実施場所、点検実施者氏名、異常の有無、不具合時の処置内容。

### 5.3 様式3: 点検整備記録
- 機体の生涯にわたる整備台帳:
  - 点検・整備実施年月日
  - 総飛行時間（整備実施時点の累計）
  - 実施理由（定期点検20時間/100時間、修理、部品交換、ソフトウェア更新等）
  - 実施内容・交換部品名
  - 点検整備実施者氏名および確認者氏名

### 5.4 機体累計飛行時間の自動起算
- 運航完了時、当該飛行の実飛行時間を機体原本累計に自動加算。
- 手動修正が入った場合でも、過去データを破壊せず新たな起点として加算を継続できること（手修正追従性）。
- 実機を飛ばさない「アプリテスト（シミュレーション）」は、機体正式累計から完全に除外できること。

## 6. 地図・ポリゴン要件

現場での直感的な空間把握と正確な通報を実現するための要件です。

### 6.1 地図表示基盤
- 国土地理院標準地図、淡色地図、航空写真（オルソ画像）の切り替え表示。
- スムーズな拡大・縮小、パン、現在地GPS追従。

### 6.2 空域・規制情報レイヤー
- 国土交通省 DID（人口集中地区）レイヤーの重畳表示。
- 空港等周辺空域、進入表面等の規制エリア表示。
- 他者の通報済み飛行計画（DIPS API経由で取得可能な場合）のマップ上表示。

### 6.3 飛行範囲描画ツール
- **円形指定モード**:
  - 地図上を長押しまたはタップして中心マーカーを設置。
  - 半径スライダーまたは数値入力（m単位）により、半透明の円を描画。
- **ポリゴン指定モード**:
  - 地図上を順次タップして頂点を追加。
  - 頂点のドラッグ移動、削除、頂点間の自動線引き。
  - 描画中のポリゴン面積（㎡ / ㎢）および外周長をリアルタイム表示。
- **座標出力**:
  - DIPS通報仕様で求められる世界測地系（WGS84）の緯度・経度配列（GeoJSON準拠）を正確に生成。

## 7. オフライン要件（現場運用保証）

携帯電波が届かない、または極めて不安定な現場（山間部、沿岸部、離島等）での運用を保証するための要件です。

### 7.1 スタンドアロン動作
- アプリの起動、過去データの閲覧、新規運航の開始、飛行前点検、離着陸記録、バッテリー交換、飛行後点検、日誌の一時確定までを、**通信が一切発生しない状態でも100%実行可能**とすること。

### 7.2 ローカルファーストストレージ
- すべての入力・打刻・状態変更は、端末内のローカル永続領域（LocalStorage / IndexedDB / SQLite等）へミリ秒単位で即時永続化。
- ブラウザのリロード、端末のバッテリー切れ、誤ってアプリを閉じた場合でも、直前の画面・状態を完全復元。

### 7.3 オフライン地図キャッシュ
- 事前に現場の地図タイル（地理院地図・航空写真）を端末内へキャッシュし、電波圏外でも飛行予定エリアの背景地図を表示可能とすること。

### 7.4 同期キュー（キューイング機構）
- オフライン時に作成したDIPS通報計画や飛行日誌は「未送信キュー」としてプール。
- 電波が回復した段階で、操縦者のワンタップ操作により、安全に外部システム（DIPS 2.0、クラウド保存先等）へ一括同期。

## 8. 出力・取込要件

多様な監査・報告・共有ニーズに対応するための要件です。

### 8.1 帳票出力（PDF）
- **国交省様式1〜3帳票PDF**: A4縦/横に最適化され、印刷してそのまま飛行日誌原本として保管できるレイアウト。
- **地図付き飛行計画書PDF**: 飛行範囲の地図画像、飛行空域座標、連絡先、許可承認番号をまとめた関係者提出用帳票。

### 8.2 データエクスポート（CSV / Excel）
- 日常点検シートおよび飛行明細の一括CSV/Excel出力。
- バッテリー個別履歴（`BAT_1`〜`BAT_n`）のCSV出力。
- 機体累計台帳のCSV出力。

### 8.3 データインポート（CSV）
- 過去の運航記録や他社ツールで蓄積した飛行データを、新システムへ移行するためのCSV取込機能。
- バリデーション機能（必須項目チェック、日付形式チェック、重複判定）。

## 9. 保存・履歴・監査要件

データの正真性と将来の監査に耐えうる信頼性を確保するための要件です。

### 9.1 記録の原本性・不変性と手修正の調和
- 一度確定した飛行記録には、作成日時、更新日時、端末識別情報、通報ID等のメタデータを記録。
- 誤記や計測誤差による人間による手修正を認める一方、手修正の履歴や理由を記録できる構造（またはスプレッドシートのような直接検証可能な形態）を維持する。

### 9.2 重複保存防止（Idempotency）
- 運航セッションごとに一意のUUIDを発行。
- ネットワーク瞬断時の再試行によって同一フライトが二重登録される事故を構造的に防ぐ。

### 9.3 データの透明性とベンダーロックイン排除
- 特定の独自データベースにデータを囲い込まず、ユーザー自身がいつでも全データをエクスポート・バックアップ可能とすること。
- Googleスプレッドシート等との連携も含め、日常的な閲覧・共有が平易であること。
