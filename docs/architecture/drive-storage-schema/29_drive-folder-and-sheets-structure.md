## 1. 目的と基本思想

本書は、ドローン運航管理システムにおける各運用環境（OperationalEnvironment）のルートストレージ（Google Drive）配下に展開される**「01〜07 物理フォルダー構造」**、および各フォルダー内に配置されるSpreadsheet・テンプレートの物理配置規則を規定します（`CURRENT-ACCEPTED`）。

### 基本思想
1. **人間による可読性・透明性の重視**:
   - アプリを介さずとも、現場責任者や監査担当者がPCやスマートフォンのGoogle Drive/Sheetsから直接フォルダーを開き、日常点検・飛行記録・点検整備履歴・DIPS台帳を目視確認・手動補記できる透明性を維持します。
2. **責務ごとのフォルダー分離（01〜07）**:
   - 人員、機体、バッテリー、運航記録、点検整備、DIPS、派生出力をそれぞれ独立したフォルダーとして分離し、障害や運航頻度の差異が他の台帳に影響しない境界を設けます。
3. **中央集約データベース不保持の低コスト方針**:
   - 本システムでは、全利用者の運航記録・飛行日誌・機材台帳等を一括して集約保持する中央データベース（有償のマルチテナントDBサーバー等）を設けません。
   - 各運用環境が所有するGoogle Drive/Sheetsの容量を正本ストレージとして利用することで、インフラ運用費用を最小化します（※DIPS 2.0 API連携において固定送信元IPアドレスと認証情報隔離を担うGoogle Cloudバックエンドゲートウェイとは責任境界を明確に区別します）。

## 2. 運用環境ルート直下の 01〜07 物理階層ツリー（CURRENT-ACCEPTED）

各運用環境（個人運用環境または組織運用環境）のGoogle Driveルート直下には、以下の7つの物理フォルダーを標準構造として配置します。

```text
<運用環境ルートフォルダー>
 ├ 01_人員管理/
 ├ 02_機体管理/
 ├ 03_バッテリー管理/
 ├ 04_運航記録/
 ├ 05_点検整備記録/
 ├ 06_DIPS関連/
 └ 07_出力_PDF・KML/
```

### 各フォルダーの役割と配置台帳

| フォルダー名 | 役割と配置台帳 | 主なデータ形式・特徴 |
|---|---|---|
| **`01_人員管理`** | 運用環境に所属する人員（Personnel）および認証アカウント（UserAccount）の管理台帳。 | 人員マスターSpreadsheet（業務役割、所属状態、資格情報） |
| **`02_機体管理`** | 保有・運用する機体モデル（AircraftModel）および個別機体（Aircraft）の台帳。 | 機体マスターSpreadsheet（登録記号、機体番号、当方管理累計飛行時間） |
| **`03_バッテリー管理`** | バッテリーモデル（BatteryModel）、個別バッテリー（Battery）、および機材型式互換マッピング（`BatteryCompatibility`）の台帳。 | バッテリー台帳Spreadsheet（型式、シリアル、充電サイクル数、健全性メモ）※特定機体の固定所属としない |
| **`04_運航記録`** | 日常点検および飛行記録の正式正本台帳。操縦者が現場で入力した運航実績の保存先。 | 統合運航記録Spreadsheet（原本テンプレート＋日付連番シート群） |
| **`05_点検整備記録`** | 機体別の生涯点検整備記録（定期点検、修理、改造、部品交換、取得時確認）の保管場所。 | 機体別サブフォルダー ＋ 機体専用点検整備Spreadsheet |
| **`06_DIPS関連`** | DIPS 2.0への通報予定・通報実績スナップショットを恒久保管する台帳。 | DIPS・飛行計画台帳Spreadsheet（手動/API通報履歴、受付番号、提出スナップショット） |
| **`07_出力_PDF・KML`** | 運航帳票PDFや飛行計画KMLなど、外部連携・共有のために派生生成されたファイルの一時/恒久保管場所。 | `PDF/`, `KML/` などの派生出力フォルダー |

## 3. 04_運航記録の物理保存構造とA4原本複製（ADR-0012準拠）

`04_運航記録` フォルダーは、日々の運航における日常点検および飛行記録の正式な保存先です。

### 3.1 原本テンプレートと日付連番シート
1. **原本テンプレートの配置**:
   - `04_運航記録` 直下に、実物手動調整版に準拠した固定A4縦1枚テンプレート（`原本_日常点検・飛行記録` 等）をあらかじめ配置します。
2. **日付複製シートの自動生成**:
   - 現場での運航完了時、操縦者が飛行後点検を済ませて最終送信を実行した時点で、システムは原本テンプレートを複製し、当該日の日付シート（例: `YYYY.M.D`）を自動作成して確定データを記入します（操縦者による手動転記は不要）。
3. **8明細目の同日連番シート使用（`YYYY.M.D_2`）**:
   - 1枚のA4縦シートに収容可能な最大飛行明細行数は「7行」です。
   - 同一日の飛行明細が7行を超過し、8明細目が必要となった場合は、同日連番の新しいA4複製シート（`YYYY.M.D_2`, `YYYY.M.D_3`...）を自動生成して記録を継続します。
4. **機体交代・場所変更時の扱い（PENDING-C1）**:
   - 機体交代や飛行場所切替が発生した場合に、同一シート内で継続するか、新しい別シートへ切り替えるかは、運用内容やDomain層のFlight境界設計に応じて扱うこととし、場所変更それ自体のみを理由に自動的に `_2` シートを発行する一律の確定ルールとはしません（C1運用設計へ保留）。

## 4. 05_点検整備記録の物理保存構造と運用境界

`05_点検整備記録` フォルダーは、機体の生涯にわたる点検整備履歴（国交省様式3相当）を管理します。

### 4.1 物理構造（CURRENT-ACCEPTED）
```text
05_点検整備記録/
 ├ <機体名>_<登録記号>/
 │   └ 点検整備記録 (Spreadsheet)
 └ <機体名>_<登録記号>/
     └ 点検整備記録 (Spreadsheet)
```
- **1機体 = 1フォルダー = 1点検整備Spreadsheet**:
  - 各機体ごとに専用のフォルダーとSpreadsheetを独立して保持します。
  - 機体登録時に、システム（または環境セットアップ処理）が①機体フォルダー、②機体専用点検整備Spreadsheet、③コピー元テンプレート（`原本_点検整備記録`）を用意します。

### 4.2 運用境界と手動原本コピー（CURRENT-PROPOSAL）
- **アプリの責務境界**:
  - アプリが自動で行うのは、機体登録時における上記フォルダー・台帳・原本テンプレートの準備までを基本とします。
- **実記録時における手動原本コピー方式（CURRENT-PROPOSAL）**:
  - 点検整備の実記録時は、操縦者または管理者がGoogle Sheets上で原本テンプレートを手動複製し、`YYYY-MM-DD`（同日複数なら `_02`, `_03`...）のシートを作成して点検整備内容を記入・転記する運用を現在有力な運用案（`CURRENT-PROPOSAL`）としています。
  - 機体別履歴を人間が直接追いやすくするため、点検整備Spreadsheet内での日付タブ増殖を許容する運用方針も、この現在案とセットで位置づけられます（確定事項としての断定は行いません）。
- **実施者Actorと転記者Actorの分離**:
  - 外部修理業者へアプリ直接入力を強制せず、業者報告書・点検結果・交換部品資料等を根拠に、編集権限を持つ利用者が転記できる運用境界を厳守します。

## 5. 端末ローカル下書き・cacheとの接続と保留事項

### 5.1 端末ローカル下書き・cacheとの接続
- **共有正本とローカル複製の関係**:
  - 正式な台帳正本は各運用環境のGoogle Drive/Sheetsです。
  - 端末側のデータ保持（ローカル下書き保護、および端末cache）は、現場での片手操作高速化およびオフライン環境での自律運航を支援するための複製境界です。
- **保存・反映の二段階境界**:
  - 現場進行中の操作はローカル下書きとして端末内に保護されます。
  - 飛行後点検後の最終送信によって、04_運航記録のA4日付シート自動記入、BAT使用実績更新、および機体累計飛行時間の更新が一括して確定反映されます。

### 5.2 保留事項（PENDING-C1）
- **PENDING-C1-SCHEMA**:
  - 各Spreadsheetの具体的セル番地、列定義、ヘッダー行フォーマット。
  - 端末ローカル保存の具体的物理実装技術（IndexedDB / Dexie.js 等は有力候補として `CURRENT-PROPOSAL` に留め、C1スキーマ確定時に最終決定）。
- **PENDING-C1-SYNC**:
  - 具体的なリトライ回数・間隔、オフライン競合解決アルゴリズム（詳細はStep 8の [14_offline-and-sync.md](../14_offline-and-sync.md) にて整理）。
  - 長期運用に伴う年度ごとのSpreadsheetロールオーバー規則（年度別フォルダー分割要否等）。
