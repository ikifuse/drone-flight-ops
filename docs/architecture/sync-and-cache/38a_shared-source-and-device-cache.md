## 1. 本書の位置づけ

本書は「共有データを端末にどう持ち、いつ正本と照らし、offlineで何を最新と扱うか」の意味を保持する。権威のライフサイクルと手修正の保護は[11](../11_data-authority.md)、同期キューの型・再試行・ストレージ保護は[14](../14_offline-and-sync.md)、環境の入口は[34a](../presentation/34a_setup-and-environment-entry.md)、共有飛行リストの画面は[34c](../presentation/34c_shared-flight-worklist.md)、リスト整理の意味は[24b](../dips-submission/24b_dips-plan-records-and-worklist-lifecycle.md)が正本。本書はそれらを再定義しない。

## 2. 共有の正本と端末cacheを分けた因果

**発端（99.2 §9）**: 現場での高速な表示・オフライン耐性と、複数端末での共有を両立する必要がある。

**当初状態（既存Docs）**: 11とADR-0002（Accepted）は、現場運航中は端末のローカルDBが一次権威、外部同期後はSheetsが確定原本・台帳権威とし、手修正を過去データで上書きしないと定めた。14 §1は、マスターを端末のIndexedDBに保持して、オフラインでも選択できるとする。一方、共有のマスターや飛行リストを、いつ正本で確認し、端末のcacheをどう扱うかは記述がなかった。

**現在の到達点（CURRENT-ACCEPTED。99.2 §9）**: 各運用環境のGoogle Drive／Sheetsを共有の正式な正本とし、端末のcacheは、高速表示とoffline時の一時保持のための複製とする。

**11・ADR-0002との関係（既存Docsからの帰結）**: 本書のcacheは、共有のマスター・共有の飛行リスト・確定済みの台帳の複製を指す。現場で作成中の下書きや、未同期の確定データはcacheではなく、11のライフサイクル権威（端末のローカルDBが一次権威）に従う。99.2 §9自身も、飛行計画の確定時に端末へ先行して確定し、飛行中の操作を端末へ逐次保存すると述べる（[38b](38b_confirmation-and-sync-timing-separation.md)）。このため、本書はADR-0002の決定を変更しない（Clarifies、ADR-0026）。

## 3. cacheの捨て方

**現在の到達点（CURRENT-ACCEPTED。99.2 §9）**:

- 人員・機体・BAT等の一般のマスターのcacheは、固定TTLだけで機械的に捨てない。
- 飛行リストは、履歴ではなく将来・当日の作業予定を共有するキューなので、予定日時の経過・飛行完了・飛行中止等の業務状態に基づいて、正本側と端末側の対象の行を整理する（意味は[24b §3](../dips-submission/24b_dips-plan-records-and-worklist-lifecycle.md#3-計画が作業対象でなくなる意味取消整理)）。
- この業務上の期限整理を、一般のcacheを固定TTLで破棄することと混同しない。

## 4. 正本を確認する時点とcacheの表示

**現在の到達点（CURRENT-ACCEPTED。99.2 §9）**:

1. 起動、環境切替、［新規飛行］の開始、［飛行リスト］の表示、飛行前点検の開始等の重要な時点で、正本の更新を確認し、変更のある台帳だけを再取得する。毎画面・毎選択でSheets全体を読み直す方式にはしない。
2. cacheがあれば、まず端末内のデータを即時に表示し、online時に裏側で正本を確認する。
3. 飛行リストは、複数端末・複数人の運用を前提とする。事務担当者が別のPCから新しい計画を通報済みにしている可能性があるため、端末の古いcacheだけを一覧の正本として扱わない。online時に共有Drive／Sheets側の最新の飛行リストを確認して反映し、別端末から追加された計画も表示する。
4. cacheあり＋offlineでは、最後に取得済みの飛行リストやマスターを参照できるが、最新とは断定しない。cacheなし＋offlineでは、未取得の環境は利用できない。
5. onlineで対象がcacheにない場合は、新規登録の前に正本を最新に確認して、重複を減らす。

**CURRENT-PROPOSAL（方向）**: 同期状態は、単なる経過日数ではなく、最終同期日時、未同期の件数、最新確認済みかどうか等で判断する方向。14 §3.4が定める記録ごとの「ローカル保存済／同期待ち／同期済」の表示とは別の、データの鮮度の見方で、置き換えるものではない。

## 5. 未確定・確認待ちと再検討条件

- **PENDING-S7E-CACHE-DETAIL**: cacheの具体的な実装、retryの回数と間隔、競合の解決方針、backgroundの挙動、UIの表示。
- **VERIFY-S7E-DEVICE-DIFF**: iPhoneとAndroidの実機での差。
- **競合の解決方針の限界**: 11 §4.1の競合防止の原則（サイレント上書きの禁止、手修正の保護、人間の確認UI）は維持する。99.2が「競合解決」を未確定とすることを根拠に、A4の採番に排他制御を戻さない。特殊な同時競合専用の高度な対策を採らない判断は[35c §3.3](../operation-recording/35c_a4-operation-record.md#33-特殊な同時競合を検討したうえで簡素な方式を選ぶ理由)に従う。
- 既存のまま維持: PENDING-S5-LIST-DETAIL（34c。共有反映・cache）、PENDING-S5-HOME-DETAIL（offline表現）、34aの環境切替時の未保存作業のPENDING、PENDING-LOCAL-RESTORE（04）。

**再検討条件**: 実機で、cacheの整合や表示が運用に合わないと確認された場合、共有リストの反映の遅れが現場の運用を妨げると確認された場合、正本確認の時点を変える必要が実証された場合。
