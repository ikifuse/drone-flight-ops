# バックエンド候補とセキュリティ比較（02_backend-and-security-comparison.md）

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`

---

## 1. バックエンドが必要となる背景と責務

本アプリにおいて、クライアント（スマートフォン）単体で完結させず、バックエンドを導入する主要な理由は以下の3点です。

1. **DIPS 2.0 APIの秘密情報（client_secret）の保護**:
   - DIPS APIはOpenID Connectの認可コードフローを採用しており、トークン取得時に `client_secret` が必要。これをブラウザやスマホアプリ内に直接保持すると漏洩リスクがあるため、**秘密情報を安全に隠蔽・実行するサーバー境界（APIプロキシ）**が必要。
2. **DIPS APIのCORS（Cross-Origin Resource Sharing）制限の回避**:
   - ブラウザから国交省DIPS APIへ直接Ajax/Fetch通信を行う場合、ブラウザのCORSセキュリティ制限により遮断される可能性が高い。中継サーバーを介することで安全に通信する。
3. **データバックアップとマルチデバイス同期**:
   - iPhone、Pixel、iMac間で同じ運航記録や機体・バッテリー台帳を共有・同期するためのハブ。

## 3. 各候補の詳細評価

### 候補1: Cloudflare Workers + Pages（最有力候補）
- **特徴**: 世界最速のグローバルエッジ環境。Webフロントエンド（Pages）とサーバーレスAPI（Workers）を同一プラットフォームで統合管理できる。
- **長所**:
  - **無料枠が個人利用としては実質無制限**（1日10万リクエスト無料。1人のドローン運航記録なら1日数百回程度であり、完全無料で永久運用可能）。
  - クレジットカード登録不要、コールドスタートが0ミリ秒（待ち時間なし）。
  - `wrangler secret` により、DIPSの `client_secret` やトークン暗号化キーを安全に隔離・保管可能。
  - DIPS APIへのリクエスト中継（リバースプロキシ）が標準の `fetch` APIで極めて軽量・安全に書ける。
- **短所**:
  - Node.jsの特殊なバイナリライブラリは動かない（ただし標準Web API準拠のTypeScript/JavaScriptで全て記述できるため本プロジェクトには無影響）。

### 候補2: Firebase (Google Cloud)
- **特徴**: Googleの提供するBaaS（Cloud Functions, Firestore, Authentication）。
- **長所**: Googleアカウント連携が強力。リアルタイム同期やオフラインSDKが手厚い。
- **短所**:
  - 外部API（DIPS等）へアウトバウンドHTTPリクエストを送る場合、無料の「Sparkプラン」では制限され、従量課金の「Blazeプラン（クレジットカード登録必須）」への移行が必要。
  - Firebase独自SDKにフロントエンドが強く結合し、将来の移行性が下がる。

### 候補3: Supabase
- **特徴**: オープンソース版Firebase。PostgreSQLをバックエンドに持つ。
- **長所**: リレーショナルDB（SQL）が使えるため、機体・バッテリー・フライト記録・点検台帳のデータ整合性を強固に保てる。
- **短所**:
  - 無料枠のプロジェクトは**1週間アクセスがないと自動的に休止（ポーズ）**される仕様がある。個人運用で「数週間ぶりに現場でドローンを飛ばす」際にサーバーが停止しているリスクがあり、現場運用としては致命的。

### 候補4: 現行GAS Backend（Google Apps Script）
- **特徴**: 既存アプリのサーバー側コード（`src/*.gs`）。
- **長所**: 費用ゼロ、Googleスプレッドシートとの親和性が100%。
- **短所**:
  - コールドスタート（初期起動）に5〜10秒以上の待機時間が頻繁に発生し、現場でストレスになる。
  - DIPSのOAuthコールバックやリバースプロキシとして使うにはHTTP仕様上の制約（リダイレクトやヘッダー制御）が厳しく、実装が複雑化する。

### 候補5: 自前サーバー / VPS
- **特徴**: さくらVPS、Linode、ConoHa等のLinuxサーバー。
- **短所**:
  - 月額費用（最低500円〜1,000円）が永久にかかる。
  - OSアップデート、SSL証明書更新、セキュリティパッチの管理など、個人利用の保守負荷が過大。**不採用が妥当**。

## 4. バックエンド選定の結論（方向性）

- **推奨構成**: **Cloudflare Workers + Cloudflare Pages**
  - **理由**:
    1. **費用完全0円**（個人利用のトラフィックでは無料枠を超えることはあり得ない）。
    2. **最高レベルの秘密情報保護**（DIPS APIの `client_secret` をクライアントに出さず、Workersの環境変数/シークレットで安全に保護）。
    3. **コールドスタートなし**（現場で即座に応答）。
    4. **休止リスクなし**（Supabaseのような無アクセス停止ペナルティがない）。
    5. **疎結合の実現**（フロントエンドを標準Fetch通信で作るため、将来バックエンドを別システムへ移行するのも極めて容易）。
