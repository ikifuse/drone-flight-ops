## 1. バックエンドが必要となる背景と設計上の責務

本アプリにおいて、クライアント（スマートフォン）単体で完結させず、バックエンド境界を設けることを検討する主な理由は以下の3点です。

1. **将来のDIPS 2.0 API秘密情報（client_secret等）の保護**:
   - **国交省公式ガイドラインで確認済みの事実**（2026年9月確認）:
     - DIPS 2.0外部接続APIは、OpenID Connect（OIDC）準拠の Authorization Code Flow を採用している。
     - DRS（機体登録系: `drs-utm`）、FPA（飛行許可承認系: `drs-req`）、FPR（飛行計画通報系: `drs-fpl`）の3系統で、それぞれ認可エンドポイント・トークンエンドポイントが規定され、`client_id`, `client_secret`, `redirect_uri`, `access_token`, `refresh_token` を用いる仕様となっている。
   - **現在の公式案内と未確認事項**:
     - 現在の国交省案内ページでは「本サービスは、無人航空機に関する運航管理システム等を整備する法人・団体の方が手続きを行うサービス」と記載されており、個人事業主や個人の利用可否・申請要件は公に未確定である。
     - また、発行される `client_id` / `client_secret` が3系統で共通か個別か、複数realmのSSO運用実態なども未確認である。
   - **設計上の判断**:
     - この利用資格の課題により設計を諦めるのではなく、`client_secret` を安全に保管・中継できるバックエンド境界（プロキシ）を設ける設計とすることで、正式資格・credential取得時にスムーズに接続できる構造を担保する。
2. **CORS（Cross-Origin Resource Sharing）制限の回避**:
   - ブラウザから直接国交省DIPS APIへアクセスする場合、DIPS側がCORSヘッダーを許可していなければ通信が遮断されます。自前の中継プロキシを介することで、ブラウザのCORS制約を受けずに安全にAPI通信を中継できます。
3. **データバックアップとマルチデバイス同期**:
   - 将来的にiPhone、Pixel、iMac間で運航記録や機体台帳を共有・同期するための通信ハブとしての役割。

## 3. 各候補の詳細評価

### 候補1: Cloudflare Workers + Pages（最有力推奨候補）
- **特徴**: グローバルエッジ環境。Webフロントエンド（Pages）とサーバーレスAPI（Workers）を同一基盤で統合管理可能。
- **長所**:
  - **現行無料枠が個人利用に十分**（公式仕様: 1日100,000リクエスト無料。1人のドローン運航記録の利用量であればリクエスト数上限には十分収まる見込み）。
  - クレジットカード登録なしで開始可能。
  - V8 Isolate実行モデルにより、一般的なコンテナ型サーバーレスに見られる数秒のコールドスタートを回避し、現場で極めて低遅延に応答可能。
  - `wrangler secret` により、DIPS認証の `client_secret` や暗号化キーを安全に隔離・保管可能。
  - 標準のWeb `fetch` APIで書けるため、中継プロキシの実装が極めて軽量。
- **短所・注意点（検証課題）**:
  - 無料プランでは「CPU時間 10ms / HTTPリクエスト」およびサブリクエスト数・メモリ上限の制限がある。DIPS認証処理、トークン暗号化、レスポンスのJSONパース等を実装した際に、10ms制限内で安定動作するか実測検証が必要。
  - 将来のCloudflare側の規約・無料枠改定のリスクはゼロではない。

### 候補2: Firebase (Google Cloud)
- **長所**: Googleアカウント連携が強力。リアルタイム同期やオフラインSDKが手厚い。
- **短所**: 外部API（DIPS等）へアウトバウンド通信を行う場合、無料のSparkプランでは制約があり、従量課金プラン（Blazeプラン：カード登録必須）への移行が必要となる。

### 候補3: Supabase
- **長所**: PostgreSQLベースであり、複雑なリレーションのデータ整合性を強固に保てる。
- **短所**:
  - **無料枠の休止仕様**: Supabase公式仕様として、7日間の低アクティビティ（Low activity for 7 days）や十分なユーザーデータベース活動がないプロジェクトは自動的に一時停止（Paused）される。ダッシュボードから手動再開可能だが復帰に数分を要するため、数週間ぶりに現場でドローンを飛ばすような利用形態において、現場で即座に通信・同期できない運用リスクがある。

### 候補4: 現行GAS Backend（Google Apps Script）
- **長所**: 既存アプリの資産を直結でき、追加インフラ費用がかからない。
- **短所**:
  - コールドスタート（初期起動）に5〜10秒以上の待機時間が発生することが多く、現場での軽快な操作感を損ねやすい。
  - DIPSのOAuthリダイレクト処理やHTTPヘッダー制御に独自の制限がある。

### 候補5: 自前サーバー / VPS
- **短所**: 月額費用（最低500円〜1,000円程度）が恒常的に発生し、OSアップデート、セキュリティパッチ管理、SSL更新などの個人運用負荷が過大であるため非推奨。

## 4. バックエンド選定の評価結論

- **推奨方針**: **Cloudflare Workers + Cloudflare Pages** を第一候補とする。
- **推奨理由**:
  1. **現行仕様における費用の適合性**: 個人利用の想定トラフィックであれば、現行の無料枠内で十分に運用可能。
  2. **秘密情報の安全な隔離**: クライアント側に機密情報を露出させず、エッジ側のSecretsで隠蔽できる。
  3. **現場での応答性**: V8 Isolateによる起動遅延の極小化。
  4. **無アクセス休止リスクの回避**: Supabaseのような無アクセス停止ペナルティがない。
  5. **疎結合性**: 標準Fetch通信で構築するため、将来別のバックエンドへ移行する際の影響範囲を最小限に抑えられる。
