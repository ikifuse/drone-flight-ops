## 1. 背景と基本方針

### 1.1 背景と課題
現在、国土交通省の「DIPS 2.0（ドローン情報基盤システム2.0）」API利用申請を行っていますが、以下の重要事項は現時点で**【未確認】**です：
- 個人事業主・個人パイロットに対する利用申請の承認可否
- 固定IPアドレス要件等のネットワーク審査条件を満たせるか
- 正式なcredential（client_id, client_secret）の発行時期および発行可否

もし新アプリが「DIPS APIが利用できること」を前提に設計されていた場合、審査が却下されたり長期化した場合に、アプリ本体の開発が中断し、現場で使えないアプリになってしまいます。
したがって、本アプリは**「DIPS APIが取得できなくても、現場で実用できる完成アプリ」**として設計・実装します。

そのうえで、将来国交省の審査が通りAPIが利用可能になった場合には、内部データ構造や画面を作り直すことなく、最後の提出経路だけを切り替えて自動連携できる無縫製（シームレス）な構造を確立します。

### 1.2 3大設計基本方針
1. **DIPS API非依存完結主義（API-independent Flight Planning）**:
   - DIPS APIが取得できない場合でも、アプリ内で飛行計画（円/ポリゴン/線形バッファ、日時、機体、操縦者、目的、空域、方法、保険、許可等）をスタンドアロンで作成・編集・保存・再利用できます（詳細は [26_dips-web-ui-verification.md](26_dips-web-ui-verification.md) 参照）。
   - **APIは最後の外部送信Adapterに過ぎず、飛行計画機能本体ではありません**。APIなしでも専用の手動入力支援画面を通じてスマートフォン1台で現場運用を完結でき、アプリの完成条件をAPI取得成否に依存させません。
2. **通報前独立台帳退避主義**:
   - DIPS側へ送信（または手動入力）する**前**に、端末ローカルDBへ不変 `submission_snapshot`（意味論的通報スナップショット）を先行保存し、Googleスプレッドシートの「DIPS飛行計画台帳」（確定台帳）へ非同期同期ジョブを登録します。国交省サーバー側の保存期間や参照可能期間に依存せず、利用者側の法令遵守証跡として長期に保持します（Sheets同期完了はDIPS通報の前提条件とせず、障害時でも通報を妨げません）。
   - 出力・連携境界の4原則（Sheets = 確定台帳、PDF = 人間向け帳票、KML = ユーザー向け地図出力、JSON = DIPS API内部通信のみ）に基づき、手動通報経路においてユーザーへJSONファイルを作成・保存・出力・要求することはありません。
3. **誤認防止と不変履歴保持**:
   - 「手動通報ボタンを押したこと」と「DIPS側の通報確認」を混同しない状態管理を徹底します。
   - 飛行計画が後から変更・再通報されても、過去に通報した内容を上書き破壊せず、不変スナップショット（`submission_snapshot`）として全履歴を保持します。

## 2. 全体業務フロー（手動通報 vs API通報 と 運航・離陸Gateの分離）

手動通報と将来のAPI通報は、全く同一の内部飛行計画モデルおよび提出スナップショットを共有し、最後の提出アダプターのみが分岐します。  
また、**「DIPS通報手続き」と「現場アプリでの運航準備（点検等）」は並行して進めることができ、DIPS通信完了を理由にアプリの記録フローをHard Blockしません**。ただし、実際の離陸には**「Legal & Operational Takeoff Gate」**の充足が必須です。

## 4. 不変提出スナップショット（DipsSubmission）と改訂・取消設計

### 4.1 過去提出の上書き破壊禁止
ドローン運航現場では、天候や業務都合により飛行日時や使用機体が直前に変更されることが頻繁にあります。
もし「最新のFlightPlan」のみを保持し過去データを上書き更新した場合、「午前中にDIPSへ何を通報したか」という公的証跡が消滅してしまいます。

そのため、以下の改訂プロトコルを確立します：
1. **不変スナップショットと可変メタデータの厳格分離**:
   - **不変なのは `submission_snapshot`（提出内容全文の意味論的スナップショット）のみ**: 通報準備に入った時点で生成される `submission_snapshot` は一切の改変が禁止されます。API通報経路（Phase C7 Optional）において実際にDIPS APIへ送信した電文 exact JSON が存在する場合は `api_payload_snapshot`（nullable）として記録されますが、手動通報経路においてAPI JSONは生成されず、ユーザー向けJSONファイル出力も行いません。
   - **ライフサイクルメタデータは更新可能**: `status`, `sync_status`, `dips_plan_id`, `confirmation_method`, `submitted_at`, `confirmed_at`, `superseded_by_id`, `cancelled_at` 等の進行状態はライフサイクルに応じて更新されますが、状態遷移の都度 `AuditEvent`（変更理由・日時）を記録し、監査履歴を完全に追跡可能とします。
2. **計画変更と新リビジョン起票**:
   - 計画内容を変更して再通報する場合、`FlightPlan.revision` をインクリメント（例: Revision 1 → Revision 2）し、新しい `submission_id` を持つ別の `DipsSubmission` を起票します。
3. **履歴リンクの形成**:
   - 旧提出（Revision 1）の `superseded_by_id` に新提出IDを記録し、ステータスを `SUPERSEDED` に変更。
   - 新提出（Revision 2）の `supersedes_id` に旧提出IDを記録。
4. **計画取消（Cancellation）**:
   - 運航中止等で計画を取り消す場合、操縦者がDIPS側で取消手続きを実施した上で、アプリ側で「取消」を打刻。
   - `cancelled_at`（取消日時）および `cancellation_reason`（強風、体調不良、機体不調等）を記録し、ステータスを `CANCELLED` に更新。過去スナップショット自体は削除せず長期にわたり保持します。

## 5. 手動入力支援画面（Manual Assistance Screen）の設計

DIPS APIがない場合でも、現場でスマートフォン片手に最小限のストレスでDIPS Web画面へ入力できるよう、専用の「手動入力支援画面」を実装します。

### 5.1 画面仕様
- **上部ナビゲーション**:
  - 「DIPS 2.0 Webを開く」ボタン（タップでブラウザの別タブを起動）。
  - 注意メッセージ: *「※DIPS側へ自動送信はされません。各項目の『コピー』を押し、DIPS画面へ貼り付けて通報してください。」*
- **入力項目カード（各項目にワンタップ『コピー』ボタン付き）**:
  1. **飛行日時**: `2026/10/20 10:00 〜 2026/10/20 12:00` ［コピー］
  2. **飛行場所名称**: `〇〇県〇〇市〇〇町 現場A` ［コピー］
  3. **代表座標 (緯度, 経度)**: `33.456789, 129.876543` ［コピー］
  4. **飛行範囲半径**: `150m` ［コピー］
  5. **計画高度 (対地高度 AGL)**: `30m` ［コピー］
  6. **機体登録記号**: `JU324XXXXXXX` ［コピー］
  7. **操縦者氏名 / 技能証明番号**: `山田 太郎 / 第XXXXX号` ［コピー］
  8. **飛行目的**: `空撮` ［コピー］
  9. **飛行形態**: `昼間飛行・目視内飛行` ［コピー］
  10. **許可承認番号**: `国空航第XXXXX号` ［コピー］
- **下部通報ステータス記録エリア**:
  - **アクション1: 「DIPSへ手動通報した」ボタン**:
    - タップすると `manual_submitted` が打刻され、「手動通報実施を記録（DIPS受付番号の確認待ち）」表示へ遷移。
  - **アクション2: 「DIPS通報確認完了」操作エリア**:
    - **パターンA（受付番号確認時）**: DIPS完了画面等に受付番号が表示された場合、番号（例: `PLN-20261020-XXXX`）を入力して「番号で確認完了」をタップ。`confirmation_method: 'displayed_id'` で `dips_confirmed` へ昇格。
    - **パターンB（飛行計画一覧目視照合時）**: 国交省Web手動操作で受付番号が明示されない場合でも、DIPS「飛行計画一覧」画面で日時・機体・範囲の一致を目視確認し、「一覧照合で確認完了」をタップ。`dips_plan_id: null` のまま `confirmation_method: 'flight_plan_list_match'` で安全に `dips_confirmed` へ昇格。
    - いずれの場合もGoogleスプレッドシート台帳へ確認ステータス・確認方法・番号（取得時のみ）が反映される。

## 6. 状態マシンと誤認防止原則（5大ルール）

### 6.1 状態管理マトリクス

※計画作成・編集中は `FlightPlan.plan_status = 'draft'` で管理され、提出確定時に不変 `submission_snapshot` が生成されて `DipsSubmission` が起票されます（初期状態: **`SNAPSHOT_SAVED`**）。

| 状態名 (State) | 説明 | UI表示 | 法的・運用上の位置づけ |
|---|---|---|---|
| **`SNAPSHOT_SAVED`** | 提出スナップショット保存済 | **「ローカル保存済（DIPS未通報）」** | ローカルDBに不変保存されたが、DIPSへは未提出 |
| **`MANUAL_SUBMIT_WAIT`**| 手動支援画面表示中 | 「手動通報待機中」 | パイロットがDIPSへ入力中（Sheets同期をブロックしない） |
| **`MANUAL_SUBMITTED`** | 手動通報実施を記録 | **「手動通報実施を記録（DIPS確認待ち）」** | **パイロットが打刻したのみ。DIPS受理確認ではない** |
| **`DIPS_CONFIRMED`** | DIPS通報確認完了 | **「DIPS確認完了（確認方法: XXX）」** | 番号入力または一覧照合による確認完了 |
| **`SENDING`** | API送信中 | 「DIPS API通報中...」 | 通信中（Sheets同期完了を待たずに実行可能） |
| **`API_CONFIRMED`** | DIPS公式API受理レスポンス受領 | **「DIPS通報完了（API自動受理・受付番号: XXX）」** | システムによる自動受理確認 |
| **`SUBMISSION_UNCERTAIN`**| API通信切断・タイムアウト | 「通報結果照合中...」 | 成否不明。自動再POST禁止・照合待機 |
| **`RECONCILIATION_REQUIRED`**| 自動照合不能 | 「要確認: DIPS登録状況を照合できません」 | パイロットによるDIPS画面目視確認要求 |
| **`FAILED`** | バリデーションエラー・拒否 | 「通報失敗（要計画修正）」 | 不変履歴として保存（修正時はFlightPlan編集・新Submission起票） |
| **`RETRY_WAIT`** | 一時通信エラー | 「一時通信エラー: 再送待機中」 | 通信復帰後再送 |
| **`SUPERSEDED`** | リビジョン更新 | 「旧版（差し替え済み）」 | 過去履歴保持 |
| **`CANCELLED`** | 計画取消 | 「計画取消済み」 | 取消履歴保持 |

### 6.2 法的・心理的誤認防止の5大ルール
1. **「ローカル保存済」≠「外部台帳同期済」≠「DIPS通報済」の3軸完全分離**:
   - 提出スナップショットが端末に保存された段階（`SNAPSHOT_SAVED`）では、DIPSへの通報もGoogle Sheetsへの同期も未完了です。
   - Google Sheetsへの同期状態（`sync_status`: `local_saved` / `sync_pending` / `syncing` / `synced` / `sync_failed`）は独立して追跡し、UIでも「ローカル保存済」「外部台帳同期待ち」「外部台帳同期済」を混同させません。
   - Sheets同期完了はDIPS通報の必須条件ではありません。Sheets障害時でもDIPS通報は妨げられません。
2. **「手動通報記録」≠「DIPS確認済み」**: パイロットが「手動通報した」ボタンを押しただけではDIPS側の受理証明にはならず、受付番号入力または一覧照合の完了（`DIPS_CONFIRMED`）を別ステップとして要求します。
3. **通報確認方法の明記（受付番号非必須化）**: DIPS Web手動通報で受付番号が取得できない場合でも、計画一覧での照合（`confirmation_method: 'flight_plan_list_match'`）をもって確認完了とでき、API自動受理（`api_response`）や番号入力（`displayed_id`）と明確に区別して記録します。
4. **「MOCK成功」≠「実通報成功」**: テスト用のMock Adapterで成功しても、「[MOCK] 疑似通報完了」と画面上明記し、本番通報と混同させません。
5. **「通報完了」≠「飛行可能」**: DIPS通報完了はいかなる場合も飛行許可そのものではありません。画面上に「飛行計画通報完了。飛行前に周囲の安全・気象・許可条件を必ず確認してください」と注意喚起を表示します。

## 7. 実運航（Mission / Flight / 飛行日誌）との紐付け設計

飛行計画（予定）と実際の飛行日誌（実績）を結合し、後からの監査や運航分析を可能にします。

1. **現場運航開始時の計画選択**:
   - パイロットが現場で運航を開始する際、保存済みの飛行計画一覧から該当する計画を選択可能（スキップして計画なしで運航開始することも可能）。
2. **ID紐付け**:
   - `Mission.planned_flight_plan_id` に飛行計画IDを格納。
   - `Mission.planned_submission_id` に、その飛行に適用されたDIPS提出スナップショットIDを格納。
3. **台帳側の逆引き**:
   - Googleスプレッドシート「DIPS飛行計画台帳」の `linked_mission_id` に、実施されたミッションIDを書き込み。
4. **監査対比**:
   - 「計画した飛行日時・範囲・高度」と「実際の離着陸時刻・飛行時間・点検結果」をワンクリックで対比・確認可能。

## 8. オフライン現場での自律動作と同期順序

山間部や海岸線などの完全電波圏外（機内モード）であっても、運航業務が停止しない自律オフライン設計を徹底します。

### 8.1 処理順序とキューイング
1. **計画作成**: オフラインで地図・範囲・日時を入力。
2. **提出確定**: IndexedDBへ不変 `submission_snapshot` を即時永続化（`SNAPSHOT_SAVED`）。
3. **台帳同期ジョブ登録**: `SyncQueue` に `target: 'spreadsheet_dips_ledger'` の同期ジョブ（`sync_status: sync_pending`）を登録。
   - 圏外時はキュー待機のまま。**Sheets同期完了を待たずにステップ4へ進むことが可能**。
4. **手動通報**: 手動入力支援画面はオフラインでも動作（端末内スナップショットから表示・コピー）。パイロットがDIPS Web等で通報後、手動通報打刻および確認記録（受付番号入力または一覧照合）を実施。
5. **電波復帰時のフラッシュ同期**:
   - 通信が回復した時点で、`SyncQueue` のジョブが順次実行され、Googleスプレッドシートの「DIPS飛行計画台帳」へスナップショット、確認ステータス、確認方法、受付番号が一括反映されます。

## 9. Phase C 実装計画の再編成（API非依存ルートの確立）

DIPS API利用承認の有無がアプリ開発全体のブロッカーとならないよう、Phase Cの実装ロードマップを以下のように再編成します。

```text
C0: 基盤・PWA Shell 構築
 └─► C1: ローカルDB (Dexie.js) & ドメイン層 (FlightPlan, DipsSubmission)
      └─► C2: 現行運航フロー再現 (点検〜離着陸〜BAT交換)
           ├─► C3: バッテリー台帳 & 機体累計管理
           ├─► C4: スプレッドシート外部台帳同期 & DIPS飛行計画台帳新設
           └─► C5: 地図・FlightArea (MapLibre & FlightAreaGeometry, ユーザーKML出力)
                └─► C6: DIPS手動入力支援・Manual/Mock Adapter & 通報状態管理
                     │   ★【DIPS API非依存の主要機能実装完了】
                     ├─► C7: 【Optional】DIPS実API接続中継 (Workers Proxy / API JSON / 審査承認時)
                     ├─► C8: 国交省様式 PDF/CSV 帳票出力 & KML/Google Drive自動保存
                     └─► C9: オフライン強化 & 実機総合検証 (本番運用可能判定)
```

- **API審査却下・未完了時の完成ルート**:
  - C0 → C1 → C2 → C3 → C4 → C5 → C6 →（C7スキップ）→ C8 → C9。
  - DIPS APIが一切なくても、C6でDIPS API非依存の主要機能実装が完了し、C8の帳票機能およびC9の実機総合検証（Shadow Run等）を経て本番運用可能判定を行います。
- **API承認・credential取得時の追加ルート**:
  - C6完了後、または本番運用開始後に、Phase C7（Workers Proxy / `ApiDipsAdapter`）を追加実装するだけで、手動運用からAPI自動通報へシームレスに拡張できます。
