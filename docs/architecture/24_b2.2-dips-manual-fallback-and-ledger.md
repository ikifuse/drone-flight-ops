## 1. 背景と基本方針

### 1.1 背景と課題
現在、国土交通省の「DIPS 2.0（ドローン情報基盤システム2.0）」API利用申請を行っていますが、以下の重要事項は現時点で**【未確認】**です：
- 個人事業主・個人パイロットに対する利用申請の承認可否
- 固定IPアドレス要件等のネットワーク審査条件を満たせるか
- 正式なcredential（client_id, client_secret）の発行時期および発行可否

もし新アプリが「DIPS APIが利用できること」を前提に設計されていた場合、審査が却下されたり長期化した場合に、アプリ本体の開発が中断し、現場で使えないアプリになってしまいます。
したがって、本アプリは**「DIPS APIが取得できなくても、現場で100%実用できる完成アプリ」**として設計・実装します。

そのうえで、将来国交省の審査が通りAPIが利用可能になった場合には、内部データ構造や画面を作り直すことなく、最後の提出経路だけを切り替えて自動連携できる無縫製（シームレス）な構造を確立します。

### 1.2 3大設計基本方針
1. **DIPS API非依存完結主義**:
   - DIPS APIが取得できない場合でも、アプリ内で飛行計画（円/ポリゴン、日時、機体、操縦者）を作成し、専用の手動入力支援画面を通じてスマートフォン1台で現場運用を完結できます。
2. **通報前自社台帳退避主義**:
   - DIPS側へ送信（または手動入力）する**前**に、必ず端末ローカルDBおよびGoogleスプレッドシートの「DIPS飛行計画台帳」へ提出予定内容のスナップショットを保存します。国交省サーバー側の保存期間や参照可能期間に依存せず、自社の法令遵守証跡として半永久的に保持します。
3. **誤認防止と不変履歴保持**:
   - 「手動通報ボタンを押したこと」と「DIPS側の受付番号確認」を絶対に混同しない状態管理を徹底します。
   - 飛行計画が後から変更・再通報されても、過去に通報した内容を上書き破壊せず、不変スナップショットとして全履歴を保持します。

## 4. 不変提出スナップショット（DipsSubmission）と改訂・取消設計

### 4.1 過去提出の上書き破壊禁止
ドローン運航現場では、天候や業務都合により飛行日時や使用機体が直前に変更されることが頻繁にあります。
もし「最新のFlightPlan」のみを保持し過去データを上書き更新した場合、「午前中にDIPSへ何を通報したか」という公的証跡が消滅してしまいます。

そのため、以下の改訂プロトコルを確立します：
1. **スナップショットの不変性（Immutability）**:
   - 通報準備に入った時点で生成される `DipsSubmission` の `payload_snapshot`（通報データ全文）は、後から一切編集できません。
2. **計画変更と新リビジョン起票**:
   - 計画内容を変更して再通報する場合、`FlightPlan.revision` をインクリメント（例: Revision 1 → Revision 2）し、新しい `submission_id` を持つ別の `DipsSubmission` を起票します。
3. **履歴リンクの形成**:
   - 旧提出（Revision 1）の `superseded_by_id` に新提出IDを記録し、ステータスを `SUPERSEDED` に変更。
   - 新提出（Revision 2）の `supersedes_id` に旧提出IDを記録。
4. **計画取消（Cancellation）**:
   - 運航中止等で計画を取り消す場合、操縦者がDIPS側で取消手続きを実施した上で、アプリ側で「取消」を打刻。
   - `cancelled_at`（取消日時）および `cancellation_reason`（強風、体調不良、機体不調等）を記録し、ステータスを `CANCELLED` に更新。過去スナップショット自体は削除せず永久保持します。

## 6. 状態マシンと誤認防止原則（5大ルール）

### 6.1 状態管理マトリクス
| 状態名 (State) | 説明 | UI表示 | 法的・運用上の位置づけ |
|---|---|---|---|
| **`DRAFT`** | 計画策定・編集中 | 「計画編集中」 | 未確定 |
| **`LEDGER_SAVED`** | 提出スナップショット保存済 | **「台帳保存済み（DIPS未通報）」** | 自社台帳に保存されたが、DIPSへは未提出 |
| **`MANUAL_SUBMIT_WAIT`**| 手動支援画面表示中 | 「手動通報待機中」 | パイロットがDIPSへ入力中 |
| **`MANUAL_SUBMITTED`** | 手動通報実施を記録 | **「手動通報実施を記録（DIPS受付番号確認待ち）」** | **パイロットが打刻したのみ。DIPS受理確認ではない** |
| **`DIPS_CONFIRMED`** | DIPS受付番号を目視確認入力 | **「DIPS通報確認完了（手動入力・受付番号: XXX）」** | 人間による番号照合完了 |
| **`SENDING`** | API送信中 | 「DIPS API通報中...」 | 通信中 |
| **`API_CONFIRMED`** | API受理レスポンス受領 | **「DIPS通報完了（API自動受理・受付番号: XXX）」** | システムによる自動受理確認 |
| **`SUBMISSION_UNCERTAIN`**| API通信切断・タイムアウト | 「通報結果照合中...」 | 成否不明。自動再POST禁止・照合待機 |
| **`RECONCILIATION_REQUIRED`**| 自動照合不能 | 「要確認: DIPS登録状況を照合できません」 | パイロットによるDIPS画面目視確認要求 |
| **`FAILED`** | バリデーションエラー | 「通報失敗（要修正）」 | 計画修正が必要 |
| **`RETRY_WAIT`** | 一時通信エラー | 「一時通信エラー: 再送待機中」 | 通信復帰後再送 |
| **`SUPERSEDED`** | リビジョン更新 | 「旧版（差し替え済み）」 | 過去履歴保持 |
| **`CANCELLED`** | 計画取消 | 「計画取消済み」 | 取消履歴保持 |

### 6.2 法的・心理的誤認防止の5大ルール
1. **「台帳保存済み」≠「DIPS通報済み」**: 自社のGoogleスプレッドシートに保存された段階では、DIPSへの通報は一切行われていません。
2. **「手動通報記録」≠「DIPS確認済み」**: パイロットが「手動通報した」ボタンを押しただけではDIPS側の受理証明にはならず、受付番号・計画IDの入力（`DIPS_CONFIRMED`）を別ステップとして要求します。
3. **「API自動受理」と「手動確認」の識別**: 監査ログ上、システム検証（`api_confirmed`）か人間目視確認（`dips_confirmed`）かを明確に区別します。
4. **「MOCK成功」≠「実通報成功」**: テスト用のMock Adapterで成功しても、「[MOCK] 疑似通報完了」と画面上明記し、本番通報と混同させません。
5. **「通報完了」≠「飛行可能」**: DIPS通報完了はいかなる場合も飛行許可そのものではありません。画面上に「飛行計画通報完了。飛行前に周囲の安全・気象・許可条件を必ず確認してください」と注意喚起を表示します。

## 7. 実運航（Mission / Flight / 飛行日誌）との紐付け設計

飛行計画（予定）と実際の飛行日誌（実績）を結合し、後からの監査や自社分析を可能にします。

1. **現場運航開始時の計画選択**:
   - パイロットが現場で運航を開始する際、保存済みの飛行計画一覧から該当する計画を選択可能（スキップして計画なしで運航開始することも可能）。
2. **ID紐付け**:
   - `Mission.planned_flight_plan_id` に飛行計画IDを格納。
   - `Mission.planned_submission_id` に、その飛行に適用されたDIPS提出スナップショットIDを格納。
3. **台帳側の逆引き**:
   - Googleスプレッドシート「DIPS飛行計画台帳」の `linked_mission_id` に、実施されたミッションIDを書き込み。
4. **監査対比**:
   - 「計画した飛行日時・範囲・高度」と「実際の離着陸時刻・飛行時間・点検結果」をワンクリックで対比・確認可能。

## 8. オフライン現場での自律動作と同期順序

山間部や海岸線などの完全電波圏外（機内モード）であっても、運航業務が停止しない自律オフライン設計を徹底します。

### 8.1 処理順序とキューイング
1. **計画作成**: 完全オフラインで地図・範囲・日時を入力。
2. **提出確定**: IndexedDBへ不変スナップショットを即時永続化。
3. **台帳同期ジョブ登録**: `SyncQueue` に `target: 'spreadsheet_dips_ledger'` の同期ジョブを登録。
   - 圏外時は `local_saved` 状態でキュー待機。
4. **手動通報**: 手動入力支援画面はオフラインでも完全動作（端末内スナップショットから表示・コピー）。パイロットが手動通報完了および受付番号を記録。
5. **電波復帰時のフラッシュ同期**:
   - 通信が回復した時点で、`SyncQueue` のジョブが順次実行され、Googleスプレッドシートの「DIPS飛行計画台帳」へスナップショットおよび受付番号が一括反映されます。

## 9. Phase C 実装計画の再編成（API非依存ルートの確立）

DIPS API利用承認の有無がアプリ開発全体のブロッカーとならないよう、Phase Cの実装ロードマップを以下のように再編成します。

```text
C0: 基盤・PWA Shell 構築
 └─► C1: ローカルDB (Dexie.js) & ドメイン層 (FlightPlan, DipsSubmission)
      └─► C2: 現行運航フロー再現 (点検〜離着陸〜BAT交換)
           ├─► C3: バッテリー台帳 & 機体累計管理
           ├─► C4: スプレッドシート外部台帳同期 & DIPS飛行計画台帳新設
           └─► C5: 地図・FlightArea (MapLibre & GeoJSON)
                └─► C6: DIPS手動入力支援・Manual/Mock Adapter & 通報状態管理
                     │   ★【アプリ本体コア完成・DIPS API未承認でも現場実運用可能】
                     ├─► C7: 【Optional】DIPS実API接続中継 (Workers Proxy / 審査承認時)
                     ├─► C8: 国交省様式 PDF/CSV 帳票出力 & DIPS計画台帳出力
                     └─► C9: オフライン強化 & 実機結合検証 (手動運用を本番基準)
```

- **API審査却下・未完了時の完成ルート**:
  - C0 → C1 → C2 → C3 → C4 → C5 → C6 →（C7スキップ）→ C8 → C9。
  - DIPS APIが一切なくても、アプリ本体および手動通報・台帳運用は完全に完成し、本番リリースできます。
- **API承認・credential取得時の追加ルート**:
  - C6完了後、または本番運用開始後に、Phase C7（Workers Proxy / `ApiDipsAdapter`）を追加実装するだけで、手動運用からAPI自動通報へシームレスに拡張できます。

## 10. 事実・設計判断・未確認事項の区分一覧

本設計において依拠している前提条件を、客観的根拠に基づいて厳格に分類します。

| 項目 | 区分 | 根拠・内容 |
|---|:---:|---|
| **国交省DIPS標準様式1〜3** | **確認済み事実** | 航空法第132条の89、施行規則第236条の84、無人航空機の飛行日誌の取扱要領で規定 |
| **DIPS 2.0 認証レルム（DRS/FPA/FPR）** | **確認済み事実** | 国交省公式外部連携API仕様書で規定（drs-utm, drs-req, drs-fpl） |
| **DIPS 2.0 APIの利用申請状況** | **確認済み事実** | 現在、国交省へ利用申請提出中・審査待ち |
| **DIPS飛行計画台帳の自社保持** | **設計判断** | DIPS側の保存期間に依存せず、過去の通報内容を自前で半永久保全するための設計 |
| **手動通報アダプターの第一級化** | **設計判断** | API取得不可時でもアプリ完成を阻害しないための基幹アーキテクチャ判断 |
| **不変スナップショット（DipsSubmission）** | **設計判断** | 計画変更・再通報時に過去の公的通報内容を上書き破壊しないための設計 |

| **固定IP等のネットワーク審査条件** | **未確認事項** | 個人環境で満たすべきIP要件等の詳細は国交省の審査・回答待ち |
