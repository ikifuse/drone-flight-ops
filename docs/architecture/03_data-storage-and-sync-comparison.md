# データ保存方式と同期モデルの比較（03_data-storage-and-sync-comparison.md）

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`

---

## 1. 比較対象のデータ保存方式

本アプリで扱うデータ（飛行計画、点検記録、離着陸実績、バッテリー個別履歴、機体累計台帳）をどこに永続化し、何を「正本（SSoT: Single Source of Truth）」とするかについて、以下の5方式を比較します。

1. **方式1: Googleスプレッドシート完全正本方式（現行自作アプリ踏襲）**
   - すべてのデータをGoogleスプレッドシートに直接書き込み・読み込み。
2. **方式2: クラウドDB完全正本方式（一般的なWeb/SaaSモデル）**
   - サーバー上のDB（Firestore / PostgreSQL等）を正本とし、端末はオンラインで問い合わせる。
3. **方式3: ローカルDB完全正本方式（スタンドアロン・端末完結モデル）**
   - 端末内（IndexedDB / SQLite）にすべて保存。外部にはPDF/CSV出力のみ。
4. **方式4: ローカルDB正本 ＋ クラウドDB同期（モダン・ローカルファーストモデル）**
   - 端末内DBを主とし、通信可能時にバックグラウンドでクラウドDB（Cloudflare D1等）へ双方向同期。
5. **方式5: 【ハイブリッド】ローカルDB正本 ＋ Googleスプレッドシート連携（同期・帳票出力）**
   - 現場の打刻・オフライン記録は端末内DBで100%高速完結。
   - 運航完了時、または電波回復時に、操縦者のワンタップでGoogleスプレッドシートへ自動反映（台帳・共有・印刷原本として活用）。

## 3. 各方式の詳細分析

### 方式1（スプレッドシート単独）の限界
- 現行アプリで確立された利点（透明性、修正性、監査性）を持ちますが、新アプリで「山間部・圏外でのオフライン継続」を目指す場合、**現場での保存時に通信必須となる点が制約**となります。

### 方式2（クラウドDB単独）の難点
- 一般的なSaaSで多用されますが、「人間が直接データを確認・手修正できない（ブラックボックス化する）」という側面があります。また、手動補記や国交省への原本提示のために、複雑な管理画面や帳票印刷UIをすべて自前で作り込む必要があります。

### 方式3（ローカルDB単独）の危険性
- オフライン性能は高いですが、スマートフォンを紛失・水没・破損させた場合や機種変更時に、航空法上保管義務のある法定飛行日誌が失われるリスクがあり、外部バックアップが不可欠です。

### 方式5（ローカル優先保存 ＋ スプレッドシート連携）の優位性
- **自作アプリの強みと現場オフライン運用の調和**:
  1. **現場での操作**: 端末内ローカルストレージ（IndexedDB等）へ即時に永続化されるため、通信圏外でも通信待ちを発生させずに点検・打刻・日誌入力が進められる。
  2. **電波復帰後・運航完了後**: 「スプレッドシートへ送信・同期」を行うことで、日常点検シート、BAT個別シート、機体原本累計へデータを安全に流し込む。
  3. **監査・手修正の担保**: 人間がスプレッドシート上で直接確認・手動補記・修正ができ、手修正後の計算継続思想も活かせる。

## 4. 「正本（SSoT）」の定義に関する検討とPhase B2への課題

B1段階では、ローカルDBとスプレッドシートのどちらかを単一の「最終原本」として拙速に固定することは避けます。データの状態やライフサイクルに応じて、以下の4つの権威モデルを比較候補としてB2へ申し送ります。

- **モデルA（ローカルDB正本モデル）**:
  - 端末内DBを正本（マスター）とし、スプレッドシートは閲覧・バックアップ・帳票印刷用の外部ビューとして扱う。
- **モデルB（スプレッドシート正式原本モデル）**:
  - スプレッドシートを唯一の正式原本とし、端末内DBは現場での一時的な未送信・下書きデータ（キュー）として扱う。
- **モデルC（クラウドDB正本モデル）**:
  - クラウドDBを正本とし、端末およびスプレッドシートはクライアント・出力先として同期する。
- **モデルD（ライフサイクル連動型ハイブリッドモデル・有力候補）**:
  - 「飛行実績の生データ（離着陸時刻・飛行時間）」は現場端末側を第一権威とし、「外部台帳・機体累計・手修正後の確定値」はスプレッドシート側を権威とする。
  - 各記録にステータス（作成中／未同期／同期済み／手動修正済み／監査確定）を持たせ、B2で詳細な競合解決・同期プロトコルを設計する。

※ 正本モデルはB1段階で決め打ちせず、Phase B2（詳細設計）において、手動補記・修正後の再同期・競合解決の具体的なデータフローを検証した上で最終確定します。

## 5. オフライン時におけるDIPS飛行計画通報の法令・運用上の厳格な区別

オフラインファースト設計において、業務データ（点検・飛行日誌・バッテリー記録）と、国土交通省へのDIPS飛行計画通報は**法的に全く異なる扱い**をしなければなりません。

1. **現場業務データ（点検・離着陸・バッテリー・日誌）**:
   - オフライン環境でも端末内ローカルDB（IndexedDB等）に即時保存され、現場での業務を継続可能。
2. **DIPS飛行計画通報（特定飛行等に必要な通報義務）**:
   - **重要**: 飛行計画通報が必要な運航において、オフラインキューにデータを保存しただけで**「通報要件充足」「飛行可能」として扱ってはならない**。
   - 航空法および国交省の通達上、飛行計画は飛行前にあらかじめ国交省DIPSへ通報が完了している必要がある。また、通報が成功したことと総合的に飛行可能であることは別問題であり、必要な許可承認、空域条件、施設管理者との調整、気象条件等の確認が別途必要となる。
   - したがって、端末内に保存された状態はあくまで**「通報データ作成済み・送信待ち」**であり、**「DIPS通報成功確認済み」**とは明確に区別する。
   - B2の設計において、以下のステータス管理を必須要件とする：
     - `未作成` → `作成済み` → `送信待ち` → `送信中` → `DIPS通報成功確認済み`（国交省サーバーからの受付番号/確認レスポンス受領により通報要件充足状態へ遷移。※総合的な飛行可否判定と同一視しない）
     - 電波不通時やエラー時は `送信待ち`、`通報失敗`、`再送待ち` として扱い、通信復帰後にユーザーの明示的確認または自動リトライによって通報を完了させる。
