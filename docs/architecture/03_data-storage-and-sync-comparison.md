# データ保存方式と同期モデルの比較（03_data-storage-and-sync-comparison.md）

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`

---

## 1. 比較対象のデータ保存方式

本アプリで扱うデータ（飛行計画、点検記録、離着陸実績、バッテリー個別履歴、機体累計台帳）をどこに永続化し、何を「正本（SSoT: Single Source of Truth）」とするかについて、以下の5方式を比較します。

1. **方式1: Googleスプレッドシート完全正本方式（現行自作アプリ踏襲）**
   - すべてのデータをGoogleスプレッドシートに直接書き込み・読み込み。
2. **方式2: クラウドDB完全正本方式（一般的なWeb/SaaSモデル）**
   - サーバー上のDB（Firestore / PostgreSQL等）を正本とし、端末はオンラインで問い合わせる。
3. **方式3: ローカルDB完全正本方式（スタンドアロン・端末完結モデル）**
   - 端末内（IndexedDB / SQLite）にすべて保存。外部にはPDF/CSV出力のみ。
4. **方式4: ローカルDB正本 ＋ クラウドDB同期（モダン・ローカルファーストモデル）**
   - 端末内DBを主とし、通信可能時にバックグラウンドでクラウドDB（Cloudflare D1等）へ双方向同期。
5. **方式5: 【ハイブリッド】ローカルDB正本 ＋ Googleスプレッドシート連携（同期・帳票出力）**
   - 現場の打刻・オフライン記録は端末内DBで100%高速完結。
   - 運航完了時、または電波回復時に、操縦者のワンタップでGoogleスプレッドシートへ自動反映（台帳・共有・印刷原本として活用）。

## 3. 各方式の詳細分析

### 方式1（スプレッドシート完全正本）の限界
- 現行アプリで大成功している思想（透明性、修正性、監査性）ですが、新アプリで「山間部・圏外でのオフライン完全動作」や「地図ポリゴンの高速保存」を目指す場合、**現場での保存時に通信必須となる点が最大のボトルネック**になります。現場で電波が圏外の時、運航記録が保存できないリスクを排除できません。

### 方式2（クラウドDB正本）の難点
- 一般的なSaaSで使われますが、「人間が直接データを確認・手修正できない（ブラックボックス化する）」という致命的な弱点があります。また、手動補記や国交省への原本提示のために、複雑な管理UIや帳票印刷UIをすべて自前で作り込まなければなりません。

### 方式3（ローカルDB単独）の危険性
- オフライン性能は最高ですが、スマホを落として破損・水没させたり機種変更した瞬間に、航空法上3年間の保管義務がある法定飛行日誌が全喪失するリスクがあります。バックアップ機構が不可欠です。

### 方式5（ローカルDB正本 ＋ スプレッドシート連携）の圧倒的優位性
- **自作アプリの強みとオフライン現場運用の完全な融合**:
  1. **現場での操作**: 端末内（IndexedDB等）に即時永続化されるため、完全圏外でも1ミリ秒で打刻・記録が完了。誤操作や電池切れでも直前の画面状態が100%復元される。
  2. **電波復帰後・運航完了後**: 「スプレッドシートへ送信・同期」を押すことで、既存の日常点検シート、BAT_1〜BAT_7個別シート、機体原本累計へデータが美しく流し込まれる。
  3. **監査・法令対応**: 人間がスプレッドシート上で直接確認・手動補記・修正ができ、手修正後の計算継続思想もそのまま生きる。

---

## 4. データ保存方式の結論（方向性）

- **推奨構成**: **方式5（ローカルファーストDB ＋ Googleスプレッドシート連携ハイブリッド）**
  - **現場での正本（実行時SSoT）**: 端末内ローカルDB（IndexedDB / Dexie.js等）
  - **最終的な法定台帳・保管原本（永続SSoT）**: Googleスプレッドシート ＋ 定期エクスポート（PDF/CSV）
  - これにより、**「圏外でも絶対に現場作業が止まらない超高速動作」**と、**「人間が直接見て直せる・印刷できる絶対的な安心感と透明性」**を両立させます。
