# 36. 機体別点検整備記録と原本コピー運用

最終更新: 2026-09-18\
由来: 99.2 §6のStep 3未移植部分、保存原則との接続は§10。取得時判断とActorの詳細は[32c](../asset-management/32c_acquisition-check-and-maintenance-actors.md)。

## 1. 通常の日常点検から分離する理由

**当初状態**: 基準[12e](../domain-model/12e_operation-inspection-maintenance.md)は日常点検とMaintenanceRecordを別Entityにしていた。[24a](../dips-submission/24a_submission-and-sheets-ledger.md)とADR-0007は全機体共通の行追加型台帳を掲げ、物理シート増殖を一律に禁じていた。独立した整備の生涯責任と正規化の意図は有効だが、実際に人が記録・閲覧する媒体まで一律に同じ構造とする部分を後から再検討した。

**問題・理由**: 通常飛行の飛行前／飛行後の日常点検と、定期点検・臨時点検・修理・改造・部品交換等は性質・発生時点・入力の詳しさが異なる。詳細な整備入力フォームを通常飛行に混ぜると、現場の流れと機体別の整備履歴の責任が混在する。

**現在到達点（CURRENT-ACCEPTED）**: 通常日常点検は運航記録へ、詳細点検整備は05の機体別記録へ分ける。整備履歴は運航のたびにゼロから作るものではない。A4の日常点検や記事・不具合・処置欄を、詳細な整備台帳全体と同一視しない。

## 2. 1機体1フォルダー1Spreadsheetに至る因果

**根拠（EVIDENCE/EXAMPLE）**: §6は実Driveの05、複数の機体別Spreadsheet、旧整備原本・旧技術モックを挙げている。取得確認の実記録もその一つであるが、内容・実施者／転記者の因果は32cに一元化する。今回、実Driveを再操作・編集したものではなく、実名・登録記号・Drive IDは公開文書へ複写しない。

**検討と変更理由**: 物理タブを避ける旧一般方針と、人が機体ごとの整備履歴を直接追う方法を比較した結果、後者の見通しを優先した。データベースの正規化を否定する判断ではなく、人間が読む整備記録の単位に対する意図的例外である。

**現在構造（CURRENT-ACCEPTED）**:

```text
<OPERATIONAL_ENVIRONMENT_ROOT>
└ 05_点検整備記録
  └ <AIRCRAFT>
    └ 点検整備記録 Spreadsheet
      ├ 原本_点検整備記録
      ├ YYYY-MM-DD
      ├ YYYY-MM-DD_02
      └ YYYY-MM-DD_03 …
```

基本は1機体＝1フォルダー＝1点検整備Spreadsheet。`<AIRCRAFT>`は機体別の識別単位を示す抽象表記で、実物の名称・登録記号や製品全体の命名規則を固定しない。機体登録時にアプリが機体フォルダー、機体専用Spreadsheet、コピー元「原本_点検整備記録」を用意する。

## 3. 自動準備と人による実記録の境界

**CURRENT-ACCEPTED**: アプリが自動で担う範囲は機体登録時の上記3点の準備まで。実際の整備記録では操縦者がGoogle Sheets上で原本を手動コピーし、`YYYY-MM-DD`、同日複数なら`_02`、`_03`等の記録タブを作る。通常運航の最終保存処理へこの手動コピーを統合しない。

コピー後はSpreadsheetのDrive編集権限を持つ利用者が実態どおり記入・転記できる。実施者・コピー者・転記者・外部業者の意味、本人入力を強制しない理由は[32c §3](../asset-management/32c_acquisition-check-and-maintenance-actors.md#3-実施者と作成転記者を分ける理由)、機能権限とGoogle実アクセスの分離は[31b](../identity-and-access/31b_roles-and-access-control.md)を参照する。本書ではActorの詳細を再定義しない。

## 4. 例外を消さず、他領域へ広げない

**採らない案と理由**: 「機体ごとの恒久タブ禁止」「正規化が普通」という一般論だけで機体別Spreadsheet・原本コピーを廃止すると、機体の整備履歴を人が直接追えるという判断理由が失われる。逆に本例外から、BAT個体やDIPSの全履歴も件数ごとに別タブへ戻すことは導かない。

内部の通常履歴を行追加・正規化で扱う原則と、人間向け媒体の例外の関係は[Drive責任構造37](../drive-structure/37_environment-storage-responsibilities.md)へ接続する。旧中央MaintenanceRecords／AircraftMaintenanceIndexのモックは概念や探索を試した証拠であり、現行の必須中央表・索引schemaとして復活させない。機体別の記録を検索・参照する具体的方式は未確定として残す。

## 5. 未確定と検証観点

- **PENDING-S6-MAINTENANCE-PHYSICAL**: 機体フォルダーの製品命名・識別との対応、索引／参照方法、テンプレートの版と更新、コピー時の衝突・重複・部分生成回復、長期運用の分割。到達済みの1機体1Spreadsheet・手動原本コピーそのものを未決へ戻すものではない。
- Actorの具体FK・根拠資料との関連等は**PENDING-S3-MAINTENANCE-ACTOR**、取得確認の物理保持は**PENDING-S3-ACQUISITION-RECORD**を32cへ残す。本Stepで新たなテーブルを決めない。
- **VERIFY-S6-MAINTENANCE-EVIDENCE**: 05の機体別実物・原本・記録タブと、原本に記録された運用との照合。記録の存在だけで全列・権限・自動準備の動作を検証済みにしない。
- **検証する意味**: 通常飛行に詳細整備入力を混ぜず、機体ごとの履歴が追え、手動コピー後に権限ある転記者が実施者の事実を保持できること。Googleの実アクセスを超えるアプリ権限や外部業者のログイン必須を作らない。
