## 1. 帳票生成の責務分離（3層構造）

帳票生成ロジックをUIコンポーネントやデータベーススキーマに直接記述することを禁止し、以下の3層パイプラインで責務を分離します。

```text
┌────────────────────────────────────────────────────────┐
│ [第1層] ドメインエンティティ (Domain Entities)         │
│   Mission, Flight, Aircraft, DailyInspection,          │
│   MaintenanceRecord, Personnel, Location, Permission 等│
└───────────────────────────┬────────────────────────────┘
                            │ (ReportModelBuilder による射影・集計)
                            ▼
┌────────────────────────────────────────────────────────┐
│ [第2層] 帳票データモデル (Report View Models)          │
│   IntegratedOperationReportDTO, FlightLogReportDTO     │
│   - 生成対象の帳票に対応したレイアウトデータ      │
│   - 機体累計計算、時刻フォーマット、表示文字列解決済   │
└───────────────────────────┬────────────────────────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
┌─────────────────┐ ┌────────────────┐ ┌────────────────┐
│  PDF Generator  │ │ CSV Generator  │ │Excel Generator │
│ (pdf-lib / Canvas)│ (RFC 4180準拠)  │ (ExcelJS / Sheets)│
└─────────────────┘ └────────────────┘ └────────────────┘
```

### 1.1 確定台帳・Geo Export・内部通信との関係

本書はPDF/印刷/CSV/Excelの生成パイプライン・射影責任を定義します。A4の実物・分割・日付連番シートと因果の詳細正本は[35c](operation-recording/35c_a4-operation-record.md)です。Sheetsは確定台帳、KMLは地理表示・共有、JSONはOptional DIPS APIの内部transportです。4境界の全体契約は [27 出力境界](output/27_output-boundaries.md) を参照します。KML導入によりPDF生成要件やSheets保存を縮小しません。

同一のDomain正本データから、帳票は `ReportModelBuilder -> PdfGenerator`、KMLは `KmlExportModelBuilder -> KmlExporter` として独立生成します。KMLはPDF帳票・Sheets台帳の代替ではありません。

---

### 1.2 帳票を先に確かめる設計順序と内部責務

`5d51315`で導入した[ADR-0007](../decisions/ADR-0007-normalized-masters-and-business-reporting.md)の正規化と本書の3層構造は、旧印刷枠に内部モデルが縛られる問題を避けるための設計である。この経緯を、利用者が必要な帳票を後回しにする理由には使わない。

99.2 §0・§1からの現在ベースラインは、[00_goal §1.1](../00_goal.md#11-記入支援を中心に置くまでの因果)に示す記録・出力・保存先からの設計である。帳票の成立を確認してから、それを支える保存・射影・入力を設計する。上図は実装時のデータの流れであり、要件を決める順序ではない。旧§3.4の「帳票のセル構造に合わせて整備DBを設計しない」は、整備記録の生涯責務を個々の印刷枠へ従属させない意味で維持する。

人間向け一枚の帳票・台帳を技術都合で分割する場合の理由・影響・合意は[設計証拠規約§5](../guidelines/03_design-evidence-and-causality.md#5-質問と技術判断の境界)、保存・更新関係の確認は[開始ゲート](23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)に従う。Step 1はその設計方法までを扱った。Step 6では最新Drive実物を直接確認し、§5・§6残り・§10の因果を35a〜35d／36／37へ移した。以下はその限定範囲の更新であり、KML・§9同期全体の移植完了ではない。

## 2. 出力帳票種別とデータソース対応

本システムでは、現場で実用的に使用する**「A4縦 統合運航帳票」**と、公的機関への提出等で必要となる**「国交省標準様式（様式1・2・3別）」**を概念上明確に分離します。双方は同一の正規化ドメインデータから生成されます。

| 帳票名 | 出力形式 | 主な内容・運用/法的根拠 | 出力タイミング・対象 |
|---|:---:|---|---|
| **A4縦 運航・日常点検記録** (`IntegratedOperationReport`) | Sheets / 印刷 / 必要時PDF | 最新実物の固定7明細・前後点検・記事等。[35c](operation-recording/35c_a4-operation-record.md)が詳細正本 | 最終保存で04の対象機体Spreadsheetへ記録、PDFは必要時07へ |
| **国交省様式1: 飛行記録** | PDF / CSV | 年月日、操縦者名、離着陸場所、離着陸時刻、飛行時間、飛行理由、不具合事項（航空法第132条の89関係） | 公的提出時、機体別月間台帳 |
| **国交省様式2: 日常点検記録** | PDF / CSV | 作成年月日、点検実施場所、点検項目合否、不具合処置（飛行前・飛行後点検） | 公的提出時、日誌監査 |
| **国交省様式3: 点検整備記録** | PDF / Excel | 点検整備実施日時、実施理由（定期/修理）、実施内容、実施者名、交換部品 | 機体生涯整備台帳出力時 |
| **地図付き飛行計画書** | PDF | 計画概要、飛行範囲地図（静止画レンダリング）、高度、周辺注意事項 | 計画作成後（事前印刷/提出用） |
| **DIPS飛行計画台帳・提出履歴**| CSV / Excel / Sheets | 計画ID、リビジョン、提出日時、通報方式(手動/API)、DIPS計画番号、飛行予定日時、場所、機体、操縦者、取消情報、紐付運航実績ID（予定と実績の監査対比） | 計画確定時、監査提出時 |
| **バッテリー生涯履歴台帳** | CSV / Excel | 個体別、累積サイクル数、累積飛行時間、異常メモ（旧スロット表示からの因果は[32b](asset-management/32b_battery-sharing-and-acquisition-history.md)） | 定期台帳点検時 |

## 4. Domain・帳票射影・発行記録の分離

**維持する責任分離**: 内部の実績を帳票用データモデルへ射影し、生成器が出力する。帳票の7枠からDomainのFlight数やPK／FKを逆算しない。ReportUnit／OperationLegは旧案で用いた射影単位名で、最終schemaや永続化単位の決定ではない。旧Mission → 機体ID×場所ID×区間 → ReportUnitという固定対応は、[35aのPENDING](operation-recording/35a_flexible-flight-and-details.md#5-未確定と検証境界)と35cの現行生成単位を照合してから具体化する。

**発行時の記録**: ReportSnapshotは発行した帳票の当時の内容・ハッシュ等を追う責任を持つ。04のSheets記録を最終保存することと、PDFを毎回必ず自動発行することは別である。必要時PDFと固定A4実物の責任は35c、発行記録の属性候補は[12e](domain-model/12e_operation-inspection-maintenance.md)。媒体間対応・テンプレート版・再生成の具体契約は未確定であり、発行記録だけで保存完了の証明が完成したとはしない。

## 5. 法令要件とUIの分離（現場負荷の極小化）

国交省標準様式のすべての項目を現場の入力フォームとして画面に並べることは**「現場片手操作の破壊」**につながるため厳禁とします。

ガイドラインで定めた**「法令8区分」**を徹底し、入力の手間を極小化します。

```text
【国交省標準様式の項目】
  ├─ [自動取得] 離着陸時刻、飛行時間、年月日、機体登録記号、型式 → GPS・時計・機体マスターから自動入力
  ├─ [既定値]   点検項目（プロペラ・モーター等） → 「全項目正常」ボタンで1タップ一括充足
  ├─ [条件発生時入力] 不具合事項、特記事項 → 異常発生時のみ入力欄を展開
  └─ [他台帳・手動補記] 包括許可番号、整備記録原本 → 別紙台帳または事後スプレッドシート手動補記で充足
```
- **設計目標**: 現場の操縦者が行う操作は、**「点検正常タップ」→「離陸」→「着陸」→「BAT選択」→「終了」**の最小限のタップ数で完結しながら、出力されるPDFは国交省取扱要領で求められる記録項目を満たすことを目標とし、Phase Cで標準様式1〜3との項目照合テストを実施します。現行アプリで確立された「別紙参照・手動補記・柔軟運用」もそのまま尊重します。

## 6. オフラインPDF生成の成立条件

端末がオフライン（圏外）である場合のPDF生成は、帳票の性質に応じて以下の条件付き動作とします。

1. **帳票本文PDF（統合運航帳票・様式1〜3・バッテリー台帳）**:
   - **条件**: `pdf-lib` ライブラリおよび日本語フォント（Noto Sans JPサブセット等）がPWA Service Workerによって端末へ事前キャッシュされていること。
   - **挙動**: 端末内IndexedDBからデータを抽出し、完全にオフラインでPDFを生成・端末内保存可能。
2. **地図画像付き飛行計画書PDF**:
   - **条件**: 背景となる国土地理院タイル等の地図画像がブラウザキャッシュまたはオフライン領域に事前保存されていること。
   - **フォールバック**: 該当エリアの地図タイルがキャッシュされていない圏外環境では、地図画像領域に「※オフラインのため地図画像未取得」の注記を行い、代わりに飛行範囲の緯度経度座標リスト・半径数値を印字してPDF生成を中断させないフェイルセーフ設計とします。

## 7. 人物役割の正本への接続

操縦者・記録者を帳票の別欄で保持する要件、日常点検実施者の意味、法定欄とアプリ独自Recorderを分けた因果は[31c](identity-and-access/31c_operational-actors.md)を正本とする。本書はその射影先であり、役割規則を複製しない。具体的な欄・配置はStep 6の[35c](operation-recording/35c_a4-operation-record.md)、物理schemaの未確定は35a／35dへ接続する。

Step 5では[34b](presentation/34b_home-and-navigation.md)へ［飛行履歴・出力］の入口責任だけを移した。04／06を確認して07の派生出力へ進む画面接続であり、本書のA4帳票・射影・出力単位の再移植や変更ではない。

Step 6のA4印刷経路・実物とのフォント／改行一致は35cのVERIFY-S6-A4-PRINT。§6の端末PDF生成条件はその検証完了を意味しない。
