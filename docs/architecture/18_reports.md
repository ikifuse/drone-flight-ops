## 1. 帳票生成の責務分離（3層構造）

帳票生成ロジックをUIコンポーネントやデータベーススキーマに直接記述することを禁止し、以下の3層パイプラインで責務を分離します。

```text
┌────────────────────────────────────────────────────────┐
│ [第1層] ドメインエンティティ (Domain Entities)         │
│   Mission, Flight, Aircraft, DailyInspection,          │
│   MaintenanceRecord, Personnel, Location, Permission 等│
└───────────────────────────┬────────────────────────────┘
                            │ (ReportModelBuilder による射影・集計)
                            ▼
┌────────────────────────────────────────────────────────┐
│ [第2層] 帳票データモデル (Report View Models)          │
│   IntegratedOperationReportDTO, FlightLogReportDTO     │
│   - 1枚の帳票・続紙に1対1対応したレイアウトデータ      │
│   - 機体累計計算、時刻フォーマット、表示文字列解決済   │
└───────────────────────────┬────────────────────────────┘
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
┌─────────────────┐ ┌────────────────┐ ┌────────────────┐
│  PDF Generator  │ │ CSV Generator  │ │Excel Generator │
│ (pdf-lib / Canvas)│ (RFC 4180準拠)  │ (ExcelJS / Sheets)│
└─────────────────┘ └────────────────┘ └────────────────┘
```

### 1.1 確定台帳・Geo Export・内部通信との関係

本書はPDF/印刷/CSV/Excelの帳票射影・区切り・続紙を正本として定義します。Sheetsは確定台帳、KMLは地理表示・共有、JSONはOptional DIPS APIの内部transportです。4境界の全体契約は [27 出力境界](output/27_output-boundaries.md) を参照します。KML導入によりPDF生成要件やSheets保存を縮小しません。

同一のDomain正本データから、帳票は `ReportModelBuilder -> PdfGenerator`、KMLは `KmlExportModelBuilder -> KmlExporter` として独立生成します。KMLはPDF帳票・Sheets台帳の代替ではありません。

---

### 1.2 帳票を先に確かめる設計順序と内部責務

`5d51315`で導入した[ADR-0007](../decisions/ADR-0007-normalized-masters-and-business-reporting.md)の正規化と本書の3層構造は、旧印刷枠に内部モデルが縛られる問題を避けるための設計である。この経緯を、利用者が必要な帳票を後回しにする理由には使わない。

99.2 §0・§1からの現在ベースラインは、[00_goal §1.1](../00_goal.md#11-記入支援を中心に置くまでの因果)に示す記録・出力・保存先からの設計である。帳票の成立を確認してから、それを支える保存・射影・入力を設計する。上図は実装時のデータの流れであり、要件を決める順序ではない。§3.4の「帳票のセル構造に合わせて整備DBを設計しない」は、整備記録の生涯責務を個々の印刷枠へ従属させない意味で維持する。

人間向け一枚の帳票・台帳を技術都合で分割する場合の理由・影響・合意は[設計証拠規約§5](../guidelines/03_design-evidence-and-causality.md#5-質問と技術判断の境界)、保存・更新関係の確認は[開始ゲート](23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)に従う。本Stepは記録の優先順位と設計方法を移植するもので、以下の帳票レイアウト・ページネーションや物理シート方式について§2以降の比較・置換を済ませたものではない。

## 2. 出力帳票種別とデータソース対応

本システムでは、現場で実用的に使用する**「A4縦 統合運航帳票」**と、公的機関への提出等で必要となる**「国交省標準様式（様式1・2・3別）」**を概念上明確に分離します。双方は同一の正規化ドメインデータから生成されます。

| 帳票名 | 出力形式 | 主な内容・運用/法的根拠 | 出力タイミング・対象 |
|---|:---:|---|---|
| **A4縦 統合運航帳票** (`IntegratedOperationReport`) | PDF / 印刷 | 1枚の中に「飛行記録」「日常点検記録」「点検整備記録概要」の3領域を統合。1機体×1場所×1運航区間単位 | 現場日報・運航単位出力・社内保管 |
| **国交省様式1: 飛行記録** | PDF / CSV | 年月日、操縦者名、離着陸場所、離着陸時刻、飛行時間、飛行理由、不具合事項（航空法第132条の89関係） | 公的提出時、機体別月間台帳 |
| **国交省様式2: 日常点検記録** | PDF / CSV | 作成年月日、点検実施場所、点検項目合否、不具合処置（飛行前・飛行後点検） | 公的提出時、日誌監査 |
| **国交省様式3: 点検整備記録** | PDF / Excel | 点検整備実施日時、実施理由（定期/修理）、実施内容、実施者名、交換部品 | 機体生涯整備台帳出力時 |
| **地図付き飛行計画書** | PDF | 計画概要、飛行範囲地図（静止画レンダリング）、高度、周辺注意事項 | 計画作成後（事前印刷/提出用） |
| **DIPS飛行計画台帳・提出履歴**| CSV / Excel / Sheets | 計画ID、リビジョン、提出日時、通報方式(手動/API)、DIPS計画番号、飛行予定日時、場所、機体、操縦者、取消情報、紐付運航実績ID（予定と実績の監査対比） | 計画確定時、監査提出時 |
| **バッテリー生涯履歴台帳** | CSV / Excel | 個体別、累積サイクル数、累積飛行時間、異常メモ（旧スロット表示からの因果は[32b](asset-management/32b_battery-sharing-and-acquisition-history.md)） | 定期台帳点検時 |

## 3. A4縦 統合運航帳票（IntegratedOperationReport）の仕様

### 3.1 3領域の統合構造

現場運用において1回の運航を1枚（必要に応じて続紙）で俯瞰・保管できるよう、以下の3領域を1つの帳票に収容します。
1. **日常点検記録領域**: 飛行前点検・飛行後点検の実施日時・点検者・項目合否・不具合処置。
2. **飛行記録領域**: 各フライトの飛行番号・操縦者・離着陸時刻・飛行時間・飛行目的・安全措置・使用バッテリー・バッテリー残量・不具合。
3. **点検整備記録領域**: 直近の定期点検整備日、次回点検予定日、総飛行時間、重要整備状況のサマリー。

### 3.2 運航区間境界（境界分割ルール）

帳票の基本単位は **「1機体 × 1場所 × 1連続運航区間」** とします。
- **バッテリー交換**: 同一機体・同一場所での連続飛行におけるバッテリー交換は、**同一帳票内で飛行記録行を追加して継続**します。
- **機体交代**: 同一現場であっても、別の機体（Aircraft）へ交代した場合は**別帳票（新規帳票）**を発行します。
- **場所変更**: 別の飛行場所（Location）へ移動した場合は**別帳票（新規帳票）**を発行します。
- **明示的新規運航**: 翌日や午前/午後の区切りなど、操縦者が明示的に新規運航を開始した場合は**別帳票**を発行します。
- ※旧GASシステムの「左右No.1 / No.2（2運航並列）」構造は採用せず、1運航区間＝1系列の独立帳票として出力します。

### 3.3 自動改ページ（続紙）と行数固定の廃止

- **ドメインルールでの行数固定禁止**: 旧GASの「1運航あたり最大5飛行または6飛行」という制約をドメインルールとして継承しません。
- **動的ページネーション**: 帳票レンダラー（PDF生成エンジン）がフォントサイズ、余白、各セクション高さに基づき、1ページ目に収容可能な行数を超過した場合は自動的に「続紙（Page 2, Page 3...）」を生成します。

### 3.4 点検整備記録とデータベースの独立

- `MaintenanceRecord`（点検整備記録）は機体の生涯台帳（ライフサイクルデータ）であり、運航ごとにゼロから生成されるものではありません。
- 統合運航帳票の「点検整備記録領域」には、機体マスターおよび生涯整備台帳から**「直近の整備実施状況」「累積飛行時間」「次回点検基準」の最新スナップショットを射影（Projection）して表示**します。帳票のセル構造に合わせて整備DBを設計してはなりません。

Step 3で取得確認の記録意味と整備実施者／作成・転記者の区別を[32c](asset-management/32c_acquisition-check-and-maintenance-actors.md)へ接続した。累計の表示・射影では[32a](asset-management/32a_aircraft-acquisition-and-cumulative-time.md)の「取得前不明」と「管理開始後累計」を混同しない。ここで具体的な欄・配置を追加せず、§6の点検整備全体・保存構造の再移植を完了したとは扱わない。

## 4. 運航セッション（Mission）と帳票単位（ReportUnit）の分離

現場の運用フローと帳票の出力境界を切り離すため、以下の概念モデルを採用します。

```text
┌────────────────────────────────────────────────────────┐
│ 運航セッション (Mission)                               │
│ - 現場での一連の作業単位                                │
│ - バッテリー交換（継続）や機体交代（切替）を含む       │
└───────────────────────────┬────────────────────────────┘
                            │
                            │ 射影・分割 (Projection & Partitioning)
                            │ [機体ID × 場所ID × 連続運航区間] で分割
                            ▼
┌────────────────────────────────────────────────────────┐
│ 帳票射影単位 (ReportUnit / OperationLeg) - View Model  │
│ - 1 機体 × 1 場所 × 1 連続運航区間                      │
│ - 通常はDB永続化せず、動的に集計・生成                 │
└───────────────────────────┬────────────────────────────┘
                            │
                            │ 確定・出力・監査保存時
                            ▼
┌────────────────────────────────────────────────────────┐
│ 帳票スナップショット (ReportSnapshot) - Immutable Audit │
│ - 生成日時の不変PDFバイナリ / ハッシュ / メタデータ    │
│ - 監査証拠としてIndexedDBおよび外部ストレージへ保存    │
└────────────────────────────────────────────────────────┘
```

## 5. 法令要件とUIの分離（現場負荷の極小化）

国交省標準様式のすべての項目を現場の入力フォームとして画面に並べることは**「現場片手操作の破壊」**につながるため厳禁とします。

ガイドラインで定めた**「法令8区分」**を徹底し、入力の手間を極小化します。

```text
【国交省標準様式の項目】
  ├─ [自動取得] 離着陸時刻、飛行時間、年月日、機体登録記号、型式 → GPS・時計・機体マスターから自動入力
  ├─ [既定値]   点検項目（プロペラ・モーター等） → 「全項目正常」ボタンで1タップ一括充足
  ├─ [条件発生時入力] 不具合事項、特記事項 → 異常発生時のみ入力欄を展開
  └─ [他台帳・手動補記] 包括許可番号、整備記録原本 → 別紙台帳または事後スプレッドシート手動補記で充足
```
- **設計目標**: 現場の操縦者が行う操作は、**「点検正常タップ」→「離陸」→「着陸」→「BAT選択」→「終了」**の最小限のタップ数で完結しながら、出力されるPDFは国交省取扱要領で求められる記録項目を満たすことを目標とし、Phase Cで標準様式1〜3との項目照合テストを実施します。現行アプリで確立された「別紙参照・手動補記・柔軟運用」もそのまま尊重します。

## 6. オフラインPDF生成の成立条件

端末がオフライン（圏外）である場合のPDF生成は、帳票の性質に応じて以下の条件付き動作とします。

1. **帳票本文PDF（統合運航帳票・様式1〜3・バッテリー台帳）**:
   - **条件**: `pdf-lib` ライブラリおよび日本語フォント（Noto Sans JPサブセット等）がPWA Service Workerによって端末へ事前キャッシュされていること。
   - **挙動**: 端末内IndexedDBからデータを抽出し、完全にオフラインでPDFを生成・端末内保存可能。
2. **地図画像付き飛行計画書PDF**:
   - **条件**: 背景となる国土地理院タイル等の地図画像がブラウザキャッシュまたはオフライン領域に事前保存されていること。
   - **フォールバック**: 該当エリアの地図タイルがキャッシュされていない圏外環境では、地図画像領域に「※オフラインのため地図画像未取得」の注記を行い、代わりに飛行範囲の緯度経度座標リスト・半径数値を印字してPDF生成を中断させないフェイルセーフ設計とします。

## 7. 人物役割の正本への接続

操縦者・記録者を帳票の別欄で保持する要件、日常点検実施者の意味、法定欄とアプリ独自Recorderを分けた因果は[31c](identity-and-access/31c_operational-actors.md)を正本とする。本書はその射影先であり、役割規則を複製しない。具体的な欄配置・物理schemaや後続章の帳票移植は未実施。§2以外の帳票レイアウト・ページネーションを今回変更しない。

Step 5では[34b](presentation/34b_home-and-navigation.md)へ［飛行履歴・出力］の入口責任だけを移した。04／06を確認して07の派生出力へ進む画面接続であり、本書のA4帳票・射影・出力単位の再移植や変更ではない。
