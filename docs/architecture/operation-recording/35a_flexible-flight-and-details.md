# 35a. 柔軟な取扱いの1飛行と明細・機体交代

最終更新: 2026-09-20\
由来: 99.2 §5。意味の現在ベースラインと、Domainの最終schemaの未確定を分離する。

## 1. 旧運用と既存Domainを同じ論点として読む

**当初状態（HISTORICAL）**: 旧GASは、同一機体で途中着陸・BAT交換・再離陸を挟む柔軟な運用を扱っていた。一方、基準Docsの[12e](../domain-model/12e_operation-inspection-maintenance.md)はMissionを現場の作業束、Flightを個々の離陸〜着陸とし、AircraftSwitchを独立Entityとして列挙していた。旧技術モックにもMissions／Flights／FlightLegs／AircraftSwitchesが存在したが、99.2はMissionとの最終分担や交代イベントの独立保持を未確定として記録している。

**問題**: 一度着陸するたびに意味上も別飛行とすると、BAT交換等を含む一続きの運用を表せない。逆に現場の全作業を一つのFlightに入れると、同一機体という集約条件を機体交代で失う。旧UIのブロックや既存の型名だけでは、この意味の境界を決められない。

**根拠と検討**: §5は旧GASの柔軟な取扱いと現場操作資料を継承元に挙げる。個々の離着陸を捨てて集約値だけにするのでも、旧テーブルを存在だけで最終schemaにするのでもなく、運用上の1飛行とその内部明細を分ける。帳票の物理的な収容限界もDomainの飛行回数上限とは別に扱う。

## 2. 現在の1飛行の意味

**CURRENT-ACCEPTED**: 同一機体・同一エリア・同一目的／同一ミッションの連続運用は、途中着陸、電源OFF／ON、BAT交換、再離陸を含めて、柔軟な取扱い上の1飛行として集約できる。常に集約を強制する規則ではなく、集約条件が切れれば別飛行となる。

個々の離陸〜着陸、使用BATと交換等は、その1飛行の内部明細として保持する。集約によって実際の機体・時刻・使用個体・安全に影響した事項を消さない。`flight_id`、帳票、KMLの基本単位もこの意味上の1飛行へ接続する現在案である。KMLの単位・生成契機・内容は[27e](../output/27e_kml-generation-timing-and-content.md)が詳細正本で、意味上の1飛行と計画・改訂・複数日・複数機体との対応は未確定（PENDING-S7C-KML-UNIT-MAPPING）。本書はKMLのIdentity・階層を再設計しない。

BAT管理のON／OFFは、この飛行の区切りとは別の責任である（CURRENT-ACCEPTED。2026-09-20のオーナー指示）。同じ1飛行の途中でBATを何回交換しても、BAT交換だけを理由にA4の飛行記録を複数行へ分けない。BAT管理がONの機体の場合だけ、その飛行の裏側にBAT使用履歴を関連付ける。詳細は[32e §3](../asset-management/32e_battery-management-scope-and-flight-separation.md#3-bat管理と飛行記録の区切りを分ける因果)。

時間何分以内、距離何m以内、BAT何本までといった数値条件は原本にないため追加しない。場所の表示名・Location IDと「同一エリア」の判定を自動的に同一視しない。原本の柔軟運用を継承する設計判断であり、本Stepで法令適合や行政の個別承認を新たに認定するものではない。

## 3. 機体交代で引き継ぐ文脈と未確定のデータ境界

**旧フローから残す意味（CURRENT-ACCEPTED）**: 機体交代では場所・目的・操縦者・許可情報等のミッション文脈を引き継ぐ。未点検機体は正式な飛行前点検へ接続する。具体的な通常操作は[35b](35b_normal-operation-and-final-save.md)、点検・離陸評価は[13a](../state-machines/13a_operation.md)／[13c](../state-machines/13c_takeoff-readiness.md)に従う。

**接続課題**: §5は同一機体を集約条件に含める一方、画面の機体交代とMission／Flightの最終区分は未確定とする。同じFlightへ異なる機体を当然に含めることは決定済みではない。文脈を引き継ぎながら新しいFlightへ切り替える可能性は**CURRENT-PROPOSAL**として残す。その切替履歴をAircraftSwitch等の独立イベントとして保持するかは**PENDING-S6-OPERATION-SCHEMA**であり、画面側や帳票分割だけから確定しない。

FlightLegは内部明細を表す旧候補名（HISTORICAL）である。明細が必要という現在の意味から、同名テーブル、PK／FK、基数、FlightとMissionの最終役割まで自動採用しない。12eの旧属性一覧はこの違いを明示し、各BATの使用事実・非飛行イベントを区別する[32b](../asset-management/32b_battery-sharing-and-acquisition-history.md)の責任を維持する。

## 4. 正式実飛行とテストを混同しない

**EVIDENCE/EXAMPLE**: 原本§5は、その記録時点の正式運航記録を0件とする。今回実Driveを再集計した現在値ではなく、アプリテスト・確認用操作を正式な実飛行へ加算していない状態の証拠である。

**CURRENT-ACCEPTED**: アプリテスト・確認用・シミュレーションから正式実飛行や累計を自動生成・加算しない。テスト用の画面打刻を実飛行の証拠としない。実機で行った中古取得時短時間確認の個別判断は[32c §1](../asset-management/32c_acquisition-check-and-maintenance-actors.md#1-取得時の短時間動作確認をどう残すか)が詳細正本であり、一般のアプリテスト除外と混同しない。実際の管理開始後の飛行を、単に「テスト」と名付けただけで除外する新規規則は作らない。

## 5. 未確定と検証境界

- **PENDING-S6-OPERATION-SCHEMA**: Mission／Flight／明細の最終分担、交代前後のFlight境界・独立イベント、ID・FK・基数と具体保存形式。既存PENDING-C1-SCHEMAも維持する。
- **VERIFY-S6-OPERATION-EVIDENCE**: 旧操作資料、旧モック、現在の04記録との対応。今回のコード読解は実機操作や実Drive確認ではない。
- **検証する意味**: 条件を満たす途中着陸・BAT交換で明細が失われず、条件を失った運用を無条件集約しないこと。機体交代時に文脈継承と飛行境界を別々に判断でき、テストから正式時間が増えないこと。未確定schemaの先行実装は行わない。
