# 35d. 運航の最終確定と一括保存の責任

最終更新: 2026-09-19\
由来: 99.2 §5の途中下書き・飛行後点検後の最終保存、2026-09-19のA4保存追補。§9の同期全体は再移植しない。

## 1. 旧一括保存が守っていたもの

**当初運用**: 原本は、旧アプリで飛行中の各操作を都度GASへ送らず、端末下書きに保持し、使用機体の飛行後点検まで終えた運航全体を一度の保存要求へ含めたと記録する。これは通信中の待ちや飛行後の別途転記を通常操作へ持ち込まない運用資産である。

**実物確認記録と今回の補助読解**: 原本は旧`buildFixedCommitPlan_()`が日付／飛行記録、BAT個体履歴、飛行後点検、使用機体の累計更新を固定保存計画へ含めたと記録する。今回、基準アプリcommit `e8560b03e1220cb3b38e927190bdcb03191ddc57`の[保存計画組立](https://github.com/ikifuse/autel-evo-lite-flight-log/blob/e8560b03e1220cb3b38e927190bdcb03191ddc57/src/14_commit_plan.gs)、[帳票への記入](https://github.com/ikifuse/autel-evo-lite-flight-log/blob/e8560b03e1220cb3b38e927190bdcb03191ddc57/src/21_sheet_records.gs)、[Web保存入口](https://github.com/ikifuse/autel-evo-lite-flight-log/blob/e8560b03e1220cb3b38e927190bdcb03191ddc57/src/web/33_web_engine.js)をローカルの同版から読んだ。

組立には上記4種類の処理があり、Web入口には飛行後点検入力を下書きへ保持したうえで運航全体を送る処理、圏外・失敗時に保持する処理がある。これはコードの静的確認（EVIDENCE/EXAMPLE）であり、実GASの再実行や旧版の全復旧経路の検証ではない。新アプリへ旧関数・GAS基盤をコピーする根拠にもならない。

## 2. 途中保護と正式保存を分ける

**問題・検討**: A4だけを最終保存するとBAT個体履歴・累計が脱落する。一方、各画面の操作で正式記録を都度完成扱いにすると、飛行後点検を含む運航全体の確定という旧思想が失われる。内部の逐次永続化と、正式記録の最終確定は別の時点である。

**現在到達点（CURRENT-ACCEPTED）**: 飛行前点検、離着陸打刻、BAT交換、各明細、飛行後点検は端末で逐次保護する。操縦者が飛行後点検を済ませて最後の送信／保存を行った時点で、その運航の確定データから必要な記録を完成させる。操縦者に飛行後の手動転記を要求しない。

| 同じ最終確定から接続する責任 | 唯一の詳細正本・未決境界 |
|---|---|
| A4の運航・日常点検記録 | [35c](35c_a4-operation-record.md)。途中入力と正式04記録を区別し、対象機体個体のSpreadsheetへ接続する |
| 飛行に伴うBAT個体履歴・使用回数／累計時間等 | [32b](../asset-management/32b_battery-sharing-and-acquisition-history.md)。飛行明細と非飛行イベントを二重に計上しない |
| 使用機体の累計更新 | [32a](../asset-management/32a_aircraft-acquisition-and-cumulative-time.md)。管理開始後と取得以前不明の意味を保持 |
| 使用機体の飛行後点検・異常等 | 日常点検の意味は35b／12e、人物は31c。05の詳細整備台帳とは分ける |

旧BAT_1〜BAT_7や旧機体原本の物理配置を復活させない。02／03／04／05のどの表へどの行を置くかは32a〜32c等の未確定に従う。「同じ最終確定から派生する」という必要要件は、Google側の複数ファイル書込みが単一transactionで成功する保証ではない。

## 3. 保存に到達できない場合と重複防止

**問題・旧根拠**: 通信断の後に別の運航として保存し直すと、帳票・履歴・累計が二重になる。原本は旧`draftId`、固定保存計画、complete証明を重複防止の根拠として記録している。

**CURRENT-ACCEPTED**: Sheetsへ到達できない場合も運航完了データを端末から消さず、未同期として保持し、通信復帰後に同一運航として再送する。再送で別シート・履歴行・累計加算を二重生成しないため、不変の識別と冪等性を新方式でも必要要件とする。

方式は**PENDING-S6-FINAL-SAVE-CONTRACT**。旧Properties構造、保存計画形式、complete判定、lock方式を新実装へそのまま採用しない。[12f](../domain-model/12f_common-lifecycle-id-and-audit.md)の共通ID、[14](../14_offline-and-sync.md)のSyncQueueへ接続し、具体的な対象割当・部分完了・再送・成功判定は依存実装前に詰める。既存の「同一行UPSERT」だけで全ての帳票と履歴の重複防止が完成したとも扱わない。

**2026-09-19追補との境界**: 新規A4が必要な通常保存は[35c §3.2](35c_a4-operation-record.md#32-機体内の日付と次空き連番)の機体別・日付次空き連番に従う。同じ保存要求の再送のたびに新しいA4へ採番する意味ではない。不変の識別という既存要件から、今回新しい帳票ID・採番ID体系を追加しない。同一機体への極端な同時保存専用の中央採番・高度な排他を現時点で採らない因果と再検討条件は[35c §3.3](35c_a4-operation-record.md#33-特殊な同時競合を検討したうえで簡素な方式を選ぶ理由)が唯一の詳細正本であり、本書のPENDINGをその実装要求と読まない。

外部反映前の端末保持と反映済みを区別し、[11](../11_data-authority.md)の確定台帳・手修正保護を維持する。端末ストレージ自体を失った場合の限界は[19](../19_failure-recovery.md)。通常保存の再送をDIPSの結果不明POSTと混同せず、後者の理由は[33b](../dips-infrastructure/33b_api-availability-and-retry-boundaries.md)へ委譲する。

## 4. 検証と残る範囲

- **PENDING-S6-FINAL-SAVE-CONTRACT**: 最終保存と既存識別・schemaの対応、保存対象への割当、部分失敗・同一運航再送・完了証明の具体契約。A4の保存先と通常命名は35cで到達済み。特殊な同時競合専用の高度な対策は意図的非採用であり、未実装の必須要件へ含めない。§9全体の同期方式は今回確定しない。
- **VERIFY-S6-FINAL-SAVE-EVIDENCE**: 旧操作資料・実GASでの運航全体保存と、新アプリの候補保存物との照合。今回読んだ3コードの範囲を超える旧復旧の保証や新実装成功は未検証。
- **受入時の確認**: 途中離脱しても保護済み入力を保持すること。最後の確定からA4・BAT・飛行後点検・機体累計が脱落せず、同一運航の再送が二重生成・二重加算を起こさないこと。人の手修正を古い値で破壊せず、部分完了を全体成功と誤表示しないこと。
