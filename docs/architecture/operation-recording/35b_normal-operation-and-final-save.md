# 35b. 通常運航の画面と現場記録

最終更新: 2026-09-22\
由来: 99.2 §5。画面仕様の記録は[30](../presentation/30_screen-specification-standard.md)の10項目を用いる。最終保存の対象と重複防止の因果は[35d](35d_operation-finalization-and-write-boundary.md)。

## 1. 旧現場フローを継承する理由と境界

**当初状態・実物の記録**: §5は旧GASとPixel6a操作資料に、飛行前点検→離着陸→BAT記録→続行／BAT交換／機体交代／終了→飛行後点検→一括保存という運用があると記録する。入力途中を端末下書きに保持し、現場の順序に沿った入力から最後に記録を完成させる設計だった。今回の旧コード読解でも、通常操作の端末処理と最終保存時の一括要求を確認した（35d）。端末実機・当時のマニュアル操作の再検証ではない。

**問題・検討・現在到達点（CURRENT-ACCEPTED）**: 操作順だけを移して途中で正式Drive記録を確定させたり、飛行後の手動転記を別作業にすると、旧運用の入力負荷と保存上の意味が失われる。現場の流れと途中保護・最後の確定を継承する。旧No.1／No.2枠、固定機体・BAT枠、旧表名は画面やschemaの必須条件にしない。

**入口**: DIPS対象飛行は[34d](../presentation/34d_dips-accepted-and-plan-content.md)の通報内容から［飛行前点検へ］で接続する。DIPS対象外も必要な飛行情報を確定して同じ点検以降へ合流できる。通報要否・手動確認・離陸評価を本書で再定義せず、[13_overview](../state-machines/13_overview.md)／[13c](../state-machines/13c_takeoff-readiness.md)／[33b](../dips-infrastructure/33b_api-availability-and-retry-boundaries.md)に従う。

## 2. 現在の論理画面順

```text
飛行前点検 → 離陸待機 → 離陸 → 飛行中 → 着陸 → 着陸後入力
                                                ↓
                           続行／BAT交換／機体交代／終了を選ぶ
                           ├ 続行・BAT交換 → 必要な準備 → 再離陸
                           ├ 機体交代 → 文脈継承・対象機体の点検確認
                           └ 終了 → 飛行後点検 → 最終送信／保存
```

離陸・着陸で時刻を記録し、着陸後にその区間のBAT、場所、飛行時間、安全に影響した事項等を確定する。途中入力は端末下書きとして逐次保護し、画面を進んだだけで正式Drive記録が都度確定したことにしない。BAT交換は35aの集約条件を維持すれば次明細として続行できる。機体交代では場所・目的・操縦者・許可情報等を引き継ぎ、未点検機体を点検へ接続するが、Flightの切替・交代イベントschemaは35aの未確定に従う。

以下は論理上の画面責任であり、物理画面数や新しいボタン文言を確定する表ではない。初期値は[31c](../identity-and-access/31c_operational-actors.md)、互換・個体は[32b](../asset-management/32b_battery-sharing-and-acquisition-history.md)、異常時の事実記録は13cが正本。30の項目9で権限とonline/offlineを一緒に扱う。対象機体（機種と登録記号）を取り違えない表示の責任は[34g §2](../presentation/34g_settings-aircraft-management-and-context-display.md#2-現在の運用環境の表示と対象機体の表示)。

## 11. 未確定と受入時の確認

**PENDING-S6-OPERATION-UI**: 表内で未確定とした戻る・中断・詳細レイアウト・保存状況の表示。既存UI例の大きな打刻ボタン等は13aに保持するが、旧画面の枠数・配置をそのまま新アプリの最終UIにしない。人物・schema・帳票・保存の各PENDINGを画面仕様から解消しない。対象機体の表示位置・固定表示はPENDING-D-AC-CONTEXT-DISPLAY（34g）。

**VERIFY-S6-OPERATION-EVIDENCE**: 旧Pixel6a等の現場資料と実機操作、現在の新アプリ画面・記録の照合。実機未検証と、§5に記録された現在の論理順の未確定は別である。C1以降の実装は開始しない。

## 12. 旧現場UIを継承した設計候補（2026-09-22）

**発端・因果**: 旧現場フローの論理順は継承していたが、点検を簡略化し、飛行中にも操作を置くモックでは現場UIの思想を十分に追跡できなかった。オーナー指定の「現場用操作マニュアル Pixel6a版 v2026.09.05.4」の継承指示と、§1の既存証拠に基づき、以下へ修正した（CURRENT-PROPOSAL）。補助比較では基準アプリの公開コード`35_web_flight.js`等と公開画面のv2026.09.09.3を読んだ。指定マニュアル原版を今回再閲覧した証拠とは扱わない。

| 場面 | モックへ反映した候補 |
|---|---|
| 飛行前点検 | 装着BATを先に確認し、サイクル数は任意。実機の11項目を未確認で開始。実機確認の申告後のみ［全て正常］が使える。異常は外して特記事項を保持し、正常扱いで離陸待機へ進めない |
| 離陸待機 | 点検済みBAT・対象機体・離陸場所を確認し、大きな離陸開始操作。離陸前の機体交代を残す |
| 飛行中 | スマホ操作ゼロを基本に、経過時間・対象機体等の最低限情報と大きな［着陸完了（プロペラ停止後）］だけを置く。早送り等は右側。着陸後に記録を確認する |
| 着陸後 | 着陸場所・実飛行時間の訂正・安全影響事項・任意のBAT所感を入力。着陸内容を確定してから続行／BAT交換／機体交代／終了の選択へ進む |
| 続行・BAT交換 | 同じ機体の正式11項目を毎回繰り返さない。交換後は「装着・ロック」「残量・温度・警告表示」の2項目を確認して離陸待機へ。交換を取り消す場合は直前の選択を保持する候補 |
| 機体交代 | 場所・目的・操縦者・許可を引き継ぐ。未点検機は正式点検へ、点検済み機へ戻る場合は必要な簡易確認へ |
| 飛行後点検 | 今回実際に飛ばした全機体の、機体全般／プロペラ・フレーム／発熱／その他を確認。全機体の実機確認後のみ一括正常操作。異常と特記事項を保持する |
| 最終保存 | 途中では正式履歴を書き込まない。最後の1操作で各飛行行・BAT履歴・点検等をまとめて保存する。複数飛行を1行へ集約する意味ではない。失敗を表示して下書きと各飛行行を保持し、通信回復後に再試行する |

§3の「新しい一括操作を定めない」は従来の記録範囲であり、今回の実機確認後に限る操作候補を禁止する趣旨ではない。画面仕様の「10項目」と実機点検の「11項目」を混同しない。保存の責任・重複防止・部分成功は[35d](35d_operation-finalization-and-write-boundary.md)が正本であり、ここで通信契約を追加しない。

**限界と未決**: モックはメモリ内の擬似保存・擬似失敗で、端末再起動後の永続復旧・実通信・サーバー側冪等性は検証していない。PENDING-S6-OPERATION-UI、各記録schema、BAT状態の選択肢、戻る・中断・復旧の最終UIを解消しない。実機確認の申告UIや画面分割もオーナー確認待ち。C1は未着手。
