# 35c. A4運航・日常点検記録の実物と生成単位

最終更新: 2026-09-19\
由来: 99.2 §5・§10、最新Drive実物の直接確認、旧帳票設計のGit履歴、2026-09-19のオーナー追加判断。A4の詳細・因果の正本。

## 1. 旧帳票から最新実物へ至った理由

**当初運用（HISTORICAL）**: 旧GASの日常点検帳票は横長の左右No.1／No.2、各7明細の構成だった。8明細目、機体交代、新しい場所等では次ブロックへ進み、原本をコピーした日付・連番シートへ最終保存で自動記入した。99.2 §5は、分割先それぞれへ基本情報・飛行前点検・該当明細を入れ、最後の飛行後点検を対応先すべてへ反映したと記録する。[35d](35d_operation-finalization-and-write-boundary.md)が参照する旧コードでも、7件単位の割当と各割当への点検記入を静的に確認した。

**既存Docsの再設計（HISTORICAL）**: `5d51315`のADR-0007 §2.9と旧18は、内部データが印刷枠へ縛られる問題を避け、正規化したデータをReportUnitへ射影する案とした。A4縦へ日常点検・飛行記録・点検整備サマリーを入れ、可変行数でPage 2以降へ続ける設計だった。旧18の「5または6飛行」という旧制約の説明と、99.2／旧保存コードの7明細は一致しないため、旧説明を現物の行数証拠には使わない。

**問題と実物調整**: 内部の正規化だけでは、人が直接確認・印刷する帳票の読みやすさは確定しない。99.2はAI作成の改行・列幅・行高等をオーナーが手作業で整えた経緯を保持する。2026-09-18の追加指示で、下記のDriveファイル1つを最新実物と指定した。古い試作、旧main、旧Excelコピーで置き換えず、その実ファイルを直接読み取った。

**変更理由**: 現在はそのA4縦1枚の見通しを優先する。内部データの正規化と帳票生成の責務分離は残すが、存在しない点検整備サマリーの追加、文字縮小による8行目の押込み、自動続紙を現在仕様として残さない。詳細整備の独立責任は[36](../maintenance-storage/36_aircraft-maintenance-records.md)、内部モデルと帳票モデルの分離は[18](../18_reports.md)へ接続する。

### 3.1 機体個体別の保存先を確認したことによる補正

**追加事実（EVIDENCE/EXAMPLE）**: 2026-09-19のオーナー追補指示は、現在Driveの04が機体個体ごとに分かれ、各機体フォルダーに「無人航空機・飛行記録・日常点検記録」Spreadsheetがあることを確認結果として提示した。既存の機体情報・登録記号による個体の区別がある。これはオーナーによる実物確認の報告であり、§2の前回エージェントによるA4直接確認とは別の証拠である。本追補ではDriveを再取得・編集していない。機体数・実登録記号・個別Drive IDを製品仕様に固定しない。

**当初解釈と問題（HISTORICAL）**: 99.2 §5とStep 6初版（`b1d5788`）は`YYYY.M.D`を用い、機体交代も次の連番シートへ進む条件としてまとめていた。保存先の機体別境界を明示しないまま、交代だけで同一ファイルの`_2`へ進む解釈を残すと、別の物理機体を使う操縦者同士の保存まで同一の命名空間で競合すると誤認する。

**変更理由・現在到達点（CURRENT-ACCEPTED）**: 04の保存境界には既存の機体個体を使う。別機体を使う通常の同日・別場所運航は、そもそも別のSpreadsheetへ保存される。操縦者コードや新しい帳票・採番IDをA4名へ追加する必要はなく、新しい識別子体系を導入しない。保存構造は概念的に`04_運航記録 / <機体個体> / 無人航空機・飛行記録・日常点検記録 Spreadsheet`。Drive全体との責任関係は[37](../drive-structure/37_environment-storage-responsibilities.md)。

### 3.2 機体内の日付と次空き連番

**CURRENT-ACCEPTED（出典: 同オーナー追加判断）**: 対象機体のSpreadsheet内で、その日の最初のA4を`YY.M.D`、次を`YY.M.D_2`、さらに`YY.M.D_3`とする。年は2桁で、例は`26.9.19`、`26.9.19_2`、`26.9.19_3`。既存シートを確認し、日付名が使用済みなら`_2`、それも使用済みなら`_3`と順に確認して次の空き名を使う。これは新規A4が必要な通常保存の方針であり、新しいIdentityではない。操縦者名・操縦者コードは付加しない。

機体交代では交代後の機体Spreadsheetへ移る。機体Aに`26.9.19`があっても、機体Bでその日最初ならBも`26.9.19`でよい。交代自体を同一ファイル内の`_2`発行条件にしない。Bにも同日記録があれば、Bの既存シートに従って次の空き名を選ぶ。

同じ機体・同日で次のA4が必要になる代表例は、7枠を使い切った後の8明細目以降、別の場所へ移動して別運航記録として分ける場合、その他別A4として区切る必要が生じた場合である。場所変更の詳細判定、柔軟な1飛行との境界、Mission／Flight／FlightLeg／AircraftSwitchの最終schemaは命名規則から確定しない。通常の同一運航の再送を新規A4と取り違えない責任は35dに残す。

### 3.3 特殊な同時競合を検討したうえで簡素な方式を選ぶ理由

**検討した競合と成立条件**: 2端末がほぼ同時に同一機体の同一Spreadsheetへ保存し、同じ次連番を選ぶ可能性は理論上ある。同じ物理機体を2人が同時に別場所で使うことはできないため、想定例は、Aが運航終了時に圏外等で未同期のまま機体をBへ渡し、Bが同日中に次の運航を行い、Bの保存とAの遅延同期がほぼ同時に到達する場合である。

**頻度・復旧可能性についての判断**: オーナーは、受渡しまでの移動・帰社等で通信可能な場所へ戻る可能性が非常に高く、複数条件が重なるこの競合は通常利用では非常に限定的と判断した。これは運用前提に基づく判断であり、発生頻度を測定済みという事実ではない。順に到達する保存では既存名を避けて次の空き連番へ進める。一方、この確認だけでほぼ同時の選択を完全に排他できるとは扱わず、競合時の復旧を実証済みとも扱わない。

**意図的な非採用（CURRENT-ACCEPTEDの設計判断）**: この限定的な可能性だけを理由に、新しい操縦者ID・帳票ID体系・操縦者コード付き名・中央採番サービス・大掛かりな排他制御・分散ロックを追加しない。通常保存は§3.2で十分とし、極端な同時競合専用の高度な仕組みを現時点の設計対象にしない。競合の見落としでも、全保存の障害・再送を考慮しない判断でもない。[35d](35d_operation-finalization-and-write-boundary.md#3-保存に到達できない場合と重複防止)の途中保護・通常再送・重複防止要件は維持する。

**再検討条件**: 実運用・試験で、同一機体を未同期のまま渡すことが頻発する、同じ機体Spreadsheetへの並行保存競合を観測する、複数拠点での短時間受渡しが常態化する、次空き連番方式では復旧できない事象を確認する、のいずれかが生じた場合、実証された問題を根拠に競合制御を再検討する。将来の理論的可能性だけで非採用案を復活させない。重要判断の要約は[ADR-0021](../../decisions/ADR-0021-a4-record-layout-and-sheet-boundary.md)に接続する。

## 4. 未確定事項と再検討の境界

- **PENDING-S6-A4-DETAIL**: 補助者0人時の空欄／「なし」等、年度替わりと長期・複数環境でのSpreadsheet分割、テンプレート版・項目対応、日付境界や複製・記入の実装詳細。機体別保存・`YY.M.D`・次空き連番は§3の到達点であり、採番方針全体を未決へ戻さない。高度な同時競合対策の意図的非採用を未解決の必須実装として残さない。
- **PENDING-S6-OPERATION-SCHEMA**は35a。場所変更で別A4へ区切る厳密条件と柔軟な1飛行との関係も未確定のまま。再送時に同じ割当を二重生成しない契約は35dへ委譲し、新しい帳票IDを本追補で追加しない。
- **VERIFY-S6-A4-PRINT**: A4実寸・フォント・改行・余白の印刷経路検証。長い氏名／複数補助者／長文不具合等を入れた場合の読める状態も未検証。実物を改変せず将来の検証用出力で確認する。
- 現在ベースラインは変更可能だが、人が整えた配置をAIの一般論だけで再設計しない。変更時は実物・理由・影響・オーナー判断を[規約03](../../guidelines/03_design-evidence-and-causality.md)に従って追跡する。
