# 31. DIPS 専用固定送信元IPゲートウェイ設計

最終更新: 2026-09-18\
状態: 設計整合（C1未着手・C7 Optional基盤）\
主責務: Google Cloud NAT経由の固定送信元IPゲートウェイ論理構成、認証情報隔離、障害影響局所化、外部仕様検証。\
入口: [DIPS 接続インフラ設計群](README.md)

## 1. 背景・申請経緯・インフラ要件

国土交通省のドローン情報基盤システム（DIPS 2.0）APIとの連携においては、利用申請手続きおよびシステム接続要件として「接続元（送信元）のグローバル固定IPアドレスの事前登録」が確認されています。
航空局DIPS担当への照会により、アクセス元は利用中に第三者へ再割当されず、サーバー停止や再作成等でも同一IPを維持し、契約環境に専有される固定IPを少なくとも1つ登録する必要があることが確認されました。

これに基づき、一般的なサーバーレス環境からの動的IP直接通信を排除し、Google Cloud NATを経由した専用の固定送信元IPゲートウェイ構成を採用します。
また、ブラウザ（PWA）からDIPS APIへの直接通信は、CORS制約、Client Secret等の機密情報保護、および固定IP要件を理由に禁止し、必ずバックエンド中継層を経由する境界を設けます。

## 2. 論理責任境界アーキテクチャ

システム全体の論理的な通信経路および責任境界は以下の通りです。

```text
┌─────────────────────────────────────────────────────────────┐
│ クライアント層（PWA / ブラウザ / 端末ローカル）            │
│  - 現場運航管理、飛行記録、日常点検、点検整備履歴            │
│  - DIPS手動通報支援（Manual: 第一級運用）                   │
│  - submission_snapshot（意味論的通報スナップショット）保持  │
│  - ※DIPS API直接通信を行わない（CORS回避・認証情報露出防止）│
│  - ※アプリ自身のセッション情報のみ保持（DIPS平文鍵なし）    │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS (内部REST / セッションCookie)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ クラウド中継層（Google Cloud DIPS連携バックエンド）        │
│  - 限定的BFFプロキシ（全運航データの中央DBを持たない）       │
│  - DIPS API認証情報（Client Secret / トークン等）の管理     │
│  - 25c準拠電文の送信・通信障害処理                          │
└──────────────────────────────┬──────────────────────────────┘
                               │ 固定送信元IPを実現するVPC egress経路
                               │ （具体的接続方式は PENDING-C7-INFRA）
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ ネットワーク出口層（Google Cloud NAT）                      │
│  - 専有された静的外部IPアドレス（固定送信元IP）             │
│  - パケットの送信元IPアドレス変換（SNAT）                   │
│  - ※公開リポジトリには実IP値を一切書かない（抽象化）        │
└──────────────────────────────┬──────────────────────────────┘
                               │ HTTPS (固定送信元IP <DIPS_FIXED_EGRESS_IP>)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 外部システム（国土交通省 DIPS 2.0 API ゲートウェイ）        │
│  - 送信元固定IPフィルタリングによる接続受付                  │
│  - 飛行計画通報受付・受付番号発行                           │
└──────────────────────────────┘
```

### 各層の責任境界
1. **クライアント層**:
   - 現場の運航管理、飛行前/後点検、飛行日誌保存、A4帳票出力を完結。
   - DIPS通報においては、意味論的スナップショット（`submission_snapshot`）を保持。
   - DIPS APIサーバーへの直接通信は行わず、DIPS APIの認証鍵やトークンも保持しない。
2. **クラウド中継層（Google Cloud DIPS連携バックエンド）**:
   - クライアントからのAPI通報要求を受け、DIPS APIとの認証・電文送出を中継する限定的なBFF（Backend For Frontend）プロキシ。
   - [25c API payload mapping](../dips-flight-plan/25c_api-payload-mapping.md) が定義するマッピング結果電文を受け取り、安全に送信する（本インフラ層でマッピング規則を再定義しない）。
   - 全利用者の飛行記録や個人データを蓄積する中央データベースを持たず、ステートレスな中継に留める（プライバシー保護および低コスト運用の維持）。
3. **ネットワーク出口層（Google Cloud NAT）**:
   - 事前予約した専有静的外部IPアドレス（固定送信元IP）を用いて、バックエンドからの送信パケットの送信元IPアドレスを変換（SNAT）し、国交省APIゲートウェイへ送出。
4. **外部システム（DIPS 2.0 API）**:
   - 登録済み固定IPアドレスからのアクセスを検証し、APIリクエストを受付・処理。

## 3. 機密情報と固定IP実値の非公開管理境界

- **公開リポジトリにおける表現**:
  - 本設計書およびリポジトリ内のコード・設定例においては、実固定IP値を一切記述せず、`<DIPS_FIXED_EGRESS_IP>` 等の抽象プレースホルダーおよび環境変数名テンプレート（`DIPS_CLIENT_ID`, `DIPS_CLIENT_SECRET`, `DIPS_EGRESS_IP` 等）を使用する。
- **固定IP実値と認証機密情報の分離**:
  - 固定IP実値（ネットワーク構成・運用情報）と、Client Secret等の認証情報（クレデンシャル）を別種の情報として扱う。
  - 実固定IP値は、非公開のGoogle Cloudインフラ構成・運用情報として管理する境界を確定し、環境変数かシークレット管理ツールかといった具体的格納先は本Stepで先行固定しない（インフラ構築設計段階へ委ねる）。
- **ブラウザ側への機密情報露出防止**:
  - クライアントには DIPS APIの Client Secret やマスター認証情報は一切渡さない。
  - ブラウザ側に存在するのはアプリ自身のユーザー認証・利用セッションのみであり、DIPS APIの認証情報やトークンをブラウザ（Session Cookie含む）へ保持させない境界を徹底する。

## 4. 手動通報（Manual）支援との独立性と運航工程境界

- **インフラ独立性**:
  - 手動通報支援（Phase C6、[24 手動通報](../dips-submission/24_manual-submission.md)）は、本APIインフラ（Phase C7）の稼働状況や申請状況に依存せず、独立して動作可能な境界を設ける。
  - パイロットはアプリ内で `submission_snapshot` を生成し、DIPS Web画面への手動転記（コピー支援）を行い、発行された受付番号を手動登録することで運航を記録できる。
- **運航工程進行の境界**:
  - DIPS通報が必要な運航において、APIインフラの障害や未開通を理由に「通報なしで飛行可能」と見なすことは禁止する。
  - 必要な通報が **Manual支援経由またはAPI連携経由のいずれかで完了** するまで、通報完了を前提とする運航工程（離陸前確認等）へ進めない境界を維持する。

## 5. 障害影響の局所化（Fault Isolation）と二重通報防止

- **API通信障害時の局所化**:
  - 影響範囲: DIPS API自動通報リクエストのみがエラー（または結果不明）となる。
  - 局所化方針: 現場の飛行前点検、離陸・着陸打刻、飛行日誌保存、バッテリー交換、日常点検、点検整備履歴、A4運航帳票出力、Google Drive保存への波及を避ける設計とする。通報手段は手動通報（Manual）への切り替えが可能である。
- **通信途絶時の二重通報防止**:
  - DIPS正式通報の送信中にタイムアウトや通信断が発生し成否が不明となった場合、システムは自動で盲目的な再POSTを行わず、「結果不明（UNKNOWN）」状態を保持して照合フローへ進む（[13b 通報FSM](../state-machines/13b_dips-submission.md)）。
  - 通常のDrive/Sheets保存やKML保存の再試行処理と、DIPS API通報再試行を結合しない（KMLや台帳の保存失敗を理由にDIPSを再通報してはならない）。

## 6. 外部仕様の確認済み事項とVERIFY事項（未確定）

外部仕様を推測で確定させず、根拠資料に基づく確認済み事実と、仕様書受領待ちの検証事項を明確に区別します。

### 6.1 確認済み事項（根拠資料あり）
| 確認済み項目 | 内容・事実 | 根拠資料 |
| :--- | :--- | :--- |
| **個人によるAPI申請** | 法人のみならず個人事業者・個人開発者によるDIPS 2.0 API利用申請が可能であること | 航空局DIPS担当への照会回答 |
| **専有固定送信元IP要件** | APIアクセス元として、利用中に第三者へ再割当されず、契約環境に専有されるグローバル固定IPを少なくとも1つ登録必須であること | 航空局DIPS担当への照会回答、API利用申請書「利用システム」欄 |
| **システム接続情報の申請** | 接続システムURL、OIDCリダイレクトURL、固定IPアドレスを記載して申請書を航空局へ提出済みであること | `DIPS2.0_API_Application_Forms_<USER_NAME>_提出用_固定IP追記.xlsx` |

### 6.2 正式仕様受領後 VERIFY 事項（本番仕様書受領待ち）
| VERIFY項目 | 未確定・検証待ちの内容 | 理由・現在の扱い |
| :--- | :--- | :--- |
| **API認証方式・発行形態** | Client ID / Secret の実際の発行形態、OIDC/OAuth等の具体的フロー、認可エンドポイント仕様 | 航空局からの設定通知および本番接続仕様書が未受領のため推測で確定しない。申請書にリダイレクトURLを記載した事実をもって仕様確定と見なさない。 |
| **トークンライフサイクル** | トークンの有効期間、リフレッシュ要否、失効（Revoke）エンドポイント仕様、サーバー側での保持要否 | 正式接続仕様書を受領後に照合・確定する。ブラウザ側への保持は行わない。 |
| **ゲートウェイ詳細挙動** | IPフィルタリングの適用タイミング、レートリミット、同時接続数制限、エラーレスポンス形式 | 正式仕様書受領後の結合検証環境にて確認する。 |
| **Google Cloud実行基盤・VPC接続方式** | バックエンドの具体的実行コンピュート（Cloud Run等）およびVPC/Cloud NATへの接続具体方式 | **PENDING-C7-INFRA** としてPhase C7着手時に決定する。 |
