## 2. 最有力推奨構成を採用する理由

### ① 個人利用における「維持費0円」と「保守負担ゼロ」の両立
- **完全無料の運用**: Cloudflare Pages（フロントホスティング）、Cloudflare Workers（API中継プロキシ）、国土地理院タイル（地図データ）、Googleスプレッドシート（台帳）のすべてが無料枠内で永久に稼働します。
- **年間1.3万円のApple Developer費用を回避**: iOSネイティブアプリに必須のApple年会費や、90日ごとのTestFlight更新・証明書更新の手間が一切不要です。

### ② 現場での「完全オフライン動作」と「データロストゼロ」の保証
- **ローカルファースト設計**: 端末内のIndexedDBにすべての入力・打刻がミリ秒単位で永続化されます。山間部などの完全圏外でも、飛行前点検、離陸、着陸、バッテリー交換、機体交代、飛行後点検、日誌確定までが100%停止せずに動作します。
- **直前状態の復元**: 現場でスマホの電池が切れたり、ブラウザが再読み込みされても、直前の画面状態が完全に復旧します。

### ③ 自作アプリの最大の強み（バッテリー個体管理・透明性）の完全継承
- 最終的な保管先としてGoogleスプレッドシートを活用するため、**「人間がいつでも直接見て直せる」「手修正しても計算が壊れない」「国交省や監査にそのまま原本印刷・提示できる」**という安心感を100%維持できます。
- バッテリー7本（BAT_1〜BAT_7）の充放電、飛行時間、所感の生涯追跡をそのまま引き継げます。

### ④ セキュリティと法令要件の完全クリア
- 国交省DIPS APIの `client_secret` や認証トークンを端末側に一切置かず、Cloudflare Workersの暗号化Secretsで安全に保護します。
- 航空法の飛行日誌3様式（飛行記録、日常点検、点検整備）の出力に完全準拠します。

## 3. 第2候補と採用を見送る理由

### 第2候補: Web技術 ＋ Capacitor（ネイティブラッパー）構成
- **概要**: 基本的なコードは推奨案と同じWeb標準で作り、Capacitorを用いてiOS（Xcode）およびAndroid（Android Studio）のネイティブシェルに固める方式。
- **長所**: アプリストア（またはTestFlight/APK）経由でのネイティブ配布が可能。将来的にバックグラウンドでのGPS連続追跡やBluetooth連携が必要になった際に拡張しやすい。
- **今回採用を見送る理由**:
  - iPhoneで動かすために年間12,980円のApple Developer契約が必要になる。
  - OSのメジャーアップデート（iOS 18等）のたびにXcodeでの再ビルド・ライブラリ更新の手間が発生し、個人運用の保守コストが高くなる。
- **将来への含み**:
  - 推奨案（PWA）のフロントエンドコードは**100%そのままCapacitorへ流用可能**です。まずはPWAで「完全無料・審査なし」で運用を開始し、将来どうしてもネイティブ機能が必要になった段階でCapacitorを追加導入する「無駄のない二段階アプローチ」が可能です。

## 4. 不採用とする候補と理由

| 候補 | 不採用の理由 |
|---|---|
| **完全ネイティブ開発 (Swift + Kotlin)** | iOSとAndroidでコードが完全に2重化し、航空法改定やDIPS仕様変更のたびに2言語で同じ改修が必要。個人開発・保守として破綻リスクが極めて高いため不採用。 |
| **現行GAS単独構成 (Google Apps Script)** | サーバー通信前提のため、山間部・圏外での**「オフライン完全動作」が構造上不可能**。また、地図ポリゴンのレスポンスが悪く、現場操作性に耐えられないため不採用。 |
| **自前VPS / クラウドサーバー (Linux)** | 月額費用が必ず発生し、OSアップデートやSSL更新、セキュリティパッチの管理負担が重すぎるため不採用。 |
| **Supabase (無料枠)** | 1週間無アクセスでDBが自動休止される仕様があり、数週間ぶりに現場でドローンを飛ばす際に停止している致命的リスクがあるため不採用。 |

## 5. 主な想定リスクと対策

1. **iOS SafariのPWAキャッシュ消去リスク**:
   - リスク: iOS Safariでは長期間使われないWebサイトのCache Storageが消去される場合がある。
   - 対策: 運航記録などの重要データはCache Storageではなく、耐久性の高い **IndexedDB** に二重保管し、さらに運航完了ごとにGoogleスプレッドシートへ退避・同期する構造とします。
2. **DIPS 2.0 APIの個人申請可否の不確実性**:
   - リスク: 国交省側が個人に対してAPIクライアントIDを発行しない可能性がある。
   - 対策: **「疎結合設計」**を徹底します。DIPS連携が利用できない場合でも、アプリ単体で飛行計画作成、地図ポリゴン作成、飛行前点検、飛行日誌、バッテリー管理、スプレッドシート連携が100%独立稼働できる構造を維持します。

## 6. 次のPhase B2（詳細アーキテクチャ設計）で決めるべき事項

本B1で技術構成の方向性が承認された後、Phase B2では以下を詳細設計します。
1. **DIPS Proxy（Cloudflare Workers）のインターフェース設計**
   - OAuth認可フローの中継手順、トークン暗号化・セッション管理方式
2. **データモデル設計（IndexedDBスキーマ）**
   - 飛行計画、点検記録、離着陸実績、バッテリー個体台帳、機体台帳の型定義
3. **Googleスプレッドシート同期プロトコル**
   - ローカルDBとスプレッドシート間の差分更新・冪等性（UUID）キー設計
4. **地図・ポリゴン操作UIの仕様設計**
   - MapLibre GL JSによる円・ポリゴンの描画・頂点編集ロジックとGeoJSON変換仕様
5. **国交省様式PDF/Excel出力エンジン設計**
   - クライアント側（ブラウザ内）でのPDF生成ライブラリ選定とレイアウト設計
