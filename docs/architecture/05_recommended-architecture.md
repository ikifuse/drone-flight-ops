## 1. 総合評価まとめと推奨構成

Phase B1における詳細な比較・検討の結果、以下の構成を**「最有力推奨アーキテクチャ」**として提案します。

```text
【第一候補アーキテクチャ概要（条件付き推奨案）】
┌─────────────────────────────────────────────────────────────┐
│ クライアント（iPhone / Android / iMac）                     │
│  - 形態: PWA（Progressive Web App） / Web標準SPA            │
│  - 実行環境: モバイルSafari / Chrome（ホーム画面追加でフル起動）│
│  - 地図エンジン: MapLibre GL JS + 国土地理院タイル (規約準拠)│
│  - 現場ローカルDB: IndexedDB (Dexie.js) - 現場即時書込      │
```

## 2. 第一候補構成を推奨する理由（条件付き評価）

### ① 個人利用における現行仕様での「費用0円運用」と「保守性」
- **現行無料枠の活用**: Cloudflare Pages（フロントホスティング）、Cloudflare Workers（API中継プロキシ）、国土地理院タイル（地図データ）、Googleスプレッドシート（台帳）の組み合わせにより、現行の公式仕様・制限の範囲内であれば追加費用0円で運用できる可能性が極めて高い。
- **iOS開発者費用の回避**: 有料Apple Developer Program（年額約1.3万円前後）の契約や、90日ごとのTestFlight更新・証明書更新の手間をかけずに、iPhoneのホーム画面からアプリ起動できる。

### ② 現場での「通信圏外での作業継続」と「データ保護」
- **ローカルファースト設計**: 事前にアプリを読み込み済みの状態であれば、山間部などの通信圏外でも通信待ちを発生させずに、飛行前点検、離陸、着陸、バッテリー交換、機体交代、飛行後点検、日誌入力までを進められる。
- **クラッシュ・再起動対策**: 端末内IndexedDBへ即時に状態が退避されるため、現場での電池切れや不意のブラウザ再読み込み時にも直前の画面状態を復元できる。

### ③ 自作アプリの強み（バッテリー個体管理・人間中心の透明性）の継承
- Googleスプレッドシートとの連携を維持することで、**「人間がいつでも直接見て直せる」「手修正しても計算が壊れない」「国交省や監査にそのまま原本印刷・提示できる」**という確立された安心感を損なわずに移行できる。
- 7本のバッテリー個体ごとの充放電、飛行時間、所感の生涯追跡をそのまま引き継げる。

### ④ セキュリティとAPI仕様変更への耐性（疎結合）
- 将来DIPS APIの秘密情報や資格情報を扱う場合でも、端末側に秘密を置かず、サーバーレスエッジ（Workers）で安全に隔離・中継できる境界を確保できる。

## 3. 第2候補と採用を見送る理由

### 第2候補: Web技術 ＋ Capacitor（ネイティブラッパー）構成
- **概要**: コアをWeb標準技術で作り、Capacitorを用いてiOSおよびAndroidのネイティブアプリとしてビルドする構成。
- **長所**: アプリストア（またはTestFlight/APK）経由での配布が可能。将来的にバックグラウンドでのGPS連続追跡やBluetoothドローン直接連携が必要になった際に拡張しやすい。
- **今回採用を見送る理由**:
  - iPhoneで常用するためにApple Developer Program（年額約1.3万円前後）の有料契約が必要となる。
  - OSアップデートに伴うXcodeビルド・ライブラリ保守の負担が生じる。
- **将来への拡張性**:
  - PWAとして構築したWebフロントエンド資産の大部分は、将来必要になった段階でCapacitorへ流用可能であり、移行経路を確保できる。

## 4. 不採用とする候補と理由

| 候補 | 不採用の理由 |
|---|---|
| **完全ネイティブ開発 (Swift + Kotlin)** | iOSとAndroidでコードベースが2重化し、航空法改定やDIPS仕様変更のたびに2言語で同じ改修が必要となり、個人での保守が困難であるため。 |
| **現行GAS単独構成 (Google Apps Script)** | サーバー通信を前提とするため、山間部・圏外でのオフライン現場記録に適さず、地図ポリゴン操作などの現場レスポンスが重いため。 |
| **自前VPS / Linuxサーバー** | 月額費用が恒常的に発生し、OSアップデートやセキュリティパッチ管理の負荷が過大であるため。 |
| **Supabase (無料枠)** | 7日間の低アクティビティや十分なDB活動がないプロジェクトが自動一時停止（Paused）される公式仕様があり、数週間ぶりに現場でドローンを飛ばす際に即座に通報・同期できない運用リスクがあるため。 |

## 5. 主な想定リスクと対策

1. **iOS Safariのストレージ自動削除（Eviction）リスク**:
   - リスク: 端末の空き容量逼迫時等に、WebKitによってIndexedDBがクリアされる可能性がある。
   - 対策:
     - ホーム画面PWAとして Storage API（`navigator.storage.persist()`）を要求して永続化を試みる。
     - 端末内ローカルDBを唯一の長期保管場所とせず、運航完了時や電波復帰時にスプレッドシートやJSON外部ファイルへ定期的にバックアップ・同期する二重化運用を設計する。
2. **オフライン時のDIPS飛行計画通報の法令・運用上の制約**:
   - リスク: 圏外で飛行計画通報キューに入れただけで「通報完了・飛行可能」と誤認して飛行させてしまう法令違反リスク。
   - 対策: 業務データ（点検・日誌）のローカル保存とDIPS通報状態を厳格に分離する。「未作成」「作成済み」「送信待ち」「送信中」「通報成功確認済み」「通報失敗」の状態遷移を設け、国交省サーバーからの受理確認レスポンスが得られるまで通報完了・飛行可能扱いをさせないUI/UXとする。
3. **Cloudflare Workers Free PlanのCPU時間制限（10ms/req）**:
   - リスク: 将来のDIPS認証中継やトークン暗号化、データ変換処理において、Free PlanのCPU時間10ms制限を超過するリスク。
   - 対策: プロキシ処理を極力軽量に保ち、実装段階で処理時間を実測・検証する。
4. **DIPS 2.0 APIの利用主体およびcredential発行の未確定リスク**:
   - リスク: 個人へのAPI利用許可が下りない可能性や、複数realmのcredential発行関係が複雑である可能性。
   - 対策: **「疎結合設計」**を徹底する。DIPS連携が利用できない場合でも、アプリ単体で飛行計画作成、ポリゴン地図、点検、バッテリー管理、日誌、スプレッドシート連携が独立して完全稼働できる構造とする。

## 6. 次のPhase B2（詳細設計）で決定・設計すべき事項

本B1.2での最終事実訂正を踏まえ、Phase B2では以下の技術課題を詳細設計します。

1. **データ権威モデルと正本（SSoT）の決定**
   - ローカルDB主マスター案、スプレッドシート原本案、またはライフサイクル連動型ハイブリッド案（有力候補）の比較・確定。
   - 作成中／未同期／同期済み／手修正済み／監査確定のステータス遷移と競合解決プロトコルの設計。
2. **データモデル設計（IndexedDBスキーマ）と永続化対策**
   - 飛行計画、点検記録、離着陸実績、バッテリー個体台帳、機体台帳の型定義。
   - `navigator.storage.persist()` 要求処理とJSONエクスポート/インポート復旧設計。
3. **バックエンド境界（Cloudflare Workers）のインターフェース設計**
   - 将来のDIPS認証中継用プロトコル（DRS `drs-utm`, FPA `drs-req`, FPR `drs-fpl` のOIDC連携）、CPU時間10ms制限内の軽量処理設計。
4. **DIPS飛行計画通報の状態遷移・オフラインキュー設計**
   - ローカル下書き保存と国交省通報受理確認を明確に分ける安全な状態管理設計。
5. **地図・空域データソースの選定とオフライン設計**
   - MapLibre GL JSによるポリゴン描画ロジック、およびDID等の空域規制データの取得・キャッシュ方式の精査。
6. **国交省様式PDF/Excel出力エンジン設計**
   - ブラウザ内で完結する帳票生成ライブラリの選定とレイアウト設計。
