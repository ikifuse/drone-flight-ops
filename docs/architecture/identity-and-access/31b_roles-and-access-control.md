# 31b. 三層権限・アプリ管理者・機能利用

最終更新: 2026-09-18\
由来: 99.2 §2【発端・問題】【確認した実仕様】【アプリ管理者】【三層権限】【設定変更】【補助者アクセス】。\
主要責務: 業務上の立場、アプリ内で許す操作、Googleの実アクセスを混同しない権限判断。人物の正本は[31a](31a_person-account-and-environment.md)。

## 1. 二重権限管理を採らないまでの因果

**当初状態（HISTORICAL）**: 基準12aのPersonnel.rolesはpilot / inspector / assistantとadministrator / viewerを同じ配列に置き、権限詳細を[16](../16_security.md)へ案内していた。16の主題はDIPSの秘密・BFF・トークン管理であり、環境別の業務権限を具体化したものではなかった。基準内の確認範囲では三層の判定規約、初期管理者・最後の1人保護の旧設計はない。

**問題・検討案**: 99.2は業務役割とDrive共有をアプリ側でも管理すると不整合が起きると整理した。アプリ内でEditorをpending / approve / rejectし、自動共有する案、操縦者を自動Editorにする案、Drive共有設定や`writersCanShare`を最上位アプリ管理者の保護根拠とする案を区別して検討した。

**調査・変更理由**: 原本のGoogle実仕様確認では、アプリで承認してもGoogle Viewerなら書けず、Google Editorならアプリ外で直接Sheetsを編集できると確認した。Drive共有はファイル／フォルダー単位で、1 Spreadsheetの特定タブに別のDrive権限を付ける方式ではない。タブ・セルの編集制限はSheetsの保護範囲、フォルダー共有は原則として配下へ継承、Shared Driveは組織所有という異なる境界がある。このためアプリ独自のEditor承認を実アクセスの第二正本にせず、Drive共有設定をアプリ管理者権限の根拠にも採用しない。

**今回の補助照合（2026-09-18、公式文書）**: [Drive共有](https://developers.google.com/workspace/drive/api/guides/manage-sharing)のファイル等に対する権限・親からの継承と例外、[Sheets保護](https://support.google.com/docs/answer/1218656?hl=en)のシート／範囲編集制限、[Shared Drive](https://support.google.com/a/users/answer/7212025?hl=en)の組織所有を確認した。保護範囲は閲覧秘匿の仕組みではない。公式文書の照合は実アカウントの共有動作試験ではなく、`writersCanShare`やAPIによる共有処理を今回採用する根拠にも用いない。

## 2. 現在の三層とGoogleアクセス

**CURRENT-ACCEPTED**。①業務役割、②アプリ機能権限、③Google Drive実アクセスを分離する。①は対象環境の所属に登録された役割、②はアプリの操作可否、③はGoogle標準共有を正本とする実アクセスである。以下はこの境界を具体化したもの。

- Drive Viewer / Editorの付与・取消はGoogle側で行う。アプリ内Editor承認待ち／承認／却下／自動共有は採用しない。
- 操縦者であるだけでは自動Editorにしない。本人のGoogleアカウントで直接記録する操縦者・記録者には、Google側の必要な編集権限を付与する。
- Google側に権限がない人物でも、既存編集者が操作してその人物を操縦者等として記録できる。記録対象と操作者の分離は[31c](31c_operational-actors.md)に従う。
- Drive Viewer / Editorをアプリ管理者と同一視しない。アプリ内で許可した操作であっても、Google側の権限を超えた読書きを可能にしたことにはならない。

## 3. 初期管理者・追加解除・最後の1人

**検討からの到達点（CURRENT-ACCEPTED）**: §1の共有設定案を採らず、アプリ管理者の成立・変更をアプリ側の責任として定める。「新しい運用環境を作成」で最初にGoogle認証し本番構造を作成したアカウントを、最初のアプリ管理者とする。追加・解除は既存管理者のみが行い、最後の1人は代替管理者なしに自分の管理者役割を解除できない。操縦者であるだけでは管理者へ昇格させる権限を持たない。

人物・アカウント・MembershipRolesの対応を保存する方式は[31aのPENDING](31a_person-account-and-environment.md#2-現在の概念境界とorganization)へ残す。初期管理者の決め方が確定したことから、メールアドレスを人物IDにする等の方式を導かない。My Drive所有者交代・Shared Driveは管理者解除とは別の物理所有・事業継続課題であり、[31d §4](31d_membership-lifecycle.md#4-組織所有と事業継続の未確定境界)の未確定を維持する。

## 4. 設定・補助者・Viewerへ具体化した境界

**設定変更（CURRENT-ACCEPTED）**: 環境によって役割が異なり、同じ人物が兼務するため、アプリ機能判定を「その飛行で何役だったか」だけで行わない。対象環境の人員台帳に登録された役割の組合せを使う。設定変更は操縦者またはアプリ管理者に許可し、記録者だけでは許可しない。記録者が別途操縦者／管理者役割を持つ場合はその役割によって可能となる。Google実アクセスは§2の別判定である。

**補助者（CURRENT-ACCEPTED）**: 補助者という業務上の立場だけで、元Drive / Sheets / KML / My Mapsへの恒常アクセスを与えない。必要な1飛行記録は権限者がPDF等を生成し個別共有する。補助者に元台帳全体の権限を自動付与する方法では、必要な記録を渡すことと元データへのアクセスが混ざるため、原本は両者を分けた。

**Viewerの旧整理との関係（HISTORICAL → 現在の境界）**: 原本が挙げる旧権限整理では、元台帳は閲覧可能でも、通常飛行記録の編集、設定変更、PDF作成／印刷、KML / My Maps利用を行わせないとしていた。現在はこれをGoogleのViewer属性だけで全機能が一意に決まる権限表として採らず、Googleで見えることとアプリで操作できることを分ける。元台帳を閲覧できるだけで上記のアプリ操作を許可する意味にはしない。複合役割の設定変更は前段を適用し、Google実アクセスと衝突する場合にアプリ側の許可だけで権限を増やさない。原本が定めていない全機能×全複合役割の許否・UI表現は**PENDING-S2-ACCESS-DETAIL**。旧Viewer制限の一括撤廃も、旧制限を新たな三層共通enumに固定することも行わない。

## 5. 例外・検証・確認待ち

アプリでの離任とGoogle共有解除が別処理になる因果・未確定は[31d](31d_membership-lifecycle.md)に一元化する。Google側Editorの直接編集をアプリの操作制限で全面防止できるとは扱わない。直接編集時のデータ権威は[11](../11_data-authority.md)、秘密・トークン管理は[16](../16_security.md)を維持する。

**VERIFY-S2-ACCESS-EVIDENCE**: 99.2が記録する実Drive共有確認と旧98.2の実物を今回は再操作・再読していない。公式文書で補助照合した範囲と区別し、実環境への適用時に確認する。検証ではGoogle Viewer＋アプリ側の役割、Google Editor＋非管理者、複合役割、補助者のみ、最後の管理者の解除という境界を照合する。新しい認証・承認フローは追加しない。重要判断の要約と見直し条件は[ADR-0016](../../decisions/ADR-0016-environment-membership-and-access-separation.md)。
