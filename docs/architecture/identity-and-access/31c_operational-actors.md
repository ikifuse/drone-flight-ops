# 31c. 操縦者・通報者・記録者と現場担当

最終更新: 2026-09-24\
由来: 99.2 §2【人物役割】、基準12a / 12d / 12e / 26。\
主要責務: 飛行に関わる人物役割の意味、分離・初期値の理由。人物マスターは[31a](31a_person-account-and-environment.md)、環境内の機能権限は[31b](31b_roles-and-access-control.md)。

## 1. 固定役割案を実画面・帳票から見直す

**当初状態（HISTORICAL）**: 基準12aはPilot / Assistant / InspectorをPersonnel.rolesと各記録の割当として表し、SubmissionActor（操作UserAccount）、Actual Pilot、EmergencyContactPersonを分離していた。99.2の検討には操縦者・補助者・立入管理措置担当者・記録担当を固定役割として持つ案もあった。

**問題・調査**: 同じ人物の別マスター化だけでなく、DIPSの入力項目、実際の飛行・点検をした人、入力担当をすべて独立必須人物欄として扱うことが適切かを再確認した。99.2はDIPS現行画面、飛行日誌要領、旧GAS実装を根拠に、DIPSでは操縦者情報、補助者人数、立入管理措置が別項目で、独立人物欄の「立入管理措置担当者」を確認できなかったと記録している。これは当時観測した画面の範囲であり、DIPS全機能にその人物入力が存在しないという証明ではない。

**変更・却下理由**: 飛行記録の操縦者氏名と、日常点検の実施者氏名は記録として保持する。一方、記録者は新アプリの実入力担当を明確にする独自役割であり、独立した法定必須人物欄として追加しない。立入管理措置を独立人物役割にする案は上記の項目分離と一致しないため採らず、安全措置として扱う。毎回別人の点検者・記録者を選ぶ前提にせず、通常運用の同一人物を初期値とし、別人の場合を区別する。

**根拠の確認範囲**: 99.2は2026-09-14のPC版DIPS実操作、スマホ版`uafpi.dips.mlit.go.jp`新規作成画面、過去会話13:04 / 13:31 / 14:12:54付近の操作・スクリーンショットを証拠系列として挙げる。基準の[26](../26_dips-web-ui-verification.md)も操縦者・補助者・安全措置・連絡先の観測を保持する。今回はログイン操作、元スクリーンショット、旧GASの再確認を行っていない（**VERIFY-S2-ACTOR-EVIDENCE**）。

2026-09-18に[国交省の掲載入口](https://www.mlit.go.jp/koku/operation.html)から[飛行日誌の取扱要領](https://www.mlit.go.jp/koku/content/001574394.pdf)を確認し、§7(1)cの操縦者氏名・技能証明を受けている場合の番号、§7(2)gの点検実施者記名を補助照合した。同要領の記録事項とアプリ独自Recorderを区別する。これは当該人物欄の照合であり、代理通報の法的可否、全法令・全画面の再監査ではない。[法令8区分](../../guidelines/02_legal-and-operations-rules.md)を維持し、記録義務とアプリの毎回の強制選択を同一視しない。

## 2. 現場役割の現在到達点

**CURRENT-ACCEPTED**。以下は役割の意味・割当ルールであり、最終enumや列名一覧ではない。

| 役割・対象 | 現在の扱い |
|---|---|
| Pilot（操縦者） | 実際に飛行する人物。人物役割として扱い、Googleアカウントの有無で記録可否を決めない |
| Assistant（補助者） | 0人以上。補助者人数と人物の選択を区別し、恒常アクセスは[31b §4](31b_roles-and-access-control.md#4-設定補助者viewerへ具体化した境界)による |
| 立入管理措置 | 安全措置。独立した人物役割を新設しない |
| Recorder（記録者） | 実飛行時の入力担当。操縦者選択時に同一人物を初期値とし、別人入力時のみ変更する。帳票では操縦者と記録者を別欄で保持する |
| 日常点検実施者 | 実施者を記録として保持する。通常飛行では操縦者が基本であり、常時別選択を要求しない。実施者と操縦者が異なる事実を消す初期値規則ではない |

別人による点検時の具体的な入力UI、Recorderの保持先・列名、補助者の複数割当の物理形式は**PENDING-S2-ACTOR-SCHEMA/UI**。既存`Mission.assistant_id`を0〜1人という現行上限と解釈しない。計画の人数／選択は[12d](../domain-model/12d_flight-plan-and-dips.md)、実績・点検は[12e](../domain-model/12e_operation-inspection-maintenance.md)へ接続する。通常の日常点検の初期値を整備・改造等の全実施者へ一般化しない。

## 3. さらに通報者と操縦者を分離した理由

**追加の問題・検討**: DIPS通報後すぐに飛行するとは限らない。99.2は事務担当が翌日・翌々日や同日の複数現場の計画を先に作成・通報し、現場の操縦者が後から担当計画を選んで飛行前点検へ引き継ぐ運用を検討した。通報・飛行・実飛行時の入力を一人一時点にまとめるとこの引継ぎを表せない。

**現在到達点（CURRENT-ACCEPTED）**: Submitter（通報者）はDIPSへその計画を実際に送信した利用者、Pilotは実際に飛行する人物で、同一でも別人でもよい。基準のSubmissionActor分離をこの意味で具体化する。FlightPlanでは通報者と操縦者を別項目で保持し、共有された飛行リストの一覧でも識別できるようにする。Recorderは実飛行時の入力担当で、Submitterとも別概念である。単に計画を下書き入力した人を、実際に送信した通報者として確定しない。

**既存設計との接続・例外**: [12d](../domain-model/12d_flight-plan-and-dips.md)の`submitted_by_user_id`はこの通報者の参照、`pilot_ids`は予定操縦者の参照として読む。実操縦者・記録者・操作アカウントの監査接続は[12e](../domain-model/12e_operation-inspection-maintenance.md#8-実績と点検の未定義参照pending-c1-schema) / [12f](../domain-model/12f_common-lifecycle-id-and-audit.md#6-操作アカウントと人員の監査接続pending-c1-schema)の未確定を維持する。UserAccountと人物のIDを代入可能と決めない。

基準12aのContact / EmergencyContactPersonは連絡先として選ばれた役割名であり、別人物マスターを作らないという意味を維持する。連絡先の選択元は12d / [25b](../dips-flight-plan/25b_manual-web-mapping.md)。操縦者・通報者・連絡先の分離が可能であることから、第三者代理通報の法的範囲まで認定しない（基準の**VERIFY**を維持）。DIPS利用規約等との照合と、運用主体の責任で委任関係の成立を確認するという基準の留意事項を保持する。本書で移す共有飛行リストの要件は、§2にある担当計画の選択・引継ぎと人物識別まで。後続章の画面・遷移・共有方式は先取りしない。

## 4. 利用側への反映と検証

[18](../18_reports.md)は操縦者・記録者の別欄と日常点検実施者を本書から参照し、法定欄とアプリ独自欄を混同しない。Presentationは[30](../presentation/30_screen-specification-standard.md)の規約に従い、初期値と別人入力、環境・権限・保存を追跡する。帳票レイアウトや最終schemaを本書から推測で完成させない。

同一人物がPilot / Submitter / Recorderを兼ねる場合、事務担当と現場担当が異なる場合、Google権限のない人物を編集者が記録する場合、補助者0人／複数人、通常と別人による日常点検を照合する。これは§2の要件を検証する観点であり、飛行ごとの役割だけで設定権限を決める規則ではない。機能判定は31bを唯一の詳細正本とする。

## 5. 現場担当のモック接続の訂正（2026-09-23）

**HISTORICAL（モックの不整合）**: 記録者をログイン中の本人として表示し、実操縦者・記録者を各実績へ保存していなかった。帳票見本も閲覧時の本人を参照していた。

**EVIDENCE/EXAMPLE**: 既存§2に従い、通常運航では記録者・点検者は操縦者と同じを既定にする。別人のときだけ既存画面の折畳み欄で変更し、着陸後にも実績の担当を訂正できる。飛行前後点検の実施者は機体別、操縦者・記録者は実績別に保存して履歴・帳票見本で再利用する。Googleアカウントを持たない人員の選択を妨げない。入力UIと物理schemaのPENDING-S2-ACTOR-SCHEMA/UIは維持する。


## 6. 個人環境の本人操縦者を新規飛行の初期値にする（2026-09-24）

**発端・旧状態（HISTORICAL）**: 動くモックは個人環境でも新規飛行の操縦者を空にし、登録済みの本人を毎回選ばせていた。人物とアカウントを分離することを、既知の本人操縦者の再選択まで要求する理由にはしない。

**現在の判断（CURRENT-ACCEPTED。2026-09-24のオーナー指示）**: 個人環境で、認証済みGoogleアカウントとその環境の本人Personの対応が分かり、その本人が有効な操縦者として登録済みなら、新規飛行の操縦者に本人を自動選択する。これはUI・運用上の初期値であり、操縦者登録や役割付与の自動化ではない。通常ケースでは選択画面を開くことも毎回の明示選択も要求せず、選択済みの氏名を表示する。

本人未登録・無効・本人対応不明の場合は自動選択せず、既存の登録・選択経路を使う。会社・団体環境にはこの自動選択を適用しない。候補が複数でも本人を初期値とし、別人が飛ばす場合、事務担当と操縦者が異なる場合、実際の操縦者を変更する場合には、既存の選択・変更操作を使える。手動変更後の再描画や前後移動で本人へ戻さない。過去飛行の複製で選ばれた操縦者や、既存計画・実績を初期値で上書きしない。

**境界と未確定**: [31a §2](31a_person-account-and-environment.md#2-現在の概念境界とorganization)の人物・アカウント・環境内役割の分離と、本書§3の通報者・操縦者・記録者の分離を維持する。「Googleアカウント＝操縦者」にはしない。本モックのメール対応・meId・pilotは照合を見せるための仮表現で、物理schemaや本番認証方式の決定ではない。初回の人物登録だけで操縦者役割も付与するかはPENDINGのまま（モックは自動付与しない）。この役割付与の未決と、登録済み本人の初期選択の決定を区別する。PENDING-S2-IDENTITY、PENDING-S2-ACTOR-SCHEMA/UIの保存・別人点検等の残りは維持し、この本人初期値を未決には戻さない。既存[ADR-0016](../../decisions/ADR-0016-environment-membership-and-access-separation.md)の責務内の具体化として参照し、新ADRは追加しない。
