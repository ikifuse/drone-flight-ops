# 02. 運用環境・アカウント・所属ライフサイクル設計（02_environment-and-personnel-lifecycle.md）

最終更新: 2026-09-18\
状態: Phase C0完了・Phase C1未着手（Step 2正本化）

主要責務: PersonnelとUserAccountの分離、複数アカウント紐付け、OrganizationとOperationalEnvironmentの境界、所属ライフサイクル意味論（所属中／所属終了／再所属）。

---

## 1. 人物（Personnel）と認証アカウント（UserAccount）の分離原則

実在する人物と、システムにアクセスするためのログイン・認証アカウントを概念上厳格に分離します。

```text
┌─────────────────────────────────────────────────────────────┐
│ [実在する人物] Personnel (人員マスター)                     │
│  - 氏名、連絡先、技能証明プロファイル（所持時）等を保持     │
│  - アカウントを持たない補助者や外部点検者も1人物として登録可│
└──────────────────────────────┬──────────────────────────────┘
                               │ 0..N 関連付け（任意）
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [認証アカウント] UserAccount / Google Identity              │
│  - Google OAuth / OpenID Connect 等の認証主体               │
│  - 個人用Googleアカウント、組織用Google Workspaceアカウント │
└─────────────────────────────────────────────────────────────┘
```

- **アカウントを持たない人物の登録**:
  - 運航記録に登場する補助者や同行者がGoogleアカウントを持たない場合でも、`Personnel` レコードとして適正に登録・記録できます。
- **複数Googleアカウントの紐付け**:
  - 同一人物が、個人運用環境では「個人用Googleアカウント」を用い、会社等の業務環境では「組織管理Google Workspaceアカウント」を利用する場合があるため、1人の `Personnel` に対して環境ごとに異なる認証アカウントを紐付けられる論理構造を維持します。
- **会社利用における原則**:
  - 個人私用アカウントへの依存を排除するため、会社・組織運用では組織管理Googleアカウントを使用することを推奨します。
  - 1つのGoogleアカウントを複数人でパスワード共有して使い回す運用は採用しません。

## 2. Organization（組織マスター）と OperationalEnvironment（運用環境）の責任境界

実社会の法的管理主体と、アプリケーション上のデータ隔離スコープを混同しないよう、明確な責任境界を定義します。

### 2.1 Organization（組織マスター）の定義
- **概念**: ドローン運航の所有・法的管理主体（実世界に実在する法人、個人事業主、自治体等の団体そのもの）。
- **属性と正本**: [12a](../domain-model/12a_organization-and-personnel.md) に基づき、`organization_id` (UUID v4)、事業者名称（`name`）、`operator_code`（DIPS事業者コード / 法人番号、任意）、`contact_email`、`contact_phone`、状態（`status`）を管理します。C1初期は単一デフォルト組織で動作します。

### 2.2 OperationalEnvironment（運用環境）の最小定義
- **概念**: アプリケーション上における**論理的な「運用・データスコープ」の境界**。
- **責務**:
  - ユーザーが操作時にアクティブにし、対象となる正本ストレージ、設定マスター群を切り替える運用単位。
  - 現在の設計ではGoogle Driveのルートフォルダや連携スプレッドシート台帳群がその環境に紐づく正本ストレージとして扱われますが、**Environment概念そのものをGoogle実装へ固定しません**。
- **個人利用における自律性**:
  - **個人運用においては、Organization（法人等の組織マスター）を持たない OperationalEnvironment も成立可能**とします。個人利用のために不要な架空法人レコードを作成させる強制は行いません。
- **保留事項**:
  - OrganizationとOperationalEnvironmentの多重度（1:1、1:N、N:M等）や物理外部キー設計は、**`PENDING-C1-SCHEMA`** とします。
  - OperationalEnvironmentを「バックアップ境界」とは定義せず、全DB復旧方式はPENDINGのまま維持します。

## 3. EnvironmentMembership（環境所属）とライフサイクル意味論

人物（Personnel）が特定の運用環境（OperationalEnvironment）において活動する関係を「環境所属（EnvironmentMembership）」として定義します。

### 3.1 所属ライフサイクルの3状態（意味論の正本）
物理的なenum値（英語表記等）を先回りして固定化せず、以下の**意味論（セマンティクス）を正本**とします。物理状態値は **`PENDING-C1-SCHEMA`** です。

```text
       ┌──────────────┐
       │   所属中     │◀────────────────┐
       └──────┬───────┘                 │
              │ 権限者による明示操作    │ 再所属（同一ID維持）
              ▼                         │
       ┌──────────────┐                 │
       │   所属終了   │─────────────────┘
       └──────────────┘
```

1. **所属中（意味論: Active）**:
   - 当該運用環境において有効に業務役割（操縦者、通報者、記録者、補助者）を担当し、アプリ機能を利用可能な活動状態。
2. **所属終了（意味論: Terminated / Departed）**:
   - 退職、離任、契約満了等により、当該運用環境における活動資格を終了した状態。
   - **物理削除の全面禁止**: 人物レコードや所属関係を物理削除してはなりません。
   - **過去実績の恒久保持**: 過去の飛行日誌、日常点検記録、監査証跡におけるPersonnel参照は恒久的に保持されます。
   - **新規選択候補からの除外**: 今後作成される新規運航計画や現場打刻において、操縦者・通報者・記録者・補助者の選択候補から自動的に除外されます。
   - **自動所属終了の禁止**: 長期未使用、臨時講師の空白期間、スポット勤務、休職等のみを理由としてシステムが自動的に所属終了に変更してはなりません。権限者が明示的に操作したときのみ移行します。
3. **再所属（意味論: Re-affiliated）**:
   - 過去に所属終了となった人物が、同一運用環境で再び業務を担当することになった状態。
   - **人物レコードの二重作成禁止**: 新規の人物IDを発行せず、過去実績を持つ既存の同一人物IDを維持して所属を再開します。
   - 現在必要な業務役割を再設定して活動を再開します。

## 4. 複数環境の運用と表示境界

- **複数環境所属時の環境明示**:
  - 同一人物が複数の運用環境に所属している場合、アプリ画面上に「現在の運用環境名」を明示し、環境切替を行えるようにします。取り違え防止上必要に応じて、現在使用中のGoogleアカウントも併記します。
  - 所属環境が単一（個人環境のみ等）である場合は、環境切替UIや常時表示を省略して現場の画面をシンプルに保ちます。
- **環境切替時のデータ境界**:
  - 環境を切り替えた際は、対象となる運用環境のルートストレージおよび台帳群へ正本を切り替えます。環境を跨いでデータが意図せず混ざらない独立スコープを維持します。

---

## 5. PENDING / WARN の明示

- **PENDING-C1-SCHEMA**:
  - `Organization`, `OperationalEnvironment`, `EnvironmentMembership` の物理DBカラム名、キー型、インデックス定義。
  - 所属状態の物理enum値（英語識別子等）。
  - 複数環境の招待・参加UIフロー（個人利用を最優先とし、C1では過剰なIAM/招待UIを構築しない）。
  - 全DBバックアップ・復旧方式（ADR-0008に従いPENDINGを維持）。
- **WARN: 実環境機微情報の非公開**:
  - 本設計書およびリポジトリ内には、実在の個人名、個人メールアドレス、特定のGoogle DriveフォルダID、固定IP実値等の機微情報を一切記載してはなりません。
- **WARN: Google Drive実共有との非連動**:
  - アプリ内で「所属終了」の操作を行っても、Google Drive側のファイル共有（Viewer/Editor）は自動的には解除されません。実共有の解除はGoogle Workspace / Drive側で管理者が別途行う必要がある運用境界を厳守してください。
