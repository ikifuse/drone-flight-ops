# 01. 三層権限モデル・業務役割・機能権限設計（01_three-tier-permissions-and-roles.md）

最終更新: 2026-09-18\
状態: Phase C0完了・Phase C1未着手（Step 2正本化）

主要責務: 三層権限の完全分離、業務上の役割（Pilot/Submitter/Recorder/Assistant）、アプリ機能権限、層間制約ルール、管理者交代。

---

## 1. 三層権限モデルの根本原則（レイヤー分離）

ドローン運航管理におけるアクセス制御は、以下の**3つの独立したレイヤー**として分離し、相互に混同・自動昇格・二重管理を行わない設計を徹底します。

```text
┌─────────────────────────────────────────────────────────────┐
│ 【第1層：業務上の役割 (Operational Roles)】                 │
│  - 現場の操縦者、通報者、記録者、補助者等の実務・法令上の役割 │
│  - Personnelマスターが保持し、運航計画・日誌で割り当てられる │
└─────────────────────────────────────────────────────────────┘
                               ▲
                 【非連動】相互に自動決定・自動昇格しない
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 【第2層：アプリ機能上の権限 (App Functional Permissions)】    │
│  - 設定変更、運航入力、計画作成、管理者管理 等の操作制御     │
│  - アプリケーション内部の認可機能（大枠・制約以外はPENDING） │
└─────────────────────────────────────────────────────────────┘
                               ▲
                 【非連動】相互に自動決定・自動昇格しない
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 【第3層：外部ストレージ実アクセス権 (Physical Drive Permissions)】│
│  - Google Drive上の Viewer / Editor / Owner 等の実ファイル権限│
│  - Google側が唯一の正本（アプリ側で自動付与・管理を行わない） │
└─────────────────────────────────────────────────────────────┘
```

## 2. 第1層：業務上の役割（Operational Roles）

現場の運航実務および法令上の役割分担として、Personnelが担当可能な業務役割を以下の**4役割**に純化して定義します。

| 業務上の役割 | 役割の定義 | 実務・法令上の位置づけ・99.2根拠 |
|:---|:---|:---|
| **操縦者（Pilot）** | 現場でドローンを実運航・操縦する責任者。 | 技能証明プロファイル（所持時）を持つ。日常点検（飛行前・飛行後点検）の原則的な実施者。 |
| **通報者（Submitter）** | DIPS 2.0へ飛行計画を実際に通報・送信する手続き担当者。 | 操縦者と同一人物でも、オフィス事務・運航管理者等の別人でもよい（会社での事前一括通報を許容）。 |
| **記録者（Recorder）** | 現場でアプリ画面への打刻・実績入力を担当する実務者。 | 通常は操縦者選択時に同一人物を初期値とし、別人入力時のみ変更可能。操縦者と別欄で保持。 |
| **補助者（Assistant）** | 現場で周囲警戒・目視補助等を行う者（0人以上）。 | 立入管理措置は安全措置プリセットとして扱い、独立役割にしない。原本台帳への恒常アクセスは持たない。 |

- **業務Roleのスコープと保持構造の保留**:
  - 同一人物が複数の運用環境（OperationalEnvironment）に異なる立場で関与できる設計（99.2 §2）であるため、業務RoleはPersonnel固有の全環境共通の恒常属性とは限らず、特定運用環境における所属（Membership）や役割割当に紐づく可能性があります。
  - 業務Roleの意味論（Pilot, Submitter, Recorder, Assistant）は本節で確定しますが、物理的にどこへ保持するか（Personnelマスター直下、EnvironmentMembership、別RoleAssignment等）は **`PENDING-C1-SCHEMA`** とし、三層権限を再結合する具体的DB構造はこのStepで決定しません。

### 2.1 Role（役割）と Actor（実施者）の厳格な分離原則
- **Personnel側の業務役割（Role）** は、「その人物がその運用環境において担当資格・能力を持つ役割」を表す属性です。
- **個別記録における実際の実施者（Actor）** は、特定の飛行計画、実際の飛行、または点検記録において「実際にその操作・業務を担当した人物」を指します。
- **Roleから今回のActorを自動推測・同一視してはなりません**。
  - 例：操縦者Roleを持つ人物であっても、あるフライトでは補助者Actorとして参加することがある。
  - 例：通報者Roleを持つ人物が計画を作成・通報（通報Actor）し、実際の現場飛行は別の操縦者Actorが担当する。

### 2.2 点検・整備実施者（Inspector）の位置づけ
- 点検・整備記録（[12e](../domain-model/12e_operation-inspection-maintenance.md) の `PreflightInspection`, `PostflightInspection`, `MaintenanceRecord`）における実施者は、**「記録側のActor参照（`inspector_id`）」** として扱います。
- **根拠**:
  - 99.2 §2 において「通常飛行の日常点検は操縦者が基本で、日常点検実施者を常時別選択させない」と規定されており、日常運航において恒常的なPersonnel Roleを設ける運用根拠がありません。
  - 点検・整備記録において実施者（Personnel）への参照を保持することで、**点検・整備記録上、実施者をPersonnelとして特定・追跡できる**ため、Personnel側に恒常的な `inspector` ロールを常時持たせる必要はありません。

## 3. 第2層：アプリ機能上の権限（App Functional Permissions）

アプリケーション内の画面操作やデータ編集に関する認可レイヤーです。

- **アプリ管理者（App Administrator）**:
  - 運用環境の作成、管理者アカウントの追加・解除、機体・BAT・人員マスターの設定変更を行える特権権限。
  - 初回セットアップ時に最初のGoogle認証を行ったアカウントが初期アプリ管理者となる。
- **操作主体（SubmissionActor）と業務役割（Submitter）の区別**:
  - DIPS通報手続きをアプリ画面で実際に操作した操作主体は `SubmissionActor`（UserAccount。`submitted_by_user_id`）として記録されます。
  - 業務上の通報責任者・担当者である `Submitter`（Personnel）や現場の `Pilot`、緊急連絡窓口である `ContactPerson` / `EmergencyContactPerson` とは概念上明確に分離されます。
- **権限Grantモデルの保留（PENDING）**:
  - 各種画面の閲覧可否、CSVエクスポート可否等の細粒度な権限プロファイルや、ユーザーへの具体的Grant方式は本Stepで確定させず、**`PENDING-C1-SCHEMA`** とします。

## 4. 第3層：外部ストレージ実アクセス権（Physical Drive Permissions）

本システムが連携する外部ストレージ（Google Drive / Sheets）における物理的なアクセス権限レイヤーです。

- **Google側を唯一の正本とする**:
  - Google Workspace / 個人Googleアカウント標準の共有設定（Viewer / Commenter / Editor / Owner）が唯一の正本です。
  - アプリケーション内部から Google Drive のアクセス権を自動付与・自動剥奪したり、アプリ内でEditor申請・承認ワークフローを二重構築することは行いません。
- **Google実仕様の尊重**:
  - Google Driveの共有はファイル／フォルダ単位であり、1つのSpreadsheet内の特定シートタブのみに別Drive権限を付与することはできません（シート保護は別機能）。
  - アプリ側でいくら編集を許可しても、Google側でViewer権限しか持たないアカウントは直接Spreadsheetを編集できず、Google側で書き込み拒絶されます。この物理制約を設計の前提とします。

## 5. 禁止する「自動連動」と許される「制約ルール」

### 5.1 禁止する「自動連動」（Anti-patterns）
以下の自動的な権限昇格・連動は、セキュリティ境界を破壊するため厳禁とします。
1. **業務役割 → アプリ機能権限の自動昇格の禁止**:
   - 操縦者（Pilot）だからといって、自動的に「アプリ管理者」権限を与えてはならない。
2. **業務役割 → Drive実アクセス権の自動付与の禁止**:
   - 操縦者や記録者だからといって、アプリが自動的にGoogle DriveのEditor権限を付与してはならない。
3. **Drive実アクセス権 → アプリ機能権限の自動付与の禁止**:
   - Google DriveでEditor権限を持っていることのみを理由に、アプリ管理者権限を与えてはならない。
4. **Google実仕様の無視の禁止**:
   - Google側でViewer権限のアカウントに対し、アプリ内で直接同期完了を保証するような偽の権限判定を行ってはならない。

### 5.2 層間で許される「制約ルール（Guardrails）」
99.2 §2に基づく業務上の安全性確保のため、以下の制約ルールを適用します。

- **制約1: 設定変更の制約**
  - 機体・BAT・人員マスターの登録・変更、およびアプリ設定を変更できるのは、**「アプリ管理者」** または **「操縦者」** として認可されている者のみとする。
  - **「記録者」単独の立場では設定変更を行わせない**（同一人物が別途操縦者または管理者として認可されている場合を除く）。
- **制約2: 補助者アクセスの制約**
  - **「補助者」の業務役割を持つことのみを理由として、元台帳（Google Drive / Sheets / KML / My Maps）への恒常的なアクセス権を与えない**。
  - 補助者が特定フライトの記録を必要とする場合は、権限者がPDF等を生成して個別に提供・共有する。
- **制約3: 管理者交代と最後の1人保護**
  - アプリ管理者の追加・解除は、既存のアプリ管理者のみが行える。操縦者であることのみを理由に管理者の追加・解除はできない。
  - **最後の1人の管理者は、代替の管理者を指定・追加しない限り、自分自身の管理者権限を解除できない**。

## 6. PENDING / WARN の明示

- **PENDING-C1-SCHEMA**:
  - 第2層における機能権限の内部データ構造（RBAC/ACL/Claimsの物理表現）。
  - 未確定の画面・機能に対する個別権限マトリクス（未確定セルは独自判断で補完しない）。
- **WARN: Google Drive実アクセス権との二重管理誤認の防止**:
  - アプリ側でユーザーの役割や所属を変更しても、Google Drive側の実共有設定（Viewer/Editor）は自動的には変更されません。退職時や役割変更時は、Google側での共有解除・変更作業が別途必要となる運用境界を厳守してください。
