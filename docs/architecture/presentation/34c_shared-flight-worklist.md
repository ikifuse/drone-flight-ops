# 34c. 共有飛行リストと通報済み計画の選択

最終更新: 2026-09-19\
由来: 99.2 §3、§7の共有リスト・カード・通常導線に直接必要な部分。\
主要責務: これから扱う計画の共有作業リスト、カード、絞り込みの方向、対象選択。掲載契機と受付後画面は[34d](34d_dips-accepted-and-plan-content.md)。

## 1. 保存済み計画の選択から共有作業リストへ

**当初状態**: 基準[24a §5](../dips-submission/24a_submission-and-sheets-ledger.md#5-実運航mission--flight--飛行日誌との紐付け設計)には、現場運航開始時に保存済み計画を選び、Missionと提出記録を結び付ける設計があった。同書のDIPS台帳は提出試行・Snapshot・履歴を保持するためのものだった。これだけでは、別日に別担当者が「これから扱う計画」を選ぶホーム入口・一覧表示を規定していない。

**問題・検討**: 先に通報した計画を後で操縦者が引き継ぐ運用では、履歴全体から探すことと現場の作業対象を選ぶことを分ける必要がある。ホームの新規／続行分離の詳細因果は[34b §1](34b_home-and-navigation.md#1-2入口から3入口4入口へ進んだ因果)、担当者の分離は[31c](../identity-and-access/31c_operational-actors.md)に置く。

**現在到達点（CURRENT-ACCEPTED）**: ［飛行リスト］はDIPS正常受付済みで、これから実飛行または中止等を扱う計画を共有する軽量な作業リスト。共有Drive／Sheets側の作業用リストを正本として参照する。完了済みFlightを探す［飛行履歴・出力］や、通報履歴を恒久保持する監査台帳と同一視しない。人物・所属・実アクセスのモデルは31a〜31dに従い、環境や利用者をまたいで無制限に公開するリストにはしない。

**実物の位置づけ（EVIDENCE/EXAMPLE）**: §7は「DIPS・飛行計画台帳_叩き台」を、人が予定日時・場所・機体・操縦者／通報者・DIPS状態を確認する1シートの実物として記録している。技術用の複数タブが利用者の1枚台帳の前提と違い、整理された経緯も記録する。これは一覧の見え方を検討した証拠であり、今回その実Driveを再確認・編集したものではない。実物の存在から内部schemaやDrive全体構造を採用済みにせず、旧技術タブを現在の利用者画面へ復活させない。

## 2. カードの情報と絞り込み

**問題・現在案**: 原本は、一覧で対象計画と担当者・DIPS状態を判別し、その計画の通報内容へ進む構成に詰めた。初期カードは以下の5系統を**CURRENT-ACCEPTED**として保持する。表示を絞ることは、計画正本や提出証跡の内容を5項目へ切り捨てる意味ではない。

| 系統 | 初期カードに表示する意味 |
|---|---|
| 予定日時 | これから扱う計画の日時 |
| 飛行場所 | 対象現場を識別する場所 |
| 機体 | 計画の対象機体 |
| 操縦者／通報者 | 両者を識別する。概念とアカウントの対応は31c |
| DIPS状態 | 通常系は「通報済み・重複なし」、重複が返れば「通報済み・重複あり」 |

飛行計画名・新しい検索欄・独自の警告件数等をAI判断で必須カード項目へ加えない。既存FlightPlanに計画名称が存在することは、カード必須表示の根拠ではない。重複ありの表示は保持するが、具体的な調整操作は今回扱わない。

**絞り込みの方向（CURRENT-PROPOSAL）**: ［すべて］［自分が操縦］［自分が通報］［重複あり］。§7の通常系記述では上部へ置く具体案があり、保存節では「等で絞り込める方向」としているため、この4分類を現在のUI候補として保持する。4入口や5系統のカードと同じ確定度の最終フィルタ仕様にはしない。初期選択、複数条件の組合せ、件数の見せ方、並び順は未確定。一般的な検索・ソート・日付フィルタを追加しない。

## 4. 通報内容へ直接進み、ローカル編集を置かない理由

**さらに詰めた内容（CURRENT-ACCEPTED）**: 対象を選んだ後の目的は、通報した内容を確認して飛行前点検へ進むこと。原本は汎用の中間詳細画面を挟まず、直接「DIPS通報内容」を表示するとした。余分な中間画面案を現在仕様へ加えない。

日時・場所等の変更は、ローカルだけの編集ではDIPS側の通報計画と一致しなくなるため、DIPS側の変更／再通報を伴う別処理として扱う。通常詳細に大きな［編集］を常設しない。これは原本の変更と送信の境界を保持するもので、別処理の入力・再通報・取消の全フローを完成させるものではない。内容画面の10項目・主操作は34dを唯一の詳細正本とする。

## 5. 未確定と適用限界

- **PENDING-S5-LIST-DETAIL**: UI候補のフィルタ・初期値・件数表示、具体的な作業リストの物理保持・cache・共有反映。既存24aの履歴列をそのままリストschemaにしたり、別Spreadsheetの新設を決めたりしない。cache・正本確認の方針は[38a](../sync-and-cache/38a_shared-source-and-device-cache.md)。
- **PENDING-S5-MANUAL-LIST**: API正常受付の条件と、番号なしの目視照合も認める既存Manual確認からリストへ接続する詳細との照合。今回のAPI通常系からManualへ計画ID必須を機械適用しない。[24](../dips-submission/24_manual-submission.md)と[25b](../dips-flight-plan/25b_manual-web-mapping.md)の第一級Manualを維持し、別の完成フローを推測しない。
- **後続範囲**: 重複調整、日時等の変更・再通報、取消、予定日時経過・中止・完了時のリスト／cache整理。原本の正確な自動整理時点・条件は未確定だが、作業リストを履歴DBとしない意味は到達済み。本Stepではこれらの詳細移植を行わない。後続のStep 7bで、取消・整理の意味と06の記録責任・作業台帳との関係を[24b](../dips-submission/24b_dips-plan-records-and-worklist-lifecycle.md)へ配置した。正確な時点・条件と重複あり調整は未確定のまま。
- **VERIFY-S5-LIST-EVIDENCE**: 原本が挙げる実Driveの1枚作業台帳、旧画面資料と表示5系統との対応。今回は再操作していない。通信成否不明の因果は[33b](../dips-infrastructure/33b_api-availability-and-retry-boundaries.md)を参照し、本書へ複写しない。
