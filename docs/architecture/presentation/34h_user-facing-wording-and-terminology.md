## 1. 内部概念名が利用者画面へ出た因果

**発端・当初の状態（HISTORICAL）**: 2026-09-20時点の設計と、それを確かめるために作った設計確認用モックは、内部設計の概念名や設計書の参照番号を、そのまま画面の文言にしていた。初回の入口は［新しい運用環境を作成］／［既存の運用環境に参加］、招待された人の確認は「あなたは誰ですか」「人物の紐付け」、保存場所の一覧は「01 人員」「04 運航記録」などの番号つき、保存の状態には「同期」「未同期」「反映」「端末に保護」などの技術語、画面の注記には設計書の節番号が出ていた。これらは設計上は正確な語である。

**問題（2026-09-21のモック確認）**: オーナーがモックを一通り操作し、内部の概念名・技術用語・設計書番号が一般利用者向けの画面へ漏れていることを確認した。このアプリの大前提は、現場で利用者を迷わせず、飛行計画・DIPS通報・飛行前点検・実飛行・飛行後点検・飛行日誌保存までをスマートフォン1台で進められることである。内部的に正しくても、利用者が画面の言葉の意味を考えないと操作できない状態は採らない。

**検討と採らない案**: 内部モデル（OperationalEnvironment、EnvironmentMembership、MembershipRoles、Personnel、GoogleIdentity／UserAccountなど）を利用者向けの言葉に合わせて作り替える案、設計文書の概念名を一括置換する案は、人物・Googleアカウント・所属・役割を分けた設計（[31a](../identity-and-access/31a_person-account-and-environment.md)・[31b](../identity-and-access/31b_roles-and-access-control.md)）と過去の因果を壊すため採らない。**内部名と表示名を分け、表示名だけを利用者に見せる**。

**新文書にした理由（Responsibility Check）**: 内部の概念名と利用者向け表示の対応は、画面の10項目規約（30）にも、各画面の仕様（34a〜34g）にも収まらない。変更の契機（表示名の確定・改訂）が個々の画面仕様とは別に起こり、複数の画面文書と失敗の表示（[19](../19_failure-recovery.md)）にまたがるためである。規約の本文は30 §4に置き、本書は対応表と文言の型だけを持つ。

**現在の到達点**: §2〜§7の対応・型に従い、利用者向けの画面文言を内部語から分離する（CURRENT-ACCEPTED）。個々の表示名は案である（CURRENT-PROPOSAL）。過去に採った表示名（［新しい運用環境を作成］など）は、現在へ至る経緯（HISTORICAL）として34a §1・§7に残す。

## 2. 内部の概念名と利用者向け表示（案）の対応

内部名は設計Docs・コード・設計確認メモで使い続ける。右欄は、モックの左側（本番アプリを模した画面）に出す言葉の案である。

| 内部の概念・用語 | 利用者向けの表示（案） | 補足 |
|---|---|---|
| OperationalEnvironment（運用環境） | 「個人」「○○株式会社」など**実際の名称**。使用中は「個人で使用中」「○○株式会社で使用中」。切替の操作は［切り替える］ | 「運用環境」を表示名にしない。抽象名詞を増やさない（オーナー指示の例） |
| 新規のOperationalEnvironment作成（個人／会社・団体） | 個人は初回に自動で作られるため表示名を持たない。会社・団体はホームの［会社・団体で新しく使い始める］ | 新規作成時のGoogle Drive上の保存構造の生成は34a §1のとおり。会社／スクール／臨時業務などの種類は分けて聞かず「会社・団体」にまとめる（[34a §7.7](34a_setup-and-environment-entry.md#77-どのように使いますかで種類を分けて聞かないことの確定2026-09-22)）。初回の［個人で使う］はHISTORICAL（34a §9.2） |
| 既存のOperationalEnvironmentへのEnvironmentMembership追加 | ［すでに使っている会社・団体に参加する］→ 参加する会社・団体を選ぶ | ホームから進む（[34a §9.4](34a_setup-and-environment-entry.md#94-会社団体はホームからその会社で使うgoogleアカウントで追加する)）。新しい保存構造を重複して作らない（34a §1・§2）。初回に選ばせていた［会社・団体から招待を受けている］はHISTORICAL |
| GoogleIdentity／UserAccount | 入口の操作は［利用登録を始める］［ログイン］。認証後は「このGoogleアカウントで、このアプリを使い始めます」（[34a §7.6](34a_setup-and-environment-entry.md#76-初回の入口を1画面にまとめた訂正2026-09-22)・[§7.9](34a_setup-and-environment-entry.md#79-利用登録とアカウントの表示の訂正2026-09-22)） | 独自のパスワードもアプリ専用のIDも作らない。**「アカウントができました」のように、アプリ専用のアカウントを発行したように見える表現を使わない**。「利用登録」は、新しいGoogleアカウントやアプリ専用IDを作る意味ではない。説明だけの中間画面（［Googleアカウントで続ける］）は廃止 |

| EnvironmentMembership／MembershipRoles | 「参加」「役割」。離れた人は「離任」 | 離任は人物の削除ではない（[31d](../identity-and-access/31d_membership-lifecycle.md)） |
| 最初のアプリ管理者 | 「管理者」 | 新しく個人／会社・団体を始めた人が最初の管理者。招待で参加しただけの人は自動では管理者にならない（31b §3） |
| root、01〜07、正本 | 「保存場所」「フォルダー」。フォルダーは番号を付けず名前だけ（人員・機体・バッテリー・運航記録・点検整備記録・DIPS関連・出力） | 内部の領域番号・正本という語は画面に出さない |

## 3. 利用者画面に出さないもの

次は、本番アプリの画面には表示しない。設計Docs・コード・設計確認メモ（モックの右欄）には残す。

- 内部モデル名・技術用語（OperationalEnvironment、EnvironmentMembership、MembershipRoles、GoogleIdentity、UserAccount、root、正本、cache、SyncQueue、ManualDipsAdapter、payload、snapshot、FSM、FlightLeg、Mission、schema、UUID、IndexedDB など）
- 設計書の参照番号・節番号（31b、32h、34g、24b、27e など、§つきの参照）
- 内部の保存領域の番号（01〜07）
- 設計状態のラベル（PENDING、VERIFY、CURRENT-ACCEPTED、CURRENT-PROPOSAL、HISTORICAL など）
- 英語のエラー分類名（Network Error、Sync Error、Unsupported State、Data Corruption など。[19](../19_failure-recovery.md)の分類名は内部用）

## 4. 維持する言葉

**現場で使ってきた言葉（変えない）**: 機体、操縦者、補助者、BAT／バッテリー、飛行目的、飛行計画、飛行前点検、離陸、飛行中、着陸、飛行後点検、飛行記録、飛行日誌、点検整備、飛行履歴、保存、オンライン、オフライン。旧アプリの現場思想（画面どおり進めば迷わない／飛行中は操作を極力しない／最後にまとめて保存する／保存に失敗しても入力を消さない）も維持する。

**DIPS公式の項目名（勝手に言い換えない）**: DIPS Webと見比べられるよう、確認済みの公式名称を優先する。例: 計画名称、飛行許可番号、飛行目的、飛行空域、飛行方法、立入管理措置、係留飛行、補助者人数、開始日時、飛行高度、保険に関する情報、連絡先。選択肢の名称もDIPS Webの表記のままとする（[26](../26_dips-web-ui-verification.md)・[25b](../dips-flight-plan/25b_manual-web-mapping.md)）。「分かりやすくする」ことを理由に別名称へ変えない。

## 5. 保存・同期の表示

内部のSyncQueueや正本・外部台帳の区別はそのままとし、利用者には**いま何が起きているか**が直接分かる言葉で示す（CURRENT-PROPOSAL）。

| 状況 | 表示の例（案） |
|---|---|
| Google Driveへ保存済み | 「Google Driveに保存しました」 |
| 通信できず未保存 | 「まだGoogle Driveに保存されていません。この端末には保存されています。通信が戻ったら自動で保存します」 |
| 保存に失敗した | 「Google Driveに保存できませんでした。入力内容はこの端末に残っています。通信が戻ったら、もう一度［保存］を押してください」 |
| 一覧の印 | 「未保存」（保存済みは印を出さない） |

## 6. エラー表示の型

エラーは、必ず次の順で利用者へ伝える（規約は[30 §4](30_screen-specification-standard.md#4-内部設計用語と利用者表示文言の分離)）。

1. **問題**: 何ができなかったか
2. **データ保護状態**: 入力した内容・記録が残っているか
3. **次の操作**: 次に何をすればよいか

例（案）: 「Google Driveに保存できませんでした。入力内容はこの端末に残っています。通信が戻ったら、もう一度［保存］を押してください。」「DIPSに登録されたかどうか分かりません。同じ内容を自動で送り直すことはしません。DIPS Webの一覧で登録されているか確認してください。」内部のエラー分類・ログ用の名称は[19 §1](../19_failure-recovery.md#1-エラー分類と対応方針マトリクス)の分類名のままとし、画面には出さない。

## 7. 通報方式の表示

DIPSへの通報の主操作は、［アプリからDIPSへ送信する］と［DIPS Webで通報する］とする。前者はAPI経路、後者はManual経路（[24](../dips-submission/24_manual-submission.md)）の内部方式に対応する。APIが使えない場合でも、DIPS Webで通報する経路で最後まで進める（[33b](../dips-infrastructure/33b_api-availability-and-retry-boundaries.md)）。「Manual」「API」「Optional」などの方式名は、主ボタン名にも、状態を示す印にも使わない。補助説明として「API」と書くのは構わない。

## 8. 未確定と、確定してはならないこと

- **PENDING-U-WORDING**: 本書の表示名・表示例の最終形。オーナーが指示した例（利用登録を始める／ログイン／会社・団体で新しく使い始める／すでに使っている会社・団体に参加する／はじめの登録／登録してホームへ／どこで使いますか？／個人で使用中／切り替える。［個人で使う］［会社・団体から招待を受けている］は2026-09-23にHISTORICAL）と、§10のDIPSログイン情報の表示も、確認のための例であり、製品用語として確定していない。AIが画面の見え方から勝手に製品用語を確定しない。
- 初回の入口で使う「利用登録」と、既存のGoogleアカウントを指す「アカウント」の言い分け。2026-09-22に、アプリ専用のアカウントを発行したように見える表現（「アカウントができました」）は使わないことを確定した（34a §7.9）。個々の言い換えの最終形は未決。
- 「環境」は画面に出さない（§3）。会社・団体の追加は、内部では新規OperationalEnvironmentの作成と既存OperationalEnvironmentへの所属追加だが、画面では［会社・団体で新しく使い始める］［すでに使っている会社・団体に参加する］とする（2026-09-23。表示名の最終形は未決）。
- 設定名「保存・同期」の言い換え（「保存状態」など）、「離任」の表記、「BATを共用する機体のグループ」の最終名称、「対象機体」など、個々の言葉の最終決定はオーナー確認後。
- 表示名の未確定は、設計確認メモ（モックの右欄）へ残す。本番の画面へ「仮」「未確定」の注記を出さない。

**ADR判断**: 新しいADRは追加しない。既存のAccepted ADRの決定は変えず（初回の表示名はADRで固定されていない）、訂正の因果は[34a §7](34a_setup-and-environment-entry.md#7-利用者向けの表示名と初回導線の訂正2026-09-21)・[§7.6](34a_setup-and-environment-entry.md#76-初回の入口を1画面にまとめた訂正2026-09-22)と本書§1に記録する。オーナーがADRとして残すと判断した場合に、ADR化を検討する。

**検証**: 設計確認用モックでは、左側の利用者画面の文字に§3の語が出ていないことを自動で検査する。右側の設計確認メモは検査の対象外である（モックは実装ではない。C1未着手）。

## 9. サンプルと設計確認用の状態の置き場所（2026-09-22）

**発端・当初の状態（HISTORICAL）**: 2026-09-21の訂正後のモックは、Googleアカウントの選択画面にテスト用のアカウント3件と状態の説明を並べ、各画面に「確認用」の枠や切替を出していた。**問題・現在の到達点（CURRENT-ACCEPTED）**: [30 §5](30_screen-specification-standard.md#5-設計確認用モックの左右の役割と未決事項の扱い)のとおり、左側は本番の画面の候補だけにし、確認用の情報は右側へ移す。置き場所は次のとおり。

| 種類 | 左側（利用者画面） | 右側（設計確認） |
|---|---|---|
| テスト用のGoogleアカウント、テスト用の人物、仮の会社名など、状態を切り替えるためのデータ | 出さない | 状態の切替とともに示す |
| 登録前／登録済み／個人のみ／個人と会社／閲覧のみ／未共有／DIPSへ送信できる・できない／オフライン | 選ばれた状態で、本番のアプリが見せる画面だけ | 切替の操作と、いまの状態 |
| Googleが表示する公式の画面（アカウントの選択・Google Driveの許可） | 「実際はGoogleが表示する」ことが分かる程度。細部は再現しない | 認証後・許可後の状態の選択 |
| 入力欄の記入例（会社・団体名、DIPSログインID、電話番号、メールアドレスなど） | placeholderなどの薄い文字（例：○○株式会社、1234567890、090-1234-5678、name@example.com）。登録済みの値のように並べない | 記入例の意図（必要なとき） |
| 一覧などに必要な仮のデータ | 一般的な名前・値。「サンプル」「確認用」「テスト用」などの語を含めない | 「表示中の名前や値は仮のデータ」の説明 |
| 未確定・比較したい案・オーナー確認待ち | 出さない。完成品として見せない | 「オーナー判断が必要な設計論点」「未決・仮置き（いま決めなくてよいこと）」「一般的なUI判断（AI側の標準案）」の3つに分ける（[30 §5.2](30_screen-specification-standard.md#52-オーナーに判断を求める粒度2026-09-22)）。比較用の切替 |
| 内部の用語・設計書番号・状態ラベル・設計の根拠 | 出さない（§3） | 出してよい |

利用者画面の文言は最小にする。画面のタイトル、いまやること、入力欄、主ボタンが一目で分かる構成にし、詳しい説明は右側へ置く。モック自体は設計を決める道具であり、モックを完成させるために未決の設計を決めない。右側で何をオーナー判断として尋ねるかの粒度は30 §5.2に従い、一般的なUI・UXはAI側の標準案として置き、オーナー確認待ちにしない。

## 10. DIPSログイン情報の表示（案。2026-09-22）

DIPSのログインID・パスワードをアプリへ登録・保存できる方針（[34a §8](34a_setup-and-environment-entry.md#8-dipsログイン情報の登録と初回設定の候補2026-09-22)。オーナーの指示。CURRENT-PROPOSAL）に対する、利用者向けの表示の案である。

| 内部の対応 | 利用者向けの表示（案） | 補足 |
|---|---|---|
| DIPSログイン情報の登録画面 | 画面名「DIPSのログイン情報」。入力欄「DIPSログインID」「DIPSパスワード」。主ボタン［登録する］、副ボタン［あとで設定する］ | パスワードは伏字。［表示］／［非表示］で切り替える。記入例はplaceholder |
| 未登録のまま、アプリからDIPSへ送信する段階へ来たとき | 「DIPSのログイン情報がまだ登録されていません」［今設定する］［あとで行う］ | 行き止まりにしない。登録後は元の飛行計画へ戻る |
| ［各種設定・管理］からの登録・変更 | 「DIPSのログイン情報」。状態は「登録済み」「未登録」 | 保存先などは画面に出さない（未決） |

「credential」「シークレット」などの内部語は画面に出さない。個々の言葉の最終形は§8のPENDING-U-WORDINGのままである。

### 10.1. 空欄と登録済み状態の訂正

未登録時に伏字のplaceholderを置くと入力済みに見えるため、空欄＋「パスワードを入力」へ修正する。登録済みは状態として表示し、欄そのものは空で「変更するときだけ入力」。入力後だけ伏字とし、表示／非表示は現在入力中の文字だけに作用する。保存できる製品方針を変更せず、モックでは入力した秘密を永続保存・送信しない差を右側へ記す（34a §8）。

### 10.2. 利用者画面の自動検査を補強

登録記号の`JU-SAMPLE-*`等が表示に残っていたため、モックの仮データを一般的な値へ訂正した。左側の表示テキストに加え、表示中のinput／textareaの現在値・selectの選択中表示値を検査する。sample／test／dummyは大文字小文字を問わず検出し、日本語の設計専用語も失敗扱いとする。placeholderは入力例として対象外とし、例をvalueへ流し込むことは許容しない。右側の説明・状態操作は検査対象を分ける。PENDING-U-WORDINGは維持する。
