# 30. 画面仕様の記録単位

最終更新: 2026-09-22\
状態: CURRENT-ACCEPTED（規約）。個別画面の未確定内容を確定するものではない。§4は2026-09-21、§5・§5.2は2026-09-22のオーナーの指示で追加した。\
由来: 99.2 §0「画面仕様の記録単位」。識別情報は[Step 1監査](../../migration/99-2-step-1-causal-audit.md)。

## 1. 発端から現在の規約まで

**当初の状態**: 基準Docsの[20](../20_source-structure.md)にはPresentationとUsecases等の責務境界があり、[25b](../dips-flight-plan/25b_manual-web-mapping.md)にはDIPS固有画面の仕様がある。全画面に共通する以下の10項目規約については、基準Docsの検索・該当文書確認の範囲で旧設計なし。

**問題**: 99.2 §0では、「次にどの画面へ進むか」や画面名だけでは、会話で説明済みの表示・操作・保存の意味を実装へ引き継げないため、記録単位を定めた。

**検討・理由・到達点**: 画面名・遷移のみの短縮記録を採らず、同じ画面の論点内に目的から保存・権限差・通信状態差・未確定まで保持する。表示と保存タイミングの結びつきを追うための規約であり、未知の画面仕様を埋めるための規約ではない。99.2 §0の10項目を現在の記録ベースラインとする。独立した別候補の比較や却下理由は同節に記載されていないため、追加しない。

## 2. 画面ごとに保持する10項目

| 番号 | 記録項目 | 保持する意味 |
|---|---|---|
| 1 | 目的 | 利用者がこの画面で何をするか |
| 2 | 入口・入れる条件 | どこから入るか、どの条件で入れるか |
| 3 | 表示情報 | 利用者に何を見せるか |
| 4 | 初期値・自動入力 | 入力済み情報を何から引き継ぎ、自動で何を埋めるか |
| 5 | 主操作・副操作 | 利用者に用意する操作 |
| 6 | 操作後の遷移 | 各操作を行った後にどこへ進むか |
| 7 | 戻る・中止・削除 | 中断・戻る・削除をしたときの扱い |
| 8 | 保存・更新時点 | 端末下書き、Drive、DIPSのどれを、どの操作・時点で更新するか |
| 9 | 権限・online/offline差 | 誰が操作でき、通信状態で何が変わるか。両方を記録する |
| 10 | 未確定 | まだ決まっていない内容、根拠を確認すべき内容 |

分かる範囲で記述し、説明済みの意味を画面名へ縮めない。項目8で必要となるファイル間・記録間の流れは[23の開始ゲート](../23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)へ接続し、台帳・状態・権限そのものの定義は各領域の詳細正本を参照する。画面文書へ別のschemaや権限正本を作らない。

## 3. 未確定と証拠の扱い

個別画面の記載が本Stepにないことは、設計自体がPENDINGであることを意味しない。各画面を担当する後続Stepで、その画面の因果・現物・既存Docsを確認する。実際に未確定の内容はPENDINGを維持し、本規約だけから埋めない。VERIFY: 画面の実機動作をこの文書の成立によって検証済みと扱わない。

試作画面はEVIDENCE/EXAMPLEとして、操作して分かったことと採用した仕様を区別する。状態の定義、訂正関係と根拠の保持は[設計証拠規約](../../guidelines/03_design-evidence-and-causality.md)に従う。今回は共通規約の移植までで、個別画面の設計・コード・モック生成は行わない。

## 4. 内部設計用語と利用者表示文言の分離

**発端・問題**: 2026-09-21の設計確認用モックの確認で、内部設計の概念名・技術用語・設計書の参照番号が、そのまま一般利用者向けの画面へ漏れていることが分かった。内部設計として正確でも、利用者が画面の言葉の意味を考えないと操作できない状態は、現場で利用者を迷わせず、飛行計画から飛行日誌の保存までをスマートフォン1台で進めるという大前提に反する。因果と対応表は[34h](34h_user-facing-wording-and-terminology.md)。

**現在の到達点（CURRENT-ACCEPTED）**: 画面仕様の10項目を記録するときも、実際に画面へ出す文言を決めるときも、次の規約に従う。内部モデルと責務分離を作り替える規約ではなく、**利用者へ見せる言葉を内部の言葉から分ける**規約である。

1. 内部モデル名（OperationalEnvironment、EnvironmentMembership、GoogleIdentity、Personnel など）を、そのまま利用者向けの表示名にしない。
2. 設計書の参照番号・節番号（31b、32h、34g §2 など）と、内部の保存領域の番号（01〜07）を、本番の画面に表示しない。
3. PENDING、VERIFY、CURRENT-ACCEPTED、CURRENT-PROPOSAL などの設計状態ラベルと、英語のエラー分類名を、本番の画面に表示しない。
4. DIPSなど外部の公式名称・項目名は、利用者が公式画面と照合できるよう維持する。分かりやすくするという理由だけで言い換えない。現場で使ってきた言葉（機体、操縦者、飛行前点検など）も維持する（[34h §4](34h_user-facing-wording-and-terminology.md#4-維持する言葉)）。
5. 表示名が未確定の間は、AIが製品用語として確定しない。表示例は「案」として34hと設計確認メモへ残し、未確定を本番の画面へ注記しない。
6. 内部用語・状態・根拠は、設計Docs・コード・設計確認メモ（モックの右欄など、本番アプリには出ない場所）に残す。10項目の項目3（表示情報）・項目5（主操作）を記録するときは、内部名と利用者向けの表示（案）を区別して書く。
7. エラーや失敗の表示は、①問題（何ができなかったか）、②データ保護状態（入力した内容・記録が残っているか）、③次の操作（次に何をすればよいか）を、この順で示す（[34h §6](34h_user-facing-wording-and-terminology.md#6-エラー表示の型)）。

**適用限界**: 本節は表示文言の規約であり、個別の表示名を確定しない（PENDING-U-WORDING）。内部の概念・責務分離（[31a](../identity-and-access/31a_person-account-and-environment.md)・[31b](../identity-and-access/31b_roles-and-access-control.md)）と、過去の表示名の経緯（HISTORICAL）は書き換えない。設計確認用モックは、この規約に反する語が左側の利用者画面へ出ていないことを自動で検査する。実装（C1以降）は開始しない。

## 5. 設計確認用モックの左右の役割と、未決事項の扱い

**発端・問題**: 2026-09-21の訂正（§4）のあとも、設計確認用モックの左側（スマートフォンの利用者画面）に、設計確認のためだけのデータや注記が混ざっていた。Googleアカウントの選択画面には、状態を切り替えるためのテスト用アカウント（登録前・個人だけ・個人と会社の両方の3件）と、それぞれの状態の説明が並んでいた。「確認用」と書いた枠や、状態を切り替えるボタンも左側に出ていた。これでは、利用者が実際に見る画面と、設計を確認するための情報を区別できず、完全な初回利用者が左側だけを見て進めるかどうかを確かめられない。あわせて、AIが未決の点を完成した仕様のように埋めたモックになっており、オーナーが実際に触って画面・文言・順番・操作方法を相談しながら決めるという、モックの目的を果たせなかった。

**現在の到達点（CURRENT-ACCEPTED。オーナーの2026-09-22の指示）**: 設計確認用モックは、設計を決めるための道具である。モックを完成させるために未決の設計を決めるのではなく、モックを使って設計を決める。次の規約に従う。

1. 左側は、採用候補として実際に確認したい利用者向けの画面だけにする。右側（と、スマートフォン幅ではアプリの枠の外に置く設計確認の操作）は、設計根拠、状態の切替、テスト条件、サンプル、未決、オーナー判断が必要な設計論点を置く。何をオーナー判断として尋ねるかの粒度は§5.2に従う。
2. サンプルデータ、テスト用アカウント、状態の説明、設計上の都合で置いた確認用の情報を、利用者画面（左側）へ出さない。テスト用の人物、テスト用のGoogleアカウント、仮の会社名は、右側にだけ示す。
3. テストする状態（登録前、登録済み、個人のみ、個人と会社、閲覧のみ、未共有、DIPSへ送信できる／できない、オフラインなど）は、右側の切替で選ぶ。左側は、選んだ状態で本番のアプリが見せる画面だけを表示する。
4. Googleなど外部が表示する公式の画面は、左側では「実際は外部が表示する」ことが分かる程度にとどめ、細部を再現しない。状態ごとの分岐は、右側の切替で選ぶ。
5. 入力欄の記入例は、原則としてplaceholderなどの薄い文字で示す（例：会社・団体名は「例：○○株式会社」）。登録済みのデータのように並べない。一覧などに出す仮のデータにも、「サンプル」「確認用」などモックの都合を示す語を含めない。
6. 未確定の点を、AIが完成した仕様として埋めない。右側の設計確認メモに「未決」「この2案を比較したい」「オーナー確認待ち」を残す。比較したい案は、右側の切替で切り替えて確かめられるようにしてよい。左側に、未確定を完成品として見せない。
7. 利用者画面の説明文は最小にする。画面のタイトル、いまやること、入力欄、主ボタンが一目で分かる構成を優先し、詳しい設計の説明は右側へ移す。

**適用限界**: 本節は、モックの見せ方と未決の扱いの規約である。個々の画面の仕様や表示名を確定しない。右側に置く切替は設計確認のためのもので、本番のアプリの機能ではない。置き場所の対応表は[34h §9](34h_user-facing-wording-and-terminology.md#9-サンプルと設計確認用の状態の置き場所2026-09-22)。設計確認用モックは、左側に確認用の部品、サンプルを示す語、内部用語が出ていないことを自動で検査する。実装（C1以降）は開始しない。

### 5.1. 各画面の設計根拠の分類

2026-09-22の修正指示に従い、各画面の右側に、A: DIPS iPhone実画面、B: 旧運航記録アプリ、C: ワンエビ™️のスマホUI、D: 新アプリで必要な接続画面、E: 未決・比較中、の該当分類と正本参照を置く。複数該当を許す。Cは押しやすさ・placeholder・選択状態・次操作の分かりやすさを参考にする意味で、ブランド・色・固有デザインの複製ではない。分類は根拠の所在を示すもので、独自配置を確定仕様へ昇格させない。

### 5.2. オーナーに判断を求める粒度（2026-09-22）

**発端・当初の状態（HISTORICAL）**: §5に従って未決を右側へ残した結果、設計確認用モックの右側の「相談したい点（比較したい案・オーナー確認待ち）」が、全画面で約100件たまった。

**問題（2026-09-22のオーナーの指示）**: その多くは、選択肢の一般的な並び、余白、改行、ボタンの位置、「戻る」の配置と動作、説明文をどこに置くか、一覧に何をどの順で見せるか、意味や処理が変わらない画面の分け方といった、一般的なUI・UXの判断だった。これらを一件ずつオーナー確認待ちにすると、オーナーの時間を使い、本当に判断が必要な論点が埋もれる。

**現在の到達点（CURRENT-ACCEPTED。オーナーの2026-09-22の指示）**:

1. オーナー判断として表示するのは、答えによって次のいずれかが変わる、本当に未確定な設計判断だけとする。**アプリの意味・業務処理／責任主体／必須登録内容／保存する内容／権限／安全性／データの保持・削除・復旧／外部連携の意味や運用／記録として残す内容**。
2. 一般的なUI・UXの判断（上記の例）は、オーナー判断として表示しない。既存の画面と一般的なスマートフォンUIに合わせて、**AI側が自然な標準案を置く**。オーナーがモックを見て違和感があったときに修正する扱いとする。
3. 右側の記録は3つに分ける。(a)**オーナー判断が必要な設計論点**、(b)**未決・仮置き（いま決めなくてよいこと）**、(c)**一般的なUI判断（AI側の標準案。オーナー確認待ちではない）**。(c)は必要ならAI側の設計メモとして保持するが、オーナー確認待ちとして表示しない。
4. 右側の説明そのものに、この考え方（一般的なUI配置・並び・改行・標準操作はAI側で標準案を置き、違和感があれば修正する）が分かるように書く。
5. **オーナー判断から外すことは、その点を確定させることではない。** §5-6のとおり、未確定をAIが完成した仕様として埋めない。既存のPENDING・VERIFYは、右側の分類を変えても解消しない。

**適用限界**: 本節は、右側に何を置き、何をオーナーへ尋ねるかの規約である。個々の画面仕様・表示名・未決の内容を確定しない。設計確認用モックは、一般的なUIの語がオーナー判断の欄に残っていないことと、3つの区分が分かれていることを自動で検査する。実装（C1以降）は開始しない。
