# 30. 画面仕様の記録単位

最終更新: 2026-09-18\
状態: CURRENT-ACCEPTED（規約）。個別画面の未確定内容を確定するものではない。\
由来: 99.2 §0「画面仕様の記録単位」。識別情報は[Step 1監査](../../migration/99-2-step-1-causal-audit.md)。

## 1. 発端から現在の規約まで

**当初の状態**: 基準Docsの[20](../20_source-structure.md)にはPresentationとUsecases等の責務境界があり、[25b](../dips-flight-plan/25b_manual-web-mapping.md)にはDIPS固有画面の仕様がある。全画面に共通する以下の10項目規約については、基準Docsの検索・該当文書確認の範囲で旧設計なし。

**問題**: 99.2 §0では、「次にどの画面へ進むか」や画面名だけでは、会話で説明済みの表示・操作・保存の意味を実装へ引き継げないため、記録単位を定めた。

**検討・理由・到達点**: 画面名・遷移のみの短縮記録を採らず、同じ画面の論点内に目的から保存・権限差・通信状態差・未確定まで保持する。表示と保存タイミングの結びつきを追うための規約であり、未知の画面仕様を埋めるための規約ではない。99.2 §0の10項目を現在の記録ベースラインとする。独立した別候補の比較や却下理由は同節に記載されていないため、追加しない。

## 2. 画面ごとに保持する10項目

| 番号 | 記録項目 | 保持する意味 |
|---|---|---|
| 1 | 目的 | 利用者がこの画面で何をするか |
| 2 | 入口・入れる条件 | どこから入るか、どの条件で入れるか |
| 3 | 表示情報 | 利用者に何を見せるか |
| 4 | 初期値・自動入力 | 入力済み情報を何から引き継ぎ、自動で何を埋めるか |
| 5 | 主操作・副操作 | 利用者に用意する操作 |
| 6 | 操作後の遷移 | 各操作を行った後にどこへ進むか |
| 7 | 戻る・中止・削除 | 中断・戻る・削除をしたときの扱い |
| 8 | 保存・更新時点 | 端末下書き、Drive、DIPSのどれを、どの操作・時点で更新するか |
| 9 | 権限・online/offline差 | 誰が操作でき、通信状態で何が変わるか。両方を記録する |
| 10 | 未確定 | まだ決まっていない内容、根拠を確認すべき内容 |

分かる範囲で記述し、説明済みの意味を画面名へ縮めない。項目8で必要となるファイル間・記録間の流れは[23の開始ゲート](../23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)へ接続し、台帳・状態・権限そのものの定義は各領域の詳細正本を参照する。画面文書へ別のschemaや権限正本を作らない。

## 3. 未確定と証拠の扱い

個別画面の記載が本Stepにないことは、設計自体がPENDINGであることを意味しない。各画面を担当する後続Stepで、その画面の因果・現物・既存Docsを確認する。実際に未確定の内容はPENDINGを維持し、本規約だけから埋めない。VERIFY: 画面の実機動作をこの文書の成立によって検証済みと扱わない。

試作画面はEVIDENCE/EXAMPLEとして、操作して分かったことと採用した仕様を区別する。状態の定義、訂正関係と根拠の保持は[設計証拠規約](../../guidelines/03_design-evidence-and-causality.md)に従う。今回は共通規約の移植までで、個別画面の設計・コード・モック生成は行わない。
