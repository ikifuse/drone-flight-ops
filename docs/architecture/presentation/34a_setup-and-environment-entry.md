# 34a. 初回セットアップと運用環境への入口

最終更新: 2026-09-18\
由来: 99.2 §3。初回・再起動・環境選択の画面責任を扱う。状態は節内で区別する。\
規約: [30の10項目](30_screen-specification-standard.md)、人物・環境・権限の正本は[31a](../identity-and-access/31a_person-account-and-environment.md)／[31b](../identity-and-access/31b_roles-and-access-control.md)。

## 1. 環境作成と参加を分けた因果

**発端・当初状態**: 99.2 §3は、1つのPWAで複数運用環境を扱いながら現場の操作へ短く入ることを課題にしている。基準DocsのPWA導入・ローカル保存・Drive出力設定だけでは、環境を作る人と既存環境へ参加する人を区別する初回仕様になっていなかった。今回の基準検索範囲に、以下の二択とroot再発見の詳細正本はない。

**調査記録（EVIDENCE/EXAMPLE）**: 原本は、過去にGoogle Identity ServicesによるGoogle認証／OAuth同意と、Drive API `files.create`による認証ユーザーのMy Driveへの生成まで実現可能性を確認し、「Google公式認証→権限同意→本人Driveの本番構造生成」を可能な前提として扱ったと記録する。旧99.1 §3、98.2の画面→保存先整理、個人運用環境の01〜07と現在地確認用資料が根拠である。今回それらの原操作・Drive実物を再確認したとは扱わない。

**現在到達点（CURRENT-ACCEPTED）**: 初回は［新しい運用環境を作成］／［既存の運用環境に参加］から始める。新規作成ではGoogle公式のアカウント選択・OAuth同意を経て必要権限が許可された後、本人Driveへ本番rootと必要な確定済み構造を生成する。アプリ独自画面でGoogleのメールアドレス／パスワードを入力させず、PWAをホーム画面へ追加しただけでも生成しない。既存環境への参加では新rootを作らず、参加者本人のGoogleアカウントを既存環境へ紐付ける。

**配置の境界**: §3は新環境の生成対象を01〜07とし、一般利用者へ00／98／99等の設計管理資料を生成しないとする。これは初回画面から必要構造を作る責任であり、§10のフォルダー名・物理シート・全保存構造を本書で確定するものではない。参加方式から自動Drive共有や独自Editor承認を導かず、31bの三層権限に従う。

## 2. 再起動とroot重複防止

**問題・検討**: 再ログイン、再インストール、端末変更、環境切替を新規作成と同じ扱いにすると、同名rootの重複や個人／会社環境の混在が起きる。原本は環境ごとの固有IDとDrive root IDを結び、保持・再発見する必要を整理した（**CURRENT-ACCEPTED**）。環境モデル・所属の意味は31aに一元化し、本書で別のID体系を作らない。

**過去候補と未決**: appDataFolderまたはアプリ側バックエンドは過去の検討候補（HISTORICAL）であり、最終方式は**PENDING-S5-ROOT-DISCOVERY**。特定metadata、Drive検索方式、専用バックエンド等を自動採用しない。同名判定だけで再発見できるとも確定しない。Step 4のDIPS限定バックエンドへ環境管理責任を追加する根拠にもならない。

**最小権限**: 必要最小限とする原則はCURRENT-ACCEPTED。原本の`drive.file`第一候補は**CURRENT-PROPOSAL**で、正式実装時の確認は**VERIFY-S5-GOOGLE-CONTRACT**。再発見・既存環境参加・必要ファイルの利用まで、このscopeだけで充足するとは未確認である。

## 3. 初回必須登録を見直した経緯

**当初案（HISTORICAL）**: 最低1機と操縦者等をセットアップ時に登録し、空台帳だけで終わらせない方向だった。**再検討**: 最初のGoogle認証者を初期アプリ管理者とすることと、実飛行の操縦者登録を分離した。管理者の成立条件は[31b §3](../identity-and-access/31b_roles-and-access-control.md#3-初期管理者追加解除最後の1人)のまま維持する。

**現在到達点（CURRENT-ACCEPTED）**: 飛行を始める際に操縦者を選び、未登録ならその場で登録して元フローへ戻る。初回操縦者登録を強制する案は採らない。これは毎回別のGoogleアカウントを作ることや、Google認証者を自動で操縦者とすることではない。

**さらに詰めた案（CURRENT-PROPOSAL）**: 場所・機体・BAT等も「まず選択→なければその場で新規登録→登録後に元処理へ戻る」候補。事前設定画面を探さないと現場入力を続けられない不都合と登録漏れを減らすためである。選択時登録の方針と、初回に何を必須にするかは別論点とする。

**PENDING-S5-INITIAL-REQUIRED**: 最低1機案も含む初回の機体／BAT等の必須範囲。管理者と操縦者を分けたことだけで「最低1機必須」または「全マスター任意」を確定せず、後続UXとの整合で判断する。個々の登録画面・戻り先引継ぎの物理実装も今回作らない。

## 4. 初回セットアップ画面の10項目

新規作成／既存参加の二分岐を同じ入口画面の責任として記す。別の画面数やウィザード段数は定めない。

| 番号 | 記録項目 | 現在の内容・未確定 |
|---|---|---|
| 1 | 目的 | 自分が使う運用環境を作るか、既存環境へ参加するかを選ぶ |
| 2 | 入口・入れる条件 | 初回利用の入口。再ログイン等で既存環境がある場合は§2の再発見と区別する。詳細判定はPENDING |
| 3 | 表示情報 | ［新しい運用環境を作成］［既存の運用環境に参加］。独自のGoogleメール／パスワード入力欄は置かない |
| 4 | 初期値・自動入力 | Google公式のアカウント選択を利用。前回アカウントの自動固定、環境名の初期値等は原本に確定なし |
| 5 | 主操作・副操作 | 上記二択。新規作成では公式認証・同意・必要権限許可、参加では本人アカウントと既存環境の紐付け。招待コード等は選定しない |
| 6 | 操作後の遷移 | 利用する環境から[ホーム34b](34b_home-and-navigation.md)へ接続。必須登録範囲・中間画面・完了判定の詳細はPENDING-S5-INITIAL-REQUIRED |
| 7 | 戻る・中止・削除 | 認証中止・権限拒否・部分生成時の戻り方／回復／削除はPENDING。独断でroot削除や再作成を設計しない |
| 8 | 保存・更新時点 | 新規作成は必要権限許可後に本人Driveへ本番rootと確定済み01〜07構造を生成。既存参加は新rootを作らない。初期管理者は31b、環境とroot対応は§2。一般利用者へ設計管理資料は生成しない |
| 9 | 権限・online/offline差 | Googleの認証・同意・Drive生成には外部到達が必要。所属／機能権限／実アクセスは31a／31b。offline・権限拒否時の具体表示と回復はPENDINGで、成功扱いにしない |
| 10 | 未確定 | root再発見、参加手段、初回必須範囲、認証・scope検証、部分生成／中断復旧、具体画面構成 |

## 5. 通常起動と環境選択の10項目

複数環境／単一環境の意味と表示省略条件は[31a §4](../identity-and-access/31a_person-account-and-environment.md#4-会社利用と環境切替へ詰めた内容)が正本。§3の「前回使用した環境を次回起動時の初期環境とする方向」は**CURRENT-PROPOSAL**として保持し、保存場所や失効時処理を補わない。

| 番号 | 記録項目 | 現在の内容・未確定 |
|---|---|---|
| 1 | 目的 | 利用する環境を取り違えず、通常のホームへ入る |
| 2 | 入口・入れる条件 | 起動時・環境切替時。所属とアカウントの条件は31a／31dを参照 |
| 3 | 表示情報 | 複数環境では現在環境と切替手段を明示。単一環境では通常時の環境名常時表示／切替UIを省略できる |
| 4 | 初期値・自動入力 | 前回使用環境を初期環境とする方向（CURRENT-PROPOSAL）。所属終了・アクセス喪失時の代替選択は未確定 |
| 5 | 主操作・副操作 | 利用環境の切替。専用選択画面かホーム内配置かはPENDING-S2-ENVIRONMENT-UI |
| 6 | 操作後の遷移 | 選択した環境のホーム・正本へ接続。人物／root対応は31aと§2を参照 |
| 7 | 戻る・中止・削除 | 切替中止・未保存作業の扱い・所属変更後の画面復帰はPENDING。環境切替をroot削除としない |
| 8 | 保存・更新時点 | 環境ごとのroot／正本を参照し、新rootを重複生成しない。前回環境の記録方式・更新時点は未確定 |
| 9 | 権限・online/offline差 | 所属・機能・Google実アクセスは31a〜31d。offlineでの切替・再認証・最新所属確認の具体処理は未確定 |
| 10 | 未確定 | PENDING-S5-ROOT-DISCOVERY、既存PENDING-S2-ENVIRONMENT-UI／MEMBERSHIPに加え、前回環境の保持・復帰条件 |

## 6. 補助確認と実装前に残す範囲

2026-09-18の公式補助読解では、[Google Identity Services](https://developers.google.com/identity/oauth2/web/guides/overview)がサインインとAPI利用同意を分けて扱うこと、[Driveフォルダー生成](https://developers.google.com/workspace/drive/api/guides/folder)で`files.create`を使うことを確認した。[Drive scope資料](https://developers.google.com/workspace/drive/api/guides/api-specific-auth)もファイル単位の`drive.file`を説明する。これは原本の過去確認とは別の補助証拠であり、アプリの認証フロー、必要scope全体、再発見方式、実環境参加の成功を確定しない。Google認証をDIPSの認証VERIFYと混同しない。

**VERIFY-S5-SETUP-EVIDENCE**: 旧99.1／98.2、01〜07の実Drive、現在地資料の版と画面・保存責任の対応。**VERIFY-S5-GOOGLE-CONTRACT**: 正式実装時のGoogle認証・認可・必要scopeと既存環境アクセス。新しい技術案は追加しておらず、未確認だけを理由に§1の到達済み初回方針を降格しない。

Step 6の01〜07責任・設計資料と運用領域の分離は[37](../drive-structure/37_environment-storage-responsibilities.md)。本書の作成／参加・root再発見・必須初期登録の未確定は維持する。
