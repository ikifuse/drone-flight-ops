## 1. 本書の位置づけ

本書は「どのPDFが何のためにあり、いつ作るか」を保持する。A4運航記録の実物・生成単位・必要時PDFの記録は[35c](../operation-recording/35c_a4-operation-record.md)、PDF・CSV・Excelの生成パイプラインと発行記録は[18](../18_reports.md)、4つの出力境界は[27](27_output-boundaries.md)、KMLの生成契機・内容は[27e](27e_kml-generation-timing-and-content.md)、対象飛行を選んで出力へ進む画面は[34e](../presentation/34e_history-and-output.md)が正本。

## 2. 二つのPDFを役割で分けた因果

**発端・当初状態（既存Docs）**: 99.2 §8は、DIPS用に作った飛行範囲・経路を再入力せず後から使いたい一方、毎飛行でPDFを自動生成すると不要なファイルが増える、という二つの要求から出発する。既存の18 §2は、A4運航・日常点検記録と別に、計画概要・飛行範囲地図・高度・周辺注意事項を持つ「地図付き飛行計画書」を計画作成後の事前印刷・提出用として置き、03 §8.1も同様に関係者提出用帳票として記述していた。

**現在の到達点（CURRENT-ACCEPTED。99.2 §8）**: PDFは二つに分け、役割を混ぜない。

| PDF | 内容 | 源 |
|---|---|---|
| A4運航記録PDF | 飛行前点検、実飛行、飛行後点検、記事・不具合・処置 | 04の確定運航記録（[35c](../operation-recording/35c_a4-operation-record.md)） |
| 地図付きPDF | DIPS通報内容と、Geometryの地図 | 06の正本属性・共通Geometry（[24b](../dips-submission/24b_dips-plan-records-and-worklist-lifecycle.md)・[25e](../dips-flight-plan/25e_common-source-and-submission-boundaries.md)） |

**地図付きPDFを置く理由**: PC版のDIPS画面では、地図と入力項目が一つの画面に並ぶ関係で確認できる。その関係を、人が追いやすいA4の資料へ再構成する。Web UIそのものを複製する案ではなく、DIPS画面で確認できる地図と入力内容の階層・可読性をA4へ移すための案である。

**二つを合わせる意味**: A4運航記録PDFと地図付きPDFを同じ飛行へ紐づけ、2枚を合わせることで「計画・地理」から「実施・点検」への流れを追えるようにする。紐づけのキーは99.2では`flight_id`だが、既存Domainとの対応は未確定（PENDING-S7B-FLIGHT-KEY、24b）。

## 3. 生成契機・方針

**現在の到達点（CURRENT-ACCEPTED。99.2 §8）**:

- 派生出力でも、KMLとPDFは生成タイミングを分ける。KMLは飛行計画の通報時に生成・保存する（27e）。
- PDFは、飛行完了時に無条件に自動生成しない。印刷・提出・保存が必要な時だけ生成して、不要なファイルを毎飛行増やさない。
- A4のSpreadsheetは、飛行後点検後の最後の送信で04に自動で完成し、Google Sheets標準の印刷・PDF化もできる。アプリだけを唯一の印刷手段にしない。
- アプリからのPDFは、必要な時だけ07のPDF側へ派生生成する。
- KMLファイル自体を、通常のA4帳票として直接印刷する導線にしない。用途別のPDFは、06の正本属性・Geometryと04の確定運航記録から再生成する。

**適用条件**: 発行した帳票の当時の内容を追う記録（ReportSnapshot）は[18 §4](../18_reports.md#4-domain帳票射影発行記録の分離)、端末でのPDF生成の条件は[18 §6](../18_reports.md#6-オフラインpdf生成の成立条件)に従う。04のSheets記録を最終保存することと、PDFを毎回自動発行することは別である（18 §4）。

## 4. 地図付きPDFの配置の方向と未確定

**検討時の具体案**: 地図を左上に、DIPSの項目を右側に置き、入りきらない項目は地図の下へ続ける、という配置まで検討された。

**現在の到達点（CURRENT-ACCEPTED）**: 飛行範囲・経路の地図を主な視覚要素とし、その右側または下側等にDIPSの通報項目を置く方向を保持する。最終的なレイアウトは、1飛行のテストで確定する。

**未確定・確認待ち**:

- **PENDING-S7D-MAPPDF-DETAIL**: 詳細なレイアウト、命名、生成する画面。
- **VERIFY-S7D-MAPPDF-REGEN**: 同じ正本・Geometryから、地図付きPDFをどこまで再生成できるかの実物での確認（最終レイアウトの1飛行テストを含む）。
- **PENDING-S7D-MAPPDF-SCOPE**: 既存18 §2・03 §8.1の「地図付き飛行計画書」（計画概要・周辺注意事項・関係者提出用）と、99.2の地図付きPDF（通報内容＋Geometry）が同一の帳票か、内容や用途に差があるか。99.2は周辺注意事項や提出用途に触れておらず、両者の関係を決めない。当面、既存の記述は旧案（要照合）として保持する。

オフラインで地図タイルが未取得の場合の扱い（座標・半径の印字で生成を中断しない）は既存の18 §6を維持する。

## 5. 再検討条件

- 1飛行のテストで、通報内容と地図が1枚で読めないと確認された場合。
- 関係者提出用など、通報内容以外の項目が必要と確認され、PDFの役割分離を見直す場合。
- 意味上の1飛行の定義が確定し、A4運航記録PDFとの紐づけが変わる場合。
