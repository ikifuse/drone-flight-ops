# 16. セキュリティ・秘密情報・トークン管理設計（16_security.md）

最終更新: 2026-09-15
プロジェクト: `drone-flight-ops`
フェーズ: Phase B2 / B2.1（詳細アーキテクチャ・監査・実装前設計）

---

## 1. セキュリティ設計の根本原則

1. **クライアント完全非保持原則**: DIPS APIの `client_secret`、API接続資格情報等のアプリケーション機密は、ブラウザ（JavaScript）やクライアントストレージに配置・送信しない設計を徹底する。
2. **バックエンドによる機密・トークン隠蔽**: ブラウザへDIPS APIの認証鍵やトークンを直接露出させず、Google Cloud側のDIPS統合バックエンドがConfidential Clientとして管理する。ブラウザからDIPS APIへの直接通信は禁止し、必ず専用ゲートウェイを経由する。詳細は [31. DIPS接続インフラ・固定送信元IPゲートウェイ設計](dips-infrastructure/31_dedicated-egress-ip-gateway.md) を参照。
3. **ブラウザセッションと外部APIトークンの完全分離**: ブラウザが保持するのは本アプリ自身の認証セッションのみとし、DIPS APIの資格情報やトークンはブラウザ側のCookieやストレージへ一切渡さない。
4. **監査ログ・バックアップへの機密混入防止**: トークンや認証鍵は、コンソールログ、エラーログ、内部送信証跡・将来の復旧用データ、GitHubコミットから確実にマスキング・除外する。

## 2. DIPS API 接続認証および通信経路のセキュリティ方針

ブラウザ環境（PWA）におけるDIPS API連携について、以下のセキュリティ方針を適用します。

1. **ブラウザ直接通信の禁止（BFF経由原則）**:
   - PWA（ブラウザ）からDIPS APIエンドポイントへの直接HTTPリクエストは実施しない。
   - すべての通信は Google Cloud 上の DIPS 統合バックエンドを中継（BFF: Backend for Frontend）し、VPC egressおよびCloud NATによる固定送信元IPアドレス（`<DIPS_FIXED_EGRESS_IP>`）を経由してDIPS APIへ送信する。
2. **DIPS API トークンのクライアント非露出**:
   - DIPS APIの接続資格情報（Client ID / Client Secret / API Key等）および取得した認証トークンは、バックエンド側でのみ取り扱い、ブラウザ側へ渡さない。
   - ブラウザ側は本アプリ自身のユーザー認証セッション（HttpOnly Cookie等）のみを保持し、DIPS APIのトークンをブラウザセッションCookieに埋め込まない。
3. **認証方式およびトークンライフサイクルの検証方針（VERIFY）**:
   - 国交省への事前申請においてOIDCリダイレクトURL等の情報提出は実施済みであるが、DIPS APIの正式な認証認可方式（OIDC、OAuth 2.0、API Key、Bearer Token等）、トークンの種別・有効期限・失効エンドポイントの有無は、国交省からの正式接続仕様書の受領後に確認・確定（`VERIFY-C7-FORMAL-SPEC`）する。
   - 正式仕様が確定するまで、トークン保持方式やライフサイクルの推測固定は行わない。

## 3. 秘密情報の階層別管理と役割分離

「アプリケーション固定シークレット／インフラ構成情報」と「セッション情報・外部APIトークン」を厳格に分離して管理します。

```text
┌─────────────────────────────────────────────────────────────┐
│ [階層1] GitHubリポジトリ（公開正本コード）                  │
│  - 秘密情報は1行たりともコミットしない (.gitignore徹底)     │
│  - 実固定IP値、Client ID/Secret、実Drive IDは抽象化保持     │
│  - 環境変数テンプレート (.env.example) のみを配置           │
└──────────────────────────────┬──────────────────────────────┘
                               │ (デプロイ・インフラ構築)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [階層2] クラウド側固定シークレット・インフラ構成情報        │
│  - DIPS API Client Secret 等は Secret Manager 等で安全管理  │
│  - 固定送信元IPアドレス実値は Google Cloud インフラ構成・   │
│    運用情報として非公開管理（秘密鍵とは分離して扱う）       │
└──────────────────────────────┬──────────────────────────────┘
                               │ (バックエンド実行時)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [階層3] DIPS API 認証情報・トークン管理（バックエンド内部） │
│  - DIPS API Token はバックエンドメモリ／内部管理領域に保持  │
│  - ブラウザ側へは一切渡さない（Cookieへの埋め込みも禁止）   │
│  - 保持期間・保持方式は正式仕様受領後確定 (VERIFY)          │
└──────────────────────────────┬──────────────────────────────┘
                               │ (アプリ自身の認証セッションのみ)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [階層4] クライアント環境（ブラウザ / PWA）                  │
│  - アプリ自身のセッション情報のみを保持（Cookie等）         │
│  - DIPS APIのトークンやシークレットは一切保持しない         │
│  - IndexedDBにもDIPS API認証情報は一切保存しない            │
└─────────────────────────────────────────────────────────────┘
```

## 4. DIPS API 認証情報およびトークンのバックエンド管理方針

1. **トークンの隔離保持**:
   - DIPS APIの認証トークンが必要な場合、そのライフサイクル管理（取得・更新・破棄）はバックエンド側で完結させ、ブラウザ側へトークン実値を中継しない。
   - バックエンドにおけるトークンの保持要件（揮発性メモリ保持で足りるか、KVストアや永続ストレージが必要か）は、DIPS APIトークンの有効期限（短命か長命か）および再取得コストに応じて、正式仕様受領後に検証・決定（`VERIFY-C7-FORMAL-SPEC`）する。
2. **インフラ詳細の集約**:
   - バックエンドのコンピューティング選定（Cloud Run / Cloud Functions等）、VPCネットワーク構成、Cloud NATによる固定IP付与の詳細設計は、専門の正本文書である [31. DIPS接続インフラ・固定送信元IPゲートウェイ設計](dips-infrastructure/31_dedicated-egress-ip-gateway.md) に集約する。

## 5. ログ・エクスポートからの機密マスキング

- ログ出力ラッパー（`LoggerService`）により、`token`, `secret`, `authorization`, `password`, `key`, `cookie` を含むオブジェクトフィールドを自動的に `***MASKED***` に置換。
- 認証情報・セッション情報は内部送信証跡、Sheets、PDF、KMLおよび将来検討するDBバックアップから明示的に除外（Filter-out）する。旧 `exportBackupJson()` は実装要件から外れた。[ADR-0008](../decisions/ADR-0008-user-facing-export-and-recovery-boundaries.md)に従い、ユーザー向けJSON import/exportは提供せず、ローカルDB全量復旧形式はPENDINGとする。

---

## 6. 資格情報失効・ローテーション手順

- **即時ログアウト**: パイロットがログアウトを実行した際、アプリ自身のセッションを即時破棄し、バックエンド側に関連付けられたDIPS APIセッションや一時トークンが存在する場合は適切に無効化・破棄する。
- **credentialローテーション**: 国交省側で `client_secret` やAPIキーが更新された場合、Google Cloud側のシークレット管理（Secret Manager等）の値を更新することで、クライアントアプリの再配布・再ビルドなしに即座に新キーへ移行可能とする。

## 7. 機密境界の適用範囲

1. **DIPS APIシークレット・トークン**:
   - `client_secret` や API トークンは、Google Cloud DIPS統合バックエンドの機密保管境界内に完全に閉じ込め、ブラウザや外部ストレージへ一切露出させない。
2. **固定IPアドレス実値**:
   - 固定送信元IPアドレス実値は、非公開のGoogle Cloudインフラ構成・運用情報として扱い、公開リポジトリ内では `<DIPS_FIXED_EGRESS_IP>` 等の抽象表記を使用する。
3. **個人・運航機微情報**:
   - 運航人員の実名・電話・メール・住所・機体登録記号等は業務上の機微データとして扱うが、本リポジトリの設計例へ実値を含めない。DIPS入力支援に必要な表示と、共有用KMLの最小情報化は異なる目的であり、[KML SHARE_SAFE](output/27a_kml-export.md)の除外方針を維持する。

## 8. 三層権限（レイヤー分離）のセキュリティ境界

99.2 §2および[ADR-0010](../decisions/ADR-0010-three-tier-permissions-and-environment-boundary.md)に基づき、本システムのアクセス制御は以下の**3つの独立したレイヤー**として分離し、相互に混同・自動昇格させない設計を徹底します。

1. **第1層：業務上の役割（Operational Roles）**: 現場での操縦者、DIPS飛行計画の通報者、実飛行時の記録者、補助者等の実務・法令上の役割。
2. **第2層：アプリ機能上の権限（App Functional Permissions）**: 設定変更、運航入力、管理者管理等のアプリケーション内部の操作認可。
3. **第3層：外部ストレージ実アクセス権（Physical Drive Permissions）**: Google Drive上の Viewer / Editor / Owner 等の実ファイルアクセス権。Google側が唯一の正本。

三層権限の詳細仕様、業務役割の定義、層間制約ルール、および運用環境・所属ライフサイクルについては、専門の正本文書である [01. 三層権限モデル・業務役割・機能権限設計](identity-and-access/01_three-tier-permissions-and-roles.md) および [02. 運用環境・アカウント・所属ライフサイクル設計](identity-and-access/02_environment-and-personnel-lifecycle.md) を参照してください。本ファイルはインフラ・通信セキュリティの境界のみを規定します。

## 9. 公開リポジトリにおける実環境機微情報の完全非公開・抽象化規約

本リポジトリはオープン（公開）を前提とするため、以下の運用実値および機微情報は、設計文書・コード・コメントに一切記述してはなりません。

- **DIPS通報用固定送信元IPアドレス実値（例: 34.xxx.xxx.xxx）**:
  - ドキュメント上は `DIPS通報専用固定送信元IP（GCP Cloud NAT経由）` 等の抽象表現を用い、実IP値はリポジトリ外の安全な設定管理に留める。
- **Google Drive フォルダ / ファイルID実値**:
  - ドキュメント上は `環境変数（DRIVE_ROOT_FOLDER_ID等）` または設定値として抽象化し、実Drive IDは記載しない。
- **実アカウント名、個人識別情報（実名、電話番号、メールアドレス、資格証明番号）**:
  - サンプル識別子（`user_pilot_01`, `org_sample` 等）を用いて記述する。
- **DIPS ID / パスワード / API Client Secret / トークン実値**:
  - 環境変数名テンプレートのみを記載し、実値は一切コミットしない。
