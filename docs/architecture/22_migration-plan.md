# 22. 現行システムからのデータ移行・並行運用・ロールバック設計（22_migration-plan.md）

最終更新: 2026-09-15
プロジェクト: `drone-flight-ops`
フェーズ: Phase B2（詳細アーキテクチャ・実装前設計）

---

## 1. 移行の基本方針（無停止・非破壊・並行運用）

1. **現行システムの非破壊**: 新アプリの開発・検証期間中、稼働中の `ikifuse/autel-evo-lite-flight-log`（GASアプリおよびGoogleスプレッドシート）を一切変更せず、現場運用をそのまま継続可能とする。
2. **資産の確実な継承**: 現行スプレッドシートに蓄積された「機体累計飛行時間」「各バッテリー個体の累積サイクル数（旧運用例: BAT1〜7）」「過去の飛行日誌履歴」を正確に新システムへインポートする。
3. **即時ロールバック性の確保**: 新アプリの現場テスト中に不測の不具合が発生した場合、即座に現行GASアプリでの記録へ復帰できる手順を確立する。

---

## 2. 移行対象データとインポート設計

現行スプレッドシートから抽出し、新システムのローカルDB（IndexedDB）へ初期ロードするデータ項目を定義します。

| データ種別 | 現行の格納場所 | 移行先エンティティ | インポート方式 |
|---|---|---|---|
| **機体マスター** | 機体累計行 / コード内定数 | `AircraftModel` / `Aircraft` | スプレッドシート読み込み または 初期設定ウィザード |
| **機体累計時間** | 「飛行日誌」シートの最新累計行 | `Aircraft.cumulative_flight_minutes` | 最新の確定累計時間をインポート（基点設定） |
| **バッテリー台帳** | 「BAT_01」〜「BAT_07」シート | `BatteryModel` / `Battery`（抽出した全個体。旧運用例7本は上限ではない） | 各シートの最終行から累積サイクル・総飛行時間・直近所感を抽出 |
| **操縦者情報** | コード内定数 / 履歴 | `Personnel`（pilot役割） | 設定画面で確認・インポート |
| **許可承認情報** | コード内 / メモ | `Permission` | 包括申請番号・期間を登録 |
| **DIPS飛行計画台帳** | （現行システムには未存在・新設） | `DipsSubmission` | 新アプリ専用の正規化台帳に「DIPS飛行計画台帳」を作成（現行GASの稼働台帳へ追加・変更しない） |

## 3. 並行運用フェーズ（Parallel Run）

新アプリの信頼性を現場で確認するため、以下の3段階で慎重に移行します。

```text
[Step 1: 開発・シミュレーション検証]
  - 過去データを用いた机上テスト、モックによる機能検証。
      ↓
[Step 2: 現場並行記録 (Shadow Run)]
  - 実際のフライト現場において、メイン記録を「現行GASアプリ」、
    サブ検証として「新アプリ」で同時に離着陸打刻・点検を実施。
  - 計算時間のズレ、操作感、屋外視認性、ストレージ保持を比較検証。
      ↓ (実現場Shadow Runおよび総合検証シナリオ群の合格を確認)
[Step 3: 新システム主運用への切替 (Cutover)]
  - 新アプリを主記録システムとして運用開始。
  - スプレッドシート同期先を新アプリ専用の正規化台帳へ接続（稼働中の旧台帳は非破壊保持）。
```

---

## 4. ロールバック手順（Rollback Plan）

万一、新システム運用開始後に重大な問題（UIフリーズ、同期不能等）が発生した場合の退避手順です。

1. **現場での即時退避**:
   - スマートフォンのSafariでブックマーク済みの現行GASアプリURLを開き、通常の打刻・記録をそのまま続行。
2. **データの保全**:
   - 新アプリ側で途中まで記録したデータはローカル保持し、通信可能で安全に同期できる分は新アプリ専用Sheets台帳へ退避する。未同期データを捨てる初期化は行わない。ローカルDB全量バックアップ/restoreのユーザー形式は **PENDING**（[ADR-0008](../decisions/ADR-0008-user-facing-export-and-recovery-boundaries.md)）。JSON exportやKMLからのDB復旧を既存機能として前提にしない。
3. **台帳の手動整合**:
   - 現場終了後、新アプリの保持記録・同期済台帳と現行スプレッドシートの差分を確認し、必要に応じて手動補記で整合性を保つ。未同期端末も失った場合に復旧できると保証せず、[19の復旧限界](19_failure-recovery.md) に従う。

## 5. 旧台帳の読み取りと移行先の正本

上記BAT_01〜BAT_07は既存資産の読み取り元を示す歴史的配置であり、その存在だけで新アプリの最終物理構造とはしない。機種/型式/個体のUUID、N:M互換の属性は [12b](domain-model/12b_aircraft-and-battery.md)、人員統合は [12a](domain-model/12a_organization-and-personnel.md)、基準の行追加/更新型の論理台帳案は [24a](dips-submission/24a_submission-and-sheets-ledger.md) を参照する。BATの飛行明細と非飛行イベントの最終的な表・行配置の未確定は[32b](asset-management/32b_battery-sharing-and-acquisition-history.md)に従う。旧配置の無条件再現を避ける意図を維持し、最終保存形式を本書で先取りしない。全量DB復旧方式が未決でも安全に検証できる並行記録手順と、未同期データ喪失の限界を区別して切替判定する。

累計行の移行では、その値が表す期間・起算の意味も[32a](asset-management/32a_aircraft-acquisition-and-cumulative-time.md)へ照合する。取得前の正確な履歴が不明なのに最新値を生涯総時間とみなしたり、中古機を一律ゼロへ初期化したりしない。取得時BAT観測との区別も32bに従い、未確定の保存列・インポート処理は本Stepで新設しない。
