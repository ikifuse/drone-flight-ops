# 32a. 機体取得前の履歴と管理開始後の累計

最終更新: 2026-09-18\
状態: CURRENT-ACCEPTEDを中心に、証拠・過去案・未確定を節内で区別\
由来: 99.2 §4、取得時確認との接続のみ§6。属性の正本は[12b](../domain-model/12b_aircraft-and-battery.md)。

## 1. 型式と実機を分けた経緯

**当初状態（HISTORICAL）**: `0211a9a`時点の旧12は機体個体の中に製造者・型式等を持っていた。`5d51315`で同一機種を複数保有する場合の仕様重複を避けるためAircraftModelとAircraftへ正規化し、[ADR-0007 §2.1](../../decisions/ADR-0007-normalized-masters-and-business-reporting.md)に記録した。`ea73d08`で分割した12bがStep 3開始時の属性正本である。

**確認・現在到達点（CURRENT-ACCEPTED）**: 99.2 §4は実機のLite / Lite+を登録記号で識別して確認し、02の機体管理を参照している（EVIDENCE/EXAMPLE）。製品の型式仕様と実在する1機の識別・取得状態・履歴は異なる責任であり、正規化を維持する。実機の事例はAircraftModelを不要にする根拠ではなく、2機という数も上限ではない。未確認の個体値を推測入力しない。証明番号等の未発行・未確認値の扱いは[31a §3](../identity-and-access/31a_person-account-and-environment.md#3-資格の分離と確認用5タブ)に従う。

**新品と中古**: 既存要件の初期累計設定を維持する。99.2 §4の中古事例は「新品・中古を問わず一律ゼロ」の決定ではない。今回補助確認した基準アプリの[管理開始設計07](https://github.com/ikifuse/autel-evo-lite-flight-log/blob/e8560b03e1220cb3b38e927190bdcb03191ddc57/01_ドローン運航記録_設計書/07_点検整備・管理開始.md)も、新品と、前歴を取得できない中古の管理開始を区別している。新品であることや未観測の初回飛行日まで、この事例から他個体へ補完しない。

## 2. 不明な過去を推定せず00:00から管理するまで

**問題**: 中古Lite+には、取得以前を含む正確な製造後総飛行時間・履歴を確認できない部分があった。累計値だけを要求すると、不明をゼロと偽装するか、根拠のない過去時間を作ることになる。

**確認した根拠（99.2記録のEVIDENCE/EXAMPLE）**: 取得時に付属中古BAT3本のサイクル数を実確認し、機体の状態と合わせて使用歴がかなり少ないと判断した。各数値は低使用歴という評価の根拠であり、正確な機体飛行時間の測定値ではない。BAT観測の詳細責任は[32b §3](32b_battery-sharing-and-acquisition-history.md#3-中古batの取得時確認とその後の履歴)。実物を今回再確認したという意味ではなく、個体番号・実数は公開仕様へ複写しない。

**検討案・採らなかった理由**:

| 案・解釈 | 扱いと理由 |
|---|---|
| サイクル数から正確な過去飛行時間を逆算する | 不採用。低使用歴の判断と正確な総飛行時間は別であり、推定加算で事実を作らない |
| 中古機は必ずゼロから開始する | 不採用。99.2は旧アプリv6の初期飛行時間設定機能も確認経緯に含める。既知の前歴を無視する方針ではない |
| 不明な製造後総飛行時間と、管理開始時の00:00を分ける | 採用。管理可能な時点から追跡でき、取得前履歴の不明も失わない |

**さらに詰めた内容・現在到達点（CURRENT-ACCEPTED）**: この個体では、正確な過去を推定しない原則と、取得時観測による低使用歴の評価を合わせて当方管理開始累計00:00を採用した。00:00は製造後一度も飛行していないことを意味しない。「取得以前を含む正確な総飛行時間は不明」と「当方管理開始後を追跡する累計」を意味として分ける。旧機能を知らずにゼロを選んだのでも、低使用歴なら過去を一律消してよいとしたのでもない。

取得時の短時間動作確認を点検整備記録へ残し、正式運航時間へ算入しない個別判断と正式運航記録0件の整合は[32c §1](32c_acquisition-check-and-maintenance-actors.md#1-取得時の短時間動作確認をどう残すか)を正本とする。ここで飛行時間の一般除外規則は増やさない。

## 3. 後から記録が得られた場合と法規根拠の限界

**例外・更新原則（CURRENT-ACCEPTED、99.2 §4）**: 信頼できる前所有者の記録が後から得られたら追加・継承する。ただし当時00:00運用を選んだ根拠を消さず、当方管理開始後累計の意味を壊さない。取得以前の履歴を後日知ったことと、自分が管理した期間の実績訂正は区別する。[11](../11_data-authority.md)の確定台帳・手修正尊重を維持し、過去の推定で無言に再計算・上書きする判断はしていない。

**原本と今回の補助確認の区別**: 99.2 §4は02機体管理、05の取得確認記録、旧アプリv6、旧99.1 §4を根拠として挙げるが、法規の条番号自体を列挙していない。今回読んだ基準アプリ07は、所有者変更時の記録継承を原則とし、過去記録が得られない現場事情と起算点を示す扱いを検討根拠としている。これは同じ論点の補助証拠であり、今回の実Drive確認や行政の個別承認ではない。

2026-09-18に補助照合した[飛行日誌取扱要領 §4(5)](https://www.mlit.go.jp/koku/content/001574394.pdf)は、使用者が変わる場合の総飛行時間・点検記録の受渡しを扱う。[ガイドライン §5(1)③](https://www.mlit.go.jp/common/001599241.pdf)には記録が残らない場合の起算と明示の扱いがあるが、新制度開始時に関する文脈を持つ。これだけで全ての中古取得時にゼロへリセットできる一般規則を導かない。現在の個別運用判断は§2の条件・証拠とともに保持し、一般論によって未決へ戻さない。

## 4. 未確定と検証観点

- **PENDING-S3-AIRCRAFT-HISTORY**: 取得前の既知／不明な履歴、管理開始後累計、後日継承する根拠・値・起算点の具体的カラム・関連・表示・訂正方法。既存`cumulative_flight_minutes`と`management_start_date`だけで全て表現済みとは扱わない。一般技術論で新フィールドを確定しない。
- **VERIFY-S3-AIRCRAFT-EVIDENCE**: 99.2が参照する02・05、旧99.1、旧v6の当該設定機能の実物・版と意味の再照合。今回の基準アプリ文書読解は旧v6機能の再操作ではない。99.2に記録済みの観測とCURRENT-ACCEPTEDをこのVERIFYへ置き換えない。
- **受入時に追う意味**: 新品と中古、前歴既知と不明を区別できること。00:00から「未飛行」と誤認せず、後日記録を継承しても管理開始後の実績と当初判断を追えること。保存・表示が決まるまでは依存実装へ進まない。
