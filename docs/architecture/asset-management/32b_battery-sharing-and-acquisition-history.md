# 32b. バッテリーの共用・取得時状態・個体履歴

最終更新: 2026-09-18\
状態: CURRENT-ACCEPTEDを中心に、過去案・実例・未確定を節内で区別\
由来: 99.2 §4。型式・個体・互換・イベント属性の正本は[12b](../domain-model/12b_aircraft-and-battery.md)。

## 1. 固定スロットから型式・独立個体・互換へ

**当初状態（HISTORICAL）**: 基準アプリにはBAT_1〜BAT_7の資産があった。新アプリも`0211a9a`時点の旧12では個体のslotと主たる所属機体`aircraft_id`を持っていた。`5d51315`と[ADR-0007 §2.2](../../decisions/ADR-0007-normalized-masters-and-business-reporting.md)で、BatteryModelとBatteryを分け、機種とのN:M互換で共有する設計へ変わった。現在の属性は`ea73d08`で分割された12bへ接続する。

**問題・根拠**: 99.2 §4のLite / Lite+ではBATを共用でき、スクール等では同一機種を複数持ち多数のBATを回すことも想定する。特定Aircraftの所有物として固定すると、実際の共用と個体ごとの利用履歴が一致しない。旧7スロットの再現は比較用には役立つが、そのまま拡張可能な所有モデルにはならない。

**現在到達点（CURRENT-ACCEPTED）**: 製品型式をBatteryModel、実物1本をBatteryとして独立管理する既存正規化を維持する。BatteryCompatibilityは機体型式とBAT型式の互換関係であり、特定機体の固定所有を表さない。互換機種・利用可能機体との関係を表現できる構造とし、実使用は[Flight](../domain-model/12e_operation-inspection-maintenance.md)で追う。利用可能機体をどう具体的に保持・判定するかを本Stepで新たなテーブルやキーへ固定しない。

## 2. 機体セット別表示を所有関係と混同しない経緯

**調査・試作の変遷（EVIDENCE/EXAMPLE）**: 99.2 §4は旧BAT_1〜BAT_7を一度叩き台へ再現した後、人が見て分かりやすい機体セット別表示へ再配置したと記録する。03の途中案では2機に4本と3本を分けて見せ、1本をもう一方にも共用参照として表示していた。現03の共用管理用BAT一覧・個体使用履歴も根拠に挙げる。これは原本に記録された実物確認で、今回のDrive再検証ではない。

**検討・却下理由**: セット別に見せることと、物理的にどちらかだけが所有することは別である。表示用の所属を固定所有のFKへ読み替える案は採らない。旧モックのタブをそのまま正式schemaとする案も採らない。表示エラーを修正できたとしても、個体の共用・履歴・保存との関係が確認されなければ設計完了にならない。

**現在の位置づけ**: 独立個体・互換・個体履歴はCURRENT-ACCEPTED。03の具体的な機体セット別表示は途中案であり、CURRENT-PROPOSALとして扱う。旧アプリを再現した比較用タブはHISTORICAL / EVIDENCE/EXAMPLE。2機・7本、4本と3本の組合せや特定機種・ラベルは一般仕様ではない。将来N機・M本でも、同じBATを別個体へ複製せず共用履歴を追う必要がある。

## 3. 中古BATの取得時確認とその後の履歴

**問題・確認した事実**: 中古個体を取得した時点で既に使用履歴があり、取得後に自分が積み上げる履歴だけでは取得時状態を説明できない。99.2 §4では付属中古BAT3本のサイクル数を各個体で実確認し、機体状態と合わせ低使用歴と判断した（EVIDENCE/EXAMPLE）。実測した値と未確認値を区別し、未確認のシリアル等を推測入力しない。実数を別の架空数値で置き換えたり、全中古BATの初期値にしたりしない。

**検討・現在到達点（CURRENT-ACCEPTED）**: 取得時の確認状態・サイクル数と、その後の個体別利用履歴を分けて追う。全BATが新品ゼロで始まるとも、取得以前の全イベントを知っているとも扱わない。観測したサイクル数から正確な機体総飛行時間へ逆算しない理由と00:00の判断は[32a §2](32a_aircraft-acquisition-and-cumulative-time.md#2-不明な過去を推定せず0000から管理するまで)に一本化する。取得確認を点検整備記録へ結び付ける意味は[32c](32c_acquisition-check-and-maintenance-actors.md)に従う。

既存`condition_at_start`のNEW / USED、現在の累積サイクル・全機体での累積飛行時間は12bに維持する。ただし、現在累計を持つことだけでは取得時に何を確認したかは表現しきれない。取得時値を保持する新しい物理列・表示形式は未確定のまま残す。

## 4. 飛行実績と非飛行履歴の責任を保持する

**経緯・検討**: 旧技術モックはFlight内のBAT使用とBatteryUsageを分け、飛行以外の充電・保管・点検等も個体履歴として保持する案を作った。99.2 §4の現03にも個体の履歴を積み上げる考えが残る。しかし旧BatteryUsageタブの存在は、飛行明細と非飛行イベントをどの表・行に置くかの最終決定ではない。

**現在の責任境界（CURRENT-ACCEPTED）**: [12b §6・§7](../domain-model/12b_aircraft-and-battery.md#6-batteryusageバッテリーライフサイクルイベント)の論理分離を維持する。Flightが実際の機体・BAT・時間、BatteryUsageが非飛行ライフサイクルを受け持ち、BAT交換だけで飛行実績を重複生成しない。個体履歴を人が読む表示と、保存テーブルを同じ形にする必要はない。充電・保管・点検等の詳細フローを本Stepで増やさない。

## 5. 未確定と検証観点

- **PENDING-S3-BATTERY-HISTORY**: 取得時状態・確認サイクル数と取得後履歴の物理保持、最終的な飛行中BAT明細／飛行外イベントの表・行・タブ対応、共用参照とセット表示UI。互換のUUID／複合キー、status・健全性等の既存PENDING-C1-SCHEMAも解消しない。
- **VERIFY-S3-BATTERY-EVIDENCE**: 99.2が根拠とする03の共用一覧・使用履歴、旧BAT資産・旧BatteryUsageモックの実物対応。今回ハードウェア互換を新規試験したとも、メーカーの全製品へ適用できるとも報告しない。
- **受入時に追う意味**: 異機種間共用、同一型式複数機、N機・M本、取得時の既知／不明を区別しても個体が二重化しないこと。飛行実績と非飛行履歴の正本が競合せず、表示上のセット変更が過去履歴を壊さないこと。物理保存の決定は[開始ゲート](../23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)に従う。
