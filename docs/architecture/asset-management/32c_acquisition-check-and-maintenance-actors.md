# 32c. 取得時確認と点検整備の実施者・記録者

最終更新: 2026-09-20\
状態: CURRENT-ACCEPTEDを中心に、個別事例・確認限界・未確定を区別\
対象: 99.2 §4および§6の取得時確認、正式時間への算入、実施者と作成・転記者の分離に限る。§6の保存構造・通常整備運用は対象外。

## 1. 取得時の短時間動作確認をどう残すか

**当初状態・問題**: [12e](../domain-model/12e_operation-inspection-maintenance.md)はFlightを離陸〜着陸の実績、MaintenanceRecordを機体の生涯点検整備履歴として定義するが、中古機の取得時確認と管理開始累計の関係を説明していなかった。前歴不明の個体を短時間動作確認した事実だけで、全てを正式運航として加算するか、記録自体を捨てるかの二択にすると、取得確認の意味と00:00の根拠が失われる。これは既存定義の説明不足であり、旧Docsが取得確認を消すよう決定していたという意味ではない。

**確認した事実（99.2のEVIDENCE/EXAMPLE）**: 中古Lite+の取得時に自宅屋内で短時間の離着陸・ホバリング・前後左右の動作を確認した。§4と§6の取得確認記録は、前歴不明、短時間取得確認、正式運航への不算入、管理開始00:00、BATと機体状態に基づく低使用歴判断、推定過去時間を加算しない、という一続きの経緯を05の機体別点検整備記録に残している。実機識別子・実施日・BAT実数をここへコピーしなくても、この設計意味は保持できる。

**検討・変更理由と現在到達点（CURRENT-ACCEPTED）**: この動作確認は中古取得時の状態確認として点検整備履歴に残し、正式運航時間には算入しない。実際に確認したことを消さず、正式運航記録0件とも矛盾させない。[32a](32a_aircraft-acquisition-and-cumulative-time.md)の累計の意味と[32b](32b_battery-sharing-and-acquisition-history.md)の取得時BAT状態へ接続する。Flightや日常点検の通常の責務を破棄せず、今回の個別取得確認をそれらへ無条件に押し込まない。

**条件・例外の境界**: これは今回の取得時状態確認に関する判断である。「短時間なら全て除外」「屋内なら全て除外」「整備目的なら全て除外」という新しい一般規則にはしない。実際に機体を動かしており、アプリだけのシミュレーション／TESTで実飛行がない場合とも異なる。正式運航や管理開始後の実飛行を、この個別判断だけで除外しない。

## 2. 記録根拠と補助確認の範囲

**原本の根拠**は99.2 §4・§6が挙げる取得時の05実記録である。今回それ自体を開いて再確認してはいない。基準アプリの[管理開始設計07](https://github.com/ikifuse/autel-evo-lite-flight-log/blob/e8560b03e1220cb3b38e927190bdcb03191ddc57/01_ドローン運航記録_設計書/07_点検整備・管理開始.md)を補助的に読むと、取得直後の初期確認を管理開始前の確認工程として記録し、その完了後から追うという同じ論点の適用範囲が残る。同書は管理開始後の実飛行と区別する。これは今回の旧設計文書の直接読解であり、99.2にない文言を原本の引用として補うものではない。

2026-09-18に補助照合した[公式ガイドライン §4(1)③](https://www.mlit.go.jp/common/001599241.pdf)の試験飛行の扱いは、メーカー側の完成検査・出荷までの範囲を説明する。この条項を購入者の全動作確認へ直接拡張しない。取得前履歴と継承の原則・記録欠落時の適用条件は[32a §3](32a_aircraft-acquisition-and-cumulative-time.md#3-後から記録が得られた場合と法規根拠の限界)へ一本化する。今回の補助調査で個別事例の行政承認を新たに確認したわけではなく、既存運用判断を一般論で変更もしない。

## 3. 実施者と作成・転記者を分ける理由

**当初状態**: 12eには`technician_name`、[12f](../domain-model/12f_common-lifecycle-id-and-audit.md)には作成・更新者等の共通監査属性があったが、実際に整備した者と原本の作成・転記者の意味を十分に接続していなかった。「両者は常に同一」という既存の確定仕様があったとは扱わない。

**現場上の問題・根拠（99.2 §6）**: 外部修理業者が点検・整備した結果を、運用側が業者報告書・点検結果・交換部品資料等から原本へ記録する場合がある。業者本人にアプリやDriveへの入力を要求すると、その実運用を表せない。取得確認を残す際にも、実施した人と記録作成・転記した人が同一とは限らない。

**検討案と現在到達点（CURRENT-ACCEPTED）**: 実施者本人と原本コピー者／転記者を同一人物に固定する案は採らない。SpreadsheetのDrive編集権限を持つ利用者が、根拠資料に基づいて実態どおり記入・転記し、実施者と転記者を区別して残せるようにする。編集権限があるだけで実施者の事実まで変えてよいという意味ではない。原本コピーの実行手順やアプリの自動生成範囲は本Stepでは移植しない。

**役割の境界**: 実施者は実際の点検・整備の担当、作成・転記者は記録を作成した主体である。Googleの編集可能性は[31b](../identity-and-access/31b_roles-and-access-control.md)、人物と認証アカウントは[31a](../identity-and-access/31a_person-account-and-environment.md)に従う。[31c](../identity-and-access/31c_operational-actors.md)の通常運航Recorderや日常点検の初期値を、そのまま整備の転記者へ統合・流用しない。`technician_name`を転記者名へ読み替えず、作成者の共通メタデータだけから実施者を推測しない。

**法規の補助照合**: [取扱要領 §5(3)](https://www.mlit.go.jp/koku/content/001574394.pdf)は点検整備の実施と記載を結び付ける。今回補助確認した[ガイドライン §3(3)](https://www.mlit.go.jp/common/001599241.pdf)では外部へ依頼した整備内容の確認と資料の扱いも示される。これらの記録責任と、誰がGoogleへログインして転記するかは同じ概念ではない。業者資料を根拠とし実施者の事実を保持する99.2の運用を、単なる代理ログインや実施者名の置換へ変えない。

## 4. 未確定と後続境界

- **PENDING-S3-MAINTENANCE-ACTOR**: 実施者・原本作成者／転記者と操作アカウントの具体FK、外部業者の保持形式、根拠資料との関連、画面・列・タブ。PersonnelとUserAccountのどちらへどのIDを置くかをここで確定しない。
- **PENDING-S3-ACQUISITION-RECORD**: 取得確認の意味をMaintenanceRecord・累計基点・取得時BAT状態へ結ぶ物理保持形式。§1の判断は到達済みであり、未確定なのは実装・保存・UIの具体化である。
- 中古機を今後の管理対象にする時点の点検内容を点検整備記録へ残す考え（オーナーの2026-09-20の指示。CURRENT-PROPOSAL）は、取得時の確認とは別の論点で、定義と未確定は[32e §5](32e_battery-management-scope-and-flight-separation.md#5-中古機を管理対象にする時点の点検との関係current-proposal)（PENDING-D-BAT-INTRO-INSPECTION）。
- **VERIFY-S3-MAINTENANCE-EVIDENCE**: 99.2が参照した05の取得確認原本と、実施者・転記者・根拠資料を区別する実物対応。今回の公式文書の補助照合では解消しない。
- **後続の移植範囲（PENDINGへの降格ではない）**: §6の点検整備記録全体、機体ごとの保存構造、原本コピー運用・通常整備運用は未移植。既存のタブ方針との相違も本Stepでは採否判断しない。
- **受入時に追う意味**: 取得確認の事実と正式時間への不算入理由を辿れること。外部業者が実施し権限者が記録した場合も双方が分かり、通常運航Recorderの値で上書きされないこと。同一人物が兼務する場合も意味の区別を失わないこと。

Step 6で§6残りの通常日常点検からの分離・機体別媒体・原本コピーを[36](../maintenance-storage/36_aircraft-maintenance-records.md)へ移管した。上記のStep 3時点の未移植範囲と区別し、本書の取得確認・Actor因果とPENDINGは変更しない。
