# 24. API非依存のManual通報と入力再利用原則

最終更新: 2026-09-15\
状態: Phase C0完了・Phase C1未着手（docs再編）

主要責務: C6 Manualを第一級にする業務フロー・支援原則。画面VM・状態機械・台帳列の詳細はそれぞれの正本を参照する。

## 1. 背景と基本方針

### 1.1. 背景と課題
2026-09-14の設計記録時点で、国土交通省の「DIPS 2.0（ドローン情報基盤システム2.0）」API利用申請を行っていますが、以下の重要事項は現時点で**【未確認】**です：
- 個人事業主・個人パイロットに対する利用申請の承認可否
- 固定IPアドレス要件等のネットワーク審査条件を満たせるか
- 正式なcredential（client_id, client_secret）の発行時期および発行可否

もし新アプリが「DIPS APIが利用できること」を前提に設計されていた場合、審査が却下されたり長期化した場合に、アプリ本体の開発が中断し、現場で使えないアプリになってしまいます。
したがって、本アプリは**「DIPS APIが取得できなくても、現場で実用できる完成アプリ」**として設計・実装します。

そのうえで、将来国交省の審査が通りAPIが利用可能になった場合には、内部データ構造や画面を作り直すことなく、最後の提出経路だけを切り替えて自動連携できる無縫製（シームレス）な構造を確立します。

### 1.2. 3大設計基本方針
1. **DIPS API非依存完結主義（API-independent Flight Planning）**:
   - DIPS APIが取得できない場合でも、アプリ内で飛行計画（円/ポリゴン/線形バッファ、日時、機体、操縦者、目的、空域、方法、保険、許可等）をスタンドアロンで作成・編集・保存・再利用できます（設計正本は [12d](../domain-model/12d_flight-plan-and-dips.md)、証拠は [26](../26_dips-web-ui-verification.md)）。
   - **APIは最後の外部送信Adapterに過ぎず、飛行計画機能本体ではありません**。APIなしでも専用の手動入力支援画面を通じてスマートフォン1台で現場運用を完結でき、アプリの完成条件をAPI取得成否に依存させません。
2. **通報前独立台帳退避主義**:
   - DIPS側へ送信（または手動入力）する**前**に、端末ローカルDBへ不変 `submission_snapshot`（意味論的通報スナップショット）を先行保存し、Googleスプレッドシートの「DIPS飛行計画台帳」（確定台帳）へ非同期同期ジョブを登録します。国交省サーバー側の保存期間や参照可能期間に依存せず、利用者側の法令遵守証跡として長期に保持します（Sheets同期完了はDIPS通報の前提条件とせず、障害時でも通報を妨げません）。
   - 出力・連携境界の4原則（Sheets = 確定台帳、PDF = 人間向け帳票、KML = ユーザー向け地図出力、JSON = DIPS API内部通信のみ）に基づき、手動通報経路においてユーザーへJSONファイルを作成・保存・出力・要求することはありません。
3. **誤認防止と不変履歴保持**:
   - 「手動通報ボタンを押したこと」と「DIPS側の通報確認」を混同しない状態管理を徹底します。
   - 飛行計画が後から変更・再通報されても、過去に通報した内容を上書き破壊せず、不変スナップショット（`submission_snapshot`）として全履歴を保持します。

## 2. 通報入力支援原則の適用

原則の正本は[25 overviewのDIPS Submission Assistance Principle](../dips-flight-plan/25_overview.md#1-dips-submission-assistance-principle通報入力支援原則)。本業務フローは、入力済みのFlightPlan・Master・Preset等を不変Snapshotへ再利用し、手動通報時の再入力・判断・画面往復を減らす。原則全文・Manual/API経路の定義は正本に一元化し、以下では保存・選択支援・通報打刻・確認記録・現場記録の順序を扱う。

## 3. Manualと現場記録・外部台帳の並行フロー

1. 計画Draftは入力途中でも保存する。提出準備の必須・適用条件は [25d](../dips-flight-plan/25d_requirement-validation.md) で評価する。
2. 提出内容を確定し `submission_snapshot` をローカルDBへ不変保存する。Sheetsへの同期ジョブを登録し、同期完了を待たずにManual支援または承認済みAPI経路へ進む。
3. Manualでは [25b](../dips-flight-plan/25b_manual-web-mapping.md) の実画面順ViewModelを表示し、DIPS Webを別タブで開く。登録済み機体/操縦者/許可の選択、目的/空域/方法のcheckbox、数値/日時、構造化保険、地図Geometryを案内する。コピーは転記可能なテキスト/数値の手段として扱い、Pickerや地図作図をテキスト貼付だけで代替しない。
4. 操作者による「手動通報した」の打刻と、番号確認または日時・機体・範囲の一覧照合による「DIPS確認完了」を別に記録する。番号を取得できない場合は `dips_plan_id: null` の一覧照合も許容する。画面操作・コピー項目・確認パターンA/Bは25b、状態と5大誤認防止規則は [13b](../state-machines/13b_dips-submission.md) が正本。
5. DIPS通報手続きと現場運航準備（Mission作成・飛行前点検・現場記録）は並行可能。DIPS未確認やSheets障害で記録画面への進行をHard Blockしない。アプリ操作可能と法令上の離陸可否は別であり、[13c](../state-machines/13c_takeoff-readiness.md) の要否・点検・許可・周囲安全・気象・例外を総合確認する。アプリは未通報飛行を適法と保証するボタンを作らず、実際の離陸事実は記録する。
6. 通報結果・確認方式・受付番号（取得時）は台帳へUPSERTし、予定と実運航のIDを結合して飛行日誌・監査対比へ接続する。台帳の列・同期順序は [24a](24a_submission-and-sheets-ledger.md)、Entityは [12d](../domain-model/12d_flight-plan-and-dips.md)。

## 4. オフラインと実装Phaseの境界

支援画面の表示・コピー・既知の通報確認の記録は端末内Snapshotから動作する。DIPS Webでの通報/確認にはDIPSへ到達できる通信が必要であり、端末が完全圏外のまま外部受理できるとは扱わない。Sheetsは通信復帰時に非同期反映する。

C6 Manualは第一級の主要機能、C7 APIは承認・credential取得時のみ追加するOptional。API未取得の完成経路はC0→C1→C2→C3→C4→C5→C6→C8→C9。C6でAPI非依存の主要機能が揃っても、本番運用判定はC8帳票とC9実機/Shadow Run後に行う。C7はC6後または本番運用後に追加可能。各Phaseの正式な範囲・順序は [23](../23_implementation-roadmap.md) を正本とし、今回はC1実装を開始しない。
