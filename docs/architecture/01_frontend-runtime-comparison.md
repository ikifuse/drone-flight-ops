## 1. 比較対象の候補一覧

本アプリの完成形である「iPhone と Android の両方で、ドローン飛行の現場で実用的に使える総合運航管理アプリ」を実現するため、以下の5つの実行方式を比較します。

1. **候補A: PWA（Progressive Web App）中心構成**
   - HTML5/CSS/JavaScript(TypeScript) + Service Worker + IndexedDB。
   - ブラウザから「ホーム画面に追加」してスタンドアロン起動。
2. **候補B: クロスプラットフォームフレームワーク（Flutter / React Native+Expo）**
   - 単一のコードベースからネイティブアプリ（iOS / Android）をビルド。
3. **候補C: Web技術 ＋ ネイティブラッパー（Capacitor）**
   - Web標準技術（React/Vue/Svelte/Vanilla JS）でUIを構築し、CapacitorでiOS/Androidネイティブシェルにラップ。必要に応じてWeb（PWA）としても同時稼働可能。
4. **候補D: 完全ネイティブ開発（Swift/SwiftUI ＋ Kotlin/Jetpack Compose）**
   - iOSとAndroidをそれぞれの公式言語・ツールで個別に構築。
5. **候補E: 現行GAS（Google Apps Script）Web Appの延長**
   - 基準アプリ（autel-evo-lite-flight-log）と同様、GAS HTMLServiceを中心に機能追加。

## 3. 各候補の詳細分析

### 候補A: PWA中心構成（条件付き第一候補）
- **長所**:
  - 現行の有料Apple Developer Program（年額約1.3万円前後）の契約やストア審査を行わずに、Safari/Chromeの「ホーム画面に追加」からフルスクリーンで即座に現場利用可能。
  - バグ修正や機能追加がWebデプロイによって即座に端末へ反映される。
  - 国土地理院地図やオープンソースの地図ライブラリ（MapLibre GL JS / Leaflet）が極めて扱いやすく、GeoJSONによるポリゴン編集UIの実装例が豊富。
  - Web標準技術（TypeScript/HTML/CSS）であるため、AIアシスタントによる保守・改修の精度が高い。
- **留意点・制約事項と対策**:
  - iOS Safariでは、端末の空き容量逼迫時等にストレージ（Cache Storage / IndexedDB）が自動削除されるリスク（Eviction）がある。
  - **対策（B2検討課題）**: WebKit / SafariがサポートするStorage API（`navigator.storage.persist()`, `persisted()`）を活用し、ホーム画面PWAとして永続化ストレージ要求を試みる。ただし永続化が常に許可される保証はないため、許可されない場合にも備えて外部（スプレッドシートやJSONファイル）への二重退避・バックアップ同期を必須とする設計とする。
  - バックグラウンドでの長時間の位置情報連続追跡は行えない（現場での手動打刻や現在地確認には問題ない）。
  - 事前読み込み（Service Workerインストール）が完了していない初回アクセス時は圏外で起動できない。

### 候補B: クロスプラットフォーム（Flutter / React Native+Expo）
- **Flutter**:
  - 高性能なUI描画と強固な型システムを持つが、Dart言語への依存があり、Webの地図エコシステム（MapLibre JS等）を直接流用しにくい。
- **React Native ＋ Expo**:
  - TypeScript資産を活用でき、Expo Web等でWeb併用も可能。
- **共通の短所（個人運用上の課題）**:
  - iPhone実機で期限なく快適に動かすには、Apple Developer Programへの加入や、Mac環境でのXcodeビルド、証明書更新、TestFlightの90日更新など、個人運用としての管理負担が大きい。

### 候補C: Web技術 ＋ ネイティブラッパー（Capacitor）
- **長所**:
  - コアをWeb標準技術で構築しておけば、最初はPWAとして追加費用なしで運用し、将来的にネイティブ固有機能（バックグラウンドGPS、Bluetooth連携等）が必要になった段階でネイティブアプリ化できる柔軟性がある。
  - Webの地図ライブラリ資産を大部分流用できる。
- **留意点**:
  - ネイティブシェル化する際には、iOS/Android固有のパーミッション設定、Safe Area対応、ファイル保存先パスの差異等の調整工数が生じる（「無修正」で動くわけではない）。

### 候補D: 完全ネイティブ開発（Swift/Kotlin）
- **長所**: 各OSの最新機能や最高峰の操作性を引き出せる。
- **短所**: iOSとAndroidでコードベースが完全に2重化し、航空法やDIPS仕様変更のたびに2言語で同じ改修が必要。個人運用としては破綻リスクが極めて高いため非推奨。

### 候補E: 現行GAS（Google Apps Script）の延長
- **長所**: 既存アプリの資産を直結でき、追加インフラ費用がかからない。
- **短所**:
  - GAS HTML Serviceはサーバー通信（`google.script.run`）を基本とするため、完全圏外でのオフライン現場記録には適さない。
  - iframeサンドボックス内での動作となり、地図ポリゴン操作などの現場レスポンスが重くなりやすい。

## 4. 実行方式の評価結論

- **推奨方針**: **候補A（PWA構成）** を第一候補とし、将来の拡張を見据えて **候補C（Capacitor移行経路の確保）** を考慮した設計とする。
- **前提条件**:
  - 個人利用においてストア審査・ビルド維持コストを回避したいこと。
  - オフライン利用は「事前読み込み済み」を前提とし、重要データはIndexedDBに保持した上でスプレッドシート等へ定期退避できること。
