# アプリ実行方式の比較検討（01_frontend-runtime-comparison.md）

最終更新: 2026-09-14
プロジェクト: `drone-flight-ops`

---

## 1. 比較対象の候補一覧

本アプリの完成形である「iPhone と Android の両方で、ドローン飛行の現場で実用的に使える総合運航管理アプリ」を実現するため、以下の5つの実行方式を比較します。

1. **候補A: PWA（Progressive Web App）中心構成**
   - HTML5/CSS/JavaScript(TypeScript) + Service Worker + IndexedDB。
   - ブラウザから「ホーム画面に追加」してスタンドアロン起動。
2. **候補B: クロスプラットフォームフレームワーク（Flutter / React Native+Expo）**
   - 単一のコードベースからネイティブアプリ（iOS / Android）をビルド。
3. **候補C: Web技術 ＋ ネイティブラッパー（Capacitor）**
   - Web標準技術（React/Vue/Svelte/Vanilla JS）でUIを構築し、CapacitorでiOS/Androidネイティブシェルにラップ。必要に応じてWeb（PWA）としても同時稼働可能。
4. **候補D: 完全ネイティブ開発（Swift/SwiftUI ＋ Kotlin/Jetpack Compose）**
   - iOSとAndroidをそれぞれの公式言語・ツールで個別に構築。
5. **候補E: 現行GAS（Google Apps Script）Web Appの延長**
   - 基準アプリ（autel-evo-lite-flight-log）と同様、GAS HTMLServiceを中心に機能追加。

## 3. 各候補の分析

### 候補A: PWA中心構成
- **長所**:
  - アプリストア審査や年1.3万円のApple Developer登録が一切不要。URLにアクセスして「ホーム画面に追加」するだけで即日iPhone/Androidでアプリ同様に使える。
  - バグ修正や機能追加の反映が極めて迅速（GitHub Actions等からWebサーバーへデプロイすれば全員に即時反映）。
  - 国土地理院地図やオープンソースの地図ライブラリ（MapLibre GL JS / Leaflet）が極めて扱いやすく、ポリゴン編集UIの実装実績がWeb界隈で圧倒的に豊富。
  - AI（LLM）が最も得意とするWeb標準言語（HTML/CSS/TypeScript）であり、保守・改修の精度が高い。
- **短所**:
  - iOS Safariにおけるオフラインキャッシュ（Service Worker / Cache Storage）の永続性制限（7日間アクセスがない場合の自動削除リスクなど）に配慮が必要（LocalStorageやIndexedDBと併用した退避設計が必須）。
  - バックグラウンドでの長時間の位置情報トラッキングはネイティブほど強力ではない（ただし本アプリは「現在地の取得」「範囲描画」が主目的であり致命的ではない）。

### 候補B: クロスプラットフォーム（Flutter / React Native+Expo）
- **長所**:
  - 完全なネイティブバイナリとして動作するため、オフラインデータ保存（SQLite）、GPS、カメラ、アニメーションが滑らか。
- **短所**:
  - iPhone実機で動かすために、Apple Developer Program（年間約13,000円）への加入や、Mac上でのXcodeビルド、証明書更新、TestFlight更新（90日制限）など、開発・運用の維持コストが個人利用としては非常に重い。
  - 地図・ポリゴン描画において、Web系の優れた地図エコシステム（国土地理院タイルやGeoJSON操作ライブラリ）を直接使いにくく、ネイティブ地図SDK（Google Maps等、無料枠に注意が必要）に依存しがちになる。

### 候補C: Web技術 ＋ ネイティブラッパー（Capacitor）
- **長所**:
  - **二刀流が可能**。コアはReact/Vue/Svelte等のWeb技術で作成し、普段はPWAとしてブラウザ/ホーム画面から「完全無料・審査なし」で利用できる。
  - 将来「どうしてもiOSのネイティブ機能（バックグラウンドGPSやBluetoothドローン連携等）が必要になった」段階で、コードを書き直すことなくネイティブアプリ（iOS/Android）としてビルド可能。
  - Webの地図ライブラリ資産を100%そのまま流用できる。
- **短所**:
  - 最初からネイティブビルドを前提にするとXcode/Android Studioの管理が必要になる（ただしWebファーストで進めればこの問題は回避できる）。

### 候補D: 完全ネイティブ開発（Swift/Kotlin）
- **長所**: OS最高の操作性と安定性。
- **短所**:
  - **個人運用として破綻リスクが極めて高い**。iOS版とAndroid版でコードベースが2重になり、一人で保守しきれない。
  - 航空法やDIPS仕様の変更があった場合、2つの言語（SwiftとKotlin）で同じ修正を2度行わなければならない。

### 候補E: 現行GAS（Google Apps Script）の延長
- **長所**: 既存アプリの資産を直結でき、サーバー代が無料。
- **短所**:
  - **致命的な欠点**: GASはサーバー通信（`google.script.run`）を前提としており、**山間部・圏外でのオフライン完全動作が構造上不可能**。
  - GASのWeb Appはiframeサンドボックス内で動作するため、モバイルSafari/Chromeでの地図操作（ピンチズーム、パン、複雑なポリゴン描画）のレスポンスが重く、現場操作性が大きく劣る。
  - DIPS APIの認可コードコールバックの処理に制約が多い。

## 4. 実行方式の結論（方向性）

- **最有力推奨**: **候補A（PWA構成）** または **候補C（Web技術ファースト＋Capacitor準備構成）**
  - 個人利用において「費用0円」「ストア審査・更新不要」「Web地図エコシステムの完全活用」「AIによる迅速な保守性」をすべて満たせる唯一の現実的解である。
  - 設計段階では、ネイティブ依存のないクリーンなWeb標準（SPA/PWA）として構築し、将来必要になった場合にCapacitorでネイティブラップできるアーキテクチャを採用することが最もリスクが低く合理的である。
