## 1. 再監査の目的と位置づけ

Phase B1で提示した「PWA ＋ バックエンド境界 ＋ ローカル優先保存 ＋ Googleスプレッドシート連携」という方向性は有力な第一候補ですが、B1/B1.1ドキュメント内に**「断定が強すぎる記述」「未確認事項の過剰な未確認化または確定扱い」「内部矛盾」「公式ガイドラインとの齟齬」**が残っていました。

本フェーズ（B1.2）は、B2（詳細設計）へ進む前にこれらを国土交通省および各テクノロジーの公式一次資料と厳格に再照合し、
1. **【確認済み事実】**: 公式資料等で裏付けが取れている事項
2. **【技術上の推奨・設計目標】**: 事実を踏まえ、本プロジェクトにおいて目指すべき方針
3. **【未確認事項】**: 国交省DIPS運用の実態やcredential発行関係等、現時点で推測で断定してはならない事項
4. **【将来変更可能性】**: 料金体系、無料枠、OSやブラウザの仕様変更リスク
を客観的に分離・訂正して記録することを目的とします。

## 2. 主要な再検証・訂正項目一覧

### 2.1 「永久無料」「完全0円」表現の撤回とCloudflare Workersの正確な制約評価
- **訂正前**: 「Cloudflare Workersは永久無料」「完全0円で永久運用可能」「個人利用ならリクエスト数が少ないので必ず無料枠内」と断定。
- **確認された事実（2026-09-14時点公式仕様）**:
  - **Cloudflare Workers Free Plan**:
    - リクエスト数: **1日100,000リクエスト**
    - CPU実行時間: **10ms / HTTPリクエスト**（※重要）
    - サブリクエスト数・メモリ・タイムアウト等のFree Plan制限が存在する。
  - 個人利用のアクセス頻度であればリクエスト数制限には収まりやすいが、将来DIPS認証処理、トークン暗号化・復号、レスポンスのJSON変換・バリデーション等を実装した際に、CPU時間10ms制限を超過しないかを実測・検証する必要がある。
  - クラウドベンダーの無料枠規約や料金体系は将来改定される可能性があるため、「永久に0円」と保証することは技術的・経営的に誤りである。
- **訂正後の方針**: 「現時点の公式無料枠に照らし、個人運用想定の範囲内であれば月額0円で運用できる可能性が高い有力な低コスト候補である。ただし、実装後にFree PlanのCPU時間（10ms/req）や各制限内で安定動作するかを検証する必要がある」とする。

### 2.2 Cloudflare Workersの性能表現の適正化
- **訂正前**: 「コールドスタート0ms」「ミリ秒起動」「必ず安全」などの誇大・固定値表現。
- **確認された事実**:
  - Cloudflare WorkersはV8 Isolate技術を採用しており、一般的なコンテナ型サーバーレス（数秒〜数百ms）と比較して起動オーバーヘッドが極めて小さい（数ミリ秒以下）。しかし、ネットワークレイテンシやハンドシェイクを含めた「0ms保証」は存在しない。
- **訂正後の方針**: 「0ms保証」を撤回し、「V8 Isolateによる極めて低遅延な起動特性」として設計上のメリットを客観的に記述する。

### 2.3 PWAおよびIndexedDBの耐久性とWebKit Persistent Storage対策
- **訂正前**: 「iOS Safariのキャッシュ削除リスクはIndexedDBへの二重保存で回避可能」「IndexedDBなら安心」という単純化。
- **確認された事実**:
  - **WebKit（iOS）のストレージ管理**: SafariおよびWebKitでは、端末の空きストレージ容量が逼迫した場合、OS側でストレージ領域（Cache Storage、IndexedDB等を含む）が自動削除（Eviction）される対象となり得る。
  - **Storage API（Persistent Storage）**: WebKit / Safariでは `navigator.storage.persist()` および `navigator.storage.persisted()` がサポートされており、ユーザーがホーム画面に追加したPWA等で永続化ストレージ（Persistent mode）が認められたオリジンは、ストレージ逼迫時の自動削除から保護される仕組みがある。ただし、`persist()` が常に許可される保証はない。
- **訂正後の方針（B2設計への反映）**:
  - 端末内IndexedDB単独を唯一の長期保存場所にはしない。
  - B2では以下の多層防御策を検討する：
    1. ホーム画面追加PWAとして `navigator.storage.persist()` を要求し永続化を試みる。
    2. `navigator.storage.persisted()` で現在の保護状態を確認・UI表示する。
    3. 永続化が許可されない環境でもデータが失われないよう、Googleスプレッドシート等への外部バックアップ同期を組み合わせる。
    4. 緊急時のJSONファイル手動エクスポート・インポート復旧手段を備える。

### 2.4 オフライン時の業務継続とDIPS飛行計画通報の法的・運用上の明確化
- **訂正前**: 「完全圏外でも100%動作」「オフラインでもDIPS通報可能」等の混同。
- **確認された事実（法令・運用上の必須条件）**:
  - 航空法および国交省の運航ルール上、飛行計画通報が必要な特定飛行等においては、**飛行前にあらかじめDIPSへ通報が完了していること**が義務づけられている。
  - 電波がない現場でオフラインキューに飛行計画データを保存したとしても、**それは「端末内に下書き・送信待ちデータを保存した」に過ぎず、「DIPS通報成功確認済み」になったことにはならず、また通報成功だけで総合的に飛行可能とみなすこともできない**（許可承認、空域条件、施設管理者との調整、気象条件等の確認が別途必要）。
- **訂正後の方針（B2設計への反映）**:
  - 「飛行前点検、離着陸、バッテリー管理、日誌記録などの通信不要な現場業務」は、事前にアプリを読み込んでいればオフラインで継続可能とする。
  - 一方で、DIPS飛行計画通報については、以下の状態遷移を厳格に区別して設計する：
    - `未作成` → `作成済み` → `送信待ち` → `送信中` → `DIPS通報成功確認済み`（※通報要件充足。総合的な飛行可否は他条件の確認が必要）
    - 通信障害時は `送信待ち`、`通報失敗`、`再送待ち` とし、通報成功が国交省サーバーから確認できるまでは通報要件充足扱いにしてはならない。また、通報成功確認後もアプリ全体として法的に飛行可能と誤認させない安全確認フローとする。

### 2.5 「1ms保存」等の固定性能値の撤回
- **訂正前**: 「1ミリ秒で打刻・保存」「ミリ秒永続化」。
- **訂正後の方針**: 実装前の段階で固定数値を保証することをやめ、「ネットワーク通信の往復待ち（数秒）を発生させず、端末内ローカルストレージへ即時に近い形で永続化する設計目標」と表現を改める。

### 2.6 Capacitorへの移行表現の適正化
- **訂正前**: 「Webコードを100%そのまま流用可能」「1行も書き直すことなくネイティブアプリ化」。
- **確認された事実**:
  - CapacitorによってWeb資産のUIや主要ロジックを大幅に再利用できることは事実だが、ネイティブプラグインの初期化、iOS/Androidの権限要求（位置情報等）、Safe Area（ノッチ・ホームバー）対応、ファイル保存先パスの差異など、ネイティブシェル化に伴う追加実装・調整は必ず発生する。
- **訂正後の方針**: 「100%無修正」を撤回し、「WebフロントエンドのUI・業務ロジックの大部分を再利用でき、将来ネイティブアプリへ拡張する際の移行コストを低く抑えられる」という現実的な表現に改める。

### 2.7 Apple Developer費用・配布方式の整理
- **訂正前**: 「年間12,980円が毎年必須」「Flutter/Expoは必ず有料契約が必要」。
- **確認された事実**:
  - **無料Apple Account**: MacとUSB接続すれば無料のApple IDで個人開発用としてiPhone実機にアプリをインストール可能。ただし有効期限が「7日間」で切れ、最大3アプリまでという厳しい制約があるため、ドローンの実現場運用としては実用的ではない。
  - **有料Apple Developer Program**: 年額99米ドル（為替変動により日本円価格は改定される。2026年時点では約13,000円前後）。TestFlight（90日間配布）やApp Store公開に必須。
- **訂正後の方針**: 固定金額の断定を避け、為替や規約変更があり得ることを明示。PWAであればこれらの審査・署名更新・費用を回避してiPhoneでフルスクリーン起動できる点を公平に評価する。

### 2.8 クロスプラットフォーム（Flutter / React Native / Expo）評価の客観化
- **訂正前**: PWAを有利に見せるため、Flutter/Expoのデメリットを強調しすぎた。
- **訂正後の方針**:
  - **Expo / React Native**: TypeScript資産を共有でき、Web・iOS・Androidを単一コードで扱える強力な選択肢。
  - **Flutter**: 描画性能とUIの一貫性に優れるが、Dart言語への依存とWeb地図エコシステム（MapLibre JS等）の流用性に課題がある。
  - 個人運用の観点から「ストア公開・ビルド環境保守の手間」を理由にPWAを第1候補とする客観的なロジックに修正する。

### 2.9 Supabase無料枠休止条件の表現修正
- **訂正前**: 「1週間無アクセスで必ず停止する」。
- **確認された事実（Supabase公式仕様）**:
  - Supabase Free Planでは、「7日間の低アクティビティ（Low activity for 7 days）」や「十分なユーザーデータベース活動がないプロジェクト」が自動的に一時停止（Paused）対象となる。ダッシュボードから手動で再開（Restore）できるが、復帰に数分を要する。
- **訂正後の方針**: 「7日間アクセス0」という誤った表現を改め、「数週間ぶりに現場でドローンを飛ばすような低頻度利用パターンにおいて、Free Planの自動pause機能が現場での通信・同期の運用リスクとなる」と客観的に評価する。

### 2.10 GASのオフライン評価の精緻化
- **訂正前**: 「現行GASではオフライン完全動作が構造上不可能」。
- **訂正後の方針**: GASの「HTML Service」自体がサーバー通信を前提とする点と、フロントをPWAにしてバックエンドAPIとしてGASを呼び出す別構成を区別し、現場オフラインでの起動・保存を端末内で担保する必要性を正確に述べる。

### 2.11 DIPS 2.0 認証・連携仕様の再分類（公式確認済み事項と未確認事項の厳格分離）

#### A. 国土交通省公式ガイドラインで【確認済みの事実】
（一次資料: 国土交通省「無人航空機登録システム・飛行許可承認システム・飛行計画通報機能 外部接続インターフェース仕様書／ガイドライン」等、2026年9月確認）

1. **認証プロトコル**:
   - OpenID Connect (OIDC) 準拠。
   - Authorization Code Flow（認可コードフロー）を採用している。
   - `response_type=code` による認可リクエスト、および `grant_type=authorization_code` によるトークン取得。
2. **システムと認証レルム（Realm）の対応関係**:
   - **DRS（機体登録系）**: `drs-utm`
   - **FPA（飛行許可・承認系）**: `drs-req`
   - **FPR（飛行計画通報系）**: `drs-fpl`
3. **主要な認証エンドポイント・パラメータ**:
   - 各realmごとに Authorization endpoint、Token endpoint が規定されている。
   - トークン要求時に `client_id`, `client_secret`, `redirect_uri` を使用する。
   - レスポンスとして `access_token` および `refresh_token` が返却される仕様が定義されている。

#### B. 公式一次資料に基づく【API利用申請主体の現状】
- **確認済み事実**:
  - 現在公開されている国土交通省のAPI利用案内ページには、**「本サービスは、無人航空機に関する運航管理システム等を整備する法人・団体の方が手続きを行うサービス」**という趣旨が明記されている。
- **未確認事項**:
  - 個人事業主（屋号等）や個人開発者・個人パイロットがどのような条件で利用申請できるか、または将来制度や要件の変更・開放が行われるかについては、公に明確化されていない。
- **設計上の対応方針**:
  - この利用資格のハードルを理由にDIPS連携機能全体の設計を破棄してはならない。
  - アプリ内部に「DIPS Adapter境界」を確立し、正式な利用資格およびcredentialを取得できた段階でスムーズに接続・通報できる構造として設計を進める。

#### C. 引き続き【未確認の事項（credential発行関係・運用実態）】
- 申請書提出後、DRS / FPA / FPR の3系統で `client_id` および `client_secret` が共通の単一ペアとして発行されるのか、別々に発行されるのか。
- 1回の利用申請でFPA（許可承認）とFPR（飛行計画通報）を同時に利用可能となるのか。
- 実際の発行通知書にどのような形式でcredentialが記載されるか。
- 単一のユーザーログインによって複数realmのSSO（シングルサインオン）がどこまでシームレスに機能するか。

### 2.12 ローカルDBとGoogleスプレッドシートの「正本」問題（B2前の未確定扱い）
- **訂正前**: 「モデルD（現場はスマホ正本、後はスプレッドシートが公式原本）で決定」と決め打ちしていた。
- **訂正後の方針**:
  - B1段階では特定の正本モデルを確定しない。
  - 以下の4モデルを中立に比較対象として残し、**「モデルDが本プロジェクトの現場運用および基準アプリの柔軟性を両立する有力候補である」**という位置づけに留める。
    - **モデルA**: ローカルDB主マスターモデル（スプレッドシートは出力・バックアップ先）
    - **モデルB**: スプレッドシート正式原本モデル（ローカルDBは一時キャッシュ・同期待ち）
    - **モデルC**: クラウドDB正本モデル（端末とスプレッドシートはクライアント）
    - **モデルD【有力候補】**: ライフサイクル連動型ハイブリッドモデル（飛行中は現場端末が一次権威、同期・確認後はスプレッドシートが外部台帳・累計計算主体となり、手動補記や修正を相互に尊重する）
  - 正式な正本権威、競合解決、手動修正の反映ルールは、Phase B2（詳細設計）で詳細に検討・決定する。

### 2.13 地図・空域データの利用規約とオフライン条件の分離
- **訂正前**: 国土地理院タイルやDIDデータにより「地図API費用が完全0円で揃う」と一体化して断定。
- **確認された事実**:
  - 国土地理院タイル（標準地図・写真等）は規約に基づき無償利用可能だが、大量キャッシュのオフライン配布には利用規約の遵守が必要。
  - ドローン規制空域（空港周辺空域、緊急用務空域、進入表面等）の最新データは、地理院タイル単独では完結せず、国交省航空局の告示や外部データソースの統合が必要。
- **訂正後の方針**: 地図タイル表示と空域規制データソースを分離し、空域データの取得方式・キャッシュ可否はB2以降の技術課題として正確に整理する。

### 2.14 PWAのiPhone実用性制約の客観的整理
- **訂正前**: 「ホーム画面追加でネイティブと全く同様に動作する」という誇大表現。
- **訂正後の方針**:
  - iOSにおけるPWAの制約（Web Push通知のiOS要件、バックグラウンドでの長時間処理不可、画面ロック復帰時の再描画、カメラ・ファイルアクセス時のUIダイアログ挙動など）を明記し、本アプリの要件（現場手動打刻、地図操作、PDF出力）の範囲内であれば十分に実用的であるという条件付きの評価とする。

## 3. 最終訂正後の第一候補（推奨アーキテクチャ）の位置づけ

再監査・事実訂正の結果、**「PWA ＋ バックエンド境界（Cloudflare Workers等） ＋ ローカルファースト保存 ＋ Googleスプレッドシート等への外部連携」** という方向性は、依然として本プロジェクトに最も適した**「条件付き第一候補」**として維持します。

### 第一候補を維持する前提条件
1. **個人利用・1人運用**であり、ストア公開やApple Developer年会費の支払いを避けたいこと。
2. **Web地図エコシステム（MapLibre GL JS、GeoJSON等）**を活用して円・ポリゴン描画を迅速に構築したいこと。
3. **現場でのオフライン作業**（通信圏外での点検、離着陸記録、バッテリー交換）が必須であること。
4. 単一のTypeScriptコードベースにより、**AIアシスタントを活用した迅速・低コストな保守**を行いたいこと。

### 将来、第2候補（Capacitor等）へ見直すトリガー（条件崩れ）
- バックグラウンドでのGPS連続軌跡トラッキングが必須要件となった場合。
- 機体（ドローン本体）との直接的なBluetooth通信やローカルハードウェア連携が必要となった場合。
- オーナーが一般公開（App Store / Google Play）を望むようになった場合。
- iOSのSafari/PWA仕様が改変され、IndexedDBの永続性やオフライン運用が著しく制限された場合。
