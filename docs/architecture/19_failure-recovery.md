## 1. エラー分類と対応方針マトリクス

システム内で発生するあらゆるエラーを以下の10種に体系化し、ユーザー表示、自動再試行、手動復旧、データ保護方針を明確化します。

| エラー分類 | 主な発生契機 | ユーザーへの表示 | 自動再試行 | データ保護・回復手順 |
|---|---|---|:---:|---|
| **1. Validation Error** | 入力値不正（未来の日時、負の値等） | 「入力内容を確認してください: ○○」 | ✕ | フォームを維持し修正を促す |
| **2. Local Storage Error** | IndexedDB書込制限、容量不足 | 「端末の空き容量が不足しています」 | ◯ (1回) | メモリ内の未保存値を維持して未永続を明示。書込回復・可能な台帳同期を案内。全量退避形式はPENDING |
| **3. Network Error** | 通信圏外、電波断続 | 「通信が切断されました（オフライン継続）」 | ◯ (指数) | 同期キューへ投入し、現場業務は続行 |
| **4. Sync Error** | スプレッドシート書込失敗 | 「台帳同期が待機中です（未送信: N件）」 | ◯ (復帰時) | 永続化済みキューに保持（端末ストレージ自体の喪失は別リスク） |
| **5. DIPS Auth Error** | トークン期限切れ、認証情報無効 | 「DIPS認証の再確認が必要です」 | ✕ | 認証画面へ誘導。下書きデータは保持 |
| **6. DIPS API Error** | 登録記号不整合、4xx拒否 | 「DIPS通報エラー: [国交省からの理由]」 | ✕ | 計画修正UIへ戻す。計画データは保持 |
| **7. Spreadsheet Conflict**| 人間の手修正と端末データの競合 | 「台帳の手動修正と差分があります」 | ✕ | 差分比較ダイアログを表示し人間が選択 |
| **8. Permission Error** | GPS位置情報不許可、カメラ不許可 | 「設定から位置情報の利用を許可してください」 | ✕ | 既定値または地図上タップで代替入力 |
| **9. Data Corruption** | IndexedDBの破損、パースエラー | 「データの破損を検出しました。復旧可能な記録を確認します」 | ✕ | 破損レコードを隔離し、同期済みSheets台帳から復旧可能範囲を確認。未同期データの復元可否は未確定 |
| **10. Unsupported State** | バグ・予期せぬ状態遷移 | 「エラーが発生しました。直前の状態で復帰」 | ✕ | クラッシュ直前の安全状態へフォールバック |

## 2. 現場障害シナリオとフェイルセーフ設計

「どれか1つの外部サービスやブラウザ機能が壊れても、全体の現場記録を停止させない」フェイルセーフを設計します。

### 2.1 飛行中の端末強制終了・電池切れ・ブラウザ再読み込み

- **リスク**: 飛行時間計測が失われる。
- **フェイルセーフ**:
  - 離陸打刻時に「離陸時刻（タイムスタンプ）」をIndexedDBへ先行コミット。
  - アプリ再起動時、未着陸のフライトレコードを検出すると、自動的に「飛行中画面」を再構築し、離陸時刻からの経過時間を正確に再計算・表示。

### 2.2 完全電波圏外での現場運航

- **リスク**: サーバー依存による機能停止。
- **フェイルセーフ**:
  - DIPS通報やスプレッドシート同期が失敗しても、飛行前点検、離陸、着陸、バッテリー交換、飛行後点検のローカル記録は遮断されずに進行。

### 2.3 Cloudflare Workers / DIPS 2.0 の全面障害

- **リスク**: 外部API通信の完全停止。
- **フェイルセーフ**:
  - クライアントアプリはWorkersやDIPSがダウンしていても独立して起動可能。
  - 運航記録および飛行日誌PDFの出力はブラウザローカルで完結するため、国交省サーバー停止時でも日常業務の帳票作成は滞らない。

### 2.4 iOS WebKitのIndexedDBクリア（Storage Eviction）

- **リスク**: ローカルデータの喪失。
- **フェイルセーフ**:
  - Googleスプレッドシートに保存済みの台帳データを復旧対象とします。未同期データ・端末設定等を含む全量DB復旧を保証しません。
  - 未同期データは端末喪失により失われる可能性があります。ユーザー向け全量backup/restore形式は [ADR-0008](../decisions/ADR-0008-user-facing-export-and-recovery-boundaries.md) の `PENDING-LOCAL-RESTORE-01` です。KMLやPDFをDB復旧の代替とせず、JSON復旧UIをC1へ追加しません。

### 2.5 DIPS 2.0 API審査却下・利用不能・要件未達シナリオ（B2.2追加）

- **リスク**: 個人利用申請の却下、固定IP等ネットワーク条件の未達、審査長期化によるcredential未発行。
- **フェイルセーフ**:
  - **アプリ主要機能の非依存性**: DIPS APIの有無はアプリ主要機能完成・実運用のブロッカーとしません。
  - **手動フォールバックの第一級化**: `ManualDipsAdapter`（専用手動入力支援画面、1タップコピー、手動通報打刻、通報確認記録〔受付番号入力または一覧目視照合〕）により、APIなしでも現場スマホ1台で完結した飛行計画通報運用が成立。
  - **独立台帳による保全**: DIPS外部API通信を行わずとも、Googleスプレッドシート「DIPS飛行計画台帳」へ提出予定スナップショットが退避され、過去の計画・通報履歴が長期にわたり保全されます。
  - **将来のシームレス移行**: APIが後から承認された場合でも、内部FlightPlanや台帳のデータ構造を変更することなく、提出アダプターを `ApiDipsAdapter` に切り替えるだけで自動連携へ移行できます。

### 2.6 KML生成・Google Drive保存障害の完全隔離（Fault Isolation）

- **リスク**: KML生成エラーやGoogle Drive通信切断・容量超過・OAuth認証切れによる運航記録への波及。
- **フェイルセーフ**:
  - **障害の非波及**: KML Geo ExportおよびGoogle Drive保存は「派生出力」であり、正式な運航記録台帳（Google Sheets）およびローカル確定とは完全に分離されています。
  - **記録の保護**: Drive保存が失敗しても運航記録自体は正常完了として確定され、Driveアップロードジョブのみが `SyncQueue` の再試行キューに残ります。KML/Drive障害を理由に現場の離着陸や運航確定がブロックされることは絶対にありません。


## 3. 復旧手順と機構の正本

本書は障害時の表示・回復範囲・波及防止を定義します。ストレージ保護/SyncQueueは [14](14_offline-and-sync.md)、台帳の権威/手修正保護は [11](11_data-authority.md)、出力保存の独立性は [27](output/27_output-boundaries.md) が正本です。端末容量不足時のメモリ保持は永続化成功ではなく、アプリ終了前に保護できた範囲と未保存範囲を区別します。

DIPS通信の有無から法的な離陸可否を判断しません。現場の安全確認・通報要否・例外判断は [13 状態管理設計](state-machines/README.md)、PDF出力の事前キャッシュ条件は [18](18_reports.md) に従います。
