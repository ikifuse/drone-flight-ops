## 1. 本文書の位置づけと検証目的

### 1.1. 本文書の目的と責務境界
本文書は、2026-09-14にオーナー本人が国土交通省DIPS Web「飛行計画 新規作成」を操作し、最終通報を実行せずに確認した観測・推論・未確認事項を保持する証拠資料である。新アプリの正式要件は本書から移管し、以下を正本とする。観測日の事実を現在のDIPS全動作の保証へ拡張しない。

- [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md): Picker / checkbox / 構造化入力 / 確認操作の正式要件。
- [25a field catalog](dips-flight-plan/25a_field-catalog.md): 記録済API 1.9全88項目と一次資料の所在。
- [25d requirement validation](dips-flight-plan/25d_requirement-validation.md): 3軸要件・入力充足判定。
- [17 Geometry](17_map-and-airspace.md): 中立3図形の唯一の型定義。
- [12a Personnel / Actor / Pilot / Contact](domain-model/12a_organization-and-personnel.md): 関係者の概念分離。
- [25 overview](dips-flight-plan/25_overview.md): API非依存計画作成と通報入力支援原則。
- [25e](dips-flight-plan/25e_common-source-and-submission-boundaries.md): 本書の観測から共通の源・Manual／API・DIPS対象外の境界を採用した因果と却下案。

### 1.2. 証拠レベルの定義（Evidence Level）
実画面で確認した事実と、推測・未確認事項を明確に区別するため、本文書内の各事項に以下の証拠レベルを付与します：

- **`OBSERVED`**: 2026-09-14にオーナーがDIPS 2.0 Web実画面で直接操作・目視確認した客観的事実。
- **`OFFICIAL_SPEC`**: 国土交通省航空局の公式マニュアル、APIガイドライン、通報要領等の一次資料に明記されている仕様。
- **`INFERRED`**: 実画面の表示・挙動から技術的に蓋然性が極めて高いが、DIPS内部コードや一次資料で完全確定していない推定事項。
- **`PENDING`**: 今回の実画面操作では確認できなかった、またはアカウント条件により検証が保留されている未確認事項。

## 2. 実画面検証記録（OBSERVED & INFERRED）

### 2.1. 機体情報選択（OBSERVED）
- **実画面挙動**:
  - メイン画面の「機体情報」を開くと、DIPSに登録済みの機体一覧がポップアップ表示された。
  - 表示項目: **登録記号、型式・名称、製造者名、第一種機体認証、第二種機体認証**。
  - 操縦者は一覧のチェックボックスで機体を選択し、ポップアップ内の「登録」ボタンを押下することで、今回の飛行計画へ機体情報が反映される。
  - メイン画面側では機体詳細を常時展開せず、`✓ 機体情報` のように設定完了ステータスが表示された。
- **設計反映先**: [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md)（採用要件）。

### 2.2. 操縦者情報選択（OBSERVED）
- **実画面挙動**:
  - 「操縦者情報」も機体と同様に、登録済み操縦者一覧からチェックボックスで選択する方式。
  - 表示項目: **操縦者氏名、機体情報（紐付け）、一等技能証明、二等技能証明**。
  - 選択後はメイン画面で `✓ 操縦者情報` と表示される。
  - 氏名・電話番号・メールアドレス・国家資格番号等をこの画面で毎回手入力する構造ではない。
- **設計反映先**: [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md)（採用要件）。

### 2.3. 飛行目的（OBSERVED）
- **実画面挙動**:
  - チェックボックスによる複数選択UI。
  - 大分類として **「業務」** と **「業務以外」** に分かれている。
  - **業務の選択肢**: 空撮、報道取材、警備、農林水産業、測量、環境調査、設備メンテナンス、インフラ点検・保守、資材管理、輸送・宅配、自然観測、事故・災害対応、その他。
  - **業務以外の選択肢**: 趣味、研究開発、その他。
  - 「その他」を選択した場合のみ、理由を記入するテキスト入力欄が出現する。
- **設計反映先**: [25b](dips-flight-plan/25b_manual-web-mapping.md)の内部目的再利用と[25c](dips-flight-plan/25c_api-payload-mapping.md)のコード変換。

### 2.4. 飛行空域（OBSERVED & PENDING）
- **実画面挙動**:
  - チェックボックスによる選択UI。
  - 選択肢:
    1. **空港等周辺**
    2. **地表・水面から150m以上**
    3. **人・家屋の密集地域の上空（DID）**
    4. **上記空域の飛行は行わない**
  - 「飛行目的」と「飛行空域」は完全に直交した独立入力軸であり、例えば「趣味＋DID」のような組み合わせも正常に成立する。
- **緊急用務空域の扱い（OBSERVED / 責務分離）**:
  - 今回のDIPS Web「飛行空域」ポップアップの選択肢内には、「緊急用務空域」の選択肢は存在しなかった。
  - **設計反映先**: 空域申告と飛行直前確認の責務分離は[17 §5](17_map-and-airspace.md#5-緊急用務空域の責務分離flightplan通報-vs-飛行前現場確認)を正本とする。観測した選択肢の不在だけから法的取扱いや他画面の仕様を確定しない。

### 2.5. 飛行方法（OBSERVED）
- **実画面挙動**:
  - 複数選択チェックボックス式。
  - 選択肢:
    1. **夜間飛行**
    2. **目視外飛行**
    3. **人又は物件から30m未満**
    4. **催し場所上空**
    5. **危険物輸送**
    6. **物件投下**
    7. **上記方法の飛行は行わない**
  - 飛行空域と合わせて、特定飛行該当性判定の主要入力となる。

### 2.6. カテゴリーおよび立入管理措置（OBSERVED / INFERRED）
- **実画面構成**:
  - メイン画面上に「立入管理措置」「係留飛行」「カテゴリー」の項目枠が存在する。
  - 選択された空域、方法、立入管理措置等の組み合わせにより、飛行カテゴリー（カテゴリーI / II / III等）が連動・判定される構造が確認された。
  - ただし、画面操作のみからカテゴリー判定アルゴリズムの全容を逆算して独自実装することは行わず、国土交通省の公式制度定義を正本とする。また、カテゴリーIIだからといって補助者を機械的に必須と決めつけるロジックは採用しない。

### 2.7. 飛行経路・飛行範囲の作図ツール（OBSERVED）
- **実画面挙動**:
  - DIPS Web地図上で、以下の3種類の図形作成ツールが直接操作可能であることを確認した：
    1. **POLYGON（多角形）**: 頂点を画面上で順次指定して囲み範囲を作成。
    2. **CIRCLE（円形）**: 中心点を指定し、半径（m）を設定して円形範囲を作成。
    3. **BUFFERED_LINE（バッファライン/線形）**: 経路（線分）を描画し、幅/半径値を設定して帯状の範囲を作成。
  - 各図形について、**作成・頂点編集・削除・パラメータ（半径/幅）の微調整**が地図上で視覚的に可能。
- **内部保存形式の非断定（INFERRED / PENDING）**:
  - Web画面上で3図形が描画できたからといって、DIPS内部でGeoJSONをそのまま保存しているとは断定しない。API 1.9仕様上はPolygonとCircleの座標データが受け入れ仕様として定義されており、`BUFFERED_LINE` のAPI送信仕様は引き続き未確認（`MANUAL_ONLY` 扱いを継続）。

### 2.8. 地図背景とライセンス表示（OBSERVED）
- **実画面挙動**:
  - DIPS Webの地図右下に **`© 国土地理院`** の著作権クレジット表示が確認された。
  - 確認された事実は著作権クレジットの表示である。具体的なタイル取得先や内部実装は画面表示だけでは確定できず、国土地理院由来BaseLayerという解釈は `INFERRED` として扱う。
- **設計反映先**: BaseLayer候補・規約と出典表示・規制空域レイヤーとの分離は[17 Map / Airspace](17_map-and-airspace.md)に移管済み。観測事実は上記クレジット表示に限定する。

### 2.9. 飛行計画名称（OBSERVED / INFERRED / PENDING）
- **実画面挙動**:
  - 新規作成画面を開いた際、計画名称欄に `FlightPlan-202609142250` のような名称が自動初期セットされていた。
  - 画面を開いた時刻と分単位まで一致しており、画面滞在中に自動でリアルタイム更新はされなかった。
  - 形式としては `FlightPlan-yyyyMMddHHmm` の自動採番である可能性が高い（`INFERRED`）。
  - ただし、編集可否、重複時の挙動、保存時のリネーム規則は未確認（`PENDING`）。アプリのUUID主キー・編集可能名称の設計は[12d](domain-model/12d_flight-plan-and-dips.md)を参照する。

### 2.10. 飛行許可・承認書番号選択（OBSERVED）
- **実画面挙動**:
  - 許可番号入力欄のポップアップにおいて、DIPS側に登録されている許可情報一覧から選択するUIが存在。
  - 表示項目: **許可番号、許可書発行日、許可等の期間（自・至）、カテゴリー**。
- **設計反映先**: [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md)（採用要件）。

### 2.11. 保険情報入力（OBSERVED）
- **実画面挙動**:
  - 保険会社名、商品名、対人賠償、対物賠償、賠償能力（加入有無）の入力・選択欄が確認された。
- **設計反映先**: [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md)（採用要件）。

### 2.12. 定期・複数日指定（OBSERVED / PENDING）
- **実画面挙動**:

- **設計反映先**: [25b Manual Web mapping](dips-flight-plan/25b_manual-web-mapping.md)（採用要件）。

### 2.13. 連絡先選択と関係者分離（OBSERVED）

## 3. 正式要件への移管と証拠との区別

旧§3のAPI非依存計画作成・業務価値は[25 overview](dips-flight-plan/25_overview.md)、旧§4のGeometry型/Exporter境界は[17](17_map-and-airspace.md)、旧§5の関係者分離は[12a](domain-model/12a_organization-and-personnel.md)へ移管した。旧§4の `kind` / tuple / `buffer_width_meters` と17の `type` / LatLngPoint / `buffer_radius_meters` が食い違っていたため、型を17に一本化した。観測からDIPS内部保存形式や幅パラメータの厳密な意味を推定しない。

委任・代理通報がどの範囲で認められるかは未確認であり、関係者を分離保持するアプリ設計だけで代理権限が成立するものではない（PENDING-WEB-10）。

## 4. 実画面検証における保留・未確認事項（PENDING一覧）

今後の実機・実画面検証および国交省資料の調査により確定させる保留事項を以下に整理します。Step 7aの作図操作の未回収と証拠の再確認は§1.3（PENDING-S7A-DRAW-OPERATION／VERIFY-S7A-EVIDENCE）に置き、以下のPENDING-WEB-*を置換しません：

1. **`PENDING-WEB-01: 飛行計画自動名称の正確な生成規則`**:
   - `FlightPlan-yyyyMMddHHmm` の自動採番ルール、編集可否、重複時の挙動。
2. **`PENDING-WEB-02: 許可承認書選択時の各項目自動反映範囲`**:
   - 許可番号選択後、許可年月日・有効期間・飛行マニュアル区分・付加条件がどの程度自動反映されるか。
3. **`PENDING-WEB-03: 複数操縦者選択時のWeb UIの実画面動作`**:
   - 複数操縦者を選択した際、緊急連絡先フラグや代表操縦者の扱いがどのようにUI上展開されるか。
4. **`PENDING-WEB-04: 定期・複数日指定の詳細ルール`**:
   - 複数日選択時の開始・終了時刻の個別設定可否、通報IDが単一か日別か、取消・変更の単位。
5. **`PENDING-WEB-05: BUFFERED_LINE の DIPS API 表現`**:
   - DIPS Webで描画したバッファラインがAPI側でどのように表現・受付されるか（またはWeb専用機能か）。
6. **`PENDING-WEB-06: DIPS Web 内部の Geometry 保存形式`**:
   - DIPSサーバー側で保持されている座標データの内部フォーマット。
7. **`PENDING-WEB-07: 保存済み飛行経路の再利用方法`**:
   - 過去に通報した飛行計画のGeometryをWeb画面上で複製・再呼出できる導線の有無。
8. **`PENDING-WEB-08: 最終通報実行時の Validation Message`**:
   - 必須漏れや空域重複時のDIPS画面エラー表示メッセージの文言・形式。
9. **`PENDING-WEB-09: カテゴリー自動判定の詳細アルゴリズム`**:
   - 実画面上で立入管理措置や機体認証区分がどの組み合わせでカテゴリーI/II/IIIを確定させるか。
10. **`PENDING-WEB-10: 代理・委任通報の具体的なDIPS権限境界`**:
    - アカウント主と異なる操縦者を登録して通報する場合のDIPS側事前登録手続き。
11. **`PENDING-WEB-11: 規制空域各レイヤーの実データ提供元`**:
    - DIPS地図に重なるDID、空港等周辺空域等の更新頻度および一次データソースの仕様。

## 5. 旧25から継承した未確認事項

識別子の追跡性を保つため、旧25の `PENDING-01〜05` は `PENDING-WEB-*` へ再採番せず保持する。

1. **`PENDING-01: 機体選択時の重量自動反映挙動`**:
   - DIPS Web画面で登録済み機体を選択した際、最大離陸重量（No.26）にDRS登録自重が自動セットされるか、空欄で毎回入力が求められるか。
2. **`PENDING-02: バッファラインの保存・再編集可否`**:
