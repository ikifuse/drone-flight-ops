## 1. 本文書の位置づけと検証目的

### 1.1 本文書の目的と責務境界
本文書は、2026-09-14にオーナー本人が国土交通省「ドローン情報基盤システム（DIPS 2.0）」Webポータルの「飛行計画 新規作成」実画面を操作し、最終通報（確定提出）を実行せずに確認した**実画面挙動の観測記録、およびそれを反映した新アプリの「API非依存 飛行計画作成（API-independent Flight Planning）」の設計仕様**をまとめた文書です。

- `25_dips-flight-plan-field-mapping.md`: DIPS公式API 1.9 No.1〜88のリクエスト項目、型、3軸要件判定エンジン（`DipsFieldRequirementEngine`）の正本。
- `26_dips-web-ui-verification.md`（本文書）: **実際のWeb UI操作を通じて観測された画面遷移、入力Picker、作図ツール、および実画面とAPI仕様の差異・未確認事項の正本**。
- `17_map-and-airspace.md`: 地図背景、空域規制レイヤー、およびFlightAreaジオメトリモデルの設計書。
- `24_b2.2-dips-manual-fallback-and-ledger.md`: API未承認・オフライン時における手動通報入力支援およびGoogleスプレッドシート台帳連携の設計書。

### 1.2 証拠レベルの定義（Evidence Level）
実画面で確認した事実と、推測・未確認事項を明確に区別するため、本文書内の各事項に以下の証拠レベルを付与します：

- **`OBSERVED`**: 2026-09-14にオーナーがDIPS 2.0 Web実画面で直接操作・目視確認した客観的事実。
- **`OFFICIAL_SPEC`**: 国土交通省航空局の公式マニュアル、APIガイドライン、通報要領等の一次資料に明記されている仕様。
- **`INFERRED`**: 実画面の表示・挙動から技術的に蓋然性が極めて高いが、DIPS内部コードや一次資料で完全確定していない推定事項。
- **`PENDING`**: 今回の実画面操作では確認できなかった、またはアカウント条件により検証が保留されている未確認事項。

## 2. 実画面検証記録（OBSERVED & INFERRED）

### 2.1 機体情報選択（OBSERVED）
- **実画面挙動**:
  - メイン画面の「機体情報」を開くと、DIPSに登録済みの機体一覧がポップアップ表示された。
  - 表示項目: **登録記号、型式・名称、製造者名、第一種機体認証、第二種機体認証**。
  - 操縦者は一覧のチェックボックスで機体を選択し、ポップアップ内の「登録」ボタンを押下することで、今回の飛行計画へ機体情報が反映される。
  - メイン画面側では機体詳細を常時展開せず、`✓ 機体情報` のように設定完了ステータスが表示された。
- **設計への反映**:
  - アプリ内の計画作成画面に `Aircraft Picker` を配置。
  - 毎回、登録記号・メーカー・型式を手入力させるのではなく、登録済み機体台帳から1タップ選択で `FlightPlan.aircraft_ids` へ紐付ける（複数機体対応）。

### 2.2 操縦者情報選択（OBSERVED）
- **実画面挙動**:
  - 「操縦者情報」も機体と同様に、登録済み操縦者一覧からチェックボックスで選択する方式。
  - 表示項目: **操縦者氏名、機体情報（紐付け）、一等技能証明、二等技能証明**。
  - 選択後はメイン画面で `✓ 操縦者情報` と表示される。
  - 氏名・電話番号・メールアドレス・国家資格番号等をこの画面で毎回手入力する構造ではない。
- **設計への反映**:
  - アプリ内に `Personnel Picker` を配置。
  - 人員マスター（`Personnel`）から操縦者を選択し、`FlightPlan.pilot_ids` へ反映。電話番号やメールはマスターから自動補完する（`Input Responsibility = MASTER`）。

### 2.3 飛行目的（OBSERVED）
- **実画面挙動**:
  - チェックボックスによる複数選択UI。
  - 大分類として **「業務」** と **「業務以外」** に分かれている。
  - **業務の選択肢**: 空撮、報道取材、警備、農林水産業、測量、環境調査、設備メンテナンス、インフラ点検・保守、資材管理、輸送・宅配、自然観測、事故・災害対応、その他。
  - **業務以外の選択肢**: 趣味、研究開発、その他。
  - 「その他」を選択した場合のみ、理由を記入するテキスト入力欄が出現する。
- **内部目的（InternalFlightPurpose）とDIPS目的コードの分離**:
  - DIPS公式の目的コード体系（1〜16）とは別に、ユーザーの実業務に即した分かりやすい内部目的（例: 「操縦練習」「国家資格練習」「趣味空撮」「観光PR撮影」「不動産撮影」「工事進捗撮影」「屋根・外壁確認」「測量」「災害確認」「研究・検証」等）を扱えるよう、`InternalFlightPurpose` → `DipsPurposeMapper` → `DIPS official purpose codes[]` の変換マッピング構造を確保する。

### 2.4 飛行空域（OBSERVED & PENDING）
- **実画面挙動**:
  - チェックボックスによる選択UI。
  - 選択肢:
    1. **空港等周辺**
    2. **地表・水面から150m以上**
    3. **人・家屋の密集地域の上空（DID）**
    4. **上記空域の飛行は行わない**
  - 「飛行目的」と「飛行空域」は完全に直交した独立入力軸であり、例えば「趣味＋DID」のような組み合わせも正常に成立する。
- **緊急用務空域の扱い（OBSERVED / 責務分離）**:
  - 今回のDIPS Web「飛行空域」ポップアップの選択肢内には、「緊急用務空域」の選択肢は存在しなかった。
  - したがって、**「飛行計画通報における空域申告」と「飛行当日の緊急用務空域の事前確認」を同一UIに混同せず、別個の安全点検責務として扱う**（17番の空域レイヤーおよび飛行前確認項目として独立管理）。

### 2.5 飛行方法（OBSERVED）
- **実画面挙動**:
  - 複数選択チェックボックス式。
  - 選択肢:
    1. **夜間飛行**
    2. **目視外飛行**
    3. **人又は物件から30m未満**
    4. **催し場所上空**
    5. **危険物輸送**
    6. **物件投下**
    7. **上記方法の飛行は行わない**
  - 飛行空域と合わせて、特定飛行該当性判定の主要入力となる。

### 2.6 カテゴリーおよび立入管理措置（OBSERVED / INFERRED）
- **実画面構成**:
  - メイン画面上に「立入管理措置」「係留飛行」「カテゴリー」の項目枠が存在する。
  - 選択された空域、方法、立入管理措置等の組み合わせにより、飛行カテゴリー（カテゴリーI / II / III等）が連動・判定される構造が確認された。
  - ただし、画面操作のみからカテゴリー判定アルゴリズムの全容を逆算して独自実装することは行わず、国土交通省の公式制度定義を正本とする。また、カテゴリーIIだからといって補助者を機械的に必須と決めつけるロジックは採用しない。

### 2.7 飛行経路・飛行範囲の作図ツール（OBSERVED）
- **実画面挙動**:
  - DIPS Web地図上で、以下の3種類の図形作成ツールが直接操作可能であることを確認した：
    1. **POLYGON（多角形）**: 頂点を画面上で順次指定して囲み範囲を作成。
    2. **CIRCLE（円形）**: 中心点を指定し、半径（m）を設定して円形範囲を作成。
    3. **BUFFERED_LINE（バッファライン/線形）**: 経路（線分）を描画し、幅/半径値を設定して帯状の範囲を作成。
  - 各図形について、**作成・頂点編集・削除・パラメータ（半径/幅）の微調整**が地図上で視覚的に可能。
- **内部保存形式の非断定（INFERRED / PENDING）**:
  - Web画面上で3図形が描画できたからといって、DIPS内部でGeoJSONをそのまま保存しているとは断定しない。API 1.9仕様上はPolygonとCircleの座標データが受け入れ仕様として定義されており、`BUFFERED_LINE` のAPI送信仕様は引き続き未確認（`MANUAL_ONLY` 扱いを継続）。

### 2.8 地図背景とライセンス表示（OBSERVED）
- **実画面挙動**:
  - DIPS Webの地図右下に **`© 国土地理院`** の著作権クレジット表示が確認された。
  - これにより、国交省DIPS本番環境のBaseLayerとして国土地理院タイルが採用されている事実が確認された。
- **新アプリへの反映**:
  - 新アプリでも、国土地理院タイルを最有力なBaseLayer候補として採用する（規約準拠・出典明記）。
  - **航空法規制空域レイヤー（DID、空港周辺等）はBaseLayerとは出所・更新周期が異なるため、レイヤーとして分離管理**する（17番設計準拠）。

### 2.9 飛行計画名称（OBSERVED / INFERRED / PENDING）
- **実画面挙動**:
  - 新規作成画面を開いた際、計画名称欄に `FlightPlan-202609142250` のような名称が自動初期セットされていた。
  - 画面を開いた時刻と分単位まで一致しており、画面滞在中に自動でリアルタイム更新はされなかった。
  - 形式としては `FlightPlan-yyyyMMddHHmm` の自動採番である可能性が高い（`INFERRED`）。
  - ただし、編集可否、重複時の挙動、保存時のリネーム規則は未確認（`PENDING`）。新アプリではUUID v4を内部主キーとし、名称はユーザー編集可能とする。

### 2.10 飛行許可・承認書番号選択（OBSERVED）
- **実画面挙動**:
  - 許可番号入力欄のポップアップにおいて、DIPS側に登録されている許可情報一覧から選択するUIが存在。
  - 表示項目: **許可番号、許可書発行日、許可等の期間（自・至）、カテゴリー**。
- **設計への反映**:
  - 新アプリの `Permission` マスターの属性定義と完全に一致。台帳から1タップで引き当て可能とする。

### 2.11 保険情報入力（OBSERVED）
- **実画面挙動**:
  - 保険会社名、商品名、対人賠償、対物賠償、賠償能力（加入有無）の入力・選択欄が確認された。
- **設計への反映**:
  - 新アプリの新設マスター `InsurancePolicy`（保険台帳）から1タップで初期ロードし、計画ごとにOverride可能とする。

### 2.12 定期・複数日指定（OBSERVED / PENDING）
- **実画面挙動**:
  - 日時設定において「定期・複数日指定」のチェックボックスおよびカレンダーUIが存在し、1つの飛行計画に対して複数日を指定できる画面構造が確認された。
- **設計への反映**:
  - 飛行計画（`FlightPlan`）を「必ず単一の1日のみ」に固定せず、将来的に複数日や繰り返し予定（`planned_occurrences[]` 等）を保持できる拡張性をスキーマ設計で確保する。

### 2.13 連絡先選択と関係者分離（OBSERVED）
- **実画面挙動**:
  - 緊急連絡先として「自アカウントの情報」「申請書記載の情報」「操縦者」等から情報源を選択できるUIが存在した。操縦者を選んだ場合はプルダウンで人物を選択可能。
- **設計への反映**:
  - **「ログインアカウント」「操縦者」「緊急連絡先」を同一人物に決めつけず分離**する（`SubmissionActor`, `Pilot`, `ContactPerson` の概念分離）。

### 2.14 画面上の青いインフォメーションアイコン（OBSERVED）
- 各入力欄の横に配置されている青い丸に白文字の `i` アイコンについて、**「必須マーク」と断定せず、単なる項目説明・ヘルプアイコンとして扱う**。必須判定は公式API仕様および通報要領に基づく `DipsFieldRequirementEngine` を正本とする。

## 3. API非依存 飛行計画作成（API-independent Flight Planning）

今回の実画面検証により、DIPSにおける飛行計画作成の本質は「構造化されたフォーム入力」と「地図上のGeometry作図」であることが実証されました。  
したがって、**新アプリは国交省DIPS APIの取得承認の有無に一切依存せず、完全な飛行計画作成・管理ツールとして自律完結する設計**を正式に採用します。

```text
┌────────────────────────────────────────────────────────────────────────┐
│ [API非依存 飛行計画作成 Core Engine]                                   │
│  - 機体選択 (Aircraft Picker)                                          │
│  - 操縦者選択 (Personnel Picker)                                       │
│  - 目的選択 (Purpose Picker: 内部目的 ⇄ DIPS公式コード変換)             │
│  - 空域・方法選択 (Airspace & Method Picker)                            │
│  - 許可承認・保険選択 (Permission & Insurance Picker)                  │
│  - 飛行範囲作図 (Flight Area Editor: Polygon / Circle / Buffered Line)  │
│  - 安全確保措置・スケジュール・連絡先設定                              │
│  - 3軸要件判定 & Readiness 集計 (DipsFieldRequirementEngine)          │
│  - 提出不変スナップショット生成 (DipsSubmission / submission_snapshot)   │
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
         ┌──────────────────────────┴──────────────────────────┐
         ▼ (API未取得・オフライン時)                           ▼ (将来API認可時)
┌──────────────────────────────────────┐     ┌──────────────────────────────────────┐
│ 手動通報支援 (Manual Support)        │     │ API自動通報 (Optional API Adapter)   │
│  - DipsManualEntryViewModel          │     │  - DIPS FPR API (POST)               │
│  - 項目別1タップコピー               │     │  - 受付番号・計画ID自動受領          │
│  - DIPS Web画面順レイアウト          │     │  - クラウドプロキシ経由              │
│  - 操縦者による手動通報打刻・確認    │     │                                      │
└──────────────────────────────────────┘     └──────────────────────────────────────┘
```

### 3.1 アプリ単体で完結する提供価値
国交省からAPI接続が承認されない場合や、個人利用でAPIが開放されない場合であっても、新アプリは以下の業務価値を完全に提供します：
1. **計画の事前作成・蓄積**: 電波のある場所やオフィスで事前に飛行計画を策定し、安全チェックを完了できる。
2. **手動入力の劇的省力化**: DIPS Web画面の配置順に整理されたコピー支援画面により、現場での手動通報にかかる時間を最小化。
3. **現場運航との完全バインド**: 作成した計画データ（機体、操縦者、高度、範囲、保険、許可等）がそのまま飛行前点検、離着陸記録、飛行後点検、バッテリー台帳、および飛行日誌（様式1〜3）へ自動引き継がれる。
4. **外部台帳二重化**: DIPS側の保存期間（3ヶ月等）に依存せず、自社のGoogleスプレッドシート「DIPS飛行計画台帳」へ全履歴を永続保管。

## 4. FlightAreaGeometry 中立的ドメインモデル設計

飛行範囲（Geometry）の内部表現をDIPS APIの固有JSONに固定せず、中立的な `FlightAreaGeometry` として定義します。

### 4.1 形状モデル構造
```typescript
export type GeometryKind = 'POLYGON' | 'CIRCLE' | 'BUFFERED_LINE';

export interface FlightAreaGeometry {
  kind: GeometryKind;
  
  // POLYGON 時: 外周頂点列 (経度, 緯度)
  polygon_points?: [number, number][];
  
  // CIRCLE 時: 中心座標 (経度, 緯度) と 半径 (m)
  center_point?: [number, number];
  radius_meters?: number;
  
  // BUFFERED_LINE 時: 経路線分頂点列 と バッファ幅 (m)
  path_points?: [number, number][];
  buffer_width_meters?: number;
  
  // 共通属性
  altitude_agl_meters: number;       // 対地高度 (m)
  altitude_msl_meters?: number;      // 海抜高度 (m)
  calculated_area_sqm?: number;      // 面積 (㎡)
}
```

### 4.2 将来Exporter / Adapter の拡張ポート
`FlightAreaGeometry` を中立モデルとして保持することにより、将来的に以下の形式への変換（Exporter / Adapter）を既存ドメインを破壊することなく安全に追加可能な構造とします（詳細は [27_output-kml-drive-and-mymaps.md](27_output-kml-drive-and-mymaps.md) 参照）：
- **`KmlExporter`**: ユーザー向けGeo Exportの第一形式。Google My Maps や Google Earth での視覚的確認・共有用 KML 変換、Google Drive自動保存（詳細は27番にて確定）。
- **`MapRenderingAdapter (GeoJSON)`**: 地図描画ライブラリ（MapLibre GL JS等）が要求する場合のみ内部利用するアダプター。ユーザー向け標準エクスポート形式とは扱わない。
- **`DipsApiPayloadAdapter`**: Phase C7 Optional において、API 1.9仕様に適合する内部通信用JSON（Polygon / Circle）への変換。ユーザー非公開。
- **※GPX / CSV**: GPX等は機体実飛行ログ（AircraftFlightLog）取込側の入力候補であり、CSVは台帳側の用途として扱う。これらはKMLと同格のユーザー向けGeo Export完成要件としない。

## 5. 業務利用における関係者の責務分離（SubmissionActor / Pilot / Contact）

法人・組織でのドローン運航管理を想定し、以下の関係者ロールを概念上明確に分離します：

```text
┌─────────────────────────────────────────────────────────────┐
│ [運航管理・事務担当] SubmissionActor (アプリアカウント/操作者) │
│  - オフィスのPCやスマホで飛行計画を作成・DIPS通報手続きを実行 │
└──────────────────────────────┬──────────────────────────────┘
                               │ 計画にアサイン
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [現場パイロット] Pilot / Personnel (実運航操縦者)            │
│  - 現場で機体を操縦し、飛行前点検・離着陸打刻を実施          │
└──────────────────────────────┬──────────────────────────────┘
                               │ 連絡先として指定
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ [緊急時連絡窓口] EmergencyContactPerson (連絡先)             │
│  - 飛行中に近隣住民や関係機関からの連絡を受ける電話・メール   │
│  - 操縦者自身、運航管理者、または許可申請書記載窓口から選択 │
└─────────────────────────────────────────────────────────────┘
```

- **委任・代理通報に関する留意事項**:
  - DIPS Web画面において操縦者と連絡先が分離選択可能であることは `OBSERVED` ですが、「第三者による代理通報が法的にどの範囲で認められているか」は、国土交通省のDIPS利用規約および行政手続き法令に基づく確認を要します。
  - アプリ設計としては、属性を分離して保持できる柔軟なスキーマを用意し、法的な委任関係の成立可否は運用主体の責任において設定するものとします。
