# ADR-0026: 共有データは各環境のDrive／Sheetsを正本とし、正本確認を重要な時点で行い、確定処理を三つの時点に分ける

## 1. 背景と課題（Context）

現場での高速な表示・オフライン耐性と、複数端末での共有を両立する必要がある。ADR-0002は、現場運航中は端末が一次権威、外部同期後はSheetsが確定台帳と決めたが、共有のマスターや飛行リストを、いつ正本と照らし、cacheをどう扱うかは決めていなかった。飛行リストは、別の端末や事務担当者の別のPCから新しい計画が追加され得る。

## 2. 検討した選択肢（Options Considered）

- A. 端末の古いcacheだけを一覧の正本として扱う。
- B. 毎画面・毎選択で、Sheets全体を読み直す。
- C. マスターのcacheを、固定TTLだけで機械的に捨てる。
- D. 重要な時点で正本を確認し、変更のある台帳だけを再取得する。cacheがあれば先に端末内のデータを表示し、online時に裏で正本を確認する。
- E. 通常の飛行操作を都度外部へ送る（旧アプリが採らなかった方式）。

## 3. 決定内容（Decision）

Dを現在ベースライン（CURRENT-ACCEPTED）として38aに記録し、確定処理の時点分離を38bに記録する。

- 各運用環境のGoogle Drive／Sheetsを共有の正式な正本とし、端末cacheは高速表示とoffline時の一時保持の複製とする。現場で作成中の下書きと未同期の確定データはcacheではなく、ADR-0002・11のライフサイクル権威に従う。
- 一般のマスターcacheを固定TTLだけで捨てない。飛行リストは業務状態に基づいて整理する。
- 正本の確認は、起動・環境切替・［新規飛行］開始・［飛行リスト］表示・飛行前点検開始等の重要な時点で行い、変更のある台帳だけを再取得する。offlineでは最後に取得済みのcacheを参照できるが最新とは断定しない。
- 確定処理は、計画確定時、飛行中の逐次保存、飛行後点検後の最終送信の三つの時点に分ける。Sheets・KMLの再同期とDIPSの再試行は別系統とする。

## 4. 採用理由と他案の却下理由（Rationale）

Aは、複数端末・複数人の運用で、別の端末から追加された計画を見落とすため採らない。Bは、毎画面・毎選択でSheets全体を読み直す方式にしないと99.2が明示している。Cは、マスターを固定TTLだけで機械的に捨てないと99.2が明示している。Eは、旧アプリが採らなかった方式で、通信の待ちや失敗を通常の現場操作へ持ち込まない運用資産（35d）に反する。

## 5. メリット（Pros）

- 現場では端末内のデータを即時に表示でき、online時に正本と照合できる。
- 複数端末・複数人で、古いcacheのまま新しい計画を見落とすことを減らせる。
- 確定処理を別の時点に分けることで、通信の状態が現場の記録を止めない。

## 6. デメリット・トレードオフ（Cons / Trade-offs）

- cacheの具体的な実装、retryの回数・間隔、競合の解決方針、backgroundの挙動、UI表示は未確定（PENDING-S7E-CACHE-DETAIL）。iPhoneとAndroidの実機差は未確認（VERIFY-S7E-DEVICE-DIFF）。
- 中央のSyncQueue・監査を恒久的に残すかは未確定（PENDING-S7E-SYNCQUEUE-AUDIT）。
- A4の採番の競合は、特殊な同時競合専用の高度な対策を採らない既存の判断（35c §3.3）を変えない。

## 7. 将来この決定を見直す条件（Re-evaluation Triggers）

- 実機で、cacheの整合や表示が運用に合わないと確認された場合。
- 共有リストの反映の遅れが現場の運用を妨げると確認された場合。
- 三つの時点の分け方が、現場の操作や復旧に合わないと確認された場合。

本ADRは実装開始・Drive操作の許可ではない。
