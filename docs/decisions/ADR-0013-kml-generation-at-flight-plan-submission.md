# ADR-0013: 飛行計画通報時におけるKML確定生成および未同期再送方式の採用

- **作成日**: 2026-09-18
- **ステータス**: **提案中（Proposed）**
- **決定者**: 検討中（99.2設計検討正本反映 / オーナー最終監査待ち）
- **関連設計**: [27a KML出力](../architecture/output/27a_kml-export.md)、[27 出力境界](../architecture/output/27_output-boundaries.md)、[14 オフライン・同期](../architecture/14_offline-and-sync.md)
- **関連ADR**: [ADR-0008](ADR-0008-user-facing-export-and-recovery-boundaries.md)

## 1. 背景と課題（Context）

本システムでは、DIPS飛行計画通報で作成・使用した飛行範囲・空域（共通Geometry）を、Google My MapsやGoogle Earth等で手軽に可視化・共有するための派生物としてKMLファイルを生成します。
従来の設計文書（旧27番等）では、「KMLは飛行完了後に、飛行実績ログや点検結果等を含めて生成する」という方針が一部に残っていました。
しかし、KMLの本来の目的は「事前に計画・通報した飛行範囲を地図で確認・共有すること」であり、事後の飛行実績や点検記録、行政側の受付番号等の証跡までKMLに詰め込むと、個人情報や運航機微情報が地図共有経由で不用意に漏洩するリスクが生じます。また、飛行計画を通報した直後にMy Maps等へインポートして現場確認したいという運用ニーズを満たせません。

## 2. 検討した選択肢（Options Considered）

- **選択肢A: 全運航完了後のKML生成・実績包括方式（旧27番案）**
  全フライト・点検が終了した後に、離着陸実績や点検結果も含めてKMLを生成する案。通報時点での事前地図確認ができず、KMLに事後実績情報が混在する。
- **選択肢B: 飛行計画通報時における確定生成と未同期再送方式（推奨案）**
  KMLは「飛行計画通報時」に、その通報内容（`submission_snapshot` + 共通Geometry）を元に確定生成し、事後実績は含めない。外部保存に失敗した場合は端末に未同期KMLとして保持し、飛行後点検後の最後の確定送信時に再試行する方式。

## 3. 決定内容（Decision）

選択肢Bを Proposed として起票します。

1. **KML生成タイミングと内容の確定**:
   - KMLは、飛行計画通報時に生成する。
   - 内容は `submission_snapshot` に確定した通報項目および共通Geometryとし、飛行前・後点検、離着陸実績、BAT実績等の事後データや行政受付証跡は含めない。
2. **通報内容確定境界の維持**:
   - KMLは運航記録の正本ではなく、地理的可視化・交換用の派生物として位置づける。
3. **未同期KMLの再送ライフサイクル**:
   - 通報時に通信断やGoogle Drive障害等でKMLの外部保存のみが失敗した場合でも、実飛行は停止させず、DIPSの再通報も行わない。
   - KMLは端末内に「未同期KML」として保持され、飛行後点検完了後に操縦者が行う「最後の確定送信」において、A4運航記録やバッテリー履歴等の外部保存処理と合わせて再送を試行する。

## 4. メリット（Pros）

- 計画通報の直後からGoogle My Maps等へのインポートが可能となり、現場での空域確認に活用できる。
- KMLファイルから事後実績や行政証跡が排除されるため、外部への地図ファイル共有時における不要な情報露出を減らすことができる。
- 通信障害時でも運航を妨げず、外部保存リトライ経路が確保される。

## 5. デメリット・トレードオフ（Cons / Trade-offs）

- 実際の飛行実績（飛行軌跡や正確な離着陸時刻）はKMLには反映されない（これはA4帳票およびSheets正本側の責務とする）。
- クライアント側で未同期KMLの状態管理と再送トリガーの実装が必要となる。

## 6. 今後の検証・昇格条件（Validation Criteria）

Step 7（出力・KML同期仕様更新）において、99.2 §7, §8の記述および既存出力境界（27, 27a）との整合性を検証し、Step 8の監査を経てAccepted候補としてオーナーへ提示し、オーナーの明示承認を受けて初めてAcceptedへ変更する。
