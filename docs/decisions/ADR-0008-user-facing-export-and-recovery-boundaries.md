# ADR-0008: ユーザー向けJSON出力廃止と出力・復旧境界の再定義

- **作成日**: 2026-09-15
- **ステータス**: **承認済み（Accepted）**
- **決定者**: オーナー（2026-09-15のPhase C1前docs構造再編依頼における明示方針）
- **関連設計**: [27 出力境界](../architecture/output/27_output-boundaries.md)、[14 オフライン・同期](../architecture/14_offline-and-sync.md)、[19 障害復旧](../architecture/19_failure-recovery.md)
- **Partially Supersedes**:
  - [ADR-0003](ADR-0003-offline-storage-and-eviction-defense.md) のうち、§2選択肢C.4、§3決定項目3、§4影響評価にある **user-facing JSON backup/export/import** に関する部分のみ。
  - [ADR-0001](ADR-0001-architecture-selection.md) §6の **手動JSON退避による二重化を必須とする部分のみ**。
- **置換しない部分**: IndexedDB、Storage API永続化要求、保護状態・容量監視、Google Sheetsへの外部二重化、Model Dと手修正尊重、PWA/Workers構成。

## 1. 背景と課題（Context）

ADR-0003はブラウザストレージ喪失への多層防御として手動JSON退避を含めて承認されました。一方、後続の出力設計ではJSONをDIPS API内部通信、KMLをユーザー向け地図出力、Sheetsを確定台帳、PDFを人間向け帳票としています。ユーザーがJSONを作成・保存・取込する義務を残したままでは、両方の決定を同時に現行仕様として実装できません。

2026-09-15のオーナー依頼は、この相違をAccepted ADRの直接書換えで消さず、ユーザー向けJSON部分の置換と全量復旧形式の `PENDING` を新ADRで記録するよう明示しました。本ADRはその限定した変更を記録します。

## 2. 検討した選択肢（Options Considered）

- **A: 旧ユーザー向けJSON復旧案を維持**。旧14設計には、全テーブル（機体・バッテリー・ミッション・飛行記録・点検記録・設定）を暗号化またはプレーンJSONの1ファイル（例 `drone_flight_backup_20260914.json`）として端末の「ファイル」へワンタップ保存し、取込時はUUID照合・重複スキップまたは最新優先でマージ/restoreする案がありました。これは旧案の記録であり、現行実装指示ではありません。
- **B: JSON復旧をKMLで代替**。KMLに含まれる地理・属性情報から全DBを復元するとみなす案。
- **C: ユーザーJSONを廃止し、台帳保管を維持、全量復旧形式は未決として明示**。

## 3. 決定内容（Decision）

選択肢Cを採用します。

1. **JSON = DIPS API内部transport**。C7 OptionalでAPI利用資格がある場合に生成・送信します。Manual DIPSではAPI JSONを表示・作成・保存・コピー・取込させません。内部DBのオブジェクトやsnapshotのシリアライズは実装詳細であり、ユーザー向けJSONファイル出力ではありません。
2. **KML = 地理表示・共有用の派生出力**。full database backupではなく、KMLをDB backup/restoreの代替にしません。
3. **Google Sheets = 確定台帳・長期外部保管**。Model Dに従い、外部同期完了後の台帳権威・手修正・集計を維持します。PDF・KML追加によって台帳保存を廃止・縮小しません。
4. **PDF = 人間向け帳票**。法的提示・印刷・監査用の記録スナップショットです。CSV/Excelの表形式帳票も維持します。
5. **全量DB backup/restore = `PENDING-LOCAL-RESTORE-01`**。将来的なユーザー向け形式、退避対象（未同期データ・設定を含む範囲）、暗号化、バージョン互換、破損検査、UUID衝突・競合時の扱い、復元検証を実装前に設計・承認します。今回新形式を発明しません。
6. **C1でユーザー向けJSON import/exportを実装しません**。この決定でC1に別形式のバックアップ実装を追加することもしません。

## 4. 採用理由と他案の却下理由（Rationale）

Aは現在のオーナー指定出力境界と矛盾します。BはKMLにないデータ・参照・設定・未同期状態を復元できると誤認させるため採用しません。Cはユーザー操作の単純化と台帳保全を維持し、未設計の復旧能力を確認済みと扱わない選択です。

## 5. メリット（Pros）

ユーザー向け出力とDIPS内部通信が明確になり、手動通報にAPI JSONを持ち込むことを防ぎます。旧ADRを保存したまま、現行実装要件と置換範囲を追跡できます。

## 6. デメリット・トレードオフ（Cons / Trade-offs）

未同期データを含むローカルDB全量の独立した手動退避・復元機能は、現時点で設計完了していません。Sheetsから復元できるのは実際に同期・保存された台帳範囲であり、端末喪失時に未同期データまで復元できる保証はありません。永続化要求・監視とSheets同期を維持し、欠けた復旧経路をKMLやPDFで埋めたと表示しません。

## 7. 将来この決定を見直す条件（Re-evaluation Triggers）

全量復旧機能の実装に着手する前、同期対象が拡大するとき、端末移行・長期オフラインで追加保全が必要となるときに `PENDING-LOCAL-RESTORE-01` を解決します。新形式・運用を採用する場合は新ADRで根拠と検証結果を残します。Phase C1の開始許可は本ADRに含みません。
