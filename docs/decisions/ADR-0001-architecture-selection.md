# ADR-0001: 総合運航管理システムのアーキテクチャ選定（PWA + Cloudflare Workers + Hybrid Storage）

- **作成日**: 2026-09-14（B1.1再監査・訂正版）
- **ステータス**: **提案中（オーナーレビュー待ち）**
- **決定者**: オーナー（システム設計者）、AIアシスタント（技術検討パートナー）
- **関連要件**: [docs/00_goal.md](../00_goal.md), [docs/03_integrated-requirements.md](../03_integrated-requirements.md), [docs/architecture/05_recommended-architecture.md](../architecture/05_recommended-architecture.md), [docs/architecture/00_b1-audit-and-corrections.md](../architecture/00_b1-audit-and-corrections.md)

## 1. 背景と課題（Context）

本プロジェクト `drone-flight-ops` は、「iPhone と Android の両方で、現場で実用的に使える総合ドローン運航管理アプリ」の実現を目指している。
現場では、準備〜DIPS確認〜計画作成〜地図ポリゴン〜通報〜飛行前点検〜離着陸〜バッテリー交換〜機体交代〜飛行後点検〜日誌確定〜帳票出力までを一続きに行う必要がある。
また、オーナーの個人利用を前提としており、以下の制約・要求を満たすアーキテクチャを決定する必要があった。
1. **初期費用・月額維持費を現行無料枠内で極小化すること**（有料Apple Developer費用や有料サーバー代を回避）。
2. **事前読み込み完了を前提として、山間部等の電波圏外でも現場記録業務が継続できること**。
3. **将来DIPS APIの秘密情報（client_secret等）を扱う場合に備え、クライアント側に秘密を露出させないバックエンド境界を確保すること**。
4. **自作アプリ最大の強みである「バッテリー個体管理」と「Googleスプレッドシートによる監査・手修正の透明性」を継承すること**。

---

## 2. 検討した選択肢（Options Considered）

- **選択肢A: PWA ＋ Cloudflare Workers ＋ ローカルDB(IndexedDB)・スプレッドシート連携ハイブリッド（推奨案）**
- **選択肢B: Web技術 ＋ Capacitor（ネイティブラッパー）構成**
- **選択肢C: 完全ネイティブ開発（iOS: Swift / Android: Kotlin の2重開発）**
- **選択肢D: クロスプラットフォームフレームワーク（Flutter / React Native + Expo）**
- **選択肢E: 現行GAS（Google Apps Script）Web Appの延長**

---

## 3. 提案内容（Proposal / Recommended Direction）

**選択肢A（PWA ＋ Cloudflare Workers ＋ ローカルDB・スプレッドシートハイブリッド構成）** を第一候補として推進することを提案する。

- **クライアント実行形態**: PWA（Progressive Web App） / Web標準SPA
  - モバイルSafari / Chromeで「ホーム画面に追加」してフルスクリーン起動。
  - 地図描画: MapLibre GL JS ＋ 国土地理院タイル（利用規約準拠）。
- **ローカルオフライン一時永続化**: IndexedDB（Dexie.js等）
  - 通信圏外でも通信待ちを発生させず即時ローカル書き込み。クラッシュ・電池切れ保護。
- **バックエンド / API境界**: Cloudflare Workers ＋ Cloudflare Pages
  - 将来のDIPS API秘密情報を安全に隔離・中継。現行仕様では1日10万回まで無料枠内。V8 Isolateによる超低遅延起動。※実装時にFree PlanのCPU時間10ms制限内で安定動作するかを検証する。
- **法定台帳・共有原本**: Googleスプレッドシート連携
  - 運航完了後、または電波復帰時にワンタップ同期。人間による確認・手動修正・印刷原本の透明性を維持。
  - ※具体的な「正本（SSoT）」の定義やステータス管理モデル（ローカル正本 vs スプレッドシート原本 vs ライフサイクル連動型ハイブリッド）はPhase B2にて確定する。

---

## 4. 採用理由と他案の却下理由（Rationale）

- **選択肢Aを第一候補とする理由**:
  1. **現行仕様での低コスト運用**: Appleへの年次有料登録（年約1.3万円前後）や有料サーバー代を回避し、現行無料枠内で運用可能。
  2. **現場オフライン継続性**: 事前ロード済み状態であれば、通信圏外でも点検・打刻・日誌作成を継続可能。
  3. **秘密情報の安全な隔離境界**: Cloudflare Workersのエッジ環境で将来のAPIシークレットを隠蔽可能。
  4. **既存強みの継承**: スプレッドシート連携により、手修正後の計算継続や原本印刷の安心感がそのまま残る。
- **他案を第一候補から外した理由**:
  - **選択肢C（完全ネイティブ）**: iOSとAndroidでコードが2重化し、個人での維持・保守が困難であるため。
  - **選択肢D（Flutter/Expo）**: Apple Developerの年次費用や審査・ビルド維持の負担が重く、地図エコシステムもWebに比べ制約があるため。
  - **選択肢E（GAS延長）**: サーバー通信前提のため、山間部等の完全圏外での現場記録に適さず、地図操作のレスポンスが重いため。
  - **選択肢B（Capacitor）**: 将来の拡張経路として極めて有望だが、現時点ではビルド管理負担を避けるため、まずはWeb（PWA）ファーストで進める。なお、Web資産の大部分は将来Capacitorへ流用可能。

---

## 5. メリット（Pros）

- iPhone・Android・iMacのすべてで、ブラウザから即座に同等の一気通貫UIが動く。
- アプリストアの審査待ちやリジェクトの心配がない。
- 修正や機能追加がWebデプロイ経由で即時反映される。
- AIアシスタントによるコード保守・リファクタリングの親和性が高い。

---

## 6. デメリット・トレードオフ・運用制約（Cons / Trade-offs）

- iOS Safariにおいて、端末空き容量逼迫時等にIndexedDBがOSにより自動削除されるリスクがある（対策: ホーム画面PWAとして `navigator.storage.persist()` 要求を試みつつ、外部スプレッドシートやJSON退避による二重化を必須とする）。
- オフライン時のDIPS飛行計画通報の法的制約: 電波がない現場でオフラインキューに入れただけでは「通報完了・飛行可能」とはみなせないため、国交省サーバーからの受理確認が取れるまで飛行可能状態へ遷移させない厳格な状態管理を要する。
- バックグラウンドでの長時間のGPSトラッキングはネイティブほど自由度が高くない（手動打刻と現在地測位の要件には充足）。
- 初回アクセス前やキャッシュクリア後は、通信環境がないと起動できない。

---

## 7. 将来この提案を見直す条件（Re-evaluation Triggers）

- ドローン機体との直接的なBluetooth通信や、バックグラウンドでのGPS連続軌跡記録が必須要件となった場合（→ Capacitorを導入してネイティブ化を検討）。
- 国交省DIPS APIの仕様により、クライアント証明書等のネイティブ特有の機能が要求された場合。
- オーナーがApp Store / Google Playでの一般配布を希望するようになった場合。
- iOSのPWA仕様が大幅に変更され、オフライン利用やストレージ永続性が実運用に耐えなくなった場合。
