# ADR-0001: 総合運航管理システムのアーキテクチャ選定（PWA + Cloudflare Workers + Hybrid Storage）

- **作成日**: 2026-09-14
- **ステータス**: 提案中（オーナーレビュー待ち）
- **決定者**: オーナー（システム設計者）、AIアシスタント（技術検討パートナー）
- **関連要件**: [docs/00_goal.md](../00_goal.md), [docs/03_integrated-requirements.md](../03_integrated-requirements.md), [docs/architecture/05_recommended-architecture.md](../architecture/05_recommended-architecture.md)

---

## 1. 背景と課題（Context）

本プロジェクト `drone-flight-ops` は、「iPhone と Android の両方で、現場で実用的に使える総合ドローン運航管理アプリ」の実現を目指している。
現場では、準備〜DIPS確認〜計画作成〜地図ポリゴン〜通報〜飛行前点検〜離着陸〜バッテリー交換〜機体交代〜飛行後点検〜日誌確定〜帳票出力までを一続きに行う必要がある。
また、オーナーの個人利用を前提としており、以下の厳しい制約・要求を満たすアーキテクチャを決定する必要があった。
1. **初期費用・月額維持費を0円（無料）に抑えること**（年1.3万円のApple Developer費用や有料サーバー代を回避）。
2. **完全オフライン環境（山間部等の電波圏外）でも現場業務が100%停止しないこと**。
3. **国交省DIPS 2.0 APIの秘密情報（client_secret）を安全に保護・中継できること**。
4. **自作アプリ最大の強みである「バッテリー個体管理」と「Googleスプレッドシートによる監査・手修正の透明性」を完全に継承すること**。

---

## 2. 検討した選択肢（Options Considered）

- **選択肢A: PWA ＋ Cloudflare Workers ＋ ローカルDB(IndexedDB)・スプレッドシート連携ハイブリッド（推奨案）**
- **選択肢B: Web技術 ＋ Capacitor（ネイティブラッパー）構成**
- **選択肢C: 完全ネイティブ開発（iOS: Swift / Android: Kotlin の2重開発）**
- **選択肢D: クロスプラットフォームフレームワーク（Flutter / React Native + Expo）**
- **選択肢E: 現行GAS（Google Apps Script）Web Appの延長**

---

## 3. 決定内容（Decision）

**選択肢A（PWA ＋ Cloudflare Workers ＋ ローカルDB・スプレッドシートハイブリッド構成）** を最有力構成として採用・推進することを提案・決定する。

- **クライアント実行形態**: PWA（Progressive Web App） / Web標準SPA
  - モバイルSafari / Chromeで「ホーム画面に追加」してフルスクリーン起動。
  - 地図描画: MapLibre GL JS ＋ 国土地理院オープンデータタイル（完全無料）。
- **ローカルオフライン永続化**: IndexedDB（Dexie.js）
  - 圏外でも1ミリ秒で入力・打刻を即時永続化。クラッシュ・電池切れ保護。
- **バックエンド / APIプロキシ**: Cloudflare Workers ＋ Cloudflare Pages
  - DIPS APIの `client_secret` やトークンを安全に隔離・中継。1日10万回まで完全無料。コールドスタート0ミリ秒。
- **データ最終原本・監査台帳**: Googleスプレッドシート
  - 運航完了後、または電波復帰時にワンタップ同期。人間による確認・手動修正・印刷原本の透明性を完全維持。

---

## 4. 採用理由と他案の却下理由（Rationale）

- **選択肢Aを採用した理由**:
  1. **費用0円の実現**: Appleへの年会費（年12,980円）やサーバー維持費が一切不要。
  2. **完全オフライン耐性**: 現場での記録・点検・バッテリー管理が通信なしで100%稼働。
  3. **秘密情報の安全な隔離**: Cloudflare Workersの安全なエッジ環境でDIPS APIのシークレットを隠蔽可能。
  4. **既存強みの継承**: スプレッドシート連携により、手修正後の計算継続や原本印刷の安心感がそのまま残る。
- **他案を却下した理由**:
  - **選択肢C（完全ネイティブ）**: iOSとAndroidでコードが2重化し、個人での維持・保守が破綻するため却下。
  - **選択肢D（Flutter/Expo）**: Apple Developerの年次費用や審査・ビルド維持の負担が重く、地図エコシステムもWebに劣るため却下。
  - **選択肢E（GAS延長）**: 圏外でのオフライン動作が構造上不可能であり、地図ポリゴン操作の現場レスポンスが悪いため却下。
  - **選択肢B（Capacitor）**: 将来の拡張候補としては非常に優れているが、現時点ではビルド管理の手間を避けるため、まずはWeb（PWA）ファーストで開発を進める。なお、選択肢Aのコードは100%そのままCapacitorへ流用できるため無駄がない。

---

## 5. メリット（Pros）

- iPhone・Android・iMacのすべてで、ブラウザから即座に同等の一気通貫UIが動く。
- アプリストアの審査待ちやリジェクト（審査落ち）の心配が一切ない。
- 修正や機能追加がGitHubコミット経由で即時反映される。
- AI（LLM）によるコード保守・リファクタリングの精度がWeb標準技術のため極めて高い。

---

## 6. デメリット・トレードオフ（Cons / Trade-offs）

- iOS Safariにおいて、長期間（数週間以上）アクセスがない場合にCache Storageがクリーンアップされる挙動がある（IndexedDBへの二重保存とスプレッドシート退避で回避）。
- バックグラウンドでの長時間のGPSトラッキングはネイティブほど自由度が高くない（ただし本アプリは手動打刻と現在地測位が主であり、実運用上の支障はない）。

---

## 7. 将来この決定を見直す条件（Re-evaluation Triggers）

- ドローン機体との直接的なBluetooth通信や、バックグラウンドでのGPS連続軌跡記録がどうしても必須になった場合（→ Capacitorを導入してネイティブアプリ化する）。
- 国交省DIPS APIの仕様により、クライアント証明書等のネイティブ特有の機能が要求された場合。
- オーナーが一般ユーザー向けにApp Store / Google Playでアプリを有料/無料公開したくなった場合。
