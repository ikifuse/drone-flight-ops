## 1. 背景と課題（Context）

本システム `drone-flight-ops` は、個人の小規模運用（特定個人・特定2機体・7本バッテリー等）を最小構成としつつ、将来的な**「業務利用・会社利用・複数機材フリート運用」**（複数メーカー、多数の機種、同一機種の複数機保有、数十〜数百本のバッテリー、複数操縦者・点検者・補助者、複数現場、複数顧客、複数案件、複数許可承認、長期履歴保存、退役・廃棄機材管理）に耐えうる拡張性を備える必要がある。

先行システム（旧GASアプリ）および初期検討においては、以下の課題と制約が存在していた：
1. **旧GAS物理シート配置への引きずられ**: 旧GASはスプレッドシートの印刷枠（左右No.1/No.2ブロック、7飛行上限、8飛行目退避、1機体1シート、1バッテリー1シート、原本シート複製）にアプリ構造が縛られていた。新アプリでは印刷都合をデータモデルに持ち込まず、正規化された永続化構造が必要であった。
2. **バッテリーの固定従属問題**: 実運用上、同一シリーズ・互換機種間（例: EVO Lite と EVO Lite+）や同一機種の複数機間でバッテリーを共用する。バッテリーを特定1機体の所有物（`Aircraft 1:N Battery`）とする設計は破綻を招くため、機種・バッテリー型式間の互換（N:M）と実績側での紐付けが必要であった。
3. **個人・特定機材のハードコードリスク**: 特定個人名、固定機体名、固定バッテリー番号、単一操縦者前提などをスキーマに埋め込むと、組織利用や機材入替時に破壊的変更が発生する。
4. **人員マスター・場所マスターの未分離**: 操縦者・点検者・補助者を別エンティティで管理すると同一人物の重複登録が発生する。また現場場所がテキスト入力のみでは、同一現場での頻繁な運航時に緯度経度・安全措置の再入力負荷が高い。
5. **A4帳票出力境界の整理**: 現場での片手操作（バッテリー交換時はスムーズに次フライトへ移行）を維持しつつ、帳票としては機体ごと・場所ごとに独立したA4縦帳票を発行し、物理的行数溢れは左右分割ではなく自動続紙（Page 2...）で対応する運用設計が求められた。

## 2. 決定内容（Decision）

### 2.1 機種と個別機体の分離（AircraftModel vs Aircraft）
- **`AircraftModel`（機種マスター）**: メーカー名、型式名、型式コード、機体重量、基本仕様を保持。
- **`Aircraft`（機体個別台帳）**: 個別機体シリアル番号、DIPS登録記号、愛称（A号機/B号機等）、累計飛行データ、登録・点検期限を保持し、`model_id` で `AircraftModel` を参照する。
- 同一機種を複数機保有する場合も機種情報の重複登録を排除する。

### 2.2 バッテリー型式と個体の分離・機材互換モデル（N:M）
- **`BatteryModel`（バッテリー型式マスター）**: 製造者、製品型番、公称容量、公称電圧等の仕様を管理。
- **`BatteryCompatibility`（機材互換マッピング）**: `AircraftModel` と `BatteryModel` の多対多（N:M）互換関係を正規化管理する。
- **`Battery`（実物バッテリー個体）**: 個体シリアル、管理表示名（スロット/番号）、購入日、累計サイクル数、累計飛行時間、健全性状態を管理し、`BatteryModel` を参照する。**バッテリーは特定機体の所有物にしない**。
- **実績での紐付け**: 個々の飛行実績（`Flight`）において `aircraft_id` と `battery_id` の双方を記録することで、同一バッテリーの生涯履歴を機体横断で完全に追跡可能とする。
- **責務の重複排除**: 飛行によるバッテリー使用履歴は `Flight` から完全に導出できるため別テーブルへ二重保存しない。`BatteryUsage` は飛行以外の充電、深放電、保管、点検、容量測定等のライフサイクルイベント専用エンティティとして定義する。

### 2.3 人員マスターの一元化と利用ユーザーの分離
- **`Personnel`（人員マスター）**: 操縦者、点検者、立入管理補助者等を1人物1レコードとして一元管理する。1人の人物が複数の業務役割（`pilot`, `inspector`, `assistant`, `administrator`, `viewer`）を兼務可能とする。技能証明プロファイルは操縦者役割を持つ人物の付属属性とする。
- **UserAccount（操作ユーザー）との分離**: 運航記録に登場する人物（`Personnel`）と、アプリを操作・ログインするユーザーアカウント（`UserAccount`）を概念上分離し、将来の認証導入時にも運航記録データモデルを破壊しない構造とする。

### 2.4 運用主体（Organization）と業務案件（Client / Project）の導入
- **`Organization`（運用主体）**: 個人事業主、法人、運航事業者等の所有・運用境界を表すエンティティを定義し、全主要エンティティを `organization_id` スコープ可能とする（C1初期は単一デフォルト組織として動作し、マルチテナント実装は行わない）。
- **`Client` / `Project`（顧客・案件マスター）**: 業務空撮・インフラ点検等の案件情報を管理する任意参照マスターとし、計画（`FlightPlan`）や運航（`Mission`）から任意に紐付け可能とする（個人利用時は未入力可）。

### 2.5 場所マスターと飛行範囲プリセットの分離
- **`Location`（場所マスター）**: 現場名称、住所、代表緯度経度、現場連絡先、土地管理者メモ、駐車・立入注意事項を管理。
- **`FlightAreaPreset`（飛行範囲プリセット）**: `Location 1:N FlightAreaPreset` とし、同一現場内の複数エリア（野球場外野、南側練習範囲、30m円等）の形状（円/ポリゴン）および既定高度を再利用可能とする。

### 2.6 入力プリセットと運航テンプレート（Template as Copy Source）
- 飛行目的（`FlightPurposePreset`）および安全措置（`SafetyMeasurePreset`）を独立プリセットとして管理。
- 頻出する現場条件（場所、範囲、目的、高度、操縦者、補助者、安全措置、許可承認、任意の既定機体）を束ねた `OperationTemplate` を新設する。
- **コピーソース原則**: テンプレートを用いて計画を作成する際は値を新規Draftへコピー（実体化）して使用し、**後日のテンプレート変更が過去の計画・通報・運航履歴を改変することを厳禁**とする。

### 2.7 物理削除の排除とライフサイクル管理
- マスターデータは物理削除せず、`ACTIVE`, `INACTIVE`, `RETIRED`, `DISPOSED`, `LOST`, `EXPIRED`, `ARCHIVED` などのライフサイクル状態属性で管理し、過去履歴の外部キー参照整合性を恒久的に保護する。
- 重要エンティティには `created_at`, `created_by`, `updated_at`, `updated_by`, `version` の共通メタデータを付与し、監査証跡（`AuditEvent`）による追跡を可能とする。

### 2.8 Googleスプレッドシートの正規化台帳原則（シート増殖禁止）
- **シート自動増殖の全面禁止**: 機体数、バッテリー数、人員数、現場数、飛行回数、運航日数に比例して物理シートを新規複製することを禁止する。
- 物理シート数は「10枚固定」や「5〜7枚固定」などの具体的数値で縛らず、**「行追加型・行更新型の正規化テーブルとして設計し、CRUD・同期安全性・監査性を担保する」**ことを原則とする。

### 2.9 統合運航帳票（A4縦）の出力境界と自動ページネーション
- **統合運航帳票（IntegratedOperationReport）**: A4縦1枚の中に「飛行記録」「日常点検記録」「点検整備記録サマリ」をレイアウトした実務帳票を、正規化された内部データから動的に生成する（国交省公式の個別様式1・2・3出力機能とも両立）。
- **帳票区切りルール**:
  - **同一機体 × 同一場所 × 同一運航区間** を1つの帳票単位とする。
  - **バッテリー交換**: 同一帳票を継続し、飛行記録行を追加。
  - **機体変更 / 場所変更 / 明示的な新規運航**: 新しいA4帳票へ分割。
- **続紙ルール**: 飛行記録行数をDomain層で「5行」や「6行」と固定せず、レンダラーが実寸レイアウトに基づいて自動ページネーション（Page 1, Page 2... の続紙）を行う。

## 3. メリット（Pros）

1. **無限の機材・業務スケール耐性**:
   - 保有ドローンが10機、バッテリーが100本、操縦者が20人に拡大しても、データモデル・スプレッドシート構造の再設計が不要。
2. **現場手数の極小化と入力事故防止**:
   - 「▼ 登録済みから選択 ＋ 新規登録」パターンにより、現場での文字入力をほぼゼロにし、過去設定の安全な再利用を実現。
3. **過去データの改ざん耐性・監査適合性**:
   - テンプレートからの値コピー、不変スナップショット、ライフサイクル状態による論理管理により、国交省監査や立入検査時にも過去記録の完全な真正性を担保。
4. **印刷レイアウト都合からのデータベース解放**:
   - 旧GASのセル結合・左右ブロックの物理制約を内部DBおよびスプレッドシートから完全に排除。

## 4. デメリット・トレードオフ（Cons / Trade-offs）

1. **エンティティ数の増加**:
   - 初期Phase（C1）において定義・マイグレーションすべきテーブル数が増加する。
   - **対策**: Phase C1ではスキーマ定義・基本リポジトリを網羅的に構築するが、高度な検索UIや一括インポート機能は後続Phaseへ段階的に配置する。

## 5. 既存ADRとの関係と競合時の優先順位

- **Clarifies ADR-0001**: PWAとGoogleスプレッドシート連携において、物理シートを行追加型正規化台帳群として扱う構造を明確化した。
- **Clarifies ADR-0002**: 確定台帳（スプレッドシート側）のスキーマを行追加型とし、手動修正とシステム同期の境界を明確化した。
- **競合時の優先順位**:
  1. 現場の安全・ロストゼロ・片手操作性
  2. 過去運航記録の不変性と参照整合性
  3. 正規化による保守性・将来拡張性
  4. スプレッドシート側のシンプル性（シート増殖禁止）
