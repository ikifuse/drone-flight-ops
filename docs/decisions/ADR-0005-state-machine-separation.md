# ADR-0005: 運航状態マシンとDIPS通報状態マシンの厳格分離および飛行可能誤認防止

- **作成日**: 2026-09-14
- **ステータス**: **提案中（オーナーレビュー待ち）**
- **決定者**: オーナー（システム設計者）、AIアシスタント（技術検討パートナー）
- **関連ドキュメント**: [docs/architecture/13_state-machines.md](../architecture/13_state-machines.md)

---

## 1. 背景と課題（Context）

従来の構想では、飛行準備から離着陸に至る現場操作と、DIPS 2.0への飛行計画通報が混在し、「DIPS通報が成功したら飛行可能状態へ遷移する」といった密結合な表現が存在した。
しかし、航空法および実際のドローン運航上、以下の重大な課題がある。
1. **電波圏外での運用継続**: DIPS通報は通信必須だが、現場での飛行前点検、離着陸打刻、バッテリー交換は完全圏外でも自律動作しなければならない。
2. **法的・安全上の重大な誤認リスク**: DIPS飛行計画通報の成功は、飛行計画通報要件を満たしたことに過ぎない。実際の飛行には別途、包括許可承認の有効性、空域規制、土地管理者との調整、気象条件、日常点検合格の総合判断が必要であり、アプリが「DIPS成功＝法的に飛行可能」と断定・表示することは操縦者に致命的な油断や法令違反を招く危険がある。

---

## 2. 検討した選択肢（Options Considered）

- **選択肢A: 単一の統合状態マシン**: DIPS通報を運航フローの必須ステップとして組み込む。
- **選択肢B: 2つの独立した状態マシンへの完全分離（推奨案）**:
  - 物理的な現場作業を管理する「運航状態マシン（Operation State Machine）」
  - 電子手続きを管理する「DIPS通報状態マシン（DIPS Notification State Machine）」
  を完全に分離し、非同期に連携させる。

---

## 3. 決定内容（Decision）

**選択肢B（2つの独立した状態マシンの完全分離）** を採用することを決定した。

1. **運航状態マシン**:
   - `PREPARING` → `PREFLIGHT_INSPECTION` → `TAKEOFF_READY` → `IN_FLIGHT` → `LANDED` → `BATTERY_SWAP` / `AIRCRAFT_SWITCH` → `POSTFLIGHT_INSPECTION` → `MISSION_COMPLETED`
   - 通信状態に関係なくローカルDB完結で進行可能とする。
2. **DIPS通報状態マシン**:
   - `UNCREATED` → `CREATED` → `PENDING` → `SENDING` → `SUCCESS_CONFIRMED`
   - 失敗時は `FAILED` または `RETRY_WAIT`。
3. **安全UIの徹底**:
   - 通報成功時の表示は「DIPS通報成功確認済み（受付番号: XXXXX）」に留め、「飛行可能」という過剰な断定表示を行わない。
   - 離陸前には、DIPS通報受付番号、点検合否、許可承認状況、周辺安全確認が並列して確認できる総合セーフティチェックUIを提供する。

---

## 4. 影響と評価（Consequences）

- **メリット**:
  - DIPSサーバーがメンテナンス中や障害発生時でも、現場の日常運航・日誌記録が完全に動作する。
  - 法令上の責任境界が明確化され、操縦者が思い込みや誤認で飛行させる事故を防止できる。
- **デメリット・留意点**:
  - 2つの状態マシン間のイベント連携（計画作成から通報キューへの連携等）をユースケース層で適切にハンドリングする必要がある。
