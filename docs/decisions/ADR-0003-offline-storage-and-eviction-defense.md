# ADR-0003: ローカル永続化方式とWebKitストレージ自動削除への多層防御

- **作成日**: 2026-09-14
- **ステータス**: **提案中（オーナーレビュー待ち）**
- **決定者**: オーナー（システム設計者）、AIアシスタント（技術検討パートナー）
- **関連ドキュメント**: [docs/architecture/14_offline-and-sync.md](../architecture/14_offline-and-sync.md)

---

## 1. 背景と課題（Context）

本アプリはオフラインファーストで動作するため、ブラウザ内ストレージ（IndexedDB）へのデータ永続化が不可欠である。
しかし、iOS Safari（WebKit）には、端末ストレージの逼迫時等にIndexedDBを含むWebストレージを事前の警告なく自動削除（Eviction）する仕様が存在する。
航空法上3年間の保管義務がある法定運航記録を扱うにあたり、「IndexedDBに保存したから安心」という安易な設計では、データ消失事故を防げない。

---

## 2. 検討した選択肢（Options Considered）

- **選択肢A: IndexedDB単独保存**: ブラウザ標準のIndexedDBのみに依存する。
- **選択肢B: クラウド常時保存**: オフラインを諦め、入力ごとにクラウドへ同期する。
- **選択肢C: 多層防御アーキテクチャ（推奨案）**:
  1. WebKit Storage API (`navigator.storage.persist()`) による永続化要求
  2. 永続化ステータスの画面表示・監視
  3. Googleスプレッドシートへの定期同期による外部二重化
  4. オフラインでのワンタップJSONバックアップ・エクスポート/インポート復旧

---

## 3. 提案内容（Proposed Decision）

**選択肢C（多層防御アーキテクチャ）** を推奨候補として提案する（オーナーレビュー承認待ち）。

1. **IndexedDB (Dexie.js)** を現場ローカル作業の一次バッファとして採用する。
2. PWA起動時に `navigator.storage.persist()` を要求し、可能な限りOSによる自動削除から保護する。
3. IndexedDBを唯一の長期保管場所とはせず、運航完了時・電波復帰時のGoogleスプレッドシート同期、および手動JSONファイル退避によって原本性を恒久担保する。

---

## 4. 影響と評価（Consequences）

- **メリット**:
  - iOS Safari特有のEvictionリスクを技術的・運用的に大幅に低減可能。
  - 端末水没や機種変更時でも、スプレッドシートまたはJSONバックアップからデータを安全に復旧可能。
- **デメリット・留意点**:
  - 初回起動時のパーミッション処理やJSONインポート/エクスポートUIの実装コストが軽微に発生する。
