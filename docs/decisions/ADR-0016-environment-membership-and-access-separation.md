# ADR-0016: 人物・環境所属と三層権限を分け、離任を所属終了として扱う

- **作成日**: 2026-09-18
- **ステータス**: 提案中（Proposed）
- **設計ベースライン**: 99.2 §2の到達済み内容はCURRENT-ACCEPTED。検討方向・未確定・証拠は詳細正本の状態に従い、ADR Acceptedと同一視しない。
- **関係性**: Partially Supersedes [ADR-0007 §2.3](ADR-0007-normalized-masters-and-business-reporting.md)の人物本体に寄せた役割配列・操縦者付属資格プロファイルを、環境別所属・役割および独立した資格へ置換する設計判断を記録する。Clarifies §2.4の組織拡張性と§2.7の物理削除禁止・履歴保持。0007の承認記録を書き換えず、本ADRの承認は未了とする。
- **置換しない範囲**: 1人物の一元管理、PersonnelとUserAccountの分離、機体・BAT・案件・プリセット・帳票設計、Master全般の物理削除禁止。Organizationと環境の関連基数・物理schemaは確定しない。
- **判断の由来・記録者**: 99.2 §2およびオーナーのStep 2再移植指示に基づき、AIが因果と配置を記録。新しい業務判断やADR承認を代行しない。
- **関連要件**: [人物・環境の入口](../architecture/identity-and-access/README.md)、[統合要件](../03_integrated-requirements.md)、[移管対応](../migration/99-2-step-2-causal-audit.md)。

## 1. 背景と課題（Context）

ADR-0007は人物重複を防ぎ、アカウントなしの同行者を記録できるようにした。基準12aには役割・資格・退職状態を人物本体へまとめた形が残る。99.2 §2では同一人物が個人・会社・スクール等へ所属し、アカウントや役割が変わる運用、Google共有とアプリ権限の不一致、離任後も必要な実績の連続性が具体化した。

## 2. 検討した選択肢（Options Considered）

- 人物＝Googleログイン、役割別人物マスター、人物本体に環境を問わない役割・資格・退職状態を集約する案。
- アプリ内Editorの承認・自動共有、操縦者の自動Editor化、Drive共有設定をアプリ管理者保護に使う案。
- 人物・アカウント・環境・所属・所属内役割を分け、アプリ機能権限とGoogle実アクセスを別責任にする現在案。離任・再所属も人物の作り直しではなく所属の終了・再有効化で扱う。

これらは同一時点に実装済みだった選択肢ではなく、基準Docsと99.2が記録する検討を区別して整理したもの。詳細な変化と証拠は31a〜31dへ分担する。

## 3. 決定内容（Decision）

後者を現在の設計ベースラインとして記録する。人物・資格・環境の正本は[31a](../architecture/identity-and-access/31a_person-account-and-environment.md)、三層・初期管理者・最後の1人保護・設定権限は[31b](../architecture/identity-and-access/31b_roles-and-access-control.md)、運航時の担当意味論は[31c](../architecture/identity-and-access/31c_operational-actors.md)、所属終了・再所属・履歴は[31d](../architecture/identity-and-access/31d_membership-lifecycle.md)。操作・列・例外の規則を本ADRへ複製しない。

## 4. 採用理由と他案の却下理由（Rationale）

Googleアカウントの有無を人物の存在条件にすると外部協力者を扱えず、役割別に人物を作ると同じ人の情報が重複する。人物本体の役割・退職だけでは環境ごとに異なる立場を表せないため、既存の一元化を保って所属へ責任を分ける。資格も人物基本情報・環境内役割と混ぜない。

Google側の閲覧・編集可否をアプリ独自承認で変更したことにはできず、Google Editorにはアプリ外の編集経路もある。Drive共有を第二正本化せず、同じ理由でGoogleの共有権限をアプリ管理者権限にも転用しない。離任による人物削除や再所属時の新人物作成は過去実績との連続性を損なうため採らない。

## 5. メリット（Pros）

人物の重複を避けながら、複数環境・複数ユーザー・将来の組織利用へ拡張できる。所属変更とGoogle共有の独立性が明確になり、過去記録の検証・監査・後の設計変更で理由を追跡できる。

## 6. デメリット・トレードオフ（Cons / Trade-offs）

所属・アプリ機能・Google共有を別々に扱うため、離任だけで実アクセス取消が完了しない。初期管理者と最後の1人保護があっても、法人の物理所有交代・復旧は別の検討を要する。ID対応、schema、役割組合せの未定義部分、離任UI・offlineは詳細正本のPENDINGに残す。分離原則から認証機構や全権限表を自動生成しない。

## 7. 将来この決定を見直す条件（Re-evaluation Triggers）

運用環境・所属・物理所有の前提、Google実アクセス、実際の人物担当や記録要件が変わった場合、根拠・影響・旧判断との関係を確認して見直す。CURRENT-ACCEPTEDも変更可能であり、Proposedを承認済みと扱わない。旧mainのADR-0010〜0014は比較証拠に留め、本ADRは基準Docsと99.2 §2から新たに記述した。
