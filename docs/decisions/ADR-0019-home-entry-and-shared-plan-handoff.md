# ADR-0019: ホーム4入口と共有作業リストによる通報後の引継ぎ

- **作成日**: 2026-09-18
- **ステータス**: 提案中（Proposed）。現在ベースラインの判断記録であり、ADR自体は未承認
- **関係性**: [ADR-0005](ADR-0005-state-machine-separation.md)の運航／通報分離と成功時の誤認防止を、ホーム・共有計画・通常画面に具体化するClarifies。旧ADR本文やAccepted履歴は変更しない
- **決定者**: 99.2 §3と限定した§7の現在到達点を、オーナーのStep 5指示に基づきCodexが記録
- **詳細正本**: [Presentation](../architecture/presentation/README.md)の34a〜34d。移管と証拠の索引は[Step 5監査](../migration/99-2-step-5-causal-audit.md)

## 1. 背景と課題（Context）

ホームは2入口から3入口へ進んだが、通報と実飛行は別の日・別担当者になり得る。新規計画と通報済み計画の続行を［通常飛行］でまとめると開始対象を識別しにくい。詳細因果は[34b](../architecture/presentation/34b_home-and-navigation.md)。

## 2. 検討した選択肢（Options Considered）

- 当初の［通常飛行］［設定変更］の2入口。
- ［通常飛行］［飛行履歴・出力］［各種設定・管理］の3入口。
- 新規と通報済み計画を分けた4入口。通報済み計画は共有作業リストから続行する。

## 3. 決定内容（Decision）

99.2の現在ベースラインとして4入口を採る。正常受付で計画IDと重複有無を確定した時点をAPI経路の正式掲載契機とし、［後で飛行する］は掲載済み計画を残してホームへ戻る操作とする。共有リストは今後の作業対象を選ぶために用い、履歴DBにしない。画面の詳細は34b／34c／34dに一本化する。

## 4. 採用理由と他案の扱い（Rationale）

日付・担当者・端末をまたぐ引継ぎを、新規計画作成や過去Flightの確認と混同しないためである。旧2入口・3入口は因果として残すが、現在入口として並立させない。正常受付を送信開始や「後で飛行する」の押下と区別し、結果不明を通常の通報済みへ混ぜない。通信安全の詳細因果は既存[33b](../architecture/dips-infrastructure/33b_api-availability-and-retry-boundaries.md)を参照する。

## 5. メリット（Pros）

事前通報と現場の実飛行を、担当者の違いを保って接続できる。軽量なカード選択と正式通報内容の確認を、提出履歴の保存やAPI基盤から独立して変更・検証できる。

## 6. トレードオフと未確定（Cons / Trade-offs）

共有反映・端末cache・権限／offline表示、Manual確認との接続、リスト整理等の詳細照合が残る。フィルタは方向として保持し、初回必須登録範囲・root再発見・具体認証方式を本ADRで決めない。10項目規約に未確定を明記し、未完了件数widget・追加カード項目・汎用中間詳細・ローカル編集ボタンを独自追加しない。

## 7. 見直す条件（Re-evaluation Triggers）

利用者の引継ぎ運用、正式応答条件、権限・共有方式などの前提が変わった場合、34a〜34dの因果と証拠を更新して再検討する。CURRENT-ACCEPTEDは永久確定やADR Acceptedではない。Step 1〜4の正本・実装ゲートを維持し、通常運航全体・Geometry・KML・取消・重複調整の詳細へ本判断を拡張しない。
