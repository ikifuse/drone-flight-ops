# 新アプリの最終ゴール・ビジョン・運用思想

最終更新: 2026-09-19
プロジェクト: drone-flight-ops

---

## 1. プロジェクトの背景と大前提

本プロジェクト `drone-flight-ops` の完成形は、
**「iPhone と Android の両方で、ドローン飛行の現場で実用的に使える総合運航管理アプリ」** です。
単なるPC向けWebシステムを完成形とはしません。

現在運用中の公開版アプリ（`ikifuse/autel-evo-lite-flight-log`）は、Googleスプレッドシートを正本とし、現場での素早い入力と徹底したバッテリー個体管理を実現しています。
一方で、国土交通省の「DIPS 2.0（ドローン情報基盤システム2.0）」への飛行計画通報や、飛行禁止エリアの地図確認などは外部ツールに頼っており、現場で複数のアプリを行き来する負担が存在します。

本プロジェクトでは、現在の自作アプリの強みを完全に維持・継承しながら、参考アプリ（DIPS Viewer ワンエビneo等）が備えるDIPS連携・地図機能を取り込み、**「現場でスマートフォン（iPhone/Android）1台から、準備から通報、飛行、点検、日誌出力までを一気通貫で完結できるシステム」** の実現を目指します。

> [!IMPORTANT]
> **GAS（Google Apps Script）は必須ではありません。**
> 基準アプリがGASで作られていることは、新アプリもGASで作るという意味ではありません。Phase BでPWA、クロスプラットフォーム、ネイティブ、Web、バックエンドサービス等を比較し、PWA ＋ Cloudflare Workers ＋ IndexedDB・Google Sheets構成を採用しました。その後、DIPS API用の接続経路のみ、固定送信元IPの要件により旧Workers前提から変更しています（現在経路は[33a](architecture/dips-infrastructure/33a_fixed-egress-and-api-connection.md)・[ADR-0018](decisions/ADR-0018-dips-fixed-egress-and-limited-backend.md) Proposed）。PWA・IndexedDB・Google Sheetsの方針は維持しています。選定理由は [ADR一覧](decisions/README.md)、未選定の地図ライブラリはC5の実機評価で扱います。

### 1.1 記入支援を中心に置くまでの因果

**当初の設計と理由（HISTORICAL）**: 初期commit `3303a18`から、現行アプリの素早い入力・BAT個体管理・人が直接確認できる記録を継承し、外部ツールを往復する負担をDIPS・地図連携で減らすことを目指していた。`5d51315`の[ADR-0007](decisions/ADR-0007-normalized-masters-and-business-reporting.md)では、旧印刷枠や特定個人・機材への固定を避け、複数人・複数機材へ拡張するため正規化を採用した。DBそのものを作ることが目的だったと過去設計を読み替えない。

**問題・再検討（99.2 §0・§1）**: 内部テーブルやデータ構造を先に決めて人間側の運用を合わせると、必要な帳票・台帳や保存先が後から判明したときに、モデル・保存・同期・帳票・テスト・移行へ連鎖修正が生じる。DIPS機能を増やすことだけを中心にしても、人が必要な記録へ記入するという目的を満たせない。

**現在の設計ベースライン（CURRENT-ACCEPTED）**: 本アプリは、現場や事務所で利用者が迷わず入力し、必要な記録・帳票・台帳の正しい保存先へ自動反映できる「記入支援Webアプリ」である。必要な出力と保存先を先に確かめ、そこから入力画面・保存処理・内部実装を逆算する。DIPS通報はこの記入支援へ追加する運航支援であり、全体の中心ではない。

現在優先して固める対象は、**A4縦の飛行記録・日常点検記録、点検整備記録、バッテリー管理**。それを複数人・複数機種で使うために人物を識別・選択する人員管理と、機体を識別・選択する機体管理を置く。DIPS関連は飛行計画通報と後の飛行への引継ぎを支援する。ここで人物・権限・機材・帳票の個別schemaや画面構成を追加決定しない。

**採らない進め方・残す境界**: 技術都合で人の運用を変更する方法、出力先が未確定のまま依存コードを書き始める方法は採らない。必要性の合意なく、人が一枚で使う帳票・台帳を技術用の複数タブへ先行分割しない。一方、内部の責務分離・正規化を撤廃したり、旧物理構造を無条件に復活させたりする判断でもない。設計を決める順序と実装時の依存方向は区別する。

根拠は99.2 §0の設計の大前提・優先対象、§1の発端・判断と上記Git履歴。出典の確認範囲は[Step 1監査](migration/99-2-step-1-causal-audit.md)。実装前に確かめる流れは[23の開始ゲート](architecture/23_implementation-roadmap.md#12-保存出力を確かめてから依存実装へ進むゲート)、試作・質問・状態の扱いは[設計証拠規約](guidelines/03_design-evidence-and-causality.md)、判断記録は[ADR-0015（Proposed）](decisions/ADR-0015-record-first-design-and-implementation-gate.md)に分ける。個別の保存構造・出力単位との対照・移植は該当論点の後続Stepに残し、このStepの完了をそれらの監査完了と扱わない。

## 2. 最終ゴール（現場での一気通貫フロー）

将来的に、現場においてスマートフォン1台だけで、以下のフローが途切れず一続きで行える状態を最終ゴールとします。

```text
【飛行準備・計画フェーズ】
1. 飛行準備の開始（現場到着・天候確認）
2. DIPS登録済み機体情報の確認（登録記号・有効期限）
3. 国土交通省の許可・承認情報の確認（包括申請番号・期限）
4. 地図上での飛行禁止エリア・DID・周辺飛行計画の確認
5. 地図上で飛行範囲を作成（POLYGON、CIRCLE、BUFFERED_LINE）
6. 過去の飛行範囲・過去の通報計画の再利用（ワンタップ呼び出し）
7. 飛行計画の作成（日時、高度、飛行目的、特定飛行区分の自動判定）
8. DIPS 2.0へ飛行計画を通報（C6手動支援を標準経路とし、C7 API接続はOptional）
9. 通報結果の確認（表示IDまたは計画一覧の目視照合。API利用時は受理結果・エラー理由）

【現場運航・記録フェーズ】
10. 通報情報を引き継いで飛行前点検を開始（11項目の点検・装着バッテリー番号確認）
11. 離陸の記録（ワンタップ打刻・タイマー開始）
12. 飛行（操縦に集中、画面は経過時間と安全確認情報のみ）
13. 着陸の記録（ワンタップ打刻・実飛行時間・所感等の入力）
14. 現場での継続判断
    ├─ 同じ機体で継続（バッテリー交換画面へ → 新BAT確認 → 次の飛行へ）
    ├─ 機体交代（新機体の初回飛行前点検へ → 交代先で次の飛行へ）
    └─ 本日の全運航終了
15. 使用した全機体の飛行後点検（4項目の点検・異常有無の確認）

【保存・帳票出力フェーズ】
16. 飛行日誌の一括確定・安全保存（二重保存防止・端末内一時退避）
17. 国土交通省様式1〜3準拠の各種帳票出力（PDF / CSV / Excel / 地図付き飛行計画書。現在は必要な時だけ生成する地図付きPDFとして[27f](architecture/output/27f_derived-pdf-roles-and-map-pdf.md)）
```

## 3. 運用思想と設計原則

新システムが従うべき根本的な運用思想と設計原則は以下のとおりです。

### ① 現場ファースト・片手操作の徹底
- 屋外の直射日光下、風が強い現場、手袋を着用した状態でも迷わず操作できること。
- 入力項目を極力自動補完し、現場での手動入力を最小限にする。
- 画面の「戻る」操作や中断・再開が安全に行えること。

### ② バッテリー個体管理の最重要視（自作アプリのコア強み）
- バッテリーはドローンの安全運航を左右する最重要消耗品である。
- 機体だけでなく「バッテリー1本ごとの履歴（充電回数、総飛行時間、使用機体、劣化兆候、所感）」を徹底的に追跡する。
- 同一運航内でのバッテリー交換・再装填のサイクルを正確に記録できること。

### ③ 法令遵守（コンプライアンス）の自動支援
- 航空法に基づく「飛行日誌の記載義務（国交省様式1：飛行記録、様式2：日常点検、様式3：点検整備）」を確実に満たす。
- 「特定飛行（夜間、目視外、DID、30m未満等）」の該当判定や、カテゴリーⅠ／Ⅱの判定をシステムが自動支援する。
- 機体登録や許可承認の「有効期限切れ」を事前に警告し、許可・安全条件の確認を支援する。実際に発生した離陸の記録は拒否しない。機体を物理制御する機能を意味しない（[離陸前総合評価](architecture/state-machines/13c_takeoff-readiness.md)）。

### ④ 疎結合と耐障害性（DIPSが落ちても現場は止まらない）
- DIPS 2.0サーバーの障害やメンテナンス、あるいは現場が携帯電波の圏外（山間部・海上など）であっても、**ローカルでの飛行前点検・離着陸記録・飛行日誌作成は停止しない**こと。
- 通報機能と日誌記録機能を密結合させず、通信復帰後に同期できる設計とすること。

### ⑤ 人間による検証可能性と監査性（データの透明性）
- 保存されたデータがブラックボックス化されず、管理者がいつでも直接確認・手修正・印刷できること。
- 外部監査や国の立入検査、事故調査が発生した際、即座に信頼できる証跡（原本）を提示できること。

### ⑥ 段階的・非推測の進化
- 未確認の仕様やAPIを推測で実装しない。
- 最小限の機能検証（PoC）を経て、確実に動作することを確認しながら段階的に前進する。
