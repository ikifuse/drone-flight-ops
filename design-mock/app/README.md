# 全体アプリの設計確認用モック

最終更新: 2026-09-23

`index.html`をブラウザで開く。利用者画面は左側、設計根拠・比較・状態切替は右側（狭い画面では枠外の操作）。製品実装ではなく、C1・実API・本番認証・永続保存は扱わない。

右側は3区分に分ける。**オーナー判断が必要な設計論点**（答えによってアプリの意味・業務処理／責任主体／必須登録内容／保存する内容／権限／安全性／データの保持・削除・復旧／外部連携の意味や運用／記録として残す内容が変わるもの）、**未決・仮置き（いま決めなくてよいこと）**、**一般的なUI判断（AI側の標準案）**。並び・余白・改行・ボタン位置・「戻る」・説明文の置き場所・一覧の見せ方・意味が変わらない画面の分け方は、AI側が標準案を置き、一件ずつオーナー確認待ちにしない（[30 §5.2](../../docs/architecture/presentation/30_screen-specification-standard.md#52-オーナーに判断を求める粒度2026-09-22)）。オーナー判断から外すことは、その点を確定させることではない。

設計の正本は[画面設計の到達範囲](../../docs/architecture/presentation/34f_screen-map-and-design-coverage.md)、[DIPS入力候補](../../docs/architecture/dips-flight-plan/25b_manual-web-mapping.md)、[旧運航UIの継承](../../docs/architecture/operation-recording/35b_normal-operation-and-final-save.md)。画面ごとのA〜Eの根拠分類を右側に表示する。

- 初回は全員が個人から始まる。Googleの認証 → 個人の保存場所の作成 → **本人情報とDIPSのログイン情報を1画面で登録（はじめの登録）** → ホーム。完了通知だけの画面と、初回の［個人／会社／招待］の3択は置かない（34a §9）。機体・許可承認・保険は、［各種設定・管理］から事前に登録するか、必要になった場面でその場で登録して元の操作へ戻る。
- 会社・団体は、ホームの［会社・団体で新しく使い始める］［すでに使っている会社・団体に参加する］から追加する。どちらも、その会社・団体で使うGoogleアカウントでの認証から始まる。参加では新しい保存場所を作らない（34a §9.4）。使う場所が1つだけのときは、切替の操作を出さない。
- はじめの登録で入れた氏名・住所・電話・メールは、新規飛行の連絡先へ自動で入る（34a §9.5・25b）。
- ［新規飛行］で登録が足りないときは、エラーで止めず、足りない項目を示して［必要な設定をする］から登録し、元の新規飛行へ戻る。飛行を始める必須条件そのものは既存の確定設計（34a §3・25b・26）に従い、ここで追加しない。
- DIPS入力・確認は公式22項目順が標準候補。独自まとめ方は右側から比較する。選択UIの形式、地図の位置・操作は未決。
- 正常受付・重複なしだけが通常運航へ進む。重複時は結果画面・リスト双方で止める。結果不明・エラー・Manual登録確認だけでは進めない。入力内容は保持する。
- 飛行前11項目、着陸内容確定、BAT交換後2項目、実際に飛ばした全機体の飛行後点検、最後の一括保存と失敗時再試行を比較できる。
- 飛行中の利用者向け操作は着陸完了だけ。スマホ操作ゼロを基本にする。早送りは設計確認側だけ。
- 保存失敗・再試行はメモリ内の擬似処理。再起動後の復元、実通信、サーバー側の重複防止を保証しない。
