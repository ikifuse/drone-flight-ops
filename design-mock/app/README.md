# 全体アプリの設計確認用モック

最終更新: 2026-09-25

`index.html`をブラウザで開く。利用者画面は左側、設計根拠・比較・状態切替は右側（狭い画面では枠外の操作）。製品実装ではなく、C1・実API・本番認証・永続保存は扱わない。

右側は3区分に分ける。**オーナー判断が必要な設計論点**（答えによってアプリの意味・業務処理／責任主体／必須登録内容／保存する内容／権限／安全性／データの保持・削除・復旧／外部連携の意味や運用／記録として残す内容が変わるもの）、**未決・仮置き（いま決めなくてよいこと）**、**一般的なUI判断（AI側の標準案）**。並び・余白・改行・ボタン位置・「戻る」・説明文の置き場所・一覧の見せ方・意味が変わらない画面の分け方は、AI側が標準案を置き、一件ずつオーナー確認待ちにしない（[30 §5.2](../../docs/architecture/presentation/30_screen-specification-standard.md#52-オーナーに判断を求める粒度2026-09-22)）。オーナー判断から外すことは、その点を確定させることではない。**画面数についても、新しい画面の追加を最初の解決策にしない**。既存画面への統合・内部処理化・自動判定・登録済み情報の再利用・不足分の後聴取・外部システムの画面への依存を先に検討し、それでも利用者が本当に判断・入力・選択する必要があるときだけ独立画面を追加する（[34a §9.1](../../docs/architecture/presentation/34a_setup-and-environment-entry.md#91-発端と判断の基準)）。

設計の正本は[画面設計の到達範囲](../../docs/architecture/presentation/34f_screen-map-and-design-coverage.md)、[DIPS入力候補](../../docs/architecture/dips-flight-plan/25b_manual-web-mapping.md)、[旧運航UIの継承](../../docs/architecture/operation-recording/35b_normal-operation-and-final-save.md)。画面ごとのA〜Eの根拠分類を右側に表示する。

- 初回は全員が個人から始まる。直接 **はじめの登録**（Googleアカウントの確認・氏名［必須のみ2つ］・フリガナ／住所／電話番号／メールアドレス／DIPSログインID／DIPSパスワード［すべて任意］を1画面）→ ホーム。Google認証・Google Driveの許可・個人の保存場所の作成は、独立した中継画面を置かず、この画面の［登録してホームへ］の内部処理として行う（34a §9）。完了通知だけの画面と、初回の［個人／会社／招待］の3択は置かない。機体・許可承認・保険は、［各種設定・管理］から事前に登録するか、必要になった場面でその場で登録して元の操作へ戻る。
- 会社・団体は、ホームの［〜で使用中］ボタンで開く環境シート内の［会社・団体で新しく使い始める］［すでに使っている会社・団体に参加する］から追加する。どちらも、その会社・団体で使うGoogleアカウントでの認証（うすいシート）から始まる。新しく作る場合は、会社・団体の名前の画面の［作成してホームへ］が、許可・作成の内部処理を兼ねる（別の許可画面は挟まない）。参加では新しい保存場所を作らない（34a §9.4）。使う場所が1つでもボタンは有効。現在地確認・会社追加ができ、切替候補だけは複数環境時に表示する。ホームに会社利用や役割・アカウントの大きな常設カードは置かない。
- はじめの登録で入れた氏名・住所・電話・メールは、新規飛行の連絡先へ自動で入る（34a §9.5・25b）。
- 初回に任意項目を空のままにした人は、通報しようとしたときに**足りないものだけ**をまとめて補う。連絡先（フリガナ・住所・電話番号・メールアドレス）は**登録されている人の情報（人員台帳）へ**、DIPSのログイン情報は**DIPSのログイン情報へ**保存し、元の飛行計画へ戻って通報を続ける。次の飛行からは聞き直さない。2種類を別々の案内に分けず、1つの重なる案内にまとめ、新しい独立画面は作らない（[25b §1.1](../../docs/architecture/dips-flight-plan/25b_manual-web-mapping.md#11-通報時に不足している登録情報を補う受け皿2026-09-23)・34a §8.3）。連絡先の情報源に「申請書記載」を選んだときは人物に紐づかないため、人物情報へは保存しない。
- ［新規飛行］で登録が足りないときは、エラーで止めず、足りない項目を示して［必要な設定をする］から登録し、元の新規飛行へ戻る。飛行を始める必須条件そのものは既存の確定設計（34a §3・25b・26）に従い、ここで追加しない。
- DIPS入力・確認は公式22項目順が標準候補。独自まとめ方は右側から比較する。選択UIの形式、地図の位置・操作は未決。
- 正常受付・重複なしだけが通常運航へ進む。重複時は結果画面・リスト双方で止める。結果不明・エラー・Manual登録確認だけでは進めない。入力内容は保持する。
- 飛行前11項目、着陸内容確定、BAT交換後2項目、実際に飛ばした全機体の飛行後点検、最後の一括保存と失敗時再試行を比較できる。
- 飛行中の利用者向け操作は着陸完了だけ。スマホ操作ゼロを基本にする。早送りは設計確認側だけ。
- 保存失敗・再試行はメモリ内の擬似処理。再起動後の復元、実通信、サーバー側の重複防止を保証しない。
